# Section B Phase 1 · Chapter 1.02: Where HTTP Lives

Where HTTP lives—on top of TCP—and how to think clearly when nothing came back.

## Learning Objectives

By the end of this chapter, you should be able to:
- Explain where HTTP sits in the protocol stack
- Distinguish HTTP errors from transport failures
- Describe what HTTP assumes and what it does not guarantee
- Debug "no response" failures by separating layers

## Key Terms

- **Application layer**: Where HTTP operates; deals in message meaning (methods, headers, status codes), not in packets or delivery
- **Transport layer**: Where TCP operates; provides a connection and reliable byte stream between two endpoints
- **HTTP error**: The server sent back a response with a status code (e.g. 4xx or 5xx); the exchange completed at the HTTP layer
- **Transport failure**: No HTTP response arrived; connection refused, timeout, DNS failure, or network unreachable—the layer below HTTP failed

## 1) Protocol Layers Are Contracts

A protocol layer is a contract. Each layer assumes something about the layer below and provides guarantees to the layer above. It refuses responsibility outside its scope. HTTP is one such layer. It assumes something else moves bytes across the network. If that assumption fails, HTTP does not compensate. It stops. Understanding that separation is what lets you debug "nothing came back" without guessing. You ask which layer failed: the application layer, where HTTP lives, or the transport layer, where TCP and the network live. The answer determines where you look and what you can fix. See the MDN: HTTP entry in resources for protocol overview and reference.

Layers are useful precisely because they limit what each part of the system must understand. Your Flask app or Express server does not need to know how TCP retransmits a dropped packet. Your client does not need to know how IP routes packets through your local network. You write HTTP: methods, paths, headers, status codes. The rest is someone else’s contract. When something goes wrong, you narrow the problem by layer. If the server returned 404, the transport worked and the issue is in your routing or resources. If the client never got a response, the issue is in the transport or network. That narrowing saves time and prevents you from changing application code when the real problem is that the Pi’s Wi‑Fi dropped or the port is closed.

## 2) HTTP Is Not the Network

HTTP does not send packets, route traffic, retransmit lost data, discover IP addresses, or handle congestion. HTTP describes meaning: methods, headers, status codes, and message structure. When HTTP "sends" a request, it writes text into a stream and assumes the stream works. That stream is provided by the layer below. HTTP does not see packet loss, retransmission, or fragmentation. It sees a pipe. If the pipe delivers bytes, HTTP can parse them. If the pipe breaks or never connects, HTTP has nothing to work with. So when your coop dashboard fails to load, the cause might be an HTTP problem—the server returned 500—or a transport problem—the request never reached the server or the response never came back. The fix is different in each case. HTTP is not the network; it is the language spoken over the network once the connection exists.

That is why "the server is down" and "the server returned an error" are different. When the server is down, there is no TCP connection. HTTP never gets to send or receive. When the server returns 503 Service Unavailable, the connection worked; the server chose to respond with that status. Your client code and your debugging path differ. For "server down" you check the host, the port, the process, the network. For "server returned 503" you might retry later or check why the server is overloaded or in maintenance. Keeping "HTTP is not the network" in mind prevents you from treating every failure as if the server were broken. Often the problem is earlier: DNS, routing, firewall, or the client’s inability to reach the server at all.

## 3) The Stack: Where HTTP Sits

Conceptually the stack looks like this. At the top is the application layer, where HTTP operates. Below that is the transport layer, where TCP operates. Below that is the network layer, where IP operates. HTTP deals in semantics: get this resource, post this body, status 200, status 500. It does not deal in packet loss, retransmission, or routing. That separation is deliberate. It allows you to reason about your coop API or your solar logger endpoint without thinking about Ethernet frames or Wi‑Fi signal strength—until something breaks. When something breaks, you need to know which layer to look at. If the server responded with a status code, the transport worked and the failure is in the application. If you never got a response, the failure is likely in the transport or below. The stack is not just theory; it is the map you use to decide where to debug.

In practice you may also have TLS (or SSL) between TCP and HTTP. TLS provides encryption and often authentication; it runs on top of TCP and HTTP runs on top of TLS when you use HTTPS. For this chapter the important point is unchanged: HTTP still assumes a stream. The stream might be a raw TCP connection or an encrypted TLS connection. Either way, if the stream does not exist or breaks, HTTP has nothing. When you use HTTPS, connection failures can also be TLS handshake failures—wrong certificate, expired, or unsupported version. Those are still below HTTP: the application layer never got a chance to send or receive an HTTP message. So the mental model—application (HTTP), transport (TCP), and the stream—extends to HTTPS; TLS is another layer in the middle that can fail independently.

## 4) What TCP Provides

TCP provides ordered delivery, a reliable byte stream, and a connection abstraction. From HTTP’s perspective, TCP is a pipe. When the client sends a request—for example a GET for the voltage endpoint on your Pi—HTTP formats that request as text and writes the bytes into the TCP connection. TCP guarantees that the bytes arrive at the other end in order, or the connection fails. TCP hides packet loss, retransmissions, and fragmentation. HTTP never sees those details. If TCP cannot deliver the bytes—because the network is down, the host is unreachable, or the connection was reset—the connection closes. HTTP then sees absence: no response, no status code, no body. So the first thing to internalize is that HTTP’s world is the stream. The stream is TCP’s responsibility. When the stream works, HTTP works. When the stream does not work, HTTP has nothing to report except that something below it failed.

TCP also establishes the connection before any data flows. The client and server perform a handshake; only then does HTTP send the first byte of the request. If the handshake fails—wrong port, firewall blocking, or host unreachable—TCP reports failure and HTTP never gets to send. So "connection refused" and "connection timed out" are TCP-level outcomes. They mean the pipe was never established. Your HTTP client or library will surface these as exceptions or error codes, but they are not HTTP status codes. They come from the layer below. When you see them, you are debugging the transport or the environment (is the server process running? is the port open? can the client reach the host?), not the HTTP message format or your application logic.

## 5) HTTP’s Core Assumption

HTTP assumes that if it can write bytes to the stream and the stream stays open, those bytes will arrive at the other end. That is the entire assumption. HTTP does not guarantee that a connection will succeed, that it will remain open, that it will be fast, or that the other side exists. If the transport fails—connection refused, timeout, DNS failure, network unreachable—HTTP has nothing to report. There is no HTTP status code for "the connection never completed." The client might raise an exception or return a timeout error; that is the client or the library deciding how to represent the absence of a response. HTTP itself never got a response to parse. So when you see "nothing came back," the first question is: did I receive a valid HTTP response at all? If not, the problem is below HTTP. If yes, the problem is in the application—the status code, the body, or the server’s logic. Programmers and tools sometimes blur this by mapping transport failures to synthetic "errors" like "connection timeout" or "connection refused." Those are not HTTP status codes; they are representations of transport failure chosen by the client or library. When you log or handle them, treat them as "no HTTP response" so that your retry logic, user messaging, and debugging stay aligned with the layer model.

## 6) Error vs Absence

This distinction is foundational. An HTTP error means you received a response. It has a status code—4xx or 5xx—and the exchange completed at the HTTP layer. The server spoke. For example your Pi might respond with 500 Internal Server Error. That is application-layer failure. The transport worked; the server received the request and sent back a response. You can log it, retry according to your rules, or show an error to the user. The response is real. Transport failure is different. There is no response object, no status code. You get a timeout, a connection-refused exception, a DNS error, or a network-unreachable error. The server may never have seen the request. That is transport-layer failure. Mixing these up leads to wrong fixes. If you treat a timeout as if it were a 500, you might waste time debugging server code when the problem is the network or the service not running. If you treat a 503 as if it were a timeout, you might add retries in the wrong place. Always ask: did I receive a valid HTTP response? Yes means HTTP layer. No means transport layer.

Even a 4xx or 5xx is useful information. It tells you the server is reachable, the request arrived, and the server chose to respond with that code. You can improve the request (fix the path, add auth, send the right body) or handle that code in the client (show a message, retry with backoff for 503). When you get nothing, you have no such information. You do not know if the request left your machine, if it reached the server, or if the response was lost on the way back. So "no response" forces you to consider the whole path: client, network, server, and back. Logging and monitoring should distinguish "HTTP error" from "transport failure" so that over time you can see whether your problems are mostly application logic (lots of 4xx/5xx) or mostly connectivity (lots of timeouts and connection errors). That split guides where you invest in fixes.

## 7) Homestead Debugging: Which Layer Failed

Your dashboard cannot load coop temperature. First question: did you receive a status code? If yes, HTTP worked. The transport delivered the request and the response. Debug application logic: why did the server return 500 or 400? Maybe the server crashed while processing, or the request was malformed. If no status code—you got a timeout, connection refused, or DNS error—the transport failed. Debug the network or the service. Connection refused usually means nothing is listening on the port: the Pi is up but the web server or API process is not running. DNS failure means the hostname did not resolve: wrong name, or DNS unavailable. Timeout means the client gave up waiting: the Pi might be offline, Wi‑Fi unstable, or the client’s timeout too short. Network unreachable means the client cannot reach the network at all. The layer determines the fix. Checking "did I get a response?" before opening server logs or tweaking application code saves time and keeps you from debugging the wrong layer.

Same discipline for other homestead systems. Your solar production logger stops updating. If the client receives 200 with stale or empty data, the problem is application logic or the data source. If the client gets a timeout, check whether the Pi running the logger is on the network, whether the Wi‑Fi link is stable, and whether the client’s timeout is long enough for a slow response. Your ESP32 in the barn fails to post temperature. If the server never logs the request, the failure is transport: the ESP32 might not be reaching the server (wrong IP, port, or network), or the connection might be dropping before the request completes. If the server logs the request but the ESP32 never sees a response, the response might be getting lost on the way back—again transport. Building the habit of "status code or not?" turns vague "it doesn’t work" into a clear next step: either fix the app or fix the network and deployment.

## 8) Why "Nothing Came Back" Feels Confusing

When nothing comes back, it is tempting to assume the server is broken. But absence usually means a network issue, the service down, the port closed, the wrong host, a firewall rule, or the client’s timeout being too short. HTTP cannot describe these failures because it never received a response. There is no HTTP message that says "connection timed out." The timeout is a decision made by the client or the transport layer. So when you see "no response," the cause lives below HTTP. Separating layers removes guesswork. You stop asking "why did the server fail?" and start asking "did the server ever get a chance to respond?" If the connection never completed, the server never had a chance. Your debugging moves to: Is the host correct? Is the port open? Is the service running? Is the network path working? Is the client’s timeout reasonable? Those are transport and deployment questions, not HTTP semantics.

On a homestead, "nothing came back" often has simple causes. The Pi lost power or Wi‑Fi and is no longer on the network. The hostname is wrong—you typed pi.local but the device is at a different .local name or a static IP. The service is not running because the process crashed or was never started on boot. A firewall on the Pi or the router is blocking the port. The client is on a different subnet or VLAN and cannot route to the server. Working through that checklist is faster than staring at application code. Once you confirm the transport works—you can reach the host and port and get some response—you can focus on HTTP: status codes, headers, and body content. Layer separation turns a vague failure into a short list of concrete checks.

## 9) Time Lives Outside HTTP

HTTP does not define how long a server may take to respond, how long a client should wait, or what "too slow" means. Timeouts are client decisions, library defaults, or transport-level settings. So the same endpoint can behave differently for different clients. A curl call might succeed because curl’s default timeout is long enough. Your Python script might hang because the library uses a longer timeout or no timeout. Your ESP32 might time out quickly because it is designed for low power and cannot wait long. Same server, same request; different behavior. That is why you cannot rely on HTTP to define "request took too long." You configure timeouts in the client or the stack below HTTP. When you design a homestead API that might be slow—for example a report that aggregates many sensor readings—you need to either make the operation faster or ensure clients use timeouts that match reality. HTTP will not do that for you.

When you integrate multiple clients—a browser, a script, an ESP32, Home Assistant—document or enforce reasonable timeouts so that "works in the browser but not on the ESP32" has a clear explanation: different timeout policies. If the server sometimes takes ten seconds under load, the ESP32’s five-second timeout will often fail while the browser’s thirty-second timeout succeeds. Fixing that might mean speeding up the server, increasing the ESP32 timeout where power allows, or returning a quick acknowledgment and doing the slow work asynchronously. In every case the fix is in your design and configuration, not in the HTTP protocol. HTTP stays silent on timing.

## 10) Reliability Is Not Absolute

TCP improves reliability. It retransmits lost segments and delivers bytes in order. It does not guarantee perfection. On a homestead network, a solar-powered Pi might reboot and drop all connections. Wi‑Fi can drop in cold weather or when the barn door is closed. An ESP32 in the garden might lose signal for minutes. The router might reset. In those cases TCP may fail to establish a connection or may lose an existing connection. HTTP cannot repair this. Your system must handle retries, backoff, graceful degradation, and cached fallback. Failure is not rare; it is structural. Designing for it means: clients retry when appropriate, with backoff so they do not hammer a struggling server; clients show "unavailable" or use cached data when the network is down; servers do not assume every request will complete. Chapter 1.01 established that request–response is the unit of work. This chapter adds that the unit of work depends on a transport layer that can fail. Your application layer design should assume that and plan for retries, timeouts, and fallbacks.

Retries must be aware of idempotency: repeating a GET is safe; repeating a POST might duplicate an action. Later chapters in this phase cover HTTP methods and safety. For now, the point is that when the transport fails, you often retry. When you retry, you need to know whether the original request might have reached the server or not. A timeout does not tell you. So retry design—how many times, with what backoff, and for which methods—builds on top of the layer model. You retry at the client because HTTP and TCP do not retry for you in a way that your application can control. The layer stack gives you a clear place to put that logic: above HTTP, in your client code, where you decide what to do when the stream fails or when the response never comes.

## 11) Message Boundaries vs Byte Stream

TCP provides a byte stream. It does not preserve message boundaries. So when HTTP sends a request or a response, it is sending a sequence of bytes. TCP does not tell the other side "this was one message." HTTP must define where one message ends and the next begins. That is why HTTP is structured text with defined delimiters: headers end with a blank line, body length can be specified by Content-Length or chunked encoding. The receiving side parses the stream to find those boundaries. Parsing errors—malformed headers, wrong length—occur at the HTTP layer. Connection errors—connection reset, timeout—occur at the TCP layer. Different failures, different layers. When you see "incomplete response" or "invalid HTTP," that is usually the HTTP layer: the bytes arrived but did not form a valid message. When you see "connection closed" or "timeout," that is usually the TCP layer: the stream broke before a complete message was delivered. Keeping that distinction clear helps you interpret errors correctly and choose the right fix.

When a connection is reused for multiple requests—HTTP keep-alive—the same TCP stream carries several request–response pairs. The client sends request one, the server sends response one, then the client sends request two, and so on. TCP does not mark where one pair ends and the next begins. HTTP does that with its format: each request and response has a defined structure so the parser can find the start and end of each message. If the connection drops in the middle of a response, the client might get a partial body. That is a transport failure (incomplete bytes) that shows up as an HTTP-level problem (incomplete message). The root cause is still the broken stream; the symptom is "invalid or truncated response." So even when the failure mode looks like "bad HTTP," asking "did the stream complete?" can point you to the real cause: the connection dropped.

## 12) Mapping to Foundational Concepts

From Section A Phase 1, the same mental models apply. The boundary is the network edge: data crosses in and out, and you must validate at that edge. Failure shows up in two forms here: HTTP error (server responded with 4xx or 5xx) and transport failure (no response). State: the connection is either open or closed; HTTP does not define connection state beyond what TCP provides. Time: how long to wait and when to retry are your decisions, not HTTP’s. Nothing new was invented. The same ideas—boundaries, failure modes, explicit handling of absence—now span machines. When you build a client that calls your Pi’s API, you are applying the same discipline: validate what comes back, handle the case where nothing comes back, and do not assume the transport is perfect. Chapter 1.01 gave you the request–response shape. This chapter gave you where that shape lives: on top of TCP, with clear separation between application-layer meaning and transport-layer delivery. The next chapter will go deeper into what HTTP is as a text protocol and how requests and responses are structured.

Observation and action still apply. The client observes the network and the response; when nothing comes back, that observation—absence—should drive action: retry, show error, use cache. The server observes the request; when the connection never completes, the server never gets to act. Failure is still normal: Section A Phase 1 Chapter 1.10 said failure is normal. Here, transport failure is normal. Design for it. Do not assume "the request will get through." Assume "sometimes it will not" and handle that case. The layer model is just a way to categorize where the failure happened so you can choose the right response. One mental model, applied across layers and machines.

## Common Pitfalls

Treating a timeout like an HTTP 500 leads to debugging the wrong place. A timeout means no response; the server might never have seen the request. Fix the network, the service, or the timeout setting, not necessarily the server code.

Assuming HTTP guarantees delivery is false. HTTP assumes the transport works. When the transport fails, HTTP has nothing to report. Design for transport failure explicitly.

Ignoring client timeout differences causes "works on my machine" bugs. Different clients and libraries use different timeouts. The same endpoint can succeed for one client and time out for another. Document or configure timeouts so behavior is predictable and so you can distinguish "server too slow" from "client gave up too soon."

Debugging application logic when the transport failed wastes time. Always ask first: did I receive a valid HTTP response? If not, debug the layer below HTTP before opening application logs. That one question keeps you from chasing the wrong failure.

## Summary

- HTTP lives on top of TCP. HTTP defines message meaning; it does not send packets or guarantee delivery.
- An HTTP error means the server responded (e.g. 4xx or 5xx). Transport failure means no response—timeout, connection refused, DNS failure, or network unreachable.
- When nothing came back, check the layer below HTTP first: host, port, service, network, timeout.
- Timeouts and retry policy are not defined by HTTP; they are client and transport decisions.
- Reliability is not absolute. Design for retries, backoff, and graceful degradation. The layer model (HTTP on TCP) tells you where to look when nothing came back.
