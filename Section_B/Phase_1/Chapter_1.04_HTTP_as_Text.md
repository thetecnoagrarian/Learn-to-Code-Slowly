# Section B Phase 1 · Chapter 1.04: HTTP as Text

The raw form of HTTP: lines of text crossing a boundary. Start line, headers, blank line, body. The exact format that makes everything else mechanical.

## Learning Objectives

By the end of this chapter, you should be able to:
- Describe the four-part structure of an HTTP message: start line, headers, blank line, body
- Explain why the blank line matters and what it separates
- Identify the request line and status line and what each carries
- Recognize that HTTP is line-oriented text with explicit boundaries

## Key Terms

- **Request line**: First line of a request: method, path, and HTTP version; tells the server what to do and to what resource
- **Status line**: First line of a response: HTTP version, status code, and reason phrase; tells the client whether the request succeeded
- **CRLF**: Carriage return plus line feed; the line ending HTTP uses; defines where lines end and where metadata stops
- **Blank line**: A single empty line (two line endings in a row); the delimiter between headers and body; the boundary between metadata and content

## 1) HTTP Is Line-Oriented Text

Chapter 1.03 defined what HTTP is—a protocol, text-based, request–response. This chapter shows the exact format. HTTP messages are composed of lines. Each line is a sequence of characters ending with a line terminator and has semantic meaning based on position. HTTP is not a blob or free-form text. It is structured, line-based text. That structure is what allows parsers to work, humans to read, and tools to interoperate. Whether you are debugging a Pi sensor API, a coop dashboard, or a solar logger, the wire format is the same. If you understand the text format, requests and responses stop feeling opaque and debugging becomes inspection instead of guessing.

HTTP lines end with carriage return followed by line feed. That pair defines where a line ends, where headers end, and where metadata stops and content begins. Many systems tolerate just a line feed, but the protocol specifies the pair. It is historical—from early network protocols and cross-platform compatibility—but it is what parsers and generators are supposed to use. When you look at raw HTTP in a log or a debugger, you will see lines. The first line of a request is the request line; the first line of a response is the status line. Every line after that until a blank line is a header. The blank line marks the end of headers. Everything after the blank line is the body until the message ends. Line orientation is what makes the format parseable and human-readable at once. When you capture a request or response in a log or a proxy, you see one line after another. The first line tells you the kind of message and its main parameters. The following lines until the blank line are headers. The blank line is the pivot. After it, the body may be long or short, but structurally it is "everything else." No binary length prefix is required to find the start of the body; the blank line is the marker. That simplicity is why you can debug HTTP with a text editor or a simple script. You do not need a special binary decoder. You need to know where lines end (CRLF) and where the blank line is.

## 2) The Four-Part Structure

Every HTTP message is a block of text with four conceptual parts: a start line, zero or more header lines, a blank line, and an optional body. No hidden sections, no invisible metadata, no implicit boundaries. Everything is visible in the raw text. The start line is always exactly one line. For a request it carries method, path, and version. For a response it carries version, status code, and reason phrase. Headers follow, one per line, each with a name and a value separated by a colon. Headers can repeat in number but the structure is the same. Then comes the blank line—exactly one empty line, meaning two line endings in a row. That blank line is the most important boundary. Before it: control information, instructions, metadata. After it: raw content, payload, the thing being transferred. Confusing this boundary breaks parsing and breaks the contract between client and server.

The body is optional. For a request, GET typically has no body; POST, PUT, and PATCH often do. For a response, some status codes imply no body (for example 204 No Content); others include a body. The body starts immediately after the blank line. HTTP does not interpret the body; it only delivers bytes. The length of the body may be indicated by a header (Content-Length) or by chunked encoding (a later topic). The point here is structure: start line, headers, blank line, body. That order is fixed. Nothing appears before the start line. No header appears after the blank line. The body, if present, is everything after the blank line until the end of the message or until the length specified by headers. This four-part structure is the same for every HTTP message, whether it is your coop temperature request or a response from a global CDN.

## 3) Request Messages

A request starts with a request line. The request line always contains three parts separated by spaces: method, path, and HTTP version. This line tells the server what you want to do, to what resource, and using which version of HTTP. Nothing else in the request makes sense without it. The method might be GET, POST, or another verb. The path is the part of the URL that identifies the resource on the server—for example the path to the voltage endpoint or the coop temperature endpoint. The version is usually HTTP/1.1. A dashboard asking the Pi for voltage would send a request line with GET, the path to that resource, and HTTP/1.1. The request line is the only place where the method and path appear in this canonical form. Headers can repeat or extend that information, but the request line is the primary signal.

After the request line come headers. Headers are one per line. Each header is a name, a colon, and a value. Headers provide context, modify meaning, and supply metadata. They do not carry the primary intent—that is the request line’s job. Host tells the server which hostname the client is asking for. Accept describes what content types the client can handle. User-Agent identifies the client. Header names are case-insensitive; different systems may send them in different casing but parsers normalize. The order of headers usually does not matter for meaning; meaning comes from the header name and value. Headers end when the message hits the blank line. From that point on, everything is body. The request body is optional. GET requests usually have no body. POST, PUT, and PATCH often have a body—form data, JSON, or other payload. If a body exists, it starts right after the blank line. HTTP does not interpret the body; it only delivers it. The server parses the body according to Content-Type and application logic. So the request has a clear shape: one request line, zero or more header lines, a blank line, then optional body. That shape is what your server’s HTTP library parses when a request arrives. When an ESP32 posts soil moisture to your Pi, it sends a request line (e.g. POST and the path to the moisture endpoint and HTTP/1.1), headers (e.g. Host, Content-Type application/json, Content-Length), a blank line, and a body (the JSON payload). The Pi’s server reads the stream, finds the blank line, and then reads the body according to Content-Length. The format is the same whether the client is a browser, a script, or an embedded device. One structure, many clients. The server does not need to know who sent the request to parse it; the format is uniform.

## 4) Response Messages

Responses mirror requests structurally. A response starts with a status line: HTTP version, status code, and reason phrase. The status line tells the client which HTTP version the server used, whether the request succeeded, and a short human-readable phrase (for example OK or Not Found). The numeric status code is what clients rely on for logic. The reason phrase is for readability and may vary; the code is the contract. The Pi replying with voltage would send a status line with HTTP/1.1, 200, and OK. That means the server is speaking HTTP/1.1, the request was successful, and the reason phrase is OK. After the status line come response headers. They describe the body (Content-Type, Content-Length), control caching, set cookies, or signal other behavior. Like request headers, they are one per line, name colon value, case-insensitive.

Response headers end at the blank line. After the blank line comes the response body. The body is optional. For 204 No Content there is no body. For 304 Not Modified there is no body. For 200 OK the body often contains the resource—HTML, JSON, or other bytes. Some error responses include a body (for example an HTML error page); others do not. The presence and length of the body are determined by status code and headers (Content-Length or Transfer-Encoding). HTTP defines the structure: status line, headers, blank line, body. It does not define what the body means. The client uses Content-Type and application logic to interpret it. So when your dashboard receives a response from the voltage endpoint, it gets a status line (e.g. 200 OK), headers (e.g. Content-Type application/json, Content-Length), a blank line, and then the body (the actual voltage value or JSON). Parsing that response means finding the status line, reading headers until the blank line, and then reading the body according to the length or encoding indicated by headers. If the response has no body (e.g. 204 or 304), the message ends at the blank line. If it has a body, the client reads exactly as many bytes as Content-Length says, or follows the chunked encoding rules. Reading too few or too many bytes would corrupt the next message on the same connection (when connection reuse is in play) or leave the parser in an invalid state. So the format is not only human-readable; it is machine-parseable in a deterministic way. The blank line and the length-related headers make the boundaries explicit.

## 5) The Blank Line Is the Boundary

The blank line is the delimiter between metadata and content. It is exactly one empty line—two line endings in a row. Nothing else. No spaces, no invisible characters. Before the blank line, every line is a header (or the start line). After the blank line, everything is body until the message ends or until the length specified by headers. Parsers use the blank line to know when to stop reading headers and when to start reading body. If the blank line is missing or malformed, parsing breaks. If a header is malformed (for example missing the colon), a parser may treat the next line as part of the same header or fail. The blank line is the one unambiguous boundary that every valid HTTP message must have. Even a message with no headers and no body has a start line followed by a blank line. So when you debug "why did my server not get the body?" or "why did the client parse the wrong thing?" check whether the message actually has a blank line between headers and body and whether nothing else is confusing the parser. The blank line is what makes the four-part structure work. On some platforms or in some languages, accidentally using a single line feed instead of CRLF, or emitting an extra space on the "blank" line, can cause the other side to treat headers and body incorrectly. When in doubt, capture the raw bytes and look for the exact sequence that denotes "end of headers": CRLF followed by CRLF. Everything before that is start line and headers; everything after is body (or the end of the message if there is no body).

## 6) HTTP Does Not Interpret the Body

HTTP does not understand HTML, JSON, images, or binary data. HTTP only transfers bytes. It labels them via headers like Content-Type and Content-Encoding and delivers them intact. Meaning lives above HTTP. The client decides how to parse the body, how to render it, how to decode it, based on headers and application logic. HTTP itself remains neutral. This separation is intentional. If the response body is HTML but Content-Type says application/json, the structure is still valid HTTP—the server sent bytes and a label. The semantics are wrong, and the client should validate and handle the mismatch. If a header is malformed, the parser may break at the blank line or when reading headers. Knowing the format helps you pinpoint where the failure is: wrong start line, bad header, missing blank line, or wrong body length. For your homestead API, when the Pi returns JSON, it must send Content-Type application/json and a valid JSON body. The HTTP layer only ensures the bytes and the header are delivered. Your application code parses the JSON and validates the schema. HTTP stays at the boundary; interpretation happens inside your program.

## 7) Seeing HTTP as a Boundary

HTTP messages are boundary crossings. The request is client to server. The response is server to client. The text format is the contract, the validation surface, the explicit interface. Nothing crosses implicitly. Everything is written down in lines of text. This connects to Section A Phase 1 Chapter 1.8 (Boundaries): validation lives at edges. The raw HTTP format is that edge. When data enters your server, it enters as a stream of bytes that you parse into a request line, headers, and body. You validate the method, path, and headers before trusting them. When your server sends a response, it sends a status line, headers, and body. The client receives bytes and parses them; the client validates status and headers before trusting the body. A coop dashboard requesting temperature, a solar logger serving production data, a poultry net status API—all use the same format. The path and body content change; the structure does not. The boundary is the same. So when you build or debug an HTTP API, you are building and defending a text boundary. Validate at that boundary. Do not trust the request line or headers without checking. Do not assume the body matches Content-Type. The format is visible; use it.

## 8) Parsing and Generating

Parsing an HTTP message means: read the first line (start line), read lines until you see a blank line (headers), then read the body according to Content-Length or Transfer-Encoding. Generating a message means: write the start line, write each header line, write the blank line, then write the body. Libraries do this for you. When you use a framework or a client library, it builds the request line and headers and parses the response. When something goes wrong, you often need to see the raw text. Log the raw request and response. Use a tool that shows the wire format. Check that the request line has method, path, and version. Check that headers are name colon value. Check that there is a blank line before the body. Check that the body length matches Content-Length if present. Parsing errors usually mean a malformed start line, a header without a colon, a missing blank line, or a body that does not match the declared length. Knowing the format lets you fix or work around those errors. Generating errors usually mean you forgot the blank line, sent headers after the body, or sent a body when the status or method does not allow one. The format is strict; the tools that generate and parse must follow it. When you write a small server or client by hand (for learning or for a minimal embedded system), you must output exactly one blank line between headers and body and use CRLF for line endings if you want maximum compatibility. When you use a library, it should do that for you; when you debug, you verify that the raw output matches the format. Parsing and generating are the two sides of the same contract. Both sides must agree on where lines end and where the blank line is. Any mismatch causes "invalid HTTP" or "connection reset" or silent misparsing. Homestead example: if your Pi’s server sometimes returns a body without a Content-Length and the client expects one, the client may hang waiting for more bytes or may misread the next request as part of the body. Getting the format right is the first step to reliable communication.

## 9) Why This Mental Model Matters

If you understand HTTP as text, you stop blaming the network blindly. You can read raw logs, debug with curl or similar tools, reason about failures, and build or fix servers and clients with confidence. Libraries assemble request lines, add headers, and parse responses into objects. That is useful. But when something goes wrong, you debug the raw text. You inspect the wire format. You ask: what is the start line? Where do headers end? Is there a body? What headers describe that body? What crossed the boundary? This works for requests, responses, logs, proxies, and debug traces. The same four-part structure appears everywhere. Your Pi’s server and a browser and an ESP32 client all produce and consume the same line-oriented format. Understanding that format keeps you grounded. Abstractions become optional. You can drop to the wire when needed. You can explain to someone else exactly what was sent and what was received. That clarity is what makes HTTP debuggable and what makes the protocol durable across decades of tools and languages. When you use a command-line tool to send a request and see the raw response, you are seeing the same bytes the server sent. When you add logging to your server to print the request line and key headers, you are inspecting the boundary. No magic. Just text. That mental model—HTTP as visible, line-oriented text—scales from a single request in a terminal to a high-traffic API. The format does not change; only the volume and the tools around it do.

## 10) Headers: Names, Values, and Conventions

Headers are key-value pairs. The name is everything before the first colon on the line; the value is the rest of the line, often with leading and trailing whitespace trimmed. Header names are case-insensitive: Host and host and HOST are the same. Values may be case-sensitive or not depending on the header; the spec defines each. Some headers can appear more than once (e.g. Set-Cookie); others should appear at most once (e.g. Content-Length). Parsers typically collect headers into a structure that allows lookup by name and may preserve order for repeated headers. When you generate headers, use one line per header, name colon space value, and CRLF at the end of each line. Do not put multiple headers on one line. Do not put the body on the same line as the last header. The blank line must be its own line (two CRLFs in a row). These conventions keep the format unambiguous. When debugging, look at header names and values; do not assume casing or order. The protocol defines meaning by name and value, not by position. If your coop dashboard sends a request and the server returns 400 Bad Request, inspect the raw request: is the request line well-formed (method space path space version)? Are the headers name colon value? Is there exactly one blank line before the body (if any)? Often the bug is a missing or duplicated blank line, or a header value that accidentally contains a newline and breaks the line structure. Fixing the format fixes the error.

## Common Pitfalls

Assuming header order matters: header order usually does not matter for meaning; meaning comes from name and value. Relying on order for logic can break when proxies or servers reorder headers.

Forgetting the blank line: metadata and body are separated by exactly one blank line. Omitting it or adding extra characters breaks parsing. Generators must output it; parsers must look for it.

Malformed headers (e.g. missing colon) break parsing. Headers must be name colon value. Invalid headers can cause the parser to misidentify the boundary or fail. Validate and sanitize when generating; handle errors when parsing.

Trusting Content-Type blindly: HTTP delivers bytes; the server can send the wrong Content-Type. Validate the header and parse the body defensively. If the body does not match the claimed type, handle the mismatch.

Confusing structure with meaning: HTTP defines structure (start line, headers, blank line, body). JSON, HTML, and image decoding are the client’s job. Do not assume the body is valid JSON or HTML just because the structure is valid HTTP. Validate structure first (did I get a complete message with a blank line and the right length?), then validate content (does the body parse and match the expected schema?).

## Summary

- HTTP is plain text, line-based, with lines ending in CRLF. Every message has a start line, headers, a blank line, and an optional body.
- The blank line separates metadata from content. It is the critical boundary; without it, parsers cannot reliably find where the body begins. Before it: start line and headers. After it: body.
- The request line carries method, path, and version. The status line carries version, status code, and reason phrase.
- HTTP transfers bytes and labels them with headers; it does not interpret the body. Meaning and parsing are the client’s (or server’s) job.
- The same four-part structure applies to every message. Seeing HTTP as text makes debugging and validation straightforward. Headers are name colon value, one per line; the blank line is mandatory between headers and body; CRLF is the line ending. Parsing and generating must respect these rules so that client and server agree on boundaries.
