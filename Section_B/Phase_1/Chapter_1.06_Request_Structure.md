# Section B Phase 1 · Chapter 1.06: Request Structure

Every HTTP request has a fixed, byte-level structure: not conceptual, not framework-specific—text with a precise layout. Servers parse in a fixed order. This chapter breaks that structure down so nothing is mysterious.

## Learning Objectives

By the end of this chapter, you should be able to:
- Describe the four-part structure of an HTTP request: request line, headers, blank line, optional body
- Explain why the order matters and what happens when it is violated
- Identify the role of Content-Length and the blank line as boundaries
- Debug request failures by checking structure: request line, headers, blank line, body length

## Key Terms

- **Request line**: First line of a request: method, path, HTTP version; must come first; answers what action, what resource, what protocol rules
- **Blank line**: One empty line after headers; delimiter between metadata and body; mandatory
- **Content-Length**: Header that declares body size in bytes; the server reads exactly that many bytes; a wrong value corrupts parsing
- **Host**: Required header in HTTP/1.1; identifies the hostname the client is requesting; minimal valid requests include at least the request line and Host

## 1) A Request Is a Message, Not an Action

An HTTP request is not an action. It does not do anything by itself. It is a message that describes what the client wants, where it wants it, and how the server should interpret the message. The server receives the message, parses it, and decides what to do. The client cannot force the server to act; it can only send a well-formed request and wait for a response. That separation is important. When your dashboard asks the Pi for voltage, it sends a request. The Pi’s server parses the request and may return 200 with data, 404 if the path is wrong, or 401 if auth is missing. The request is the input; the response is the output. Understanding the request as a message—a structured piece of text—keeps you from thinking of "sending a request" as "calling a function." The server is not obligated to do what the request says; it is obligated to parse the request and respond according to the protocol and its own logic. Chapter 1.01 through 1.05 gave you the roles, the layer, the protocol, the format, and statelessness. This chapter fills in the anatomy of the request so you can build and validate it correctly.

## 2) The Four Parts and Their Order

Every HTTP request consists of four conceptual parts, always in this order: request line, headers, blank line, optional body. Servers parse sequentially. They expect the request line first, then headers, then a blank line, then the body if any. If this order is violated, the request is malformed. HTTP is forgiving in some places (e.g. unknown headers are often ignored) but unforgiving about structure. The very first line must be the request line. It must be complete and must end with carriage return and line feed. The server cannot parse anything else until this line is read. The request line answers three questions: what action is requested (method), what resource is targeted (path), what protocol rules apply (HTTP version). Nothing else in the request makes sense without this context.

Your dashboard might send a request for voltage to the Pi, or your ESP32 might send a request for fence status. Same structure. The request line comes first. Then zero or more header lines. Then exactly one blank line. Then the body, if present, for exactly as many bytes as Content-Length (or as chunked encoding specifies). There is no "optional" order. You cannot put the body before the headers. You cannot put a header before the request line. You cannot omit the blank line when there are headers. If you understand this order, you can read or construct any HTTP request by hand and predict how a server will parse it. When a request fails with 400 Bad Request or the server hangs, the first thing to check is whether the four parts are present and in the right order.

## 3) Headers

After the request line come headers. Headers are metadata. They describe the request, not the resource. They answer questions like who is making the request, what formats are acceptable, how long is the body, whether authentication is provided, whether the connection should stay open. Technically a request can have zero headers. In practice, HTTP/1.1 requires at least Host. Most real requests include many headers—Authorization, Content-Type, User-Agent, Accept. Browsers send dozens by default. Your ESP32 might send just Host and Authorization. Your coop controller might send Host, Content-Type, Content-Length, and an API key header. Servers must be prepared for missing headers (and reject or default as appropriate), extra headers (ignore unknown ones), and unknown headers (ignore unless they are critical). They must not rely on header order. Headers are a set keyed by name, not a sequence. Your Pi server must find Host and Authorization regardless of where they appear in the list.

Each header has a name, a colon, and a value. One header per line. The colon separates name and value. Header names are case-insensitive. Values may contain spaces and often have leading or trailing whitespace trimmed by parsers. Lines end with carriage return and line feed. There is no indentation or hierarchy—flat text. Most HTTP behavior lives in headers: authentication, content negotiation, caching, compression, connection control. The request line is short; headers carry the nuance. Headers express constraints: I only accept JSON (Accept), I am authenticated as X (Authorization), do not cache this (Cache-Control), keep the connection open (Connection). They are rules the server should respect, not suggestions. Your solar logger might send Accept application/json to request JSON responses. Your coop controller might send Authorization with a bearer token. Your ESP32 might send Content-Type application/json and Content-Length when posting a sensor reading. Each header adds context the server needs to process the request correctly. When you debug a 400 or 401, check that required headers are present and correctly formatted (name colon value, no stray newlines in the value). Some servers return 411 Length Required when a body is sent without Content-Length and the server requires it. That is a structural error: the request has a body but does not declare its length. Fix it by adding Content-Length with the correct value. Optional headers like User-Agent or Accept are not required for a valid request, but they can affect server behavior (e.g. content negotiation, logging). Your minimal ESP32 client might send only Host and Content-Length and Content-Type for a POST; that is enough for the structure to be valid. Add Authorization or other headers as your API requires.

## 4) The Blank Line

After the last header there must be one blank line. This blank line is not decoration. It is the delimiter that signals: headers are finished, body may follow. The blank line is exactly one empty line—carriage return, line feed—with no header content before it. This is the boundary between metadata and content, as in Chapter 1.04. Without it, the server cannot know where headers stop. It will keep reading lines, treat the first line of the body as a header (and fail when there is no colon), and never correctly identify the body. If the blank line is missing, the server may hang waiting for more headers, or it may misparse the body as headers and return 400.

Your ESP32 sends a POST with Host and Content-Type and then immediately the JSON body with no blank line. The server reads Host, reads Content-Type, then sees the first character of the JSON (e.g. a curly brace). It tries to parse that as a header line. There is no colon. The parser fails or treats the rest of the request as malformed. This is a classic bug when hand-crafting requests or when a minimal client omits the blank line. Your dashboard sends a GET with Host but forgets the blank line. The server waits for another header line. The client has nothing more to send. The server blocks reading. The request hangs until a timeout. So the blank line is mandatory whenever there are headers. For a minimal GET with only Host, you still need the blank line after Host so the server knows the request has no body and is complete. This connects to Section A Phase 1 Chapter 1.8 (Boundaries): the blank line is the boundary inside the request between "metadata" and "payload." Validate that it is present and that it is exactly one empty line (CRLF), not spaces or missing line ending.

## 5) The Body

Not all requests have a body. Typical patterns: GET usually has no body; POST often has a body; PUT and PATCH often have bodies; DELETE sometimes has a body. The presence of a body depends on the method and on the headers. Your dashboard might GET voltage (no body) but POST a temperature reading (with body). The body is raw bytes. HTTP does not parse it, structure it, or interpret it. HTTP only knows whether a body exists, how long it is (from Content-Length or Transfer-Encoding), and how to hand those bytes to the application. The meaning of the body is determined by Content-Type and by your application logic. When a body exists, the server needs to know how many bytes to read. This is usually done with Content-Length. The server reads exactly that many bytes—no more, no less. Your ESP32 sends a JSON body that is 28 bytes. It must send Content-Length: 28 and then exactly 28 bytes of body. The server reads 28 bytes and stops. Reading too much or too little corrupts the next request on the same connection. If the server reads 30 bytes, it consumes 2 bytes that belong to the next request (or to the next part of the stream). If the server reads 25 bytes, it leaves 3 bytes in the buffer that it will wrongly treat as the start of the next request. Correct boundaries matter.

If Content-Length is too small, the body is truncated and data is lost. Your ESP32 sends Content-Length 20 but the body is actually 28 bytes. The server reads 20 bytes and stops. The remaining 8 bytes are lost, and the next request starts mid-body—parsing will fail or data will be wrong. If Content-Length is too large, the server waits for bytes that never arrive. Content-Length 50 with a body of only 28 bytes: the server reads 28 bytes, then waits for 22 more. The request hangs; the connection may time out. So Content-Length must match the actual body size exactly. When you generate a request, compute the body length after serialization (e.g. after building the JSON string) and set Content-Length to that value. Do not guess or use a fixed value. Sometimes requests use Transfer-Encoding chunked instead of Content-Length; the body is sent in chunks with explicit size markers. That is a more flexible format but still has strict rules. For most homestead APIs (Pi, ESP32, dashboard), Content-Length is the common case. Get it right and the server can parse the request reliably. When you serialize a body (e.g. JSON), the length in bytes may not equal the number of characters if the encoding is UTF-8 and you have non-ASCII characters. Always use the byte length of the serialized payload for Content-Length, not the string length in your programming language. Libraries that build HTTP requests usually do this automatically. When you build a request by hand or use a low-level API, compute the byte length after encoding. A wrong Content-Length is one of the most common causes of "server hangs" or "incomplete body" when the structure is otherwise correct.

## 6) A Complete Request

A complete minimal HTTP/1.1 request has a request line (method, path, version), at least one header (Host), a blank line, and no body. That is valid. A GET request for your Pi’s voltage endpoint might have a request line with GET and the path to the voltage resource and HTTP/1.1, a Host header with the Pi’s hostname, and a blank line. No body. The server parses the request line, reads the Host header, sees the blank line, and knows the request is complete. A POST request with a body adds Content-Type, Content-Length, optional Authorization or other headers, the blank line, then the body bytes. Your ESP32 reporting temperature would send a request line with POST and the path to the temperature endpoint and HTTP/1.1; headers for Host, Content-Type application/json, Content-Length with the exact byte count of the JSON, and Authorization if required; then the blank line; then the JSON body. The server reads the request line, parses headers, finds the blank line, then reads exactly the number of bytes declared in Content-Length. Every part has a job. There is no guessing, no scanning ahead. The server does not "look for" the body; it knows where the body starts (after the blank line) and how long it is (Content-Length). When you build a client, ensure every part is present and correct. When you debug, verify each part in order. Minimal GET requests (request line, Host, blank line) are common for dashboards and sensors that only read data. POST requests with a JSON body are common when the ESP32 or a script posts a reading: request line, Host, Content-Type, Content-Length, optional Authorization, blank line, body. PUT and PATCH follow the same pattern when updating a resource. The structure is identical across methods; only the method name and the presence or size of the body change. Once you can write one correct request by hand, you can write any of them.

## 7) The Path and Query Strings

The path in the request line is not necessarily a file, a directory, or a physical location on disk. It is a logical identifier. What it means is entirely server-defined. Your Pi might map the path for voltage to a sensor reading, the path for temp to a DHT22, the path for fence status to the poultry net energizer. A freezer sensor API might use one path for internal temperature and another for external. A drip irrigation controller might use one path for schedule and another for manual override. The path can be a single segment or many segments separated by slashes. Everything after a question mark in the request line is the query string. It is still part of the request line. The server parses it separately (to get key-value pairs or other structure), but HTTP does not care—it is just part of the path component of the request line. Your dashboard might request voltage with a query parameter for which sensor (e.g. battery bank 1). The poultry net API might accept a path with a segment for which fence zone to check. Path and query are how the client specifies "which resource" and "with what parameters." The server uses them to route the request and to decide what to return or what action to take. When you design an API, you choose the path structure and the meaning of query parameters. The request structure only requires that the request line be well-formed (method space path space version). The path and query are opaque to the protocol; meaning is in your application. Paths are often hierarchical: for example a path for sensors, then a segment for voltage, then maybe a segment for which battery bank. Query strings add options: for example a date parameter for "give me production for this date." The server parses the path to dispatch to the right handler and parses the query to get parameters. Both are part of the same request line; the server splits them for application use. Encoding matters: spaces and special characters in path or query must be encoded (e.g. percent-encoding). Libraries usually do that for you; when you build requests by hand or debug raw logs, watch for invalid or unencoded characters that can cause 400 or wrong routing.

## 8) What the Server Knows and Does Not Know

The server does not know that this is "a sensor reading," that the body "is JSON," or that the client "is the coop controller." It only knows what is in the request: method, path, headers, and body bytes. Intent is inferred from structure. Content-Type tells the server how to interpret the body (e.g. application/json). Content-Length tells it how many bytes to read. The path and query string tell it what resource is targeted. Authorization or Cookie headers tell it about identity if the application uses them. The server assembles meaning from these parts. If the request line is malformed (wrong format, invalid characters), required headers are missing (e.g. no Host), or the body does not match headers (wrong Content-Length, body shorter or longer than declared), the server can reject the request with 400 Bad Request. HTTP does not promise forgiveness. The request structure is a contract. The client promises to follow the format, declare metadata accurately, and respect boundaries. The server promises to parse according to the spec and respond—with success or with a clear error. When the contract is broken, the server may close the connection or send 400 and close. So the server "knows" only what it can parse. It does not assume anything you did not send. That is why every request must be self-contained (Chapter 1.05): the server has no memory of prior requests. This request is all it has. If the client sends a request with a typo in the path, the server does not "guess" the right path; it may return 404. If the client omits Authorization and the server requires it, the server returns 401. If the client sends Content-Length 100 with a body of 50 bytes, the server waits for 50 more bytes and may time out. The server does not "fix" the request. It parses it and either succeeds or fails with a clear response. So the client is responsible for sending a complete, correct request. The request structure is the contract. Both sides must respect it.

## 9) Debugging and the Mental Model

Frameworks and libraries generate request lines, add headers automatically, and serialize bodies. They do not change the protocol. When requests fail—400 Bad Request, 411 Length Required, or the server hangs—check the structure. Is the request line correct (method, path, version)? Are required headers present (Host for HTTP/1.1, Content-Length when there is a body)? Is the blank line present after the last header? Does Content-Length match the actual body size? Are line endings CRLF? Your dashboard gets 400 from the Pi. Check Host. Check the blank line. If there is a body, check Content-Type and Content-Length. Your ESP32 sends a POST and the server returns 400. Check Host, Content-Length, blank line, and that the body length in bytes matches Content-Length. Your coop controller sends Content-Length 30 but the body is only 25 bytes. The server reads 25 bytes, then waits for 5 more. The request hangs; eventually the connection times out. The boundary is wrong. Fix Content-Length.

Think of an HTTP request as an envelope (headers), a label (request line), and optional letter (body). The protocol reads the label and the envelope; it does not interpret the letter. Your application interprets the body using Content-Type. Understanding the structure makes frameworks predictable. When you use a library like requests in Python or fetch in JavaScript, it assembles this structure for you. But when debugging—when the Pi returns 400, when the coop controller hangs, when the solar logger rejects your request—you need to know what was actually sent. Inspect the raw request. Verify the request line. Verify the headers. Verify the blank line. Verify Content-Length matches the body. If you removed your HTTP library and had to write a request by hand, could you? If you can answer that and fix these failures, the structure is yours. The next chapter (1.07) zooms in on the request line: methods, path format, and HTTP version in detail. With this chapter you have the full request anatomy: request line, headers, blank line, body, and the rules for each part. Request Line will go deeper on what methods mean, how paths are formatted, and how the first line drives server behavior. The structure does not change; the semantics of that first line do.

## Common Pitfalls

Missing blank line: the server hangs or misparses. Always include one empty line (CRLF) after the last header. Without it, the server cannot find the start of the body or know that headers are done.

Wrong Content-Length: too small truncates the body and can corrupt the next request; too large causes the server to wait and hang. Match Content-Length exactly to the body size in bytes. Compute it after serializing the body.

Assuming header order: servers must find headers by name, not position. Do not assume Authorization comes first or Content-Length comes last. Send all required headers; order does not define meaning.

Forgetting Host: HTTP/1.1 requires it. A minimal valid request still needs a request line and Host (and the blank line). Without Host, many servers return 400.

## Summary

- An HTTP request has a fixed structure: request line first, headers next, one blank line, optional body. The server parses in that order. Nothing is implied; everything is explicit.
- The request line carries method, path, and version. Headers carry metadata (Host required in HTTP/1.1; Content-Type and Content-Length when there is a body). The blank line separates metadata from body. The body length is declared by Content-Length (or chunked encoding).
- The path is a logical identifier, server-defined. Query string is part of the request line. The server knows only what it can parse from the request; it does not assume intent.
- When debugging 400 or hangs, check request line, required headers, blank line, and Content-Length vs actual body size. Structure first, then semantics.
