# Section B Phase 1 · Chapter 1.07: The Request Line

The request line is the first line of every HTTP request. Nothing comes before it. Nothing can be understood without it. If it is malformed, the request fails immediately. This single line defines what the client wants, where it wants it, and which rules apply.

## Learning Objectives

By the end of this chapter, you should be able to:
- Describe the three parts of the request line: method, path, HTTP version
- Explain why the order matters and what happens when spacing or structure is wrong
- Distinguish the request line path from the full URL (scheme, host, port)
- Debug request-line errors: unknown method, missing path, invalid spacing, wrong version

## Key Terms

- **Method**: The first token (e.g. GET, POST, PUT, PATCH, DELETE); tells the server what kind of operation the client is requesting
- **Path**: The second token; the request target—absolute path and optional query string; identifies the resource
- **HTTP version**: The third token (HTTP/1.0 or HTTP/1.1); tells the server which protocol rules apply

## 1) The Request Line Is Mandatory

Every HTTP request begins with exactly one request line. If the server does not receive a valid request line, it cannot parse headers, determine intent, or respond meaningfully. The request line is not optional or implied. It must be explicit. Chapter 1.06 showed the full request structure: request line, headers, blank line, body. This chapter zooms in on the first line. Everything else in the request—headers, body, semantics—depends on this line being correct. Whether your dashboard fetches voltage from the Pi, your ESP32 reports temperature, or your coop controller checks fence status, the request line structure is the same.

The request line always contains three components, in this order: method, path, HTTP version. They are separated by single spaces. No more, no less. In formal terms: method, space, request-target, space, HTTP-version, then carriage return and line feed. This grammar is strict. Servers parse sequentially. They expect the method first, then the path, then the version. If the order is wrong or a component is missing, parsing fails. The server does not guess, reorder, or infer. The smallest valid request line has a method, one space, at least a slash for the path, one space, and the HTTP version (e.g. HTTP/1.1). A request for the root resource might use a path of just slash. A request for your Pi’s voltage endpoint uses a path like slash api slash voltage. Same structure, different path. Once the server reads the request line, it knows whether to expect a body (depending on method and headers), which headers are required (e.g. Host for HTTP/1.1), and how to interpret the rest of the message. That is why the request line must come first.

## 2) The Method

The first token is the method. GET, POST, PUT, PATCH, DELETE are the most common. Other methods exist (e.g. HEAD, OPTIONS, CONNECT) for specific uses. The method tells the server what kind of operation the client is requesting. Servers typically allow only a subset of methods per path. Your voltage endpoint might accept only GET. Your temperature-posting endpoint might accept only POST. If the client sends a method the server does not allow for that path, the server responds with 405 Method Not Allowed. So the request line method is not just informational; it is part of the routing and authorization contract. Sending the wrong method is as fatal as sending the wrong path—you get a clear error (405) and the server does not execute the operation. Methods are not labels, documentation, or hints. They are semantic instructions. A server may accept a method, reject it with 405 Method Not Allowed, or treat different methods differently. It will not ignore the method. The HTTP specification treats methods as case-sensitive tokens. In practice, methods are always uppercase. Lowercase get or post may be rejected by strict servers. Always use uppercase when building requests.

GET retrieves a representation. The client asks: give me the representation of this resource. GET requests should not change server state and typically have no body. Your dashboard might send GET for voltage, coop temperature, solar production, or poultry net status—retrieval only. POST sends data to the server, often creates resources, and often includes a body. Your ESP32 might POST temperature data: here is the reading, store it or process it. Your drip irrigation controller might POST a manual override command. PUT replaces the entire target resource. Your dashboard might PUT configuration: this configuration should now look exactly like this. PATCH modifies part of a resource without replacing the whole thing. Your coop controller might PATCH fence settings: change the voltage threshold, leave other settings alone. DELETE asks the server to remove a resource. Your dashboard might DELETE a sensor from the system. Each method has distinct semantics. They are not interchangeable. Later chapters will cover safety and idempotency; for now, the point is that the method is the first thing the server reads and it drives routing and behavior. Many APIs are designed so that the same path supports different methods: GET to read, PUT to replace, PATCH to update, DELETE to remove. The server looks at both the path and the method to decide what to do. So the request line as a whole—method plus path—identifies the operation. A request with GET slash api slash config and a request with PUT slash api slash config have the same path but different methods and different semantics. The server might allow both and do different things, or allow only one and return 405 for the other. When you design an API, you choose which methods each path accepts. When you consume an API, you send the method the server expects. Sending POST when the server only allows GET for that path will get you 405. The request line is the contract; the server enforces it.

Important: the method expresses intent. The server decides behavior. A server may ignore semantics (bad practice), reject certain methods (405), or treat GET as mutating (wrong but possible). HTTP defines meaning; servers enforce policy. When you get 405 Method Not Allowed, the request line method is the cause. When you design an API, you choose which methods each path supports. Your voltage endpoint might allow only GET. Your temperature posting endpoint might allow only POST. The request line carries that intent; the server enforces it.

## 3) The Path

The second component is the path. The path identifies the request target. Your Pi might map the path for voltage to a voltage sensor, the path for temp to a temperature sensor, the path for fence status to the poultry net energizer. A freezer sensor API might use one path for internal temp and another for external. A solar logger might use one path for production and another for inverter status. The path does not include scheme, host, or port. Those live in the Host header or in the connection (you connected to a host and port; the path is relative to that). Only the path and optional query string appear in the request line. In HTTP/1.1, the request line uses an absolute path: it starts with a slash. The host is specified separately in the Host header. Your dashboard sends a request with path slash api slash voltage; the Host header has the Pi’s hostname. The full URL in the browser or in your head is scheme plus host plus port plus path; the request line contains only the path (and query). That separation matters when you use proxies or when you log requests: the request line alone does not tell you which host was targeted unless you also have the Host header.

Everything after a question mark in the path token is the query string. It is still part of the request line. Your dashboard might request voltage with a unit parameter to get volts, or temp with a location parameter to get coop temperature. HTTP does not parse query strings. That is application logic. The server receives the full path including query string and decides how to interpret it. HTTP does not care what the path means—whether it refers to a file, a resource, or an action. It is just text. The same path can mean different things on different servers. The voltage path on your Pi returns a JSON reading. The temp path on your solar logger might return solar panel temp. The same path on a different server might return 404. The path is a name, not a guarantee. When you design an API, you define what paths mean. When you consume an API, you send the path the server expects. Case and punctuation matter unless the server documents otherwise.

Most servers treat paths as case-sensitive. Slash API slash voltage is not the same as slash api slash voltage. Assume case-sensitive unless documented otherwise. Paths often imply hierarchy—sensors, sensors slash one, sensors slash one slash readings—but this is conventional, not enforced by HTTP. Your Pi might map sensors slash one to sensor ID 1, or treat it as a flat identifier. The server decides. Trailing slashes matter. Slash api slash voltage and slash api slash voltage slash are different paths. Some servers normalize (redirect one to the other); some do not. Do not assume equivalence. When you get 404 Not Found, check the path character for character: casing, slashes, and query string. A typo or wrong case is a common cause. Paths and query strings may need percent-encoding for special characters (spaces, ampersands, equals in query values). Libraries typically encode automatically. When you build a request by hand or log the raw request line, unencoded characters can cause 400 or wrong routing. The path is sent as-is in the request line; the server decodes it and interprets it. So the path in the request line is the encoded form. For example a space in a query value is often sent as percent-20. Understanding that the request line carries the path exactly as the client sent it helps when debugging: if the server expects a different path format, the client must send that format. No automatic normalization is guaranteed at the protocol level. The client sends the path; the server interprets it.

## 4) The HTTP Version

The third component is the HTTP version. HTTP/1.0 or HTTP/1.1. This tells the server which protocol rules apply. The version is not cosmetic. It affects required headers, connection behavior, parsing rules, and defaults. HTTP/1.1 requires the Host header. HTTP/1.1 defaults to keep-alive (persistent connections). HTTP/1.0 typically closes the connection after one response. A server may behave very differently depending on version. If the server does not support the version (e.g. it only supports HTTP/1.1), it may reject the request, return 505 HTTP Version Not Supported, or attempt to downgrade. Clients should not lie about versions. Your dashboard sends HTTP/1.0 but the Pi expects HTTP/1.1; the server might reject it or treat the request as 1.0 and close the connection after the response. Check the version in the request line when debugging. Libraries usually send HTTP/1.1 by default. If you are building a minimal client (e.g. on an ESP32), send HTTP/1.1 unless you have a reason not to; that way you get Host requirement and keep-alive behavior that match what most servers expect. Sending HTTP/1.0 to a server that supports only 1.1 might still work if the server is lenient, but the server may close the connection after one request (1.0 default). Sending a version the server does not support at all can result in 505 HTTP Version Not Supported or a closed connection. So the version in the request line is not just documentation; it affects whether the request is accepted and how the connection behaves. When you see "connection closed after first request" or "server rejected my request," check the version token. It must match what the server supports and should usually be HTTP/1.1 for modern APIs.

## 5) Whitespace and Termination

Between the three components there must be exactly one space. No tabs. No extra spaces. Two spaces between method and path—many parsers fail or treat the path as starting with a space. Two spaces between path and version—same problem. Your ESP32 must send exactly one space between each component, or the Pi may reject the request with 400 Bad Request. The request line must end with carriage return and line feed. This marks the end of the line and the beginning of the first header. Without correct line termination, the server may keep reading and try to parse the first header as part of the request line, or it may fail to find the boundary between request line and headers. So: method, space, path, space, version, CRLF. That is the only valid shape.

Extra spaces inside the path or version are also a problem. The path is a single token; if it contains spaces (which are rare and usually encoded), the server must see them as part of the path. In practice, paths do not contain raw spaces; they use percent-encoding. The version token is exactly HTTP slash 1.1 or HTTP slash 1.0—no extra spaces. When you hand-craft a request or debug raw output, verify that there is exactly one space between method and path and between path and version, and that the line ends with CRLF. Many "mysterious" 400 errors come from an extra space or a missing CRLF. On some platforms or in some languages, line endings are represented as just line feed (LF) instead of CRLF. HTTP specifies CRLF. Servers may accept LF for the request line in practice, but they are not required to. If your client runs on a system that uses LF by default, ensure you send CRLF at the end of the request line (and at the end of each header line) for maximum compatibility. When you capture a raw request and it looks correct but the server returns 400, look at the exact bytes at the end of the first line. Missing CR or LF can cause the server to misparse or reject the request. The request line is strict: three tokens, two spaces, CRLF. Nothing else.

## 6) The Request Line as Boundary

Section A Phase 1 boundary principle applies: the request line is the first boundary crossing in the request. Malformed input should be rejected immediately. Validation begins here. Common request-line errors: unknown method (e.g. FETCH is not a standard method—use GET), missing path (nothing or wrong spacing between method and version), unsupported version (server only supports 1.1, client sent 2.0), invalid spacing (two spaces, or no space, between components). These usually result in 400 Bad Request and often an immediate connection close. Your ESP32 sends a request with two spaces between method and path. The Pi responds 400 Bad Request and may close the connection. Your coop controller sends GET with HTTP/2.0 but the Pi only supports HTTP/1.1—the server may reject with 505 or downgrade. If a server responds 405 Method Not Allowed, the method in the request line caused that. If a request works in one environment (e.g. browser) but not another (e.g. script or ESP32), the path or version might differ—different client, different request line. If a server says 400 Bad Request, inspect the request line first: method, path, version, spacing. Given a raw request, ask: what is the method? What is the path? What version? Most HTTP bugs become obvious when you inspect the request line.

Proxies sometimes use a different request-target form (e.g. absolute URL including scheme and host in the path). That is for proxy use; normal clients use the absolute path form. Your homestead might use a reverse proxy that forwards requests; the proxy may rewrite the request line. Every HTTP library constructs the request line, validates spacing, and inserts the version. Understanding this line lets you debug library behavior and hand-craft requests when needed. Within a single request there is exactly one request line. Headers follow, then the blank line, then the body. If you see multiple request lines in one request, something is wrong—wrong client, wrong proxy, or corrupted stream. Think of the request line as the label on the envelope: it tells the server how to open the message and what to do next. Everything else is inside. When connection reuse is in play (Chapter 1.05), the same TCP connection may carry multiple requests. Each request still has exactly one request line. The server reads the first line of the next request only after it has finished reading the previous request (headers, blank line, body). So there is no ambiguity: the first line the server sees after the previous response is the next request’s request line. If that line is malformed, the server rejects that request and may close the connection. The request line is the start of every request, whether it is the first on a connection or the tenth. Parsing is always the same: read one line, validate method space path space version CRLF, then proceed to headers.

## 7) Mapping to Request Structure and Responses

Chapter 1.06 gave you the four-part request: request line, headers, blank line, body. The request line is the first part. The server parses it before it reads any header. If the request line is invalid, the server may not bother parsing the rest; it may send 400 and close the connection. So the request line is the gate. Once it is valid, the server reads headers, finds the blank line, and reads the body (if any). The method in the request line influences whether the server expects a body (e.g. POST usually has one; GET usually does not). The path in the request line is what the server uses to route the request to the right handler. The version determines required headers and connection behavior. All of that flows from this one line. The next chapter (1.08) switches to the response: status line, headers, blank line, body. The response has a similar structure but the first line is the status line (version, status code, reason phrase), not the request line. Understanding the request line fully prepares you to understand how the server responds—because the response is always to this request, and the status line is the server’s first-line reply. The status line (Chapter 1.08) will have a similar form: version, space, status code, space, reason phrase, CRLF. So the first line of the request and the first line of the response mirror each other in structure: fixed tokens, single spaces, CRLF. The request line carries client intent; the status line carries server outcome. Together they bookend the exchange. When you debug, you often compare them: what did the client ask for (request line) and what did the server say (status line)? That comparison tells you whether the problem was in the request (wrong method, wrong path, wrong version), in the server’s handling (500, 503), or in authorization or other headers (401, 403). The request line narrows the search. Get the request line right and you have a solid foundation; get it wrong and the rest of the request may never be interpreted correctly.

## 8) Homestead Examples: Request Line in Practice

Your dashboard requests voltage from the Pi. The request line might be GET, space, slash api slash voltage, space, HTTP/1.1. Method: GET (retrieve). Path: slash api slash voltage. Version: HTTP/1.1. The Host header carries the Pi’s hostname. Your ESP32 posts temperature. The request line might be POST, space, slash api slash readings slash temp, space, HTTP/1.1. Method: POST (send data). Path: slash api slash readings slash temp. Version: HTTP/1.1. The body contains the JSON reading; Content-Length and Content-Type are in the headers. Your coop controller checks fence status. The request line might be GET, space, slash status slash fence, space, HTTP/1.1. Same structure. Your solar logger requests production for a date. The request line might be GET, space, slash production question mark date equals 2025-01-30, space, HTTP/1.1. The path includes the query string. In every case the request line is method, space, path (with or without query), space, version, CRLF. When something goes wrong—400, 404, 405—check the request line first. Wrong method for that path? 405. Wrong path? 404. Malformed line? 400. The request line is the first place to look. When you add a new endpoint to your Pi (e.g. a new path for a new sensor), clients must use that exact path in the request line. Document the path and whether it supports GET, POST, or other methods. If you change the path structure (e.g. from slash voltage to slash api slash voltage), all clients must be updated. The request line is the contract. Both client and server must agree on method and path. Version is usually HTTP/1.1 for both. With that agreement, the rest of the request (headers and body) can be interpreted correctly. Without it, the request fails at the first line.

## Common Pitfalls

Extra spaces between method, path, and version: use exactly one space. Two spaces or no space causes 400 Bad Request or misparsing.

Wrong method: FETCH is not a standard method; use GET. Invented or typo methods may be rejected. Methods are case-sensitive; use uppercase (GET, POST, not get, post).

Wrong or unsupported version: HTTP/1.0 vs HTTP/1.1 affects Host requirement and connection behavior. A request that works with 1.1 may fail with 1.0 if Host is missing. Sending HTTP/2.0 to a server that only supports 1.1 may yield 505 or connection close.

Trailing slash: slash api slash temp and slash api slash temp slash may differ. Assume they are different unless the server documents normalization.

Path case: slash API slash voltage may not match slash api slash voltage. Paths are often case-sensitive; match the server’s expectation exactly. Missing or wrong path: the path must be present between method and version. A request with method and version but no path (or only space) is malformed. Use at least a slash for the root resource. Query string encoding: if the query string contains special characters, they must be percent-encoded. Wrong encoding can cause 400 or wrong parameter values on the server.

## Summary

- The request line is the first line of every HTTP request. It has exactly three parts: method (what the client wants to do), path (request target, including optional query string), HTTP version (which protocol rules apply).
- The three parts are separated by single spaces and terminated by CRLF. Parsed before anything else. If the request line is wrong, the server may reject the request with 400 or 405 or 505 before parsing headers or body.
- The path does not include scheme, host, or port; those are in the connection and the Host header. The method drives semantics (GET retrieve, POST send, etc.); the server enforces policy. The version affects required headers and connection behavior.
- When debugging 400, 404, or 405, inspect the request line first: method, path, version, spacing. One request line per request; exactly one space between tokens; CRLF at end. Path is absolute (starts with slash); host is in the Host header. Method and path together define the operation; the server enforces which methods each path accepts.
