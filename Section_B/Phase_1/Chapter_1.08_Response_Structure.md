# Section B Phase 1 · Chapter 1.08: Response Structure

A response is the server’s half of the HTTP contract. The client speaks first; the server responds exactly once. The response tells the client what happened, what data if any is included, and how to interpret it. If the response is malformed, the client cannot safely proceed.

## Learning Objectives

By the end of this chapter, you should be able to:
- Describe the four-part structure of an HTTP response: status line, headers, blank line, optional body
- Explain status code classes (2xx, 3xx, 4xx, 5xx) and how they affect client behavior
- Distinguish absence of response (transport failure) from HTTP error responses
- Debug response failures by checking status line, headers, and body boundaries

## Key Terms

- **Status line**: First line of a response: HTTP version, status code, reason phrase; the server’s primary signal
- **Status code**: Three-digit integer; 2xx success, 3xx redirection, 4xx client error, 5xx server error; machine signal, not decoration
- **Reason phrase**: Human-readable text (e.g. OK, Not Found); informational only; the status code is authoritative

## 1) Responses Always Follow Requests

A response cannot exist on its own. No request means no response. One request means one response. The server never sends two responses to one request. If the server sends nothing—connection drop, timeout, crash—the client experiences absence, not an error response. Chapter 1.02 and 1.12 cover that distinction. Here we focus on the structure of a valid response. Every HTTP response has up to four parts, in this order: status line, headers, blank line, optional body. This mirrors the request structure exactly, with one substitution: the status line replaces the request line. Nothing comes before the status line. Chapter 1.06 gave you the request structure; Chapter 1.07 gave you the request line. This chapter gives you the server’s reply. Whether your Pi responds to a voltage query, your ESP32 receives a temperature confirmation, or your coop controller gets a fence status update, the response structure is the same. The structure is not flexible or negotiable. It is the same line-oriented, four-part format: first line, headers, blank line, body.

## 2) The Status Line

Every HTTP response begins with a status line. If the client does not receive a valid status line, the response is invalid, the client cannot interpret anything else, and the connection may be in an undefined state. The status line always contains three parts: HTTP version, status code, reason phrase. Separated by single spaces. Terminated by carriage return and line feed. The response begins by declaring the protocol version. Your dashboard sent a request with HTTP/1.1; your Pi typically responds with HTTP/1.1 in the status line. This tells the client which parsing rules apply and which behaviors are allowed. Servers usually respond using the same HTTP version the client used in the request, or they downgrade. Version mismatch can cause parsing errors or connection handling issues. The status code is a three-digit integer. This is the most important part of the response. Clients interpret meaning from this number, not from the reason phrase. Status codes are control signals. Clients use them to decide whether the request succeeded, whether to retry, whether to redirect, whether to show an error to the user. The first digit defines the class: 1xx informational (rare in practice—e.g. 100 Continue during request body upload), 2xx success, 3xx redirection, 4xx client error, 5xx server error. That classification is foundational. Later chapters will cover specific codes (200, 201, 204, 301, 302, 400, 401, 404, 500, etc.). Here the point is that the status line carries this number and that the number’s first digit tells the client which class of outcome occurred. The client can branch on the class even before parsing the body: 2xx often means "use the body"; 3xx means "look at Location"; 4xx means "do not retry the same request"; 5xx means "retry might help." The reason phrase comes third: OK, Not Found, Internal Server Error. Clients must not rely on it. It may vary, be localized, or be omitted. The status code is authoritative. Your Pi might send 204 with no reason phrase after a successful DELETE. Clients must not break if the phrase is missing or different. So: version, space, code, space, phrase (optional in practice), CRLF. Same strict format as the request line, different content. Version and code are required; the reason phrase is optional for parsers but usually sent. The status line must be the first line the client reads after sending the request. If the connection is reused (keep-alive), the client finishes reading the previous response (status line, headers, blank line, body), then sends the next request. The next thing the client reads is the next response’s status line. So there is exactly one status line per response, and the status line is always the first line of that response. Malformed status line (wrong format, missing version or code, bad spacing) means the response is invalid. The client may close the connection or treat the stream as corrupted. Servers must generate a valid status line for every response. Clients must parse it before interpreting anything else.

## 3) Status Code Classes

A 2xx status means the server received the request, understood it, and successfully processed it. Important: 2xx means the request succeeded at the protocol level. It does not mean the body is what you expected or that the data is "good." Your dashboard sends a request for voltage and gets 200 OK with a body indicating sensor offline. The request succeeded—the server processed it and returned a valid response. The content of the body says the sensor is offline. Your solar logger returns 200 OK with an empty body because no production data exists yet today. The request succeeded. Your coop controller gets 200 OK with an HTML error page instead of JSON because the Pi returned a generic error page. The request succeeded at the protocol level; the body format is wrong. The client must validate Content-Type and parse the body accordingly. 200 OK with an empty body, or with HTML instead of JSON, is still success. Check the status code first; then check headers and body. Do not assume 200 means "I got the data I wanted." It means "the server accepted the request and sent a response."

A 3xx status means the request was valid and the resource is elsewhere; the client should take additional action (typically follow the Location header). A redirect is not an error. It is the server telling the client: you asked correctly, but look over here instead. Your dashboard requests voltage at an old path; the Pi moved it. The server responds with 301 Moved Permanently and a Location header pointing to the new path. The client can redirect the user or resend the request to the new URL. 302 Found is a temporary redirect; 304 Not Modified means the cached version is still valid and no body is needed. Redirects are instructions, not failures. The client’s job is to follow them when appropriate.

A 4xx status means the client made a request, the server understood it, and the server refuses or cannot fulfill it due to something about the request or the client. Client error does not mean the connection failed. It means the server sent a response and that response says "something is wrong with your request or your authorization." Your ESP32 sends a request without authentication. Your Pi responds 401 Unauthorized. The request is syntactically correct but missing or invalid auth. Your dashboard requests a path that does not exist. Your Pi responds 404 Not Found. Your drip irrigation controller sends a POST with malformed JSON. Your Pi responds 400 Bad Request. Each 4xx has a specific meaning. Fix the request accordingly before retrying. Retrying the same request without fixing it usually does not help. 401 means fix the token or credentials. 404 means fix the path or accept that the resource does not exist. 400 means fix the request body or headers.

A 5xx status means the request was valid but the server failed while processing it. Your dashboard requests voltage, but the Pi’s sensor reading code crashes. The server responds 500 Internal Server Error. In principle, 4xx means client responsibility—fix the request. 5xx means server responsibility—the server failed. Clients may retry 5xx responses after a delay; the server might recover. They usually should not retry 4xx responses without changing the request. Your dashboard gets 500 from the Pi. The request was valid; the server crashed. Retry might work. If you get 401, retrying with the same token will not help—fix the auth first. So the status code class drives the debugging and retry strategy: 2xx success, 3xx follow redirect, 4xx fix request, 5xx consider retry. When you build a server, you choose which status code to return for each outcome. When you build a client, you must handle each class: show success for 2xx, follow Location for 3xx, show error or fix request for 4xx, show error and maybe retry for 5xx. Do not ignore the status code. Do not assume 200. Check the numeric code every time. Libraries often expose it as response.status_code or response.status. Use it. Your dashboard should not treat 500 the same as 200. Your ESP32 should not treat 401 the same as 201. The status code is the server’s way of saying what happened. The client’s job is to react accordingly.

## 4) Response Headers

After the status line come zero or more headers. Same structure as request headers: name, colon, value, one per line, CRLF. Response headers describe the body (if any), caching rules, redirect targets, cookies, and server behavior. They do not contain the content itself. Common response headers: Content-Type (format of the body—e.g. application/json for your Pi’s voltage response), Content-Length (size of the body in bytes), Location (redirect target for 3xx), Cache-Control (caching rules—e.g. no-cache for real-time sensor data), Set-Cookie (session data if your dashboard uses sessions), Date (server timestamp). Headers are case-insensitive. Order does not matter. Clients read headers as a set keyed by name. When the response has a body, Content-Type tells the client how to interpret it. Content-Length tells the client how many bytes to read. Without Content-Length (or Transfer-Encoding chunked), the client may not know when the body ends. So for responses with a body, the server should send Content-Type and Content-Length (or use chunked encoding). Your Pi responds to a voltage request with Content-Type application/json and Content-Length 24 and a 24-byte JSON body. Your dashboard reads the status line, reads headers until the blank line, then reads exactly 24 bytes. That is the body. Parsing is deterministic. Wrong Content-Length corrupts the next response on the same connection (when keep-alive is used). The server must send exactly as many body bytes as it declares. Other response headers matter for specific features: Set-Cookie sends a cookie to the client (the client will send it back in future requests); Cache-Control tells the client (and caches) how long to cache or whether to revalidate; Date gives the server’s idea of the current time. For a simple sensor API you might only need Content-Type and Content-Length. For a dashboard with login you might add Set-Cookie. For cacheable data you might add Cache-Control. The structure is the same: name colon value, one per line, until the blank line.

## 5) The Blank Line and Body

After the last header there must be a blank line. This blank line marks the end of headers and the start of the body (if any). Section A Phase 1 boundary principle applies: everything before the blank line is metadata; everything after is payload. Clients must respect this boundary. Without the blank line, the client cannot know where headers end and body begins. A response may include a body. Some responses never include a body: 204 No Content (e.g. successful DELETE), 304 Not Modified (cached version still valid), and responses to HEAD requests. Your dashboard sends DELETE for a sensor. Your Pi responds 204 No Content with no body—the deletion succeeded, nothing to return. Your poultry net API might return 204 after a successful configuration update. For 200 OK, the response often has a body—the representation of the resource. HTTP does not interpret body content. The body is a stream of bytes. The client interprets it using Content-Type and application logic. Your Pi responds with Content-Type application/json; your dashboard parses the body as JSON. Your solar logger returns production data as JSON. Your coop controller expects JSON from the fence status endpoint. Without Content-Type, the body is ambiguous. Validate the header before parsing. The response ends when Content-Length bytes are read, or the connection closes, or the chunked stream ends. After that, the client may send another request if the connection is open (HTTP/1.1 keep-alive) or close the connection. If the server sends more bytes than Content-Length, or fewer, the client’s read of the next response can be corrupted. So the server must send exactly what it declares. Same rule as for requests (Chapter 1.06): boundaries matter. When the response uses Transfer-Encoding chunked instead of Content-Length, the body is sent in chunks; each chunk has a size and the stream ends with a zero-length chunk. The client reads until the end of the chunked stream. For many homestead APIs (Pi, ESP32, dashboard), Content-Length is the common case. When you build a server, ensure the body length matches Content-Length exactly. When you build a client, read exactly the number of bytes declared (or follow chunked rules). Reading too few leaves bytes in the buffer that will be misread as the next response. Reading too many consumes part of the next response. Both corrupt the connection when keep-alive is used.

## 6) Parsing and Debugging

Clients parse responses sequentially: read status line, parse status code (and version, reason phrase), read headers until blank line, read body if present (using Content-Length or chunked encoding). Failure at any step invalidates the response. There is no guessing or scanning ahead. The status line tells the client whether to expect a body (e.g. 204 and 304 typically have no body). Headers tell the client how to interpret the body and how many bytes to read. The blank line tells the client where the body starts. Content-Length tells the client when the body ends. Given the same response bytes, every compliant client parses them the same way. When something goes wrong, ask: did I receive any HTTP response? If no—timeout, connection reset—that is transport failure (Chapter 1.02). If yes, what status code was returned? 2xx: request succeeded; check body and Content-Type. 3xx: follow redirect. 4xx: fix the request. 5xx: server error; retry might work. Your ESP32 sends a POST and gets no response. Transport failure. Your ESP32 sends a POST and gets 400. The server understood the request but rejected it—fix the request. Your dashboard gets 500 with a body containing an error message. The request was valid; the Pi’s code crashed. Retry might work. Your dashboard gets 401. Fix the auth token first. These questions determine the entire debugging path. Frameworks and libraries parse the response structure for you. Understanding it removes mystery and lets you debug when the library’s behavior is wrong or when you are building a minimal client.

## 7) Absence Is Not a Response

If the connection drops, the server crashes before sending a response, or the network fails, there is no response. That is not 5xx. It is absence. Your dashboard sends a voltage request but the Pi’s Wi‑Fi disconnected. No response arrives. That is not 500 Internal Server Error—500 would be a valid HTTP response with a status line and (usually) a body. Absence means the client never got a status line. The client experiences a timeout or connection error, not an HTTP status. The server cannot send explanations later or clarify intent afterward. Everything it wants the client to know must fit in the response. So when you handle "no response" in your client code, you are handling transport failure. When you handle 4xx or 5xx, you are handling an HTTP response. Different code paths. When you log or debug, distinguish "no response" (transport) from "got 500" (HTTP response, server error) from "got 401" (HTTP response, client error). Your dashboard gets 200 OK with no body. The request succeeded but there is no data. Check: is Content-Length 0 present, or is the body missing? Both are valid. The status code says success. Your coop controller gets 302 Found—check the Location header for where to look next. The redirect is an instruction. Follow it. Do not treat 3xx as an error unless your application explicitly does not support redirects. Absence is the only case where there is no status code. Every HTTP response has one; if you did not get one, you did not get an HTTP response. Everything else is a response with a status line, and the status code is the first thing to inspect.

## 8) Mapping to Request and Previous Chapters

Chapter 1.06 gave you the request structure: request line, headers, blank line, body. The response structure is the same: status line, headers, blank line, body. The request line carries method, path, version. The status line carries version, status code, reason phrase. They are the same shape (three tokens, single spaces, CRLF) but different meaning. The client sends the request line; the server sends the status line. After that, headers and body follow the same rules: name colon value for headers, blank line, then body with length declared by Content-Length or chunked encoding. So the response is the mirror of the request. When you build a server, you generate a status line, then headers, then a blank line, then the body. When you build a client, you parse the status line first, then headers, then blank line, then body. Chapter 1.02 said: if you get a status code, the transport worked and the failure is at the HTTP or application layer. If you get no response, the transport failed. This chapter filled in what "get a status code" means: you got a valid status line with a three-digit code. That code, plus headers and body, is the full response. The next chapter (1.09) will go deeper into status code ranges and how clients use them. Here we established the structure. There, we establish the semantics of each range. Section A Phase 1’s boundaries apply: the response is a boundary from the client’s perspective. The client receives bytes and parses them into status line, headers, and body. The client must validate: status code, Content-Type, body length. Do not trust the body without checking the headers. Do not assume success without checking the status code. The response is the server’s output; treat it as untrusted until parsed and validated. That discipline—structure first, then interpret—matches what you learned for requests and for boundaries in general. Validate status code, then headers, then body.

## 9) Homestead Examples: Response Structure in Practice

Your dashboard requests voltage from the Pi. The Pi responds with a status line: HTTP/1.1, 200, OK. Then headers: Content-Type application/json, Content-Length 24, maybe Date and Cache-Control. Then a blank line. Then 24 bytes of JSON. The dashboard parses the status line (200 success), reads headers (Content-Type and Content-Length), finds the blank line, reads 24 bytes, and parses the JSON. Your ESP32 posts temperature. The Pi responds with 201 Created or 200 OK, headers, blank line, and maybe a body with the created resource or a confirmation. The ESP32 must check the status code. 2xx means success. 4xx means the request was wrong—maybe auth, maybe validation. 5xx means the server failed—retry later. Your coop controller requests fence status. The Pi responds with 200 OK and a JSON body with voltage and status. If the Pi moved the API to a new path, the server might respond with 301 and a Location header. The client would then request the new URL. Your solar logger returns 200 with production data or 200 with an empty array if there is no data yet. In every case the response has a status line, headers, blank line, and optionally a body. When you debug "the server returned something wrong," inspect the status code first. Then Content-Type and Content-Length. Then the body. Structure first; then content. When you add a new endpoint to your Pi that returns JSON, you must send a status line (e.g. 200 OK), Content-Type application/json, Content-Length with the exact byte length of the JSON, a blank line, and then the body. If you forget the blank line, the client will try to parse the first bytes of the body as a header and fail. If you send the wrong Content-Length, the client will read the wrong number of bytes. Getting the response structure right is as important as getting the request structure right. The server is the producer of the response; the client is the consumer. Both must agree on the format.

## Common Pitfalls

Confusing absence with 5xx: no response (timeout, connection drop) is not an HTTP error. 500 is a valid response—the server spoke. Handle "no response" as transport failure; handle 5xx as server error with a possible retry.

Retrying 4xx without fixing the request: 401 and 404 will not succeed on retry with the same request. Fix the request (auth, path, body) first.

Ignoring the status code: clients must branch on the numeric code, not the reason phrase. Do not parse the reason phrase for logic. Use the code; ignore the reason phrase for logic.

Trusting Content-Type blindly: the server can send the wrong Content-Type. Validate the header and parse the body defensively. If the body does not match the claimed type, handle the mismatch.

Wrong Content-Length: server declares one size, sends another—client misreads, corrupts the next request or hangs. Servers must send exactly the number of bytes declared. Clients should validate when possible (e.g. check body length after read). Mismatch means the connection may be corrupted for the next request.

## Summary

- An HTTP response has four parts: status line (version, code, reason phrase), headers (metadata), blank line (boundary), optional body (payload). Same structure as the request; status line replaces request line.
- The status code is the primary signal. 2xx success, 3xx redirect, 4xx client error (fix request), 5xx server error (retry might work). Clients must not rely on the reason phrase.
- Absence of response (timeout, connection reset) is transport failure, not an HTTP error. Only when you have a status line do you have an HTTP response.
- Headers describe the body (Content-Type, Content-Length). The blank line separates headers from body. The server must send exactly as many body bytes as Content-Length (or chunked rules) declare. One status line per response; parse it first, then headers, then body.
