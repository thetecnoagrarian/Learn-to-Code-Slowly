# Section B Phase 1 · Chapter 1.09: Status Codes Overview

Status codes are not messages, explanations, or opinions. They are signals. They are how the server tells the client what happened at the protocol boundary. If you misunderstand status codes, you will misdiagnose failures, retry when you should not, stop when you should retry, and blame the wrong side of the system.

## Learning Objectives

By the end of this chapter, you should be able to:
- Explain status codes as machine signals that drive client behavior (retry, redirect, abort)
- Describe the five classes: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error
- Distinguish absence of response (transport failure) from HTTP error responses
- Apply the rule: 4xx means fix the request; 5xx means retry may help; 2xx means do not retry automatically

## Key Terms

- **Status code**: Three-digit integer; the first digit defines the class; the number drives client behavior, not the reason phrase
- **2xx**: Success; the request was received, understood, and processed successfully at the protocol level
- **4xx**: Client error; the request reached the server but the server refuses or cannot fulfill it due to client-side issues; fix the request
- **5xx**: Server error; the request was valid but the server failed while processing it; retry may help

## 1) Status Codes Are Part of the Contract

When a server responds, it must choose a status code. That choice is part of the HTTP contract. Chapter 1.08 showed the response structure: status line, headers, blank line, body. The status code is the first thing in the status line after the HTTP version. It tells the client: did the request reach the server? Did the server understand it? Did the server act on it? Who is responsible for the outcome? Everything else in the response is secondary. Status codes are designed for clients first. Humans may see 404 Not Found in a browser. The client—your dashboard, ESP32, coop controller—sees 404. The number drives behavior. Your dashboard checks whether status code equals 404 to decide what to do, not the text Not Found. The reason phrase is for logs and debugging; the code is for logic.

The first digit defines the class of outcome: 1xx informational, 2xx success, 3xx redirection, 4xx client-side failure, 5xx server-side failure. This classification is deliberate and fundamental. Every status code answers one core question: did the request complete successfully, and if not, where did it fail? Not: was the data good, was the server happy, did the user get what they wanted. Just: what happened to the request. When you build a server, you choose the correct status code for each outcome. When you build a client, you branch on the code. Wrong codes break automation and make debugging harder. Correct codes make clients and servers interoperate predictably. The status code is the first thing the client should check after receiving a response. Only then should the client interpret headers and body. If the code is 404, the client may not need to parse the body—the resource is missing. If the code is 200, the client should check Content-Type and then parse the body. If the code is 301 or 302, the client should look at the Location header. So the status code is the dispatch key. It determines what the client does next. Servers that return the wrong code force clients to guess or parse the body to understand the outcome. That breaks the contract. When you add a new endpoint to your Pi—for example a new path for a new sensor—decide in advance which status codes it can return: 200 for success with a body, 204 for success with no body, 404 if the sensor ID is unknown, 401 if auth is required, 500 if the sensor read fails. Document or implement those consistently. When you build a client for that endpoint, handle each code: on 200 parse the body, on 404 show not found, on 401 refresh auth, on 500 retry or show error. The status code is the contract between your server and your client.

## 2) 1xx Informational

The 1xx range exists but most developers rarely encounter it in typical APIs. 1xx codes mean the request was received, processing is continuing, and there is no final outcome yet. They are transitional. 100 Continue means the server has received the request headers and the client may send the body (used when the client asks "should I send a large body?" and the server says "yes"). 101 Switching Protocols means the server will switch to a different protocol (e.g. WebSocket upgrade). Know they exist. Know they are rare in practice for simple request–response APIs. Your Pi’s voltage endpoint and your ESP32’s temperature POST will almost always get 2xx, 4xx, or 5xx, not 1xx. When you see a 1xx, it usually means the server is sending an intermediate response and more response data may follow, or the protocol is being upgraded. For homestead APIs you can focus on 2xx, 3xx, 4xx, and 5xx. The overview here is for completeness. If you ever see 100 Continue, it means the server is telling the client to go ahead and send the request body (after the client asked with Expect: 100-continue). If you see 101, the connection is being upgraded (e.g. to WebSocket). For most sensor APIs, dashboards, and coop controllers, you will see 200, 201, 204, 301, 302, 304, 400, 401, 403, 404, 500, 502, 503. Those are the workhorses. The class (first digit) tells you the category; the specific code (later chapters) tells you the nuance.

## 3) 2xx Success

A 2xx status means the request reached the server, the server understood it, and the server acted on it successfully. This is protocol-level success. Critical: 2xx does not mean everything is fine. A 2xx response does not mean the resource contained meaningful data (200 OK with voltage null—request succeeded, sensor returned null), the user got what they expected (200 OK with an HTML error page instead of JSON), or the system state is ideal (200 OK with body indicating sensor offline—request processed, sensor is down). It only means the request was handled successfully. Your dashboard sends a voltage request and gets 200 OK with voltage null. The request succeeded. The data indicates the sensor returned null. Success at the protocol level, not necessarily useful data. The client must still validate the body and Content-Type.

200 OK means the request succeeded and the response contains a representation of the resource. This is the most common status code. Your Pi responds 200 OK when your dashboard fetches voltage successfully, when your ESP32 reports temperature and the server processes it, or when your solar logger returns production data. Your coop controller might get 200 OK with fence status. 201 Created means the request succeeded and a new resource was created. Usually paired with POST and a Location header pointing to the new resource. Your ESP32 sends POST to register a new sensor. Your Pi responds 201 Created with Location pointing to the new resource. Your drip irrigation controller might POST a schedule and get 201 if a new schedule was created. 204 No Content means the request succeeded and there is no response body. This is intentional, not an error. Used when an update or delete succeeded and nothing needs to be returned. Your dashboard sends DELETE for a sensor. Your Pi responds 204 No Content. Your poultry net API might return 204 after a successful config update.

In general, 2xx means do not retry automatically. The request worked. Retrying may cause duplicate actions. Your ESP32 sends POST for temperature and gets 200 OK. Retrying would send the same reading twice. Do not retry success. If the client is unsure whether the request was applied (e.g. timeout after sending but before receiving), that is a different problem—idempotency and safe retries are covered in later chapters. For now: 2xx means success; do not retry as a default. When you build a server, use 200 when you are returning a representation of a resource (GET success, or POST that returns the created or updated resource). Use 201 when you created a new resource and want to tell the client where it is (Location header). Use 204 when the request succeeded but there is nothing to return (DELETE, or update that does not need to echo back state). Choosing the right 2xx code helps clients know whether to expect a body and whether to follow Location. Later chapters will detail each code.

## 4) 3xx Redirection

A 3xx status means the request was valid and the server wants the client to take another step. This is not a failure. It is guidance. A redirect is the server saying: what you want exists, but not here. The server must tell the client where to go next. That information is in headers (usually Location), not the status code alone. The client should follow the redirect by requesting the new URL (or using the cached redirect) unless the application has a reason not to.

301 Moved Permanently means the resource has permanently moved. Clients should update bookmarks or stored URLs. Caches may store this redirect. Your dashboard requests voltage at an old path; your Pi moved it. The server responds 301 with a Location header. Your dashboard should update its code or config—this is permanent. 302 Found means the resource is temporarily elsewhere. The client should not assume permanence. Common in login flows and temporary routing. 304 Not Modified is special: the client’s cached version is still valid, no body is sent, and the client should reuse its cache. This saves bandwidth. Your dashboard requests voltage with If-None-Match. Your Pi checks—data has not changed. Responds 304 with no body. Many people treat redirects as errors. They are not. Redirects are successful control-flow signals. The client’s job is to follow them when appropriate. When you get 301 or 302, read the Location header and issue a new request to that URL if your application allows it. 304 Not Modified is different: the client sent a conditional request (e.g. If-None-Match with an ETag from a previous response). The server found that the resource has not changed and tells the client to use its cached copy. No body is sent. This saves bandwidth and is common when the client is polling for updates. Your dashboard might request voltage with If-None-Match; if the reading has not changed, the Pi responds 304 and the dashboard keeps showing the last value. Redirects and 304 are both 3xx but mean different things: 301/302 say "go here"; 304 says "your cache is still valid." When you build a server that supports caching, returning 304 when the resource has not changed reduces load and bandwidth. When you build a client that caches, handling 304 by reusing the cached representation is correct. The status code tells you what to do without parsing the body.

## 5) 4xx Client Error

A 4xx status means the request reached the server, the server understood it (or understood enough to reject it), and the server refuses or cannot process it due to client-side issues. The core rule: 4xx means the client must change something. Retrying the same request will usually fail again. Your ESP32 sends a voltage request without auth and gets 401 Unauthorized. Retrying with no auth will fail again. Fix the request—add the Authorization header. Your dashboard requests a nonexistent path and gets 404 Not Found. Retrying will not help. Fix the path or accept that the resource does not exist.

400 Bad Request means the request was malformed—invalid syntax, missing required fields, unparseable body. The server could not understand the request as sent. Your ESP32 sends POST with malformed JSON (missing closing brace). Your Pi responds 400. Your coop controller sends a PUT with invalid JSON structure. 400. 401 Unauthorized means authentication is required; credentials are missing or invalid. 401 often includes a WWW-Authenticate header. It does not mean "forbidden." Your ESP32 sends a voltage request without Authorization. Your Pi responds 401. The ESP32 must include a valid token. 403 Forbidden means the server understood who you are but you are not allowed to do this. Authentication succeeded; authorization failed. Your ESP32 authenticates but tries DELETE on an admin-only resource. Your Pi responds 403. Your dashboard might get 403 when trying to access another user’s sensor. 404 Not Found means the server cannot find the requested resource. The path does not map to anything. It does not say whether the resource existed before or might exist later. Your dashboard sends a request to a nonexistent path. Your ESP32 requests a sensor that does not exist. 404. Other 4xx codes you may see: 405 Method Not Allowed (the path exists but does not support that HTTP method—e.g. POST to a path that only allows GET), 408 Request Timeout (server timed out waiting for the request), 409 Conflict (e.g. duplicate resource), 422 Unprocessable Entity (request is well-formed but semantically invalid). All of them mean something about the request or the client’s state is wrong. Fix the request or the client state before retrying. The server is not broken; it is correctly rejecting an invalid or unauthorized request.

4xx errors are not server failures. The server is functioning correctly. It is enforcing rules. Blaming the server for 401 is usually incorrect. The Pi is working—it is enforcing authentication. The ESP32 needs to fix its request. When you get 4xx, inspect the request: path, headers, body, auth. Fix the request before retrying. Do not retry 4xx blindly.

## 6) 5xx Server Error

A 5xx status means the request was valid and the server failed while handling it. This is the server admitting fault. 500 Internal Server Error means something went wrong on the server, the server cannot or does not provide more detail, and the failure occurred after request parsing. This is the generic server failure. Your dashboard sends a voltage request, but the Pi’s sensor reading code crashes. Your Pi responds 500. 502 Bad Gateway means the server is acting as a gateway or proxy and an upstream service failed. Your dashboard requests from a reverse proxy. The proxy forwards to your Pi, but the Pi is down. The proxy responds 502. 503 Service Unavailable means the server is temporarily unable to handle the request—often overload or maintenance. Clients may retry later. Your Pi is rebooting. Your ESP32 sends POST. Your Pi responds 503. The ESP32 should retry after a delay.

In general: 5xx means retry might succeed. 4xx means retry will likely fail without a change. 2xx means retry may cause harm (duplicate action). This matters for automation. Your ESP32 sends temperature readings every five minutes. If it gets 503, it should retry after a delay—the server might recover. If it gets 401, retrying will not help—fix the auth token first. Your freezer sensor API might get 502 from a reverse proxy when the backend Pi is rebooting—retry later. Your coop controller gets 500 when the fence logic crashes—retry might work once the server recovers. The status code drives the retry decision. Wrong status codes break automation. When you build a server, return 5xx only when the server is at fault. Do not return 500 when the request is bad—use 400 or 401 or 404. When you build a client, treat 5xx as "retry may help" (with backoff) and 4xx as "fix the request first." Other 5xx codes: 504 Gateway Timeout (proxy or gateway did not get a response from upstream in time). Same idea—server or gateway fault, retry may help. The distinction between 500 (generic server error), 502 (upstream failure when acting as proxy), 503 (temporarily overloaded or unavailable), and 504 (upstream timeout) gives clients and operators hints about what went wrong. For automation, the class is enough: 5xx means retry with backoff unless you have a reason not to. The specific code (500, 502, 503, 504) can inform logging and user messages, but the retry decision is driven by the class.

## 7) Responsibility and Absence

Status codes encode responsibility. 2xx means no one failed; the request was handled successfully. 3xx means the server is asking the client to take another step (redirect or use cache). 4xx means client responsibility—the request was wrong or unauthorized. 5xx means server responsibility—the server failed. No response means network or transport failure—neither client nor server can be blamed at the HTTP layer; the failure is below HTTP. Absence is not a status code. If the connection times out, DNS fails, or the network drops, there is no status code. This is not 5xx. It is absence. A missing response means the server may never have seen the request. A 500 means the server saw the request and failed. These are completely different failure modes. Your ESP32 sends POST but Wi‑Fi drops. No response. This is absence—the Pi never saw the request. Contrast with 500—the Pi saw the request, parsed it, then crashed. Different failure modes require different handling. When you log or debug, always distinguish: no response (transport), 4xx (fix request), 5xx (server error, retry may help). The status code is the first thing to check when you have a response. When you have no response, there is no status code to check—debug the transport layer (Chapter 1.02).

## 8) Status Codes Drive Behavior

Clients use status codes to decide: retry, redirect, cache, abort, prompt user. This is why correctness matters. Your dashboard checks 200 to display voltage, 404 to show "sensor not found," 500 to show "server error" and offer retry, 503 to show "temporarily unavailable" and retry later. The status code drives all these decisions. Well-designed APIs use status codes precisely. They do not overload meaning into the body. They let clients behave mechanically. Poor APIs always return 200 even on errors, hide errors in JSON with 200 OK, and break automation. Example: your Pi always returns 200 OK even when a sensor does not exist, with a body like error: sensor not found. Your dashboard cannot distinguish success from failure from the status code—it must parse the body and interpret application-specific fields. Bad design. Use 404 for missing resources. Your solar logger might return 200 with an error object when the inverter is offline—better to return 503 Service Unavailable or another 5xx so that clients can retry. Returning the wrong status code is a protocol violation in spirit. Correct status codes are part of being a good HTTP citizen.

When debugging: no response means check transport (network, host, port, timeout). 4xx means inspect the request (path, headers, body, auth). 5xx means inspect the server or retry. If you understand this, debugging HTTP becomes mechanical instead of emotional. The status code tells you where to look. Your coop controller gets 401—the request is missing or has a bad token. Your coop controller gets 500—the server’s fence logic crashed; check server logs or retry. Your coop controller gets no response—the connection failed; check network and Pi availability. Three different outcomes, three different debugging paths. When you implement a client library or a simple HTTP client on an ESP32, expose the status code to the application. Do not hide it behind "success" or "error" without the number. The application needs to know whether it got 200, 404, or 500 so it can decide what to do. When you implement a server, map your outcomes to the right codes: resource not found → 404, auth missing or invalid → 401, request body invalid → 400, server crash or upstream failure → 500 or 502 or 503. Consistent status codes make the system debuggable and automatable.

## Common Pitfalls

Retrying 4xx: 401 and 404 will not succeed on retry with the same request. Fix the request first. Do not retry 4xx blindly.

Not retrying 5xx: 503 and 500 may succeed on retry after a delay. Implement retry with backoff for 5xx when your application allows it.

Confusing absence with 5xx: no response is transport failure, not server error. There is no status code when there is no response. Handle timeout and connection errors separately from HTTP error handling.

Always returning 200: clients cannot decide behavior mechanically. Use 404 for missing resources, 401 for missing auth, 400 for bad request, 500 for server failure. Do not hide errors in the body with 200 OK—it breaks automation and makes clients parse application-specific error formats instead of using the protocol. Use the right code so clients can react without parsing error payloads.

## Summary

- Status codes are signals. The first digit defines the class: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error.
- 2xx means success—do not retry automatically. 3xx means redirect or use cache—follow Location or reuse cache. 4xx means fix the request—retry will likely fail. 5xx means server failed—retry may help. No response means transport failure. Check the status code first on every response; then interpret headers and body.
- The number drives client behavior. Use the numeric code for logic, not the reason phrase. The reason phrase can vary or be localized; the code is stable. Correct status codes are part of the HTTP contract; wrong codes break automation and debugging. When building a server, map outcomes to the right class and code. When building a client, branch on the code and handle 2xx, 3xx, 4xx, 5xx, and absence explicitly.
