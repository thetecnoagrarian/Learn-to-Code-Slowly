# Section B Phase 1 · Chapter 1.10: Status Codes — Success and Redirects

Success and redirect status codes describe completed requests. If a response is 2xx or 3xx, the request reached the server, the server understood it, and the server made a deliberate decision about how to respond. These codes are not about failure. They are about what kind of success happened and what the client should do next. We focus here on 200, 201, 204 (success with or without a body, and creation), 301 and 302 (redirects), and 304 (cache reuse). Each carries a distinct meaning that clients and servers use to coordinate without extra round-trips or guesswork.

## Learning Objectives

By the end of this chapter, you should be able to:
- Distinguish 200, 201, and 204 and when to use each
- Explain why 204 is better than 200 with an empty body for DELETE and updates
- Describe 301 vs 302 and why 301 is dangerous if misused
- Explain 304 Not Modified as cache control, not navigation

## Key Terms

- **200 OK**: Generic success with a body; the request succeeded and the response contains a representation of the result
- **201 Created**: A new resource was created; usually paired with POST and a Location header
- **204 No Content**: Success with intentionally no body; used for DELETE and updates that return nothing
- **301 Moved Permanently**: The resource has a new permanent URL; clients and caches may store this redirect
- **302 Found**: The resource is temporarily at a different URL; do not treat as permanent
- **304 Not Modified**: The client’s cached version is still valid; no body; the client should use its cache

## 1) Why Success Codes Need Precision

Chapter 1.09 gave an overview of status code classes: 2xx success, 3xx redirect, 4xx client error, 5xx server error. This chapter focuses on success (2xx) and redirects (3xx). Many systems collapse all success into 200 OK. That works until it does not. Clients rely on status codes to decide whether something new exists, whether to cache, whether to retry, whether to follow another URL, whether a response body should exist. Using the wrong success code does not break the protocol. It breaks client behavior. A 2xx response means the request was valid, the server acted on it, and the action completed. It does not mean the client is satisfied, the data is useful, or the system is healthy. Just that the request completed as requested. Your dashboard sends a voltage request and gets 200 OK with a voltage value. The request was valid, the Pi acted on it, and the action completed. It does not mean the reading is useful (maybe it is stale) or the system is healthy (maybe the Pi is about to crash). Just that the request succeeded. Within that, 200, 201, and 204 carry different meaning. Choosing the right one helps clients behave correctly without parsing the body to guess what happened. Similarly, 301 vs 302 and 304 vs 200 affect caching and navigation. Precision in status codes is not pedantry; it is the contract between server and client. When you implement an API on your Pi or consume one from your dashboard or ESP32, using the correct code makes the system predictable and debuggable.

## 2) 200 OK

200 OK is the most common success code. It means the request succeeded and the response body contains a representation of the result. Use 200 OK when a GET returns data, a POST returns a resource but did not strictly create a new one (e.g. process and return a result), a PUT returns the updated resource, or an operation succeeds and returns meaningful content. The key property: there is something in the body the client should read. Your dashboard sends a voltage request. Your Pi responds 200 OK with a JSON body. The body contains data the client should parse and use. Your ESP32 sends POST with a temperature reading. Your Pi processes it and responds 200 OK with a confirmation or the stored reading. Your solar logger returns 200 OK with production data. Your coop controller gets 200 OK with fence status. Your freezer sensor API returns 200 OK with internal and external temperatures. This is the default when no more specific success code applies—no new resource was created (not 201), no deletion or update that returns nothing (not 204), just a successful request with a body. The client’s next step is to parse the body according to Content-Type and use the data. If the server sends 200, the client should expect a body. If there is no body, the server should have sent 204 instead.

Using 200 OK for everything hides meaning. If the client created something (ESP32 registers a new sensor), deleted something (dashboard deletes a sensor), or performed an action with no return value (coop controller updates fence status and nothing needs to be echoed back), better codes exist. 201 Created and 204 No Content tell the client more. Your ESP32 creates a sensor and gets 200 OK—technically correct, but 201 Created tells the client something new exists and that it may have a URL (Location). So when you build a server, reserve 200 for "success with a body that the client should read." When the outcome is "new resource" or "success with no body," use 201 or 204 instead. On the client side, when you get 200 you should always handle the body. When you get 201 you may also want to read Location and optionally the body. When you get 204 you should not attempt to read a body. That discipline keeps your dashboard, ESP32, and other clients robust.

## 3) 201 Created

201 Created means the request succeeded and a new resource now exists as a result. This is most commonly used with POST. The difference from 200 is not subtle. 201 tells the client: you now have a new thing, it has an identity, you may want to interact with it next. This is information the client cannot infer from a body alone. Your ESP32 sends POST to register itself. Your Pi creates a new sensor record and responds 201 Created with a Location header pointing to the new resource. The status code tells the ESP32 something new exists—even if the body is empty. With 200 OK, the ESP32 might think it is just a confirmation, not a new resource. A 201 response should usually include a Location header telling the client where the new resource lives. This is not strictly required by the spec for all cases, but in practice it is expected when a resource was created and has a URL. The response may include a body (often the newly created resource) but does not have to. The critical signal is the status code. The client can use the Location header to fetch or reference the resource later. Your drip irrigation controller might POST a schedule and get 201 with Location pointing to the new schedule. Your coop controller might POST a new fence zone and get 201 with Location. When you build an API that creates resources, return 201 and set Location to the canonical URL of the new resource. When you build a client that creates resources, check for 201 and optionally follow Location to fetch the new resource or store the URL for later use. If your server creates a resource but does not have a URL for it (rare), 201 without Location is still valid—the code still means "new resource exists." But whenever you have a path for the new resource, send Location. It enables clients to discover the new resource without guessing or parsing the body. Your solar logger might POST a new panel configuration and get 201 with Location to that config; the client can then GET that URL to read or update it. Consistency across your homestead APIs—always 201 with Location for creation—makes client code simple and predictable.

## 4) 204 No Content

204 No Content means the request succeeded and there is intentionally no response body. This is not an error or incomplete. It is explicit success with silence. Use 204 when a DELETE succeeded, a PUT or PATCH succeeded but returns nothing, or an action occurred but no representation is needed. The client should not expect a body. Reading one would be a bug. Your dashboard sends DELETE for a sensor. Your Pi deletes it and responds 204 No Content with no body. Your dashboard knows deletion succeeded—no body to parse, move on. Your poultry net API might return 204 after a successful config update. Your coop controller might send PUT to update a setting and get 204 when the update is applied and nothing needs to be returned. Your freezer monitor might DELETE an old log and get 204. In every case the server is saying: the operation completed, and I have nothing to send back. The client’s job is to treat the request as successful and not block on reading a body.

Returning 200 OK with an empty body is ambiguous: did the server forget to send a body? Is it empty? Should the client wait for more data? Returning 204 No Content is explicit: intentionally no body, operation complete. The latter tells the client: there is nothing to parse, move on. Your dashboard sends DELETE. If your Pi responds 200 OK with no body, your dashboard might wait for a body that never comes or wonder whether the response is complete. If it responds 204 No Content, your dashboard knows immediately: nothing to read, deletion succeeded. This matters for automation—clients can proceed without parsing. Clients should not attempt to parse a body for 204, should not expect Content-Type in the same way, and should treat the operation as complete. Servers should not send a body with 204. If your Pi mistakenly includes a body with 204, it violates the semantics of 204; clients may be confused. The rule is clear: 204 means no body. Use it for DELETE and for updates that have nothing to return. One more nuance: some APIs use PUT or PATCH to update a resource and return the updated representation with 200. That is fine when the client needs the updated state. When the client does not need it (e.g. it already has the new state or the change is trivial), 204 is cleaner. Choose based on whether the client benefits from a body. If not, 204 keeps the response small and the contract clear.

## 5) Redirects (301 and 302)

Redirects are not errors. They are instructions. A 3xx response means the request was valid, the resource is not here, and the client should take another step. Resources change location. URLs evolve. Systems are reorganized. Redirects let servers say: yes, but not here. All redirect responses that ask the client to go elsewhere must include a Location header. Without it, the client has no instruction. Your dashboard requests voltage and gets 302 but no Location header. Where should it go? The redirect is broken. Always include Location with 301 and 302. The Location value should be an absolute URL (or a path that the client can resolve). Relative URLs are allowed but absolute is clearer for clients that might be following redirects across hosts.

301 Moved Permanently means the resource has a new permanent URL. Clients should update bookmarks or stored URLs. Caches may store the redirect and return it for a long time. This is a strong signal. Your dashboard requests voltage at an old path; your Pi permanently moved it. The server responds 301 with a Location header. Your dashboard should update its code or config—this is permanent. 301 is dangerous if misused. Once cached, a 301 can persist for a long time. If you send 301 incorrectly (e.g. you meant temporary), clients may never check the old URL again. Your Pi sends 301 for voltage to a new path. Your dashboard caches this. Later you realize the move was temporary. Too late—your dashboard may never check the old URL again. Use 302 Found for temporary moves. When in doubt, use 302; you can change to 301 later when you are sure the move is permanent. Also be aware: when redirecting non-GET requests, some clients (including some browsers) may change a POST to GET when following a 301 or 302, losing the request body. Redirecting POST is therefore tricky. For GET requests, following 301 or 302 is straightforward: issue a new GET to the Location URL. If you run a small API on your Pi and you rename a path, ask yourself: is this permanent? If yes, 301 and tell your clients to update. If no or unsure, 302 so caches and clients do not lock in the redirect forever.

302 Found means the resource is temporarily at a different URL. Clients should not update bookmarks permanently. Future requests may still go to the original URL. This is softer than 301. Use 302 when redirecting after form submission, handling login flows, routing traffic temporarily during maintenance, or when the move might be reversed. The server is saying: go there for now. Redirect responses usually have no meaningful body that the client must read; the client follows the Location header. The body may exist (e.g. an HTML page for humans), but automated clients typically ignore it and follow Location. When you reorganize your Pi’s API and move a path temporarily, use 302. When you permanently retire an old path, use 301 and document that clients should update their config. On homestead projects you might use 302 when you stand up a temporary maintenance page: requests to the main dashboard get 302 to a "back in five minutes" page. When maintenance ends, you remove the redirect and the original URL works again. No need for clients to change anything. That is the power of 302.

## 6) 304 Not Modified

304 Not Modified is not a redirect in the usual sense. It does not mean "go to another URL." It means the client’s cached version of the resource is still valid. The server is explicitly saying: use what you already have. This saves bandwidth and time. 304 occurs when the client sends a conditional request with headers such as If-None-Match (with an ETag from a previous response) or If-Modified-Since, and the server determines that the resource has not changed. Your dashboard requests voltage with If-None-Match. Your Pi checks—the data has not changed. It responds 304 with no body. Your dashboard uses its cached version. Your solar logger might use ETags for production data—if unchanged, 304. Your coop controller might cache fence status—304 when no change. A 304 response must not include a body. The body would be redundant; the client already has it cached. Sending it would waste bandwidth. The whole point of 304 is to avoid sending unchanged data. So 304 is a success response that means "your cache is valid." The client does not navigate elsewhere; it reuses its local copy. When you build a server that supports caching, you will send ETag or Last-Modified in successful responses and then, when the client sends a conditional request and the resource is unchanged, respond with 304. When you build a client that caches, you store the ETag (or Last-Modified) with the cached representation and send If-None-Match (or If-Modified-Since) on the next request. If you get 304, you reuse the cache. If you get 200, you replace the cache with the new body. Chapter 1.17 will cover caching headers in more detail; here the point is that 304 is success with no body and means "use your cache." Do not confuse 304 with 302. 302 says: request this other URL. 304 says: do not request anything; your existing copy is fine. One changes where the client goes; the other avoids a transfer entirely. For sensor data that does not change every second, 304 can significantly reduce load on your Pi and traffic on your local network.

## 7) Redirects vs Retries, and Misuse

Redirects tell the client: do not retry the same request here; try again at the URL in Location. This is different from errors. Your dashboard requests voltage and gets 302 with Location pointing to the new path. Follow the redirect—issue a new request to the Location URL. Contrast with 500: retry the same request later; the server might recover. Success and redirect codes assume the client is capable and will follow instructions. They are cooperative. Your Pi sends 301 assuming your dashboard will follow the Location header. If your dashboard does not follow redirects, it may break—but that is a client limitation, not a server error. Well-written clients follow redirects for GET and often for other methods (with care for POST, as noted). When you implement a client (dashboard, ESP32, script), support at least GET redirects: if you get 301 or 302, follow Location once or a limited number of times to avoid redirect loops. Many HTTP libraries do this by default; if you are writing low-level socket code, you must implement it yourself.

APIs sometimes misuse redirects or avoid them incorrectly. Using 200 with embedded redirect information in the response body (e.g. JSON with redirect: true and newUrl) forces the client to parse the body to know to redirect. Generic HTTP clients will not follow that automatically. Bad design. Redirects belong in the status code and the Location header. Use 301 or 302 with Location so that any HTTP client can follow. Conversely, using a redirect where the resource is simply missing is wrong. Use 404 for missing resources, not 302 to an error page, unless you really want the client to load that URL. Idempotency and method semantics matter when redirecting: GET is safe to redirect freely. POST may be rewritten to GET by some clients on redirect—losing the body. PUT, PATCH, DELETE require care; redirecting a DELETE to a different path might delete the wrong resource. Design redirects deliberately. For most homestead APIs (sensor endpoints, dashboards), redirects are less common than 200, 201, and 204. When you do move a path, use 302 for temporary and 301 for permanent, and always send Location. If your API is only consumed by your own dashboard and you never move URLs, you might never send 301 or 302. But when you do reorganize, doing it correctly with the right code and Location avoids subtle bugs and cache problems.

## 8) Mapping to Overview and Client Behavior

Chapter 1.09 gave the rule: 2xx means success, do not retry automatically; 3xx means redirect or use cache. This chapter filled in the specific codes: 200 for success with a body, 201 for created with Location, 204 for success with no body; 301 for permanent redirect, 302 for temporary redirect, 304 for "use cache." When you build a server, choose the code that matches the outcome. When you build a client, handle each code: on 200 parse the body; on 201 optionally follow Location or store it; on 204 treat as success and do not expect a body; on 301 or 302 follow Location (with care for non-GET); on 304 use the cached representation. Your dashboard, ESP32, and coop controller can all implement this behavior. The status code drives the next step. If you are debugging a client that does not behave as expected, check how it handles each of these codes. A client that always expects a body will misbehave on 204 or 304. A client that does not follow redirects will fail when you move a path. A client that does not check for 201 and Location may not know where the new resource lives. Server and client must agree on the contract. The next chapter (1.11) covers 400, 401, 403, 404, 500, 502, 503—client and server errors. Together, 1.09 (overview), this chapter (success and redirects), and 1.11 (errors) give you the full set of status codes you need for HTTP APIs.

## 9) Homestead Examples: Choosing the Right Code

Your Pi’s voltage endpoint returns a reading. Success with a body → 200 OK. Your ESP32 posts a new sensor registration. The Pi creates a sensor resource and returns its URL → 201 Created with Location. Your dashboard deletes a sensor. The Pi deletes it and has nothing to return → 204 No Content. Your poultry net API updates a config and has nothing to return → 204 No Content. Your Pi moves the voltage endpoint from slash voltage to slash api slash voltage permanently → 301 with Location. Your Pi moves it temporarily for maintenance → 302 with Location. Your dashboard requests voltage with If-None-Match; the reading has not changed → 304 with no body. In each case the code matches the outcome. When you add a new endpoint, decide at design time which success or redirect codes it can return. Document them. Implement them consistently. Clients that depend on 201 vs 200 or 204 vs 200 will work correctly when the server sends the right code. A few more: your drip system POSTs a new schedule and gets 201 with Location to the schedule. Your freezer logger GETs temperatures and gets 200 with a JSON array. Your coop controller PUTs a fence mode and gets 204 because the server does not echo back the config. Your solar panel API used to live at slash solar; you moved it to slash api slash solar and do not plan to move it again → 301 from the old path. Your ESP32 fetches its config with If-Modified-Since; the config is unchanged → 304. Building this habit—choose the code that matches the outcome—makes your APIs clear and your clients reliable across the homestead.

## Common Pitfalls

Using 200 for DELETE: use 204 No Content. The client then knows there is no body and that the operation completed. Same for PUT or PATCH that intentionally return nothing.

Using 200 for creation: use 201 Created with Location. The client then knows a new resource exists and where it is. Omitting 201 for resource creation makes client logic harder and less reliable.

Using 301 for temporary moves: use 302. Clients and caches may store 301 and not recheck the old URL. Reserve 301 for permanent moves only. When in doubt, 302 is safer.

Redirecting POST without awareness: some clients change POST to GET when following a redirect, losing the body. Design APIs so that redirects after POST are rare or so that the client handles them explicitly. Avoid redirecting POST in critical flows unless you control both server and client.

Omitting Location on redirects: a 301 or 302 without a Location header is broken. The client cannot follow. Always send Location with redirects. Validate your server responses during development.

Returning 200 with an empty body when 204 applies: ambiguous. The client may wait for a body or be unsure whether the response is complete. Use 204 explicitly when there is intentionally no body. Consistency here prevents subtle client bugs.

## Summary

- 200 OK: success with a body; the client should read and parse the body. Use for GET that returns data, POST that returns a result (without creating a new resource), PUT that returns the updated resource. Do not use 200 when 201 or 204 is more accurate.
- 201 Created: success; a new resource exists. Include Location when the resource has a URL. Use for POST that creates a resource. The client may follow Location or store it. Do not use 200 for creation when you can use 201.
- 204 No Content: success with intentionally no body. Use for DELETE and for PUT or PATCH that return nothing. The client should not expect a body. Do not use 200 with an empty body when 204 applies.
- 301 Moved Permanently: resource has a new permanent URL. Send Location. Use only for permanent moves; caches and clients may store this. Avoid 301 for temporary moves.
- 302 Found: temporary redirect. Send Location. Use for temporary moves, maintenance, or when unsure. Prefer 302 over 301 when the move might be reversed.
- 304 Not Modified: client’s cache is still valid; no body. Use when a conditional request (If-None-Match or If-Modified-Since) finds the resource unchanged. The client reuses its cache. Not a redirect. These codes are not interchangeable; they encode meaning for clients. Choosing the right one improves reliability and debuggability across your homestead APIs.
