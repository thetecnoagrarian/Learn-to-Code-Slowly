# Section B Phase 1 · Chapter 1.11: Status Codes — Client and Server Errors

Error status codes assign responsibility: 4xx means the client sent something wrong, 5xx means the server failed to fulfill a valid request. This chapter covers 400, 401, 403, 404, 500, 502, and 503 so you can signal and interpret errors correctly and design clients that recover appropriately.

## Learning Objectives

By the end of this chapter, you should be able to:
- Distinguish HTTP error responses from network failures (no response)
- Explain the difference between 4xx client errors and 5xx server errors
- Choose and use 400, 401, 403, 404, 500, 502, and 503 appropriately
- Explain the difference between authentication (401) and authorization (403)
- Design retry and backoff behavior based on error codes
- Design error responses that help clients recover

## Key Terms

- **4xx client errors**: The client sent an invalid or problematic request; the server is refusing or unable to process it as asked
- **5xx server errors**: The server failed to fulfill a valid request; responsibility is on the server
- **Authentication**: Proving identity (who you are); signaled by 401 when missing or invalid
- **Authorization**: Checking permissions (what you are allowed to do); signaled by 403 when insufficient
- **400 Bad Request**: The request is malformed or invalid; structural or semantic problem with the request
- **401 Unauthorized**: Credentials are missing or invalid; authentication required
- **403 Forbidden**: The client is authenticated but lacks permission for this action or resource
- **404 Not Found**: The requested resource does not exist at that path
- **500 Internal Server Error**: The server encountered an unexpected failure (bug, unhandled exception)
- **502 Bad Gateway**: A proxy or gateway received an invalid response from an upstream server
- **503 Service Unavailable**: The server is temporarily unable to handle requests (overload, maintenance)

## 1) Errors Assign Responsibility

Error status codes answer one question: who is responsible for fixing this? HTTP uses them to assign responsibility, not to blame. The first digit of the status code tells you whether the client sent something wrong (4xx) or the server failed to handle a valid request (5xx). Those two families are not interchangeable. They describe where the failure lives. Clients use that information to decide whether to fix the request, re-authenticate, retry with backoff, or give up. Servers use it to communicate clearly. When you build an API on your Pi or consume one from your dashboard or ESP32, using the right error code makes debugging and recovery straightforward.

Chapter 1.09 gave an overview of status code classes. Chapter 1.10 covered success and redirects. This chapter focuses on errors: 4xx for client errors and 5xx for server errors. When your ESP32 gets 400 Bad Request for malformed JSON, your dashboard gets 401 Unauthorized for missing credentials, or your Pi returns 500 Internal Server Error, the status code assigns responsibility. An HTTP error response means the request reached the server, the server understood it, the server made a decision, and the server replied intentionally. That is not a crash or silence. It is communication. Your ESP32 sends POST with malformed JSON to the temperature API; your Pi responds with 400 Bad Request. The request reached the Pi, the Pi determined it was invalid, and the Pi replied. That is an HTTP error. A failure is different: no response at all, such as a timeout, DNS failure, or connection drop. This chapter is about errors. Chapter 1.12 will cover the distinction between errors and failures in depth. When your dashboard requests the voltage endpoint and gets 404 Not Found, that is an HTTP error because the Pi responded. A timeout or connection reset is a failure with no response. Keep that distinction in mind: errors mean the server spoke. Your automation can handle errors in code (if status is 401, refresh token; if 404, treat as missing). Failures require different handling (timeout, retry later, check network).

## 2) The Line Between Client and Server Errors

4xx means the client is at fault. 5xx means the server is at fault. Everything else is detail.

A 4xx response means the request was received, the server understood it, and the server refuses or cannot process it because of the request itself. The server is saying it cannot do this as asked. Retrying the same request without change will usually fail again. Something must change on the client side. When your coop door controller sends GET to the fence status API without authentication and gets 401 Unauthorized, retrying the same request does not help. The controller must add credentials first. When your dashboard sends POST to the sensors API with invalid JSON and gets 400 Bad Request, retrying the same body fails again. Fix the request.

A 5xx response means the request was valid and the server failed to fulfill it. Responsibility is on the server. Retrying 5xx may succeed if the failure was transient. Retries should be bounded and backed off. When your ESP32 sends POST to the temperature API and gets 503 Service Unavailable, the Pi might recover. Retry after a delay; do not retry forever. If 503 persists after several attempts, back off. The client should not assume the request was wrong. 5xx means server failure. Your dashboard, ESP32, and other clients should treat 4xx and 5xx differently: for 4xx, fix or change the request; for 5xx, retry with care and back off. Summarized: 4xx says change something on the client; 5xx says the server failed, retry later if appropriate.

## 3) 400 Bad Request

400 Bad Request means the request is malformed or invalid and the server cannot parse or validate it. The problem is structural or semantic. This is the most generic client error. Typical causes include invalid JSON (e.g. your ESP32 sends a temperature reading with a missing closing brace), malformed syntax, missing required fields (e.g. your dashboard sends POST to the sensors API without a device ID), wrong data types (e.g. sending a string where a number is required), or invalid query parameters (e.g. requesting voltage data with an invalid unit). The server cannot proceed because the request does not make sense. 400 does not mean unauthorized, forbidden, or not found. It means this request is not valid as written. Do not use 400 when the problem is missing credentials (use 401) or wrong permissions (use 403) or missing resource (use 404). Reserve 400 for "the request itself is invalid."

Good servers return a clear error message in the body: what is wrong and how to fix it. Bad servers return 400 with no body. When your ESP32 sends malformed JSON and gets 400 with an empty body, it has no idea what to fix. When your Pi returns 400 with a body that says "invalid JSON: missing closing brace at line 3," the client can correct the request. Your drip irrigation controller might POST a schedule with a negative duration and get 400 with a message that the field must be positive. Your freezer logger might send a temperature value as a string and get 400. Your poultry net API might receive a voltage threshold out of range and return 400. Design your API to return 400 with actionable body content when the request is malformed or invalid. On the client side, when you get 400, parse the body if present, log it, and fix the request before retrying. Do not retry the same request. If your client cannot interpret the body, at least log the status and body so a human can debug. Consistent 400 handling across your homestead clients (dashboard, ESP32, scripts) makes failures easier to trace.

## 4) 401 Unauthorized

401 Unauthorized means the client is not authenticated. Credentials are missing or invalid. The server is asking: who are you? This is authentication, not authorization. Authentication is identity. Authorization is permission. 401 is about identity. 403 (Forbidden) is about permission. Do not confuse them. 401 occurs when no Authorization header is present (e.g. your ESP32 forgets the Bearer token), when the token is expired (e.g. your dashboard token expired after 24 hours), or when credentials are invalid (e.g. your coop controller sends the wrong API key). The request could succeed if identity were proven. So the server is not saying "you are not allowed"; it is saying "I do not know who you are" or "your proof of identity is invalid."

Many 401 responses include a WWW-Authenticate header with instructions for how to authenticate. The server is inviting the client to try again with valid credentials. When your coop controller sends GET to the fence status API without credentials, your Pi responds 401 Unauthorized and can include WWW-Authenticate: Bearer. The controller then knows it needs to add an Authorization Bearer token and retry. Retrying 401 can make sense only if credentials are added or corrected. Blind retries are pointless. When your ESP32 gets 401 from the temperature API, it should obtain a new token, add the Authorization header, and retry. Retrying the same request without credentials yields 401 again. Your solar logger, poultry net controller, and dashboard should all treat 401 as "authenticate and retry" rather than "give up." If your API uses API keys or Bearer tokens, document that 401 means missing or invalid credentials and that clients should refresh or obtain credentials before retrying. That way every client (ESP32, dashboard, scripts) implements the same recovery path.

## 5) 403 Forbidden

403 Forbidden means the client is authenticated and the server knows who they are, but the client is not allowed to do this. It is a hard stop. No amount of retrying helps unless permissions change on the server. When your solar logger sends DELETE to the config API with valid authentication and your Pi responds 403 Forbidden, the logger is authenticated but not allowed to delete config. When your ESP32 is authenticated but tries to access the admin sensors endpoint, your Pi responds 403 because the ESP32 does not have admin permissions. Retrying will not help. Permissions must change on the server.

The distinction from 401 is critical. 401 asks who are you? 403 says I know who you are, and no. Confusing them breaks client logic. Use 403 when the resource exists, authentication succeeded, and authorization failed. Do not use 403 to hide the fact that authentication is required; use 401 for that. When credentials are missing or invalid, use 401. When credentials are valid but insufficient, use 403. Your coop controller might be allowed to read fence status but not change config; reading returns 200, changing config returns 403. Your dashboard might be allowed to list sensors but not delete them; delete returns 403. Design your permission model and map it to 401 vs 403 consistently so clients can implement the right behavior (e.g. refresh credentials on 401, show "permission denied" on 403). A client that receives 403 should not retry the same request without a change in permissions on the server; it may show a message to the user or fall back to a read-only view.

## 6) 404 Not Found

404 Not Found means the server understood the request and the resource does not exist at that path. This is about absence, not permission. When your dashboard requests a sensor endpoint with a nonexistent sensor ID, your Pi responds 404 Not Found. That sensor does not exist. It is not that you are forbidden; you are allowed to read sensors, but this one is not there. 404 does not mean the server is down, the request was malformed, or the client is forbidden. It means there is nothing at that path. The client sent a valid request to a path the server understands, but no resource is mapped to that path (or that identifier). Your voltage API might have a path like slash api slash sensors slash and an ID; if the ID does not match any sensor, 404 is correct.

Some APIs return 404 instead of 403 to avoid revealing that a resource exists (information leakage). That is a design choice. Your Pi could return 403 when an authenticated but non-admin client asks for an admin-only resource, or 404 to hide that admin endpoints exist. Both are valid. 404 reduces information leakage but can make debugging harder. 404 responses can be cached. Absence is information. When your dashboard requests a nonexistent sensor ID and gets 404, it can cache that result so it does not ask again immediately. Your ESP32 might request a config that was deleted and get 404; it should treat that as "resource gone" and perhaps fall back to defaults or prompt for reconfiguration. Your drip system might GET a schedule by ID and get 404 if the schedule was removed. Your coop controller might request a fence zone that was deleted and get 404. Handle 404 by not assuming the resource exists and by not retrying the same URL blindly. On the server side, return 404 when the path is valid but the resource is absent; do not return 404 for bad paths that your API does not define (some APIs return 404 for unknown paths too, which is also a design choice).

## 7) 500 Internal Server Error

500 Internal Server Error is the generic server failure. It means something went wrong on the server: an unhandled exception, a bug, or an unexpected condition. The server is admitting failure. 500 gives the client little detail. Clients should not assume anything beyond "server failed." A 500 response should be logged on the server with full context: stack trace, request details, and any relevant state. 500 indicates broken assumptions. When your Pi responds 500 to a voltage API request, log the exception and the request that triggered it. Investigate. Do not ignore 500s. In development, you might expose more detail in the response body; in production, avoid leaking internals to clients while still logging everything server-side. The goal is to fix the bug, not to hide it.

Clients should retry cautiously and back off. Do not change the request automatically. The request may be fine. When your ESP32 sends POST to the temperature API and gets 500, the request was valid. Retry after a delay; if 500 persists, back off. The server might be down or recovering. Do not assume the request was wrong. Your dashboard might get 500 when the Pi hits a bug while processing a valid GET. Retry with backoff; do not alter the request. 500 means server failure, not client error. Distinguishing 500 from 400 or 401 in client logic is essential: on 400 or 401 the client should fix or re-authenticate; on 500 the client should retry the same request with backoff. Your solar logger, coop controller, and freezer monitor should all implement backoff so that a Pi bug does not cause a storm of repeated requests. Exponential backoff (e.g. wait 1 second, then 2, then 4) is a common pattern for 5xx retries.

## 8) 502 Bad Gateway and 503 Service Unavailable

502 Bad Gateway means the server is acting as a proxy or gateway, it contacted an upstream service, and the upstream response was invalid or the upstream failed. The failure is not local but is still server-side. This is common with reverse proxies, load balancers, and microservices. The server is saying it asked someone else and they failed. When your dashboard requests the voltage API and your Pi forwards the request to an upstream sensor service that crashes, your Pi responds 502 Bad Gateway. The Pi is reporting that the upstream failed. When you add a gateway in front of your Pi (e.g. nginx or a cloud proxy), that gateway may return 502 when the Pi is unreachable or returns something invalid. Clients should treat 502 like 500 for retry purposes: retry with backoff. The fix is on the server side (upstream or gateway). If your homestead setup has a Pi that calls another service (e.g. a weather API or a database), and that service fails, your Pi can return 502 to the client. The client cannot fix the upstream; it can only retry later.

503 Service Unavailable means the server is temporarily unable to handle the request: overload, maintenance, or temporary outage. It is a temporary condition. When your Pi is rebooting or overloaded, your ESP32 sends POST to the temperature API and gets 503. The Pi is temporarily unable to handle requests; this should pass. 503 often includes a Retry-After header (in seconds). That tells the client when to retry and helps avoid hammering the server. 503 is intentional. The server is protecting itself. When your Pi is under heavy load or rebooting, it can respond 503 to new requests instead of accepting them and failing. Once it recovers, it accepts requests again. Contrast with 500, which is an unexpected failure. Use 503 for planned maintenance, overload, or temporary unavailability. Use 500 for bugs and unhandled exceptions. Use 502 when a proxy or gateway got a bad response from upstream. If you take your Pi down for updates, having it return 503 with Retry-After 300 (five minutes) is better than leaving clients to time out. When the Pi comes back, clients that respected Retry-After will retry and succeed.

Choose among 500, 502, and 503 based on what went wrong. 500: bug or unexpected failure (unhandled exception, crash). 502: dependency failed (upstream service broke or returned invalid response). 503: temporary unavailability (overload, reboot, maintenance). When your Pi hits an unhandled exception, respond 500. When your Pi forwards to an upstream sensor service that crashes, respond 502. When your Pi is rebooting, respond 503 with Retry-After. Each code tells the client something different. Your dashboard and ESP32 can use 503 and Retry-After to wait before retrying; for 500 and 502 they can use a generic backoff strategy. Document which 5xx your API can return so client authors know what to implement.

## 9) Error Codes as Contracts

When a server returns a status code, it is making a promise about meaning. Clients rely on that promise. Breaking it causes wrong behavior. If your ESP32 expects 401 when credentials are missing so it can fetch a new token and retry, but your Pi returns 403 instead, the ESP32 may think it is authenticated but lacks permission and may not refresh the token. Error codes are contracts. Use them consistently. 401 for authentication problems, 403 for authorization problems, 400 for invalid requests, 404 for missing resources, 500 for server bugs, 502 for upstream failure, 503 for temporary unavailability. Once you establish a contract (e.g. "missing token always 401"), keep it across all endpoints and versions so every client can rely on it.

HTTP does not require error bodies, but good APIs return them. Structured error messages explain what went wrong and help clients recover. When your ESP32 sends malformed JSON and gets 400 with a body describing the issue, the status code says client error and the body says what to fix. Do not encode errors only in JSON with 200 OK. Returning 200 OK with an error message in the body is a protocol lie. Errors belong in status codes. Generic HTTP clients use status codes to decide success or failure. If you return 200 with an error in the body, those clients will treat the response as success. Use 400, 401, 403, 404, or 5xx with an explanatory body. In HTTP, errors are expected. They are part of normal operation. When your dashboard gets 404 for a nonexistent sensor, handle it gracefully. When your ESP32 gets 401, fetch a new token and retry. Clear errors let clients retry correctly, fix requests, and back off. Ambiguous errors (e.g. 200 with error in JSON) break automation. When you design your Pi API, document the error codes each endpoint can return and what the client should do for each. That documentation is part of the contract.

## 10) Homestead Examples: Choosing the Right Error Code

Your ESP32 sends a temperature reading with invalid JSON → 400 Bad Request with a body explaining the parse error. Your dashboard sends POST to create a sensor without a required device ID → 400 Bad Request. Your coop controller calls the fence API with no Authorization header → 401 Unauthorized; add credentials and retry. Your solar logger’s token expired → 401; refresh token and retry. Your ESP32 is authenticated but calls the admin-only config delete endpoint → 403 Forbidden; retrying will not help. Your dashboard requests a sensor that was deleted → 404 Not Found. Your drip system requests a schedule by ID that does not exist → 404. Your freezer monitor requests a log file that was rotated away → 404. Your Pi hits an unhandled exception while serving the voltage API → 500 Internal Server Error; log and investigate. Your Pi forwards to an upstream sensor service that crashes → 502 Bad Gateway. Your Pi is rebooting or overloaded → 503 Service Unavailable, optionally with Retry-After. In each case the code matches the cause. When you implement your API, decide which error code fits each failure mode and document it. When you implement clients (dashboard, ESP32, scripts), handle each code: fix request on 400, re-authenticate on 401, treat as permission denied on 403, treat as absent on 404, retry with backoff on 500/502/503. Consistency between server and client makes your homestead automation reliable. If you add a new endpoint (e.g. chicken counter or soil moisture API), define up front which errors it can return so all clients can implement the same recovery behavior.

## Common Pitfalls

Confusing 401 and 403: 401 means authentication failed (add or fix credentials). 403 means authorization failed (authenticated but not allowed). If the client gets 401, it should add or fix credentials. If it gets 403, retrying without permission change will not help.

Returning 200 OK with error messages in the JSON body: that breaks the HTTP contract. Clients rely on status codes for success vs failure. Put errors in status codes and use the body to explain.

Using 500 for every server problem: use 500 for unexpected failures, 502 for upstream failure, 503 for temporary unavailability. Each implies different client behavior (e.g. respect Retry-After for 503).

Retrying 4xx blindly: 4xx means the request is wrong. Retry only after changing the request (e.g. fix body for 400, add credentials for 401). Blind retries waste resources.

Ignoring 500 on the server: 500 means something unexpected happened. Log with stack trace and request context; investigate. Do not ignore.

Omitting error bodies for 400: clients need to know what to fix. Return a clear message in the body so the client (or a human debugging) can correct the request.

## Summary

Error status codes assign responsibility. 4xx means the client sent something wrong; 5xx means the server failed to fulfill a valid request. 400 Bad Request: request malformed or invalid; fix the request; do not retry the same request. 401 Unauthorized: credentials missing or invalid; authenticate (or refresh credentials) and retry. 403 Forbidden: authenticated but not allowed; no retry without permission change. 404 Not Found: resource does not exist at that path; handle absence gracefully; can cache. 500 Internal Server Error: server encountered an unexpected failure; log and investigate; client retries with backoff; do not assume the request was wrong. 502 Bad Gateway: upstream or proxy failure; client retries with backoff. 503 Service Unavailable: temporary unavailability; use Retry-After when possible; client waits and retries. The status code tells you where to look and how to react. Use them consistently so clients can implement correct retry and recovery behavior. Together with Chapter 1.09 (overview) and 1.10 (success and redirects), this chapter completes the status code set you need for building and consuming HTTP APIs on your homestead.
