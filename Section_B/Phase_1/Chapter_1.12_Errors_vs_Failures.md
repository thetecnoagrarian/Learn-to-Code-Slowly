# Section B Phase 1 · Chapter 1.12: Errors vs Failures

HTTP error responses and network failures are not the same thing. An error means the server responded with a status code. A failure means no response arrived. This chapter draws the boundary and shows how to handle each so your clients and operations stay clear.

## Learning Objectives

By the end of this chapter, you should be able to:
- Distinguish HTTP error responses (4xx/5xx) from network failures (no response)
- Explain why presence of a response differs from absence
- Recognize when problems occur at the transport layer versus the application layer
- Design retry logic that accounts for ambiguity (e.g. timeouts)
- Handle partial responses and connection drops correctly
- Branch client code on response presence before inspecting status codes

## Key Terms

- **HTTP error**: A response with a 4xx or 5xx status code; the server responded intentionally
- **Network failure**: No HTTP response received; transport-layer or connection problem
- **Presence**: An HTTP response arrived, even if it carries an error status code
- **Absence**: No HTTP response received; creates ambiguity about what happened
- **Timeout**: A failure where the client waited but received no response
- **Partial response**: Some headers or body received before the connection dropped
- **Idempotency**: A request that can be retried without changing the outcome beyond the first success (e.g. GET, PUT, DELETE in typical use); Chapter 1.14 covers this in detail for HTTP methods

## 1) Two Kinds of Something Went Wrong

When an HTTP request goes wrong, one of two different things happened. Either the server responded with an error (4xx or 5xx), or no response arrived at all. Those are not variations of the same problem. They live in different layers and need different handling. Chapter 1.11 covered HTTP error codes. This chapter separates those errors from network failures: when no HTTP response ever arrives. Your client code, your logging, and your operations runbooks should all distinguish "server responded with an error" from "no response."

Your ESP32 sends POST to the temperature API and gets 400 Bad Request. That is an HTTP error; the Pi responded. Or your ESP32 sends the same request and times out after thirty seconds. That is a failure; no response. Different problems, different handling. An error is not the same as a failure. If you treat them the same, you will write fragile clients, mishandle retries, and misdiagnose incidents. Whether your dashboard times out waiting for the voltage API, gets 500 Internal Server Error, or the connection drops mid-transfer, understanding errors versus failures is critical. This distinction also connects to Section A Phase 1: Section A Chapter 1.06 (Failure Is Normal) and 1.10 (Observation vs Action) are about designing for missing data and separating read from write; here we apply that to HTTP. Presence of a response (even an error) is like "we got an answer"; absence is like "we got nothing." Your automation must handle both. The voltage reading might be missing because the Pi returned 404 (error) or because the request never completed (failure). Only in the first case do you have a status code to guide you.

## 2) HTTP Error Responses Are Still Communication

An HTTP error response means the request reached the server, the server parsed it, made a decision, and replied. Even if the status is 404 or 500, the protocol exchange completed. You got a response. That is successful communication with an unsuccessful outcome. When your dashboard requests a sensor endpoint with a nonexistent ID and gets 404 Not Found, the request reached the Pi, the Pi decided the resource does not exist, and replied. Communication succeeded; the outcome (get the resource) failed. You can log the 404, show "not found" to the user, or update your cached list. You have information. A network failure means no HTTP response was received. The client does not know what happened. The server may never have seen the request. This is not an HTTP event; it is silence. When your ESP32 sends POST to the temperature API and waits thirty seconds with nothing coming back, did the Pi receive it? Did it crash? Did Wi‑Fi drop? Unknown. That is absence, not an HTTP error. No status code, no body, just silence. The whole chapter reduces to one idea: an HTTP error is presence of a response; a failure is absence. Presence carries information. Absence does not. When your ESP32 gets 500 Internal Server Error, that is presence with information: the Pi received the request and something broke. When your ESP32 times out, that is absence with no information. Design your client to ask first: did I get a response? Then branch: if yes, look at the status code; if no, treat as transport failure. Do not try to parse a status code when there is no response. Do not treat "no response" as 500 or 404. They are different.

## 3) Where Errors and Failures Live

HTTP errors happen after DNS resolution, TCP connection, and request transmission. They live inside the HTTP protocol. Examples: 400 Bad Request when your ESP32 sends malformed JSON, 401 Unauthorized when your dashboard omits credentials, 404 Not Found when your coop controller hits a nonexistent path, 500 Internal Server Error when your Pi crashes while processing a request. In every case the server spoke. You have a status line, headers, and possibly a body. Failures happen before or during HTTP. DNS fails when pi.local does not resolve. TCP cannot be established when the Pi is offline. The connection drops mid-transfer when Wi‑Fi disconnects while your ESP32 is sending. The request times out when your dashboard waits thirty seconds and nothing arrives. In those cases HTTP never completed. HTTP assumes a working transport. When the transport breaks, HTTP has nothing to say. There is no status code and no response body. The protocol never finishes. When your dashboard tries to connect to pi.local and DNS fails, HTTP cannot help; the protocol never starts. When your ESP32 sends a request and the TCP connection drops before the Pi responds, HTTP assumes TCP works; when it does not, you get silence, not an HTTP error. Your client must handle "no response" as a distinct case from "response with 4xx or 5xx." In practice this means: if your library gives you a response object with a status code, you are in the error path; if it gives you an exception or a "no response" result, you are in the failure path. Do not infer a status code from a failure. There is no 500 in a timeout; there is no response.

## 4) 500 Is Not a Failure

500 Internal Server Error means the server received your request, tried to process it, and failed. That is not ambiguity; that is explicit communication. You know the server exists and that it received the request. When your dashboard requests the voltage API and gets 500, you know the Pi exists, received the request, and failed while processing it. You can log it, retry with backoff, or alert. The server told you it failed. A timeout is different. The client waited and nothing came back. You do not know whether the server received the request, processed it, crashed, or whether the response was lost. Timeouts are uncertainty. When your ESP32 sends POST to the temperature API and times out after thirty seconds, did the Pi receive it? Process it? Crash? Did the response get lost? Unknown. If you treat a timeout like a 500, you may retry non-idempotent requests and duplicate operations or corrupt state. Timeouts require caution. When your solar logger sends POST to the readings API and times out, retrying blindly might send duplicate readings; the Pi may have processed the first request. You do not know. So: 500 means "server spoke and failed." Timeout means "no response; assume nothing." Handle them differently. For 500 you can retry the same request with backoff (the server said it failed, so the request was not necessarily applied). For timeout you must consider idempotency before retrying: for GET you can retry; for POST that creates or appends, retrying might duplicate. Your coop controller might get 503 Service Unavailable with Retry-After; that is presence, so follow the header. If the same request times out, that is absence; you have no Retry-After, only your own policy.

## 5) 404 Is Not a Failure

404 Not Found means the server is there, understood the request, and the resource does not exist. That is information. The client can stop retrying, fix the path, or update stored links. When your dashboard requests a sensor that does not exist and gets 404, the dashboard knows the resource is absent. That is not a transport problem. DNS failure is different. The client cannot find the server at all. No HTTP request occurred. When your ESP32 tries to connect to pi.local and DNS resolution fails, no HTTP request happened. DNS failed before HTTP could start. That is not 404; that is a transport problem. From the client’s point of view, an HTTP error means the server spoke. A failure means silence. Your code must branch on that first. When your dashboard sends GET to the voltage API and gets 500, the Pi spoke; handle it as an HTTP error. When your dashboard sends the same request and times out, that is silence; handle it as a failure. Branch on "did I get a response?" before "what status code?" Do not use 404 as a catch-all for "something is missing." Use 404 when you have a response that says the resource is not there. When you have no response, you do not have 404; you have a failure. Same for 500: you only have 500 when the server sent you a response with that status. No response means no status.

## 6) The First Question Your Code Should Ask

When something goes wrong, the first question is: did I receive an HTTP response? Everything else follows. If yes, inspect the status code (400, 401, 404, 500, etc.) and handle accordingly. If no, treat it as a transport failure: timeout, DNS failure, or connection drop. Retry logic, logging, and user messaging all depend on that first answer. Many HTTP libraries return a response object when they have a full response and throw or return an error when they do not. Your code should not assume that "error" means 4xx or 5xx. It might mean "no response." Check: do I have a response object with a status code? If not, you are in the failure path. Sometimes you receive part of the response and then the connection drops. You get headers, or headers plus part of the body, then nothing. That is not an HTTP error. It is a transport failure mid-response. When your dashboard requests the voltage API and gets headers and part of the JSON body, then the connection drops, the response was incomplete. Transport failed. Partial responses are dangerous. The server may have completed the action; the client may not know the result; retrying may duplicate side effects. When your ESP32 sends POST to the temperature API and receives 200 OK headers but the connection drops before the body arrives, did the Pi process the reading? Unknown. Retrying might send duplicate data. HTTP assumes complete request and complete response. Partial failure is outside the protocol. There is no status code for "partial success." You must treat it as a transport failure and decide carefully whether to retry (and risk duplication) or not (and risk lost data). Design for this explicitly: document how your client handles partial response (e.g. do not retry POST on connection drop; log and alert). Your drip system, poultry net controller, and freezer monitor should all have a defined behavior for "connection closed before full response." If your HTTP library reports "connection closed" or "incomplete response," route that into your failure-handling path, not your status-code path. Only use the status code from a response when you have received a complete response (or at least the full status line and headers, if your protocol allows); if the connection dropped mid-way, you are in failure territory.

## 7) Why Idempotency Matters Here

Idempotent requests (e.g. GET, PUT, DELETE in typical use) can often be retried safely when no response arrives. Non-idempotent requests (e.g. POST that creates or appends) may cause duplicate side effects if retried after a timeout or connection drop. Failures force you to care about this. When your dashboard sends GET to the voltage API (idempotent) and times out, retrying is generally safe. When your ESP32 sends POST to the temperature API (non-idempotent) and times out, retrying may duplicate the reading. You should handle HTTP errors and failures differently. For HTTP errors: inspect status code, parse body if needed, and act (e.g. 401 → refresh token and retry, 404 → treat as missing). For failures: decide whether to retry, when to give up, and how to surface uncertainty; and for non-idempotent requests, assume the request might have been processed and avoid blind retries. When your dashboard gets 401 Unauthorized, that is an HTTP error: get a new token and retry. When your dashboard times out, that is a failure: no status code, no body; decide whether to retry and how. Retrying blindly can cause duplicate operations, double writes, or corrupted state. Retries must be intentional. When your solar logger sends POST to the readings API and times out, retrying without a strategy might duplicate readings. Understand what you are retrying and why. Some APIs support idempotency keys: the client sends a unique key with a POST, and the server deduplicates so that retrying with the same key does not create two resources. If your Pi API supports that, use it for critical POSTs. Chapter 1.14 will cover safety and idempotency of HTTP methods in detail; here the point is that failures (no response) make idempotency visible and critical. When there is no response, the only safe default for non-idempotent requests is to assume the request might have succeeded and to avoid retrying unless you have a deduplication strategy.

## 8) Errors Are Explicit, Failures Are Ambiguous

Errors are explicit. Failures are ambiguous. Ambiguity is costly. When your ESP32 gets 500 Internal Server Error, that is explicit: the Pi received the request and failed. When your ESP32 times out, that is ambiguous: did the Pi see it? Process it? Crash? Unknown. Ambiguity forces assumptions, and wrong assumptions cause bugs. Good systems log errors and failures differently. For HTTP errors, log status code, relevant headers, and body (or a summary). For failures, log timing, connection state, DNS result, and transport details. They tell different stories. When your Pi logs 500 with a stack trace, that points to a server bug. When your Pi (or client) logs a timeout with connection state, that points to network or load. Do not lump them together. In your homestead setup, if you see a spike in "no response" from your ESP32s, check Wi‑Fi and power before assuming the Pi is broken. If you see a spike in 500 from the Pi, check the Pi logs and code first. The distinction saves time. From an operations perspective: rising 4xx often means client misuse (e.g. expired tokens, bad requests); rising 5xx means server bugs; rising timeouts mean network or load. If you mix these in one metric, you lose signal. Many HTTP libraries throw exceptions for both errors and failures. That can blur the distinction. You must know what you caught. When your ESP32 catches an exception from an HTTP library, is it a 400 Bad Request (HTTP error) or a timeout (failure)? Some libraries use the same exception type for both. Inspect what you caught. Do not treat them the same. HTTP errors have a status code; failures do not. An exception might represent a timeout, DNS failure, connection reset, or malformed response. Each may need different handling. Inspect the exception type and context before deciding. Design your client so that "no response" and "response with 4xx/5xx" are handled in separate branches. When you add a new client (e.g. a script that polls your Pi), implement both branches from the start so you never treat silence as an error or an error as silence.

## 9) No Response Is a First-Class Outcome

No response is not a bug. It is a valid system state. Design for it. When your solar logger sends POST to the readings API and gets no response, that is not a bug; it is a valid outcome. Networks fail, servers restart, connections drop. Treat "no response" as a first-class outcome, not something to ignore. Networks fail. Packets drop. Servers reboot. Connections reset. This is normal. When your Pi reboots, Wi‑Fi drops, or DNS fails, this happens. Your ESP32 sending temperature readings will see these failures. Design for them. Do not assume that every request will get a response. Set timeouts, handle timeouts explicitly, and have a code path for "no response" that does something sensible (log, retry if safe, alert, or degrade gracefully). On the server side, avoid leaving clients in the dark: if the Pi is shutting down, returning 503 with Retry-After is better than dropping connections, because then the client gets a response (presence) instead of a timeout (absence). HTTP errors are normal too. APIs return 404. Tokens expire and you get 401. Permissions change and you get 403. Errors are communication, not disasters. When your dashboard gets 404 for a nonexistent sensor, handle it. When your ESP32 gets 401, fetch a new token. Silence gives you no certainty. Resilient systems are designed around silence. When your ESP32 sends POST to the temperature API and gets nothing back, did the Pi receive it? Process it? Unknown. Handle that ambiguity explicitly. Do not assume success; do not assume failure. Design for absence as a normal case. Your coop controller, drip system, and freezer monitor should all have a clear path for "request sent, no response received." In runbooks and monitoring, distinguish "high 4xx/5xx" from "high timeout rate" so you know whether to fix the client, the server, or the network.

## 10) Homestead Examples: Branching on Presence vs Absence

Your dashboard sends GET to the voltage API. If you get a response, check status: 200 → use body; 404 → resource missing; 500 → retry with backoff. If you get no response (timeout, connection reset), treat as failure: retry GET safely (idempotent), log, and maybe alert. Your ESP32 sends POST with a temperature reading. If you get 201 or 200, success. If you get 400, fix the request. If you get 401, refresh token and retry. If you get no response (timeout), do not retry blindly; you might duplicate. Log, optionally retry once with a long backoff, or treat as "maybe sent" and let the next reading carry on. Your coop controller requests fence status. If you get 200, use it. If you get 404, endpoint or resource missing. If you get no response, treat as transport failure; retry GET safely. Your solar logger POSTs a reading and the connection drops after headers. Do not assume success; do not assume failure. Log "partial response" and decide policy (e.g. do not retry POST; flag for manual check). Your drip system GETs a schedule: response → use status code; no response → retry GET. Your poultry net controller POSTs a voltage reading: response → 201 or 400; no response → do not retry POST blindly. Your freezer monitor GETs temperatures: response → 200 or 404; no response → retry GET, then alert if repeated. In every case, first branch: response or no response? Then handle each branch. Document this in your client code and in your runbooks so that when things go wrong, you know whether you are debugging HTTP semantics or the network. Errors versus failures: presence versus absence. Get that right first.

## 11) Client Strategy Summary

When a request fails, first ask: did I receive an HTTP response? If yes, inspect the status code and body; handle 4xx and 5xx as in Chapter 1.11. If no, treat as transport failure. Decide retry behavior based on idempotency and risk. For idempotent requests (e.g. GET), retrying after timeout is usually safe. For non-idempotent requests (e.g. POST that creates or appends), retry only with a clear policy (e.g. at most once, or with a deduplication key). Always separate "error" (server spoke) from "failure" (silence). Log and monitor the two separately: count "responses with 4xx/5xx" and "requests that got no response" so you can see whether the problem is the server, the client, or the network. Most bugs in distributed systems come from treating silence like an error, treating errors like silence, retrying non-idempotent requests blindly, or assuming success without a response. This chapter gives you the distinction. The next chapter (1.13) covers HTTP methods (GET, POST, PUT, PATCH, DELETE) and their semantics; together with safety and idempotency in 1.14, you will have the full picture for designing and handling requests when both errors and failures are in play. Apply this consistently across every client that talks to your Pi: dashboard, ESP32, coop controller, solar logger, drip system, and any script or tool you add later. Once "response or no response?" is the first branch everywhere, debugging and operations become straightforward.

## Common Pitfalls

Treating timeouts like 500: timeouts create ambiguity. Retrying non-idempotent requests after a timeout can duplicate operations. Treat timeouts as transport failure and decide retry policy based on idempotency. Do not assume "timeout means server error."

Lumping HTTP errors and network failures in monitoring: 4xx suggests client issues, 5xx server issues, timeouts network or load. Each needs different investigation. Separate metrics and logs so you can tell whether to fix the client, server, or network.

Assuming partial responses are complete: if headers arrive but the body does not, the server may have completed the action. Retrying without a policy can duplicate side effects. Treat partial response as transport failure and document how your client handles it (e.g. no retry for POST).

Branching on status code before checking for a response: always ask "did I get a response?" first. No response means transport failure, not an HTTP error. Branch on presence vs absence before inspecting status. Otherwise you may try to read a status code that does not exist.

Using one exception handler for all failures: timeouts, DNS failures, connection resets, and malformed responses need different handling. Inspect what kind of failure occurred before deciding how to respond. Do not catch "all network errors" and retry the same way for each.

## Summary

HTTP errors and network failures are different. HTTP errors mean the server responded with a status code (4xx or 5xx); you have explicit information. Network failures mean no response arrived; you have ambiguity. Presence carries information; absence does not. HTTP errors occur at the application layer after transport succeeds. Failures occur at the transport layer or during transfer; HTTP may never complete. Always branch on whether you received an HTTP response before inspecting status codes. Handle errors (presence) and failures (absence) differently. Preserve idempotency when retrying after failure: safe to retry GET; dangerous to retry POST blindly. Design for silence as a first-class outcome. Partial responses (headers or partial body then connection drop) are transport failures, not HTTP errors; treat them explicitly. Confusing errors and failures leads to fragile clients and wrong retries. The next chapter (1.13) introduces HTTP methods; with 1.11 (error codes) and this chapter (errors vs failures), you have the foundation for robust HTTP client and server behavior on your homestead and beyond.
