# Section B Phase 1 · Chapter 1.13: HTTP Methods

The HTTP method is the verb in the request line: GET, POST, PUT, PATCH, DELETE. It encodes intent about safety, idempotency, and side effects. This chapter defines each method, when to use it, and why method choice matters most when failures and retries are in play. Choosing the wrong method often works when everything succeeds and breaks when timeouts or retries occur.

## Learning Objectives

By the end of this chapter, you should be able to:
- Explain how HTTP methods encode intent about safety, idempotency, and side effects
- Choose the correct method for retrieval, creation, replacement, partial update, and removal
- Explain why method choice matters most under failure (timeouts, retries)
- Distinguish safe from idempotent and apply both when designing retry logic
- Avoid anti-patterns that break caches, proxies, and clients

## Key Terms

- **HTTP method**: The verb in the request line that tells the server what kind of action the client intends (GET, POST, PUT, PATCH, DELETE)
- **Safe method**: A method that does not cause state changes on the server (e.g. GET)
- **Idempotent method**: A method that can be applied multiple times with the same effect as a single application (e.g. GET, PUT, DELETE)
- **GET**: Safe and idempotent; retrieves a representation of a resource; no intended side effects
- **POST**: Not safe, not idempotent; submits data or creates resources; server defines the effect
- **PUT**: Idempotent but not safe; replaces a resource at a given URL with the request body
- **PATCH**: Not safe; applies a partial modification; idempotency depends on the operation
- **DELETE**: Idempotent but not safe; removes a resource

## 1) Methods Encode Intent, Not Implementation

The HTTP method tells the server what kind of action the client intends. It is a contract. Every method encodes expectations about safety, idempotency, caching, retries, and side effects. If you misuse methods, your system will break under failure, not under success. Chapter 1.12 showed how errors differ from failures and why "did I get a response?" is the first question. This chapter shows how method semantics determine what is safe to retry when no response arrives. Whether your ESP32 times out sending temperature readings, your dashboard retries a failed request, or the connection drops mid-transfer, method choice determines whether retries are safe or dangerous. The request line (Chapter 1.07) contains the method; the server and all infrastructure between client and server use it to decide how to handle the request.

The method does not tell the server how to do something. It tells the server what kind of thing the client wants: retrieve, create, replace, partially modify, or remove. The server decides how to fulfill that intent. When a client sends GET to a resource path, it is promising it is not asking the server to change anything. When a client sends POST, it is signaling that this may cause a change. Servers, proxies, caches, and clients rely on that promise. When your dashboard sends GET to the voltage API, it promises no state change. Your Pi can cache the response, prefetch it, or retry it safely. When your ESP32 sends POST to the temperature API, it signals potential change. Your Pi knows not to cache it, not to retry it automatically, and to handle it carefully. The method is a contract. Break it and caches, retries, and automation break. On a homestead where you run your own Pi and clients (dashboard, ESP32, coop controller), honoring the contract keeps your automation predictable when Wi‑Fi drops or the Pi is slow.

## 2) Why Methods Matter Under Failure

When everything works, wrong method choice can still appear to work. When failures happen, wrong methods cause duplicate actions, corrupted state, and inconsistent systems. Methods exist for failure cases: retries, timeouts, and partial responses. When your ESP32 sends GET to an "increment counter" endpoint and it works, the counter increments. When the request times out and the client retries, GET is considered safe to retry, so the counter increments again. You have doubled the effect. When your solar logger sends POST to the readings API and times out, retrying blindly might send duplicate readings. Method semantics tell you when retry is safe (GET, PUT, DELETE) and when it is not (POST, or PATCH with non-idempotent operations). In Chapter 1.12 you learned to branch on "response or no response." Here you learn that when there is no response, the method determines whether retrying is safe. If the request was GET, PUT, or DELETE, retry is usually safe. If it was POST or a non-idempotent PATCH, retry can duplicate. This chapter focuses on the five methods you need for most APIs: GET, POST, PUT, PATCH, and DELETE. Chapter 1.14 will formalize safety and idempotency; here we define what each method means and when to use it so that your homestead clients (dashboard, ESP32, scripts) can implement correct retry behavior.

## 3) GET Retrieves Without Side Effects

GET retrieves a representation of a resource. GET is safe, idempotent, and cacheable. It must not change server state. Safe means the request does not cause a state change on the server. It does not mean harmless, free, or cheap. It means no mutation. Because safe methods can be retried automatically, prefetched, and cached, if GET mutates state, the rest of the system breaks. When your dashboard sends GET to the voltage API and times out, your HTTP library can retry automatically because GET is safe. When your browser prefetches GET links to your config API, that is safe. If GET mutated state, retries and prefetch would cause duplicate mutations. GET is idempotent: one GET or ten GETs leave server state unchanged. The response body may change over time (e.g. new voltage reading), but the act of requesting does not change state. When your ESP32 sends GET to the voltage API once or ten times, server state is unchanged. Use GET for fetching sensor readings (voltage, temperature, fence status), retrieving configuration, loading pages, or querying current state. Do not use GET to trigger actions (use POST), update counters (use POST or PATCH), or create records (use POST). Technically HTTP allows a body on GET; in practice do not rely on it. Many clients, proxies, and servers ignore or strip GET bodies. Use query parameters for input (e.g. sensor ID, time range), or use POST if you need a complex body. Your coop controller might GET fence status; your solar logger might GET production data; your freezer monitor might GET temperatures; your drip system might GET the current schedule by ID. All are retrieval with no side effects. When you add a new "read-only" endpoint on your Pi, use GET so that clients and any proxy or cache in front of the Pi can treat it correctly.

## 4) POST Submits or Creates

POST submits data to be processed. POST is for creating new resources, triggering actions, and submitting data. POST is not idempotent by default. Retrying after a timeout or partial failure can cause duplicate actions or double creation. POST does not mean "store this here" in a generic sense; it means "here is data, do something with it." The server defines what happens. When your ESP32 sends POST to the temperature API and times out, you do not know if the Pi received or processed it. Retrying might send duplicate readings. When your solar logger sends POST to the readings API and the connection drops mid-transfer, retrying might create duplicate readings. POST requires care: understand what you are retrying and whether the server supports idempotency keys or other deduplication. A common pattern is POST to create a resource. The server responds 201 Created with a Location header pointing to the new resource. The client did not choose the ID; the server did. When your ESP32 sends POST to the sensors API to register itself, your Pi creates a sensor record, assigns an ID, and responds 201 Created with Location. The ESP32 did not choose the ID. Use POST when the server assigns the identifier, when the operation is not idempotent, or when you are triggering an action (e.g. send alert, start job, create record). Your drip system might POST a new schedule; your coop controller might POST a new fence zone; your poultry net API might POST a voltage reading. In each case the server processes the body and may create something or trigger something. Do not use POST for full replacement of a known resource (use PUT) or for removal (use DELETE). Use POST when you want "do this" or "create this" and the server decides the outcome. If your API accepts POST with an optional idempotency key header (e.g. the client sends a unique key and the server deduplicates), document it so clients can retry POST safely when they reuse the same key.

## 5) PUT Replaces a Resource

PUT means "store this representation at this URL." PUT is idempotent but not safe. It is used for full replacement: after the request, the resource at that URL should look exactly like the request body. Not merge, not partial update. Replace. Sending the same PUT twice yields the same result: state is X after the first, state is X after the second. No additional effect. That makes PUT safe to retry. When your dashboard sends PUT to the config API with the same configuration twice, the result is the same. If a PUT times out, retrying with the same body is safe. PUT is typically used when the client knows the resource URL and controls the identifier. When your dashboard knows the sensor ID and sends PUT to the sensors API with that ID and full configuration, the dashboard controls the identifier. You can create with PUT when the client chooses the ID and the operation is idempotent (create twice with same ID and body = same result). When your dashboard creates a sensor with a known ID using PUT to the sensors API with full configuration, that is valid. When your ESP32 registers itself without knowing its ID, use POST and let the Pi assign the ID. Your coop controller might PUT updated config to a known config URL; your solar logger might PUT a full panel config by ID; your drip system might PUT a schedule at a known schedule ID. Use PUT for "make this resource exactly this" at a URL the client knows. The server may respond 200 OK with the updated resource in the body, or 204 No Content; both are valid. Use PUT when the client has the full representation and wants to replace the resource at that URL. If a PUT times out, retrying with the same body is idempotent and safe; the client does not need to guess whether the first attempt was applied.

## 6) PATCH Applies Partial Modification

PATCH applies a partial change to a resource. PATCH says "apply this change," not "replace everything" and not "create something new." When your dashboard sends PATCH to the config API with only the voltage threshold field, only that field is updated; other fields stay unchanged. PUT would replace the entire config. PATCH does not prescribe a format (e.g. JSON Patch, Merge Patch). It only says partial update. The server defines the format. PATCH can be idempotent if the same patch produces the same result. Setting threshold to 12.1 is idempotent. Incrementing a counter is not. If a PATCH operation is not idempotent and the request times out, retrying may apply the change twice. Design PATCH operations to be idempotent when possible: use "set to X" instead of "increment by Y." When your dashboard sends PATCH to the config API with an increment operation and times out, retrying might increment twice. When it sends PATCH with "set threshold to 12.1," retrying is safe. Your poultry net API might support PATCH to update only the voltage threshold; your drip system might support PATCH to change only the duration of a schedule. Document whether your PATCH operations are idempotent so clients know whether retry is safe. If your API supports both idempotent and non-idempotent PATCH (e.g. "set field" vs "append to list"), document which paths or operations are which so that client authors can implement the right retry policy. In general, prefer idempotent PATCH so that timeouts and retries do not cause duplicate or inconsistent updates. When in doubt, use "set to value" rather than "increment by value" so that retrying yields the same outcome.

## 7) DELETE Removes a Resource

DELETE removes a resource. DELETE is idempotent but not safe. It mutates state. Deleting twice has the same end state: the resource is gone. First DELETE removes it; second DELETE finds it already gone (often 404 Not Found). No additional effect. That makes DELETE safe to retry. When your dashboard sends DELETE to the sensors API for a sensor ID and gets 204 No Content, the sensor is deleted. Sending DELETE again typically returns 404 Not Found; the resource is already gone. Same end state. If a DELETE times out, retrying is safe. Common responses: 204 No Content for success, 404 Not Found for already gone, 403 Forbidden if the client lacks permission. DELETE means the resource is no longer accessible. It does not guarantee physical deletion or immediate removal; that is server policy. Your dashboard might DELETE a sensor; your coop controller might DELETE a fence zone; your solar logger might DELETE an old config. Use DELETE when the intent is removal. Do not use POST with a "delete" action in the body when the semantics are "remove this resource"; use DELETE so that caches, proxies, and clients can treat it as idempotent. If the client does not know the resource URL (e.g. "delete the oldest log" without a specific ID), you might still use POST for that kind of action, because the operation is not "remove the resource at this URL" but "perform this action." When the operation is "remove the resource at this URL," DELETE is the right method. The server may respond 204 No Content (success, no body) or 200 with a body; 404 Not Found for "already gone" is also valid and preserves idempotency.

## 8) Method Safety vs Idempotency

Safety and idempotency are different. GET is safe and idempotent. POST is neither. PUT is not safe but is idempotent. PATCH is not safe; idempotency depends on the operation. DELETE is not safe but is idempotent. Safe means no state change. Idempotent means doing it multiple times has the same effect as doing it once. GET: safe and idempotent. POST: not safe, not idempotent. PUT and DELETE: not safe, idempotent. PATCH: not safe; idempotency depends on the operation. Caches cache GET, do not cache POST, and invalidate or update on PUT, PATCH, and DELETE. If you use GET to mutate state, caches will cache mutations and replay them. When your dashboard sends GET to the voltage API, caches can cache the response. When it sends POST to the temperature API, caches do not cache. When it sends PUT to the config API, caches that held the old config should invalidate. Proxies may retry idempotent methods automatically and avoid retrying POST. When your ESP32 sends GET through a proxy and it times out, the proxy might retry. When it sends POST and it times out, the proxy typically will not retry automatically. Browsers prefetch GET links, warn on resubmitting POST forms, and historically may change POST to GET on redirects. All of this assumes correct method usage. Methods express intent, not authorization. GET may still return 403 Forbidden. DELETE may require authentication and return 401. Permissions are separate from method choice. When your ESP32 sends GET to an admin endpoint, the Pi may respond 403. The method says "retrieve"; the server says "not allowed." Honor method semantics so that infrastructure and clients can behave correctly. ## 9) Method Choice Is Architecture

Choosing methods correctly enables safe retries, caching, and predictable behavior under failure. Choosing incorrectly often works in development and breaks in production. When your ESP32 uses GET to send temperature readings (wrong), the Pi might process it in development. In production, caches might cache the "request," retries might duplicate readings, and proxies might retry automatically. When it uses POST to the temperature API (correct), behavior is consistent. Method choice is architecture. Common anti-patterns: using GET to trigger actions (e.g. reboot), using POST for every update instead of PUT or PATCH, and ignoring idempotency so that timeouts and retries cause duplicates. Another anti-pattern is using POST for "replace config" when the client has the full config and a known URL; use PUT so that retries are safe. Method and status code together convey full meaning. POST with 201 Created means a new resource was created; check Location. PUT with 204 No Content (or 200 with body) means the resource was replaced. DELETE with 204 or 404 means the resource is gone. Clients interpret both. HTTP does not prevent you from mutating on GET or creating on PUT. The protocol trusts you to honor method semantics. If your Pi implements GET to a reboot endpoint that reboots the server, HTTP does not stop you; caches and retries will. Discipline matters. When your Pi implements GET to an increment endpoint, it works until timeouts and retries multiply the effect. Honor the contract so that your homestead APIs work with standard clients, caches, and proxies. When you design a new endpoint, write down the method and whether it is safe and idempotent; that documentation is part of the API contract. If you are consuming an API you did not build (e.g. a third-party weather or device API), check its documentation for the method and semantics; if it uses GET for mutations, be aware that retries and caches may cause unexpected behavior and handle accordingly.

## 10) Homestead Examples: Choosing the Method

Your dashboard fetches voltage: GET to the voltage API. No side effects, cacheable, safe to retry. Your ESP32 submits a temperature reading: POST to the temperature API. Creates or appends data; server may assign ID; not safe to retry blindly. Your dashboard updates full sensor config for a known sensor ID: PUT to the sensors API with that ID and full body. Idempotent, safe to retry. Your coop controller updates only the voltage threshold: PATCH to the config API with only that field. Idempotent if the operation is "set to X." Your dashboard removes a sensor: DELETE to the sensors API with that sensor ID. Idempotent, safe to retry. Your drip system creates a new schedule: POST to the schedules API; server returns 201 with Location. Your solar logger fetches production data: GET. Your poultry net controller replaces the full config at a known URL: PUT. Your freezer monitor deletes an old log: DELETE. Your chicken counter or soil moisture API might GET current readings (GET) or POST a new reading (POST). In each case the method matches the intent. Before choosing, ask: does this change state? Is it safe to retry? Who controls the resource ID? Can the response be cached? What happens on timeout? The method encodes your answers. When you add a new endpoint to your Pi, write down the method and the intended semantics (safe? idempotent?) so that anyone building a client (or a cache or proxy) can use it correctly.

## 11) Method Choice Checklist

Think in verbs. GET means "show me." POST means "do this" or "create this." PUT means "make it exactly this." PATCH means "change this part." DELETE means "remove it." If the sentence feels wrong, the method is wrong. Before choosing a method, ask: does this change state? If no, GET is appropriate. If yes, is the operation idempotent? If yes and the client knows the URL, PUT or DELETE may fit. If the client does not choose the ID, POST. If only part of the resource changes, PATCH, and design for idempotency when possible. Consider timeout and retry: for GET, PUT, DELETE, retry is typically safe; for POST and non-idempotent PATCH, retry can duplicate. Document the methods your API supports for each path and what clients should do on timeout. When you add a new endpoint to your Pi (e.g. for a new sensor type or a new automation), decide the method first: retrieval → GET, create with server-assigned ID → POST, full replace at known URL → PUT, partial update → PATCH, remove resource at URL → DELETE. Consistency across your API (e.g. all "read" endpoints use GET, all "create" endpoints use POST with 201 and Location) makes it easier for you and others to build correct clients and to reason about retries and failures. Then document whether it is safe and idempotent so that anyone writing a client (dashboard, ESP32, script) knows the retry policy. ## Common Pitfalls

Using GET to trigger actions: GET must not change state. Using GET for reboot, increment, or create breaks caching and retry. Use POST (or another appropriate method) for actions. Caches and proxies will treat GET as safe; if GET mutates, they will replay mutations.

Ignoring idempotency when retrying: POST is not idempotent. Retrying after a timeout can duplicate operations. Consider idempotency keys or accept the risk; do not assume retry is safe for POST. After a timeout you do not know if the server processed the request; for POST, retrying may double the effect.

Using POST for everything: Use PUT for full replacement, PATCH for partial update, DELETE for removal, GET for retrieval. Using POST for updates or deletes hides intent and breaks idempotency expectations. When the client has the full representation and a known URL, PUT is correct and retry-safe.

Confusing method with permissions: Methods express intent. GET can return 403; DELETE can return 401. Handle status codes and permissions separately from method choice. The method says what the client wants; the status code says whether the server allowed it.

Non-idempotent PATCH: If PATCH does something like "increment" and the request times out, retrying can apply the change twice. Prefer idempotent PATCH (e.g. "set to X") when possible. Document PATCH idempotency so clients know whether to retry.

## Summary

HTTP methods encode intent. GET is safe and idempotent, for retrieval; do not use GET to change state. POST is not safe and not idempotent, for submitting data or creating resources when the server assigns the ID; use POST for "do this" or "create this." PUT is idempotent but not safe, for full replacement at a known URL; same body twice = same result. PATCH is for partial modification; idempotency depends on the operation; design for idempotent PATCH when possible. DELETE is idempotent but not safe, for removal; deleting twice has the same end state. Method choice matters most under failure: timeouts and retries make safe and idempotent methods essential. Choosing methods correctly enables safe retries, caching, and scale; choosing incorrectly breaks in production. Methods are contracts. Honor them so that caches, proxies, and clients behave correctly.
