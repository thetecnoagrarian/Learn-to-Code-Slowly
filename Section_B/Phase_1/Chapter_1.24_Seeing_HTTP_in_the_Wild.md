# Section B Phase 1 · Chapter 1.24: Seeing HTTP in the Wild

HTTP is observable. This chapter shows how to watch real requests and responses with curl and browser DevTools so you can debug APIs and web apps instead of guessing.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use curl to send and observe raw HTTP requests and responses
- Inspect HTTP traffic in browser DevTools (Network tab)
- Tell the difference between what browsers do automatically and what the protocol actually requires
- Debug HTTP issues by inspecting real traffic (headers, status, timing)
- Recognize common patterns (redirects, caching, compression, CORS) in real traffic
- Apply observation-first debugging to APIs and web applications

## Key Terms

- **curl**: Command-line HTTP client that sends and receives raw requests and responses; minimal automation
- **DevTools**: Browser developer tools; Network tab shows HTTP traffic, headers, timing, and bodies
- **Verbose mode (-v)**: curl flag that prints request and response lines and headers
- **Preflight**: OPTIONS request sent by the browser before certain cross-origin requests (CORS)
- **CORS**: Cross-Origin Resource Sharing; browser policy enforced via headers; visible in DevTools
- **TTFB**: Time To First Byte; time from request sent until first byte of response
- **304 Not Modified**: Response meaning the client’s cached copy is still valid; no body

## 1) HTTP Is Observable

HTTP is not abstract. It is observable. If something is wrong, you can see the request, the response, the headers, the timing, and what actually crossed the wire. Most confusion comes from not looking. This chapter closes the gap between the mental model you built in Chapters 1.01–1.23 and what really happens on the network. You will not fully understand HTTP until you have watched it move, byte by byte, across the boundary. We do not introduce new concepts here. We put the existing ones in front of your eyes.

Real traffic is messier than diagrams. Redirects chain. Browsers add headers you did not set. Compression changes what is on the wire. Caching and conditional requests produce 304 instead of 200. None of that contradicts what you learned; it extends it. When your dashboard is slow, use curl -v or DevTools to see the actual request and response. When your ESP32’s sensor data is not arriving, check the Network tab or replay the request with curl. When your coop controller’s API call fails, inspect the status code and headers. Observation turns “it doesn’t work” into “the server returned 401” or “the request never left the browser.” That is the goal of this chapter.

## 2) curl Shows Raw HTTP

curl is a command-line HTTP client. It does almost nothing automatically. You specify the method, URL, headers, and body. It sends that and shows you what comes back. No cookies unless you ask. No redirect following unless you ask. No hidden browser behavior. That makes curl a precise tool for seeing exactly what the protocol does. When your Pi receives a request, what it sees is what curl sent. When you debug an API that your dashboard or ESP32 calls, curl lets you isolate the HTTP layer: same request, same response, no framework or UI in the way.

A minimal call is: curl https://example.com. That opens a TCP connection, sends GET with a default Host and User-Agent, receives the response, and prints the body. You do not see the request line, the response status line, or the headers, because curl by default shows only the body. To see the full exchange, use verbose mode: curl -v https://example.com. Now curl prints the request line (e.g. GET / HTTP/1.1), every request header (Host, User-Agent, Accept, Accept-Encoding, and so on), the response status line (e.g. HTTP/1.1 200 OK), every response header, and then the body. Lines that represent the request are often prefixed with a greater-than sign; lines that represent the response with a less-than sign. The exact format depends on your curl version, but the idea is the same: you see what was sent and what was received. When your dashboard requests your Pi’s /api/readings endpoint, curl -v https://pi.local/api/readings shows the GET request line, Host: pi.local, Accept: */* or application/json if you set it, then the response status, Content-Type, and body. Your ESP32 or coop controller might not use curl directly, but you can use curl from your laptop to replay the same request and see exactly what the Pi gets. That is how you verify that the problem is in the client logic, the server logic, or the network.

curl does not manage cookies unless you pass a cookie file or header. It does not follow redirects unless you pass -L. It does not hide 4xx or 5xx: you see the status line and the error body. That forces you to confront what actually happened. If your app assumes a cookie was sent and the server returns 401, replaying with curl without the cookie will show the same 401. If curl with the correct Authorization header works, then the bug is in how your app sends or stores the token. Boundaries become visible. You can also use -i to include response headers in the output while still printing the body, or -I to send a HEAD request and only fetch headers. For quick checks (e.g. “does this URL return 200?”), curl -o /dev/null -w "%{http_code}" URL prints just the status code. For full debugging, -v remains the best default.

## 3) Redirects and curl Behavior

By default, curl does not follow redirects. If you request http://example.com and the server responds with 301 Moved Permanently and Location: https://example.com/, curl prints that response and stops. You see the 301 and the Location header; you do not see a second request to the new URL. Browsers, by contrast, typically follow redirects automatically. So the same URL can behave differently: in a browser you end up on the HTTPS page; with plain curl you end up with a 301 response body (often an HTML redirect page). To make curl follow redirects, use -L. Then curl will issue a new request to the URL in the Location header and continue until it gets a non-redirect response or hits a limit. When your dashboard loads http://pi.local and the Pi redirects to https://pi.local, the browser follows without asking. With curl you see the 301 and Location unless you use -L. Neither behavior is wrong. Understanding HTTP means understanding that redirects are just responses with a 3xx status and a Location header; whether the client follows them is a client choice. Your solar dashboard or poultry net config page might do a redirect on login; in DevTools you will see the 302 and the subsequent GET to the new URL. With curl you can replay the first request and see the 302 and Location, or use -L to follow and see the final 200. Both views are useful for debugging.

## 4) Controlling Requests with curl

You can set the method with -X (e.g. -X POST), headers with -H, and a body with -d. For example: curl -X POST -H "Content-Type: application/json" -d '{"voltage":12.1}' https://pi.local/api/readings. You have specified method, Content-Type, and body explicitly. Nothing is implicit. If the server returns 400, you see the status and the error body. If it returns 201, you see the Location header and the response body. This is how you test APIs: one variable at a time. When your ESP32 POSTs temperature data, the Pi receives a POST with a JSON body. You can simulate that from your machine with curl -X POST -H "Content-Type: application/json" -d '{"temp":72.5}' https://pi.local/api/readings. If the Pi responds 201 with Location, you know the endpoint and the payload format work. If your ESP32 then fails, the problem is in the ESP32 code (e.g. wrong URL, missing header, or wrong body). If curl fails too (e.g. connection refused or 500), the problem is the server or the network.

You can add any header with -H. For example, curl -H "Accept: application/json" https://pi.local/api/readings tells the server you want JSON. curl -H "Authorization: Bearer YOUR_TOKEN" https://pi.local/api/config lets you test authenticated endpoints. When something fails, strip the request down to the minimum with curl, then add headers and body back one by one and see when the response changes. That is systematic debugging. For GET with query parameters you can put them in the URL (curl "https://pi.local/api/readings?since=2024-01-01") or use -G with -d to have curl build the query string. For POST with form data instead of JSON, use -d "key=value&other=value" and often -H "Content-Type: application/x-www-form-urlencoded" so the server knows how to parse the body. Matching the client’s exact request with curl removes the “maybe the server is wrong” doubt and focuses the fix on the right layer. Your coop controller might send an API key in a header; with curl you can send the same header and verify that the server accepts it. Your dashboard might send a session cookie; with curl you can copy the cookie value from DevTools and send it with -H "Cookie: session=..." to see if the server responds correctly. Visibility beats assumption.

## 5) Browser DevTools Reveal Automatic Behavior

Browsers are high-level HTTP clients. They follow redirects, store and send cookies, cache responses, send Accept-Encoding for compression, and enforce CORS. DevTools lets you see all of that. Open the Network tab (e.g. right-click the page, Inspect, then Network; or F12 and select Network). Reload the page. You will see a list of every HTTP request made for that load. Usually the first entry is the document request (GET for the HTML). Then you see requests for CSS, JavaScript, images, fonts, and often analytics or API calls. HTTP is chatty: one page load can trigger dozens of requests. When your dashboard loads the Pi’s UI, you might see the HTML, then CSS and JS, then API calls for voltage, temperature, or fence status. Each row is one request-response pair. Click a row to see the request URL, method, status code, and timing. In the Headers (or similar) subpanel you see request headers and response headers in full. In the Response (or Preview) subpanel you see the body, often decoded (e.g. JSON or HTML). In the Timing subpanel you see DNS, TCP, TLS, TTFB, and content download. So you are not guessing whether the slowness is DNS, server delay, or large payload; you see the phases. When your coop controller’s dashboard is slow, open DevTools, reload, and look at which request is slow and which phase (waiting for server vs downloading content) dominates. That tells you whether to fix the server, the network, or the payload size. You can also filter the Network list by type (XHR, JS, Doc, etc.) or by domain, and search by URL or header. That makes it easier to find the one request that failed or the one that took 5 seconds. Saving the HAR (HTTP Archive) from DevTools gives you a snapshot of all requests and responses for that load, which you can share or re-inspect later.

## 6) Headers and Compression

In DevTools you will see request headers you did not set in your code: User-Agent, Accept, Accept-Encoding, Accept-Language, Connection, and others. The browser adds them. They matter. Servers use User-Agent for analytics or conditional behavior. They use Accept to choose the representation (e.g. HTML vs JSON). They use Accept-Encoding to decide whether to compress the body. Browsers typically send Accept-Encoding: gzip, deflate, br. If the server supports compression, it may respond with Content-Encoding: gzip and a compressed body. DevTools often shows you the decoded body (e.g. the actual HTML or JSON), but on the wire the bytes were compressed. That affects transfer size and speed. When your Pi serves a large JSON payload, enabling gzip can shrink it significantly; in DevTools you might see a smaller “transferred” size than “resource” size when compression is used. If you are debugging why a response is slow, check whether the bottleneck is TTFB (server time) or content download (payload size or bandwidth). Headers and timing together tell the story.

## 7) Redirects, Caching, and Conditional Requests

In the Network tab you may see a request that shows “301” or “302” and then a second request to a different URL. That is a redirect chain. The browser followed the Location header automatically. Click the first request and you see the response status and Location; click the second and you see the final 200 (or 404, etc.). When your dashboard hits a login page that redirects to the app, you see the 302 and the GET to the new URL. No magic—just the redirect semantics from Chapter 1.10.

On a reload you may see some requests return 304 Not Modified with no body and very short timing. That is caching. The browser sent a conditional request (e.g. If-None-Match with the previous ETag or If-Modified-Since with the previous Last-Modified). The server compared and responded 304 to say “your cached copy is still valid.” So the browser did not re-download the body. In the Network tab you see the request, the 304 status, and the small “transferred” size. When your solar dashboard reloads and the Pi’s API supports ETags, you may see 304 for the readings endpoint if the data has not changed. That is HTTP caching in action. Conditional requests and 304 are covered in Chapter 1.10 and 1.17; here you see them in practice.

## 8) Timing and Performance

DevTools breaks each request into phases: DNS lookup, initial connection (TCP), TLS handshake (for HTTPS), request sent, waiting (TTFB), and content download. If a request is slow, the breakdown shows where the time went. Long TTFB means the server was slow to start responding (e.g. overloaded or doing heavy work). Long content download means a large body or slow link. When your dashboard requests voltage from the Pi and the request takes two seconds, check whether the delay is in “waiting” (server) or “content download” (payload). If the Pi is on the same LAN, TTFB should be small; if it is large, the Pi or the app on it is the bottleneck. Your ESP32 might be slow to get a response from the Pi; from your laptop you can use curl -w with timing variables to measure the same request and see connect time, start transfer time (TTFB), and total time. Observation turns “it’s slow” into “the server took 1.5 seconds to send the first byte.”

When a request fails, the status code is visible (400, 401, 403, 404, 500), the response body is visible (often an error message or HTML), and the response headers are visible (e.g. WWW-Authenticate for 401). So you can tell whether the failure is client-side (4xx) or server-side (5xx), and what the server said. That is why HTTP debugging is tractable. In the Network tab you can right-click a request and “Copy as cURL” (or similar) to get a curl command that replays the same request from the terminal. That bridges browser behavior and curl: you see what the browser did, then you replay it in a minimal environment to confirm or isolate the issue. Your coop controller might get 403 when calling an admin endpoint; DevTools shows 403 and possibly a body explaining “insufficient permissions.” Your ESP32 might get 401 when the token expired; curl or DevTools shows 401 and maybe WWW-Authenticate. You are no longer guessing.

## 9) CORS and OPTIONS Requests

You may see an OPTIONS request before a POST or a GET to a different origin. That is a CORS preflight. The browser sends OPTIONS to ask the server whether the actual request (e.g. POST with a custom header) is allowed. The server responds with Access-Control-Allow-Origin and related headers. If the server does not allow the origin or the method, the browser blocks the real request and your code never gets the response. CORS is a browser policy, not part of the core HTTP spec. But it is implemented with real HTTP: OPTIONS is a real request with a real response. In DevTools you see the OPTIONS request and its response; then you see the subsequent GET or POST if the preflight succeeded. When your dashboard (served from one origin) calls your Pi’s API (another origin), the browser may send OPTIONS first. If the Pi does not respond with the right Access-Control-Allow-* headers, the browser blocks the call and you see the OPTIONS in DevTools and possibly an error in the console. So even though CORS is “browser magic,” it is visible and debuggable. Your ESP32 or a server-side client typically does not send preflights (CORS is a browser concern), so the same API might work from curl or from the Pi’s backend but fail from the browser. Seeing the OPTIONS request in DevTools explains why.

## 10) Comparing curl and Browser Behavior

curl is explicit, minimal, and predictable. You send what you specify. The browser is automatic, stateful, and policy-enforcing. It adds headers, follows redirects, stores cookies, enforces CORS, and caches. Both are valid HTTP clients. They serve different roles. When you build an API that the dashboard (browser) and the ESP32 (likely not a browser) both call, the browser will send Origin, cookies, and Accept-Encoding; the ESP32 might send only what you code. So the same endpoint can see different requests from different clients. Use curl to simulate the minimal request (e.g. no cookies, no CORS) and to test the server in isolation. Use DevTools to see what the browser actually sent when the app fails. When your Pi API works with curl but fails in the browser, the difference is in the request (e.g. Origin triggering CORS) or in how the response is handled. When it fails with curl too, the problem is the server or the network. Never trust assumptions. Look at the traffic.

On the server side, during development you can log the request line, key headers, and the response status code. You do not need to log every header forever in production, but when debugging, seeing “GET /api/readings HTTP/1.1”, “Host: pi.local”, “200” in the logs confirms that the request reached the server and how it responded. Your Pi might run Express or another framework; the framework logs might say “GET /api/readings 200”. That is enough to correlate with DevTools or curl. If you need to see the raw request (e.g. to verify a header), enable verbose logging temporarily or use a tool that captures the TCP stream. Visibility beats guessing.

## 11) Common Surprises and Framework Behavior

In real traffic you will see headers added by proxies (e.g. X-Forwarded-For, X-Forwarded-Proto), headers removed or normalized by frameworks, Content-Type mismatches (e.g. client sends application/json but server expects form data), implicit redirects (e.g. 301 from http to https), and cookie scope issues (domain, path, Secure, SameSite). These are normal. Proxies and load balancers add headers. Frameworks parse the body based on Content-Type; if the client sends the wrong one, the server may return 400 or parse nothing. When your dashboard POSTs JSON but the Pi expects form-encoded data, the server may return 400 or put nothing in the request body. Inspecting the request in DevTools or replaying with curl with the correct Content-Type clarifies the contract.

Frameworks like Express, Flask, or FastAPI wrap HTTP. They give you routes, request and response objects, and middleware. They do not replace HTTP. Underneath, there is still a TCP connection, a request line, headers, and a body. When something goes wrong, go one layer down: bypass the app and use curl to send the same request. If curl gets 200 and your app gets 404, the problem is in the app’s routing or middleware. If curl gets 500, the problem is in the server or the request. Framework logs might say “route not found” or “internal server error”; the actual HTTP response (status line and headers) is what the client saw. When your Pi runs Express and a route returns 404, curl shows HTTP/1.1 404 Not Found and whatever body the app sent. That is what your dashboard or ESP32 received. Debugging at the HTTP layer keeps the mental model clear.

## 12) Homestead Examples: Observing Real Traffic

Your dashboard loads the Pi’s UI: in DevTools you see GET for the HTML, then GETs for CSS and JS, then GETs for /api/voltage, /api/temperature, or /api/fence. Click one API request and see status 200, Content-Type: application/json, and the JSON body. If one of them returns 500, you see the status and the error body. Your ESP32 POSTs a temperature reading: from your laptop, curl -X POST -H "Content-Type: application/json" -d '{"temp":72.5}' https://pi.local/api/readings. You see 201 and Location, or 400 with a validation message, or 401 if you omit the token. Your coop controller fetches fence status: curl https://pi.local/api/fence shows the response. If the controller fails in the field, you reproduce with curl and the same URL and headers to see whether the Pi is returning an error or the request is not reaching the Pi at all. Your solar logger might call an external API; DevTools shows the request and response, including any CORS or redirect behavior. Your freezer monitor might GET temperatures from the Pi; curl -v from your laptop to the same URL shows exactly what the Pi returns. Your drip irrigation UI might POST a schedule; curl -X POST with the same JSON and URL lets you verify the server accepts the payload before debugging the front-end. In every case, observation—curl or DevTools—turns “it doesn’t work” into a concrete status code, headers, and body. That is the skill this chapter reinforces. Once you are in the habit of “show me the request and response,” you stop guessing and start fixing.

## 13) Debugging Strategy and Mental Model

When something is wrong, reproduce with curl. Send the minimal request (method, URL, required headers). See what the server returns. Then add headers or body back one at a time and see when the behavior changes. That is the scientific method applied to protocols. When your ESP32’s API call fails, capture the URL and headers (from code or logs), replay with curl, and compare. When your dashboard gets 401, open DevTools, find the failing request, check whether the Cookie or Authorization header is present and correct, then try the same request with curl and the same header to confirm the server accepts it.

What you should now have clearly in mind: a request is sent, a response is received (or not—then it’s a failure, not an HTTP error). Headers modify meaning. Bodies carry representations. Status codes signal outcome. Failures split into HTTP errors (4xx, 5xx, with a response) and network absence (timeout, connection refused, no response). You are not guessing anymore. You have a protocol-level mental model and the tools to observe real traffic. Section B Phase 2 (HTML, then JavaScript, Node, Express, etc.) will build on top of this. You will build servers and clients. When they misbehave, you will inspect the HTTP exchange first. That is the habit this chapter is for.

## Common Pitfalls

Not looking at actual traffic: most HTTP problems are visible if you inspect the request and response. Use curl -v or DevTools Network tab. Assumptions about what was sent or returned are often wrong.

Ignoring automatic browser behavior: browsers add headers, follow redirects, cache, and enforce CORS. That is still HTTP. Use DevTools to see what the browser actually did. Do not assume curl behavior matches browser behavior.

Ignoring compression: DevTools may show decoded bodies, but the wire carried compressed bytes when Content-Encoding is gzip or similar. Check headers and “transferred” vs “resource” size.

Confusing framework abstractions with HTTP: frameworks wrap HTTP; they do not replace it. When debugging, use curl or raw inspection to see the real request and response. Framework logs can hide the actual status or headers.

Skipping curl for API testing: testing only through the app or the browser hides the HTTP layer. Use curl to test endpoints directly (method, headers, body), then compare with application behavior. When the Pi or any server is the one making HTTP requests (e.g. to an external weather API), use the same principle: log or capture the outgoing request and response (e.g. with a proxy or server-side logging) so you see what was sent and what came back.

## Summary

HTTP is observable. curl shows raw request and response with -v; you control method, headers, and body. Browsers add behavior (redirects, cookies, caching, CORS); DevTools Network tab shows what actually happened. Use both: curl for minimal, explicit tests and to isolate server behavior; DevTools to see browser traffic and timing. Redirects, 304 Not Modified, compression, and CORS are all visible in headers and status codes. When something is wrong, look at the traffic first. When something is slow, use timing (TTFB, content download) to see where time went. When something works in one client (e.g. curl) and not in another (e.g. browser), compare the requests: headers, cookies, and origin. You now have a protocol-level mental model of HTTP and the ability to inspect, debug, and reason about real traffic. Section B Phase 2 builds on this as you build servers and clients. The same discipline—observe, then reason—applies to HTML, CSS, and JavaScript: view source and DevTools are your eyes there too.
