# Section B Phase 2 · Chapter 2.01: What HTML Is

HTML is markup: tags that describe structure and meaning around content. This chapter defines markup vs content, tags and elements, the document tree, and why structure is kept separate from presentation so you can build valid, semantic pages that HTTP delivers and the browser turns into the DOM. Once you see HTML as markup that encodes a tree, the rest of Phase 2 is learning which elements to use for which meaning and how they fit together.

## Learning Objectives

By the end of this chapter, you should be able to:
- Distinguish markup from content and explain what markup is for
- Define tag and element and use opening and closing tags and void elements correctly
- Describe HTML as a tree (parent, child, sibling) and how that affects CSS and JavaScript later
- Explain why structure (HTML) is separate from presentation (CSS) and how HTTP fits in

## Key Terms

- **Markup**: Tags and syntax that describe structure and semantics; not the visible text alone
- **Content**: The text, images, and data that users see or use; what markup wraps
- **Tag**: The angle-bracket syntax with a name (e.g. opening p tag, closing p tag)
- **Element**: The opening tag, optional content, and closing tag (or a void element) as one unit
- **Void element**: An element that has no content and no closing tag (e.g. img, br, input)
- **Document tree**: The hierarchy of elements (and text) with one root (html), parents, children, and siblings
- **DOM**: Document Object Model; the tree the browser builds from HTML so CSS and JavaScript can work with it
- **Content model**: The rules that define what an element can contain (e.g. which elements or text are allowed inside it)

## 1) Markup vs Content

Content is the text and meaning you want to convey: the paragraph about your coop temperature, the list of sensor readings, the link to the dashboard. Markup is the machinery that describes what each part is. HTML does not by itself make the page look a certain way. It describes what things are: a heading, a paragraph, a list, a link. The browser uses that description to render the page and to expose it to assistive technology and to scripts. So when you write a paragraph of text, you wrap it in markup that says “this is a paragraph.” The tag is the markup; the text inside is the content. Together they form an element. If you skip the markup and just pour text into the file, the browser has no way to know that one block is a heading and another is a paragraph. Structure and meaning come from the tags. Without markup, the browser would treat the whole file as one run of text: no headings, no lists, no links. Assistive technology would have no landmarks or structure to announce. Scripts would have nothing to hook into. So the first habit is: wrap every piece of content in the element that describes what it is. A heading gets a heading element; a paragraph gets a paragraph element; a list gets a list element. The names of the elements are the vocabulary you and the browser share.

HTML does not “look like” the final page. It encodes structure and semantics. A heading might be marked up as a first-level heading; the browser typically renders it large and bold, but that is a default. In another context (e.g. print or a screen reader) the same heading is still “the main heading” because the markup said so. Your dashboard page might have a heading “Voltage readings,” then a paragraph of explanation, then a list of readings. The HTML says: here is a heading, here is a paragraph, here is a list. The rest—fonts, colors, spacing—belongs to CSS, which we keep separate. That separation is why you can change the look of the whole site by changing CSS without rewriting every paragraph. It is also why accessibility works: screen readers and other tools rely on the structure you declare in HTML, not on how it looks. When you build a page for your Pi’s sensor UI or your coop controller, the markup is the contract. The content is what changes (today’s temperature, tomorrow’s); the structure (heading, list, link) stays consistent. Every web page you have ever seen was built this way: content wrapped in tags that declare structure. When your Pi serves a dashboard, that dashboard is HTML. When you open it in a browser, the browser reads the tags and builds an internal tree. What you see on screen is the result of that tree plus CSS and possibly JavaScript. So learning HTML is learning the vocabulary of structure: which tag for a heading, which for a list, which for a link. The content is yours; the tags are the shared language between you and the browser. If you later add a style for "all paragraphs in the main area," the browser can apply it only because the paragraphs were marked up. Without the tags, there would be no way to target them. Markup is the foundation everything else builds on.

## 2) Tags and Elements

A tag is the angle-bracket syntax with a name. An opening tag has the name inside angle brackets. A closing tag has a slash before the name inside angle brackets. So for a paragraph you have an opening p tag, the text of the paragraph, and a closing p tag. The opening tag, the content, and the closing tag together form one element. The element is the unit the browser and the DOM work with: one paragraph element, one list element, one link element. In conversation we often say "a p element" or "a paragraph element"; we mean the whole unit. The name of the element is the same as the name in the opening and closing tags. So "p" is the element name, and the element consists of the opening p tag, the content, and the closing p tag. Elements can contain text, other elements, or both. A list element contains list item elements. A list item might contain text, or a link, or another list (for nested lists). The rules of what can contain what are called the content model. For now the important rule is nesting: you must close inner elements before you close outer ones. So you close the list item before you close the list, and you close the list before you close the body. Valid HTML is well-nested: no crossing of boundaries. If you open paragraph then list then close paragraph then close list, the tree is broken and the browser will try to fix it in ways that can be hard to predict. Close in reverse order of opening. That is how you build a clear, predictable tree. For example: you open body, then main, then section, then a list, then a list item. You close the list item, then the list, then the section, then main, then body. Never close body before you have closed the list item that is inside it. The same discipline applies to every nested structure. Your dashboard might have a main that contains several sections; each section might have a heading and a list. The closing order is: list, then section, repeated for each section, then main. Getting into the habit of thinking "what did I open last?" before you close will keep your HTML valid and your DOM predictable.

Some elements have no content and no closing tag. These are void elements. In HTML5 you write them as a single tag with a name (and often attributes). Examples include img for images, br for line breaks, and input for form controls. You do not write a closing img tag or put content between opening and closing. The element is complete in one tag. Historically you might see a slash before the closing angle bracket (self-closing syntax); in HTML5 that slash is optional and the element is still void. Knowing which elements are void avoids invalid markup: adding a closing tag for img or br is wrong and can confuse parsers. When you add an image to your dashboard or a line break in an address, you use one tag only. When you add a paragraph or a list, you use opening and closing tags and put content (and possibly nested elements) between them. Void elements often carry attributes in that single tag: an img has a source and an alt description; an input has a type and a name. Attributes are the next layer of meaning: they configure the element. We cover attributes in detail in Chapter 2.17; here the point is that the element exists as one tag and does not wrap content. A few elements have unusual rules: for example, a paragraph must not contain another paragraph or a list; a link must not contain another link or an interactive control. The content model for each element is defined in the HTML spec; as you learn each element in Phase 2, you will see what it can and cannot contain. For now, the habit that matters is: always close tags in reverse order and avoid putting block-level structures inside elements that are not meant for them. That keeps the tree clean and the DOM predictable. When in doubt, look up the element in the HTML spec or in your resources: the content model tells you what is allowed inside. Many mistakes come from putting a block element where only inline content is allowed, or from nesting elements in an invalid order. The browser will often still render something, but the DOM will not match what you assumed, and your CSS or JavaScript may behave unexpectedly. Valid HTML is the baseline for predictable behavior.

## 3) HTML as a Tree

The document has a single root: the html element. Everything else is inside it: typically a head element and a body element. The head holds metadata and linked resources; the body holds the visible structure. Inside the body you have headings, paragraphs, lists, links, and so on. Each of those can contain more elements or text. So the document forms a tree. The root is html. Its children might be head and body. The body’s children might be a header, a main, several sections, and a footer. Inside a section you might have a heading and a list; the list has list items; each list item might have text or a link. That is parent, child, and sibling: the body is the parent of the header and main; the header and main are siblings; the list is a child of the section. The tree is not just a visual aid. The browser parses the HTML and builds an in-memory representation called the DOM, the Document Object Model. The DOM is that same tree: every element and every text node is a node in the tree. CSS uses the tree to apply styles; JavaScript uses it to find elements and change nodes. CSS uses it to apply styles (e.g. “style the list inside the main section”). JavaScript uses it to find and change nodes. So the tree is the backbone of the page. Valid HTML must form a well-nested tree. Skipped or crossed tags force the parser to infer structure, which can produce a different tree than you intended. When your coop dashboard has a main area with a list of sensors, the HTML tree might be: body, then main, then section, then heading and list, then list items. That hierarchy is what you style and script later. Getting the structure right in HTML makes everything else easier. Browsers are forgiving: they will try to fix bad markup, but the inferred tree may not match what you had in mind, and different browsers might fix it slightly differently. Chapter 2.20 (Block and Inline) goes deeper into how elements fit into the tree and what can nest inside what. Text inside elements also becomes nodes in the tree: a paragraph element has a text node as its child. When you script or style the page, you are working with that tree. So the mental model to keep is: HTML is the serial form of the tree; the browser parses it and builds the live tree (the DOM); everything else (CSS, JavaScript, accessibility tools) uses that tree. Writing HTML is therefore writing a tree. Every opening tag starts a branch or a leaf; every closing tag ends it. The result must be a single root with no gaps and no crossed branches.

## 4) Separation of Structure and Presentation

HTML is for structure and meaning. CSS is for presentation: how things look (fonts, colors, layout, spacing). We keep them separate. HTML says “this is a heading, this is a list, this is a link.” CSS says “headings are this big and this color, lists have this spacing, links are underlined.” Why separate? Maintainability: you can change the look of the whole site by editing CSS without touching every HTML file. One stylesheet can apply to many pages. Accessibility: screen readers and other tools rely on the structure in HTML; presentation can be adjusted per user (e.g. high contrast, larger text). Flexibility: the same HTML can be styled differently for screen, print, or different screen sizes. If you mix structure and presentation—for example by using elements only for their default look—you tie meaning to one visual and make it harder to restyle or to support different users. Early web pages often used HTML tables and presentational tags to control layout and appearance. That made pages brittle and hard to maintain. Modern practice is to use HTML for structure and semantics only and to reserve all visual decisions for CSS. Your dashboard might look completely different in a "compact" theme versus a "large type" theme with the same HTML; only the CSS changes. Section B Phase 1 covered HTTP: the client requests a resource, the server responds with a representation. When that resource is a web page, the representation is often HTML. The server sends the HTML (with Content-Type text/html); the browser receives it, parses it into the tree, and then loads any linked CSS and JavaScript. So HTTP delivers the HTML; the browser turns it into the DOM and applies CSS and runs scripts. You will see in Phase 2 how to link a stylesheet from the head and how to include scripts; the HTML document is the single entry point the browser gets from HTTP. Your Pi might serve an HTML page for the dashboard; the browser gets it over HTTP, builds the tree, and then your CSS makes it look like a dashboard and your JavaScript fills in the readings. Structure first, then presentation and behavior. Chapter 2.02 covers the document structure (DOCTYPE, head, body) in detail. Later chapters in Phase 2 cover the elements you put inside that structure: text, links, lists, forms, and so on. Phase 7 (CSS) will build on this same tree to style it. When you write HTML, you are not drawing the page; you are declaring what each part is. The browser (and any CSS or JavaScript) then uses that declaration. That is why "semantic" HTML matters: choose elements that match the meaning of the content. A navigation menu is a nav; a list of items is a list; a standalone piece of content is an article. If you use a generic container for everything, you lose the structure that styling and scripting and assistive technology depend on. Separation of structure and presentation is not just a technical rule; it is what makes the same HTML work across devices, themes, and user preferences.

## 5) Homestead Examples: Markup and Structure

Your voltage dashboard page has structure: a heading “Voltage readings,” maybe a short paragraph of explanation, then a list or table of readings. The HTML marks each part: one heading element, one paragraph element, one list or table element. The actual numbers (12.1 V, 11.8 V) are the content; the markup says “this is a heading, this is a paragraph, this is a list.” Your coop controller’s status page might have a heading, a paragraph with the door state, and a list of recent events. Same idea: structure in HTML, content inside it. Your solar production page might have a main heading, sections for “Today” and “This week,” and in each section a heading and a list or figure. The tree is main, then section, then heading and list. Your poultry net or fence status page might have a heading, a short status line, and a list of zones or readings. Your drip irrigation schedule page might have a heading, a paragraph of instructions, and a list or table of schedule entries. Your freezer or barn temperature page might have a heading, a short status line, and a list of sensors with current readings. In every case the pattern is the same: a root (body or main), then sections or blocks, each with a heading and content (paragraphs, lists, tables). When you add a new sensor or a new page, you reuse the same structural patterns—heading, paragraph, list, link—so that styling and scripting stay consistent. The markup is the contract between you and the browser (and assistive tech). Get the structure right and the rest follows. If you later want to add a "print view" that hides the nav and shows only the main content, the same HTML can support that with a different CSS file or media query, because the structure is already there. That is the payoff of keeping structure and presentation separate. Across all these examples the pattern is the same: you decide what each part of the page is (a heading, a paragraph, a list, a link), you wrap it in the right element, and you keep the tree well-nested. The content (voltages, temperatures, door states, schedule entries) changes; the structure stays consistent. When you add a new page for a new sensor or system, you reuse the same skeleton. That consistency makes it easier to write one stylesheet for the whole dashboard and one set of scripts that can find and update the right elements. HTML is the contract: you provide the structure, the browser builds the tree, and CSS and JavaScript do the rest.

## 6) What Breaks When Markup Is Wrong

Invalid or sloppy markup has real costs. The browser may produce a different tree than you intended, so your CSS selectors (e.g. "the list inside main") might not match what you think they match. Scripts that assume a certain structure (e.g. "the third list item") can break or target the wrong node. Screen readers and other assistive technology rely on correct semantics; wrong elements (e.g. using a heading only for big text) confuse the outline and navigation. Search engines use the structure to understand the page; missing or wrong headings and landmarks can hurt findability. So "the browser still shows something" is not enough. You want a tree that matches your intent and that stays predictable across browsers and tools. Validators (Chapter 2.23) help you catch nesting errors and missing required pieces. During development, view source and the browser's DevTools Elements panel show you the actual DOM the browser built. If you see extra wrappers, flattened structure, or moved nodes, the parser fixed something—and you should fix the HTML so the tree is what you expect. When your dashboard layout breaks on one browser but not another, or a script fails to find an element, the cause is often a markup mistake that led to a different tree. Fix the markup first; then recheck styling and scripting. Learning to view source and to use the Elements panel in DevTools is part of learning HTML: you see the live tree the browser built, not just your file. That habit will help you in every chapter of Phase 2 and beyond. Another consequence of bad markup is inconsistent behavior across browsers. One browser might infer a different tree than another when you leave tags unclosed or nest incorrectly. Your page might look right in one browser and wrong in another, or a script might work in one and fail in another. Writing valid, well-nested HTML from the start avoids that. Use a validator (Chapter 2.23) as you go, not only at the end. Fix the tree first; then debug CSS and JavaScript.

## Common Pitfalls

Using elements for how they look instead of what they mean: for example using a heading because you want big text, or a list because you want bullets. Pick elements for their semantics; use CSS to change appearance.

Skipping or crossing closing tags: invalid nesting forces the parser to fix the tree, which can produce unexpected DOM. Always close inner elements before outer ones and use valid structure.

Adding closing tags for void elements: img, br, and input do not have closing tags. Adding one is invalid and can cause layout or parsing issues.

Mixing structure and presentation in your head: if you think “I need something bold” and grab a heading, you are mixing roles. Use the right element for the meaning (e.g. strong for importance, heading for document structure) and style with CSS.

Ignoring the tree: the DOM is a tree. If you do not think in terms of parent, child, and sibling when writing HTML, you may create structure that is hard to style or script later.

Relying on "it looks right" without checking the DOM: the browser may fix your markup and still show something. Use view source and DevTools to confirm the tree is what you expect before writing CSS or JavaScript that depends on it.

Forgetting that the tree is global: every element has exactly one parent (except the root). If you think of the page as a flat list of pieces, you will write invalid or confusing structure. Think in branches: what contains what, and in what order do I close?

## Summary

HTML is markup around content. Tags describe structure and semantics; content is the text and data inside. Elements are the units: opening tag, content, closing tag (or a single void element). Void elements (img, br, input) have no content and no closing tag. The document forms a tree with html at the root; parents, children, and siblings are the vocabulary of that tree. Well-nested elements give you a predictable DOM for CSS and JavaScript. Structure (HTML) is separate from presentation (CSS); HTTP delivers the HTML and the browser builds the tree and applies styles and scripts. Use the right elements for meaning; keep the tree valid; reserve appearance for CSS. When markup is wrong, the parser may fix it in ways that break your assumptions—validate and inspect the DOM so the tree matches your intent. The next chapter gives you the minimal document structure (DOCTYPE, html, head, body) so you can start writing valid pages immediately.
