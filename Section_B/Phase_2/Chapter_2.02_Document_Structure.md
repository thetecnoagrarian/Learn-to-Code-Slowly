# Section B Phase 2 · Chapter 2.02: Document Structure and the DOCTYPE

Every HTML document has a skeleton: a DOCTYPE, a root html element, and a head and body. This chapter covers that structure, why character encoding belongs in the head first, how the title and meta tags work, and how to write a minimal valid page so the browser parses your markup correctly and your dashboard or status pages load as intended.

## Learning Objectives

By the end of this chapter, you should be able to:
- Write a minimal valid HTML5 document with DOCTYPE, html, head, and body
- Set character encoding with a meta charset tag and explain why it must appear early
- Use the title element and understand its role in tabs, bookmarks, and search results
- Add viewport and other common meta tags where appropriate

## Key Terms

- **DOCTYPE**: The declaration at the very start of an HTML document that tells the browser which parsing mode to use (e.g. HTML5)
- **Root element**: The single top-level element that contains all other content; in HTML this is the html element
- **head**: The section of the document that holds metadata and linked resources; not rendered as visible content
- **body**: The section that holds the visible content of the page; one per document
- **Character encoding**: The mapping between bytes and characters (e.g. UTF-8); must be declared so the browser interprets text correctly
- **viewport**: A meta tag that influences how the page is scaled and laid out on small screens (e.g. mobile)

## 1) DOCTYPE and the html Root

The first thing in an HTML file is the DOCTYPE. It is not a tag or an element; it is a declaration. For HTML5 you use the short form: the word DOCTYPE, then the word html, in angle brackets with an exclamation mark at the start. That declaration tells the browser to use standards-mode parsing for HTML5. Without it, the browser may fall back to quirks mode, where layout and parsing can differ from what you expect. The DOCTYPE has no closing tag and no content; it is a one-line declaration. Right after it comes the root element.

The root element is html. It wraps everything else in the document: the head and the body. In the opening html tag you can add a lang attribute to specify the language of the page (e.g. English). The lang attribute helps screen readers choose the right pronunciation and helps translation tools and search engines understand the content. For a page in English you would set lang to a value meaning English. The html element has two main children: head and body. There is exactly one html root, one head, and one body per document. The DOCTYPE plus the html root are the wrapper; inside html you define the head (metadata and linked resources) and then the body (the visible structure). Chapter 2.01 described the document as a tree; the root of that tree is the html element. Everything you put on the page lives inside that root, and the head and body are the first level of structure. Getting this skeleton right ensures the browser builds the DOM the way you intend and that the rest of your markup is parsed consistently. Older HTML versions had longer, more complex DOCTYPEs that referred to a DTD (Document Type Definition). For HTML5 the declaration is deliberately minimal: no version number, no URL. The browser recognizes it and switches to standards mode. You do not need to memorize anything else; just start every document with that declaration and then the html root. The lang attribute on the html element is optional but recommended. It takes a language code (e.g. for English). Screen readers use it to select the right voice; translation tools use it to detect the source language; and validators may warn if it is missing. For a homestead dashboard or status page in English, set lang to the appropriate value and keep the rest of the structure the same. The skeleton is the same whether the page is a simple status view or a full dashboard with multiple sections. No other elements sit outside the html root; no other elements wrap the html element. The DOCTYPE is not an element—it is a declaration—so it does not have a closing tag and is not part of the DOM tree. The tree starts at html. When you validate your document or inspect it in DevTools, you will see html as the root and head and body as its children. Getting the DOCTYPE and the html root right is the first step; the next is filling the head and body in the correct order.

## 2) head vs body

The head and body divide the document into two roles. The head holds metadata and linked resources. Metadata is information about the page rather than the page itself: the document title, the character encoding, the viewport setting, optional description and keywords for search engines, and links to stylesheets and scripts that the browser must load before or while rendering. Nothing in the head is displayed as part of the main page layout. The head might contain a title element (the page title that appears in the tab and in bookmarks), meta tags (for charset, viewport, description), and link elements (for CSS) or script elements (for JavaScript). The order of elements in the head matters for some things: the character encoding meta tag should come early, ideally as the first child of head, so the browser knows how to interpret the rest of the file. The body holds the visible content: headings, paragraphs, lists, links, images, forms, and everything else the user sees. There is exactly one body per document. The browser renders the body; it uses the head to understand how to render (e.g. which stylesheet) and to show things like the tab title. So when you build a dashboard page for your Pi or a status page for your coop controller, the head holds the title (e.g. "Coop status"), the charset, the viewport meta tag so it looks right on a phone, and any links to your CSS. The body holds the actual heading, the status text, the list of readings, and the links to other pages. That separation keeps identity and configuration in the head and content in the body. The head is not visible in the normal layout; the user does not see the title element as part of the page content—they see it in the tab or in the bookmark name. They see the body. So when you are editing a page and something does not show up, check whether you put it in the head by mistake. Move visible content to the body; keep only metadata and links in the head.

The document order is fixed: DOCTYPE first, then the html opening tag, then the head (with its contents), then the body (with its contents), then the html closing tag. You do not put the body inside the head or the head inside the body; they are siblings, both direct children of html. The order head then body is required. Some older or minimal examples might show a head with no charset or title; for real pages you should always include at least charset and title in the head so the browser and users can identify and correctly decode the page. You cannot put body before head or put a second head or body in the same document. The tree is strict: html contains head and body; head contains metadata and links; body contains the visible structure. Validators will report an error if you break that order or duplicate head or body. When you open a minimal HTML file in a browser, the browser expects this structure. If you omit the head, the browser will infer one when it parses the document, but you should always write it explicitly so that you can set charset, title, and viewport in a predictable place. A minimal valid document has DOCTYPE, html, head, and body; the head can be empty (though you will almost always want at least charset and title), and the body can be empty (e.g. while you are still building the page). Once that skeleton is in place, you add the elements you learned in Chapter 2.01 and the ones you will learn in the rest of Phase 2. The head can also contain base (for resolving relative URLs), which is less common, and style (for inline CSS), which is valid but often better kept in a linked stylesheet. Scripts in the head run before the body is fully parsed unless you mark them as deferred or async; for many small projects you will put script at the end of the body or in the head with defer. The important point is that head and body have distinct roles: configuration and identity in the head, visible structure in the body. Do not put paragraphs, headings, or lists in the head; do not put charset or title in the body. Keeping that boundary clear makes the document easier to maintain and ensures the browser and any tool that inspects the page can find metadata in a predictable place.

## 3) Character Encoding and meta charset

Characters in a file are stored as bytes. The browser needs to know which encoding (which mapping from bytes to characters) you used so it can interpret the text correctly. If the browser guesses wrong, you get mojibake: wrong or replacement characters where you expected accented letters, symbols, or non-Latin script. To avoid that, you declare the encoding. For HTML5 you use a meta tag with a charset attribute. The tag goes in the head and should appear as early as possible, ideally as the first child of the head element. The HTML spec recommends that the declaration appear within the first 1024 bytes of the document so the browser can decide encoding before parsing much of the page. If the meta charset is missing or late, the browser may scan the content to guess the encoding, which can fail or differ between browsers. Setting it explicitly gives you predictable behavior. Some servers send a Content-Type header with a charset parameter (e.g. charset equals UTF-8). That can override or reinforce the meta tag. For maximum compatibility, set both: send the correct HTTP header and include the meta charset in the head. The meta tag is what the HTML spec defines and what validators check; the header helps when the document is read in contexts where the HTML is not fully parsed first. The value you want almost always is UTF-8. UTF-8 can represent virtually all characters in Unicode: English, accented characters, symbols, and scripts used worldwide. Using UTF-8 by default means you can use any character in your content (e.g. in sensor labels or in user-generated text) without worrying about encoding errors. The meta charset tag is a void element: one tag, no closing tag. Place it at the top of the head, then add your title and other meta tags and links. Your editor and your server should also use UTF-8 when saving and sending the file; the meta charset tells the browser what to expect so it matches what you sent. For a homestead dashboard or status page, you might never use more than ASCII, but declaring UTF-8 is still the right default and prevents problems if you later add a degree symbol, an umlaut, or a unit character.

## 4) title and Other Meta Tags

The title element goes in the head. It contains the document title: the text that appears in the browser tab, in bookmarks, in browser history, and often as the main link text in search results. There should be exactly one title per page. The content is plain text (no other elements inside title). Choose a short, descriptive title that identifies the page: "Voltage dashboard," "Coop door status," "Solar production." Users and search engines use it to recognize the page, so avoid generic text like "Home" or "Page 1" when you can be more specific. The title is part of the page identity; it is not displayed in the body. If you omit it, the browser may show the URL or a blank tab title, which hurts usability and looks unprofessional. For a multi-page dashboard, give each page a distinct title so tabs and bookmarks are meaningful.

Besides charset and title, the most important meta tag for many pages is the viewport. The viewport meta tag tells the browser how to scale and size the page on small screens (e.g. phones). Without it, a mobile browser might render the page at desktop width and then shrink it, making text tiny and layout awkward. With a standard viewport setting (name viewport, content that sets width to device width and initial scale to one), the browser uses the device width as the layout width and allows responsive CSS to work as intended. You put this meta tag in the head; it is a void element with name and content attributes. It does not change the content of the page, only how the viewport is set up for layout. If your dashboard or status page will be opened on a phone or tablet, include the viewport meta so your layout and any responsive styles behave correctly. Other meta tags are optional: description (used by search engines for snippets; avoid keyword stuffing), robots (hints for crawlers), and so on. For most small projects and internal dashboards you need DOCTYPE, html, head, body, meta charset, title, and often viewport. The rest you add when you have a concrete need (e.g. Open Graph tags for social sharing). Keep the head focused on identity and configuration; put all visible content in the body. The title is not the same as a heading in the body. The body might have a first-level heading that says "Voltage readings"; the title in the head might say "Voltage dashboard — Homestead" so the tab and bookmarks are clear. They can match, but the title is what appears in the browser chrome and in search results; the heading is what appears in the page layout. Both matter: the title for identity and navigation, the heading for the document outline and on-page structure. Meta description is optional; if you add it, use a short, human-readable summary of the page. Avoid stuffing keywords; search engines may use the description for snippets. For internal or local dashboards you may skip description and robots; for public pages they become more relevant. Start with the minimal set (charset, title, viewport) and add others when the use case demands it. The viewport content can include other parameters (e.g. minimum or maximum scale, user-scalable). For most pages the standard "width equals device-width, initial-scale equals one" is enough. It tells the browser to use the device width as the layout width and to start at a 1:1 scale so that responsive CSS media queries and flexible layouts work as intended. If you omit the viewport meta, many mobile browsers assume a large default width (e.g. 980 pixels) and scale the page down, which often makes text small and links hard to tap. Adding the viewport meta is a one-line change in the head and fixes that for typical responsive pages. If your page is only ever viewed on a desktop or on a fixed-size kiosk, you might still include it for consistency; it does not harm desktop rendering and keeps the document ready if you later open it on a phone or tablet.

## 5) Homestead Examples: Document Structure in Practice

Your voltage dashboard page needs the same skeleton as any other HTML page: DOCTYPE, html, head, body. In the head you set the charset (UTF-8), the title (e.g. "Voltage readings"), and the viewport meta so the page is usable on a phone when you check it from the barn or the garden. In the body you put the heading, the paragraph of explanation, and the list or table of readings. Your coop controller status page has the same structure: head with charset, title ("Coop door status" or similar), and viewport; body with the status message and maybe a list of recent events. Your solar production page, your poultry net voltage page, your drip irrigation schedule page—each is one HTML document with one head and one body. The head identifies the page and configures encoding and viewport; the body holds the content. When you add a new page to your Pi or your small web server, you copy the same minimal structure and change the title and the body content. That consistency makes it easy to maintain: you know where to put a new stylesheet link (in the head) and where to put new content (in the body). If you serve these pages over HTTP (as in Section B Phase 1), the server sends the whole document; the browser parses DOCTYPE and html, then head, then body, and builds the DOM. Getting the structure right once and reusing it across pages saves time and avoids parsing or layout surprises. Your freezer temperature page, your barn or coop humidity page, your drip schedule page—each has the same skeleton. The title in the head changes ("Freezer temps," "Coop humidity," "Drip schedule"); the body content changes. The DOCTYPE, html, head, and body stay the same. When you add a shared stylesheet, you add one link in the head of each page (or use a template). When you add a favicon or a mobile web app meta tag, you add it in the head. The body stays the place for content only. That separation scales: as you add more pages or more meta tags, you always know where they go. Validators and DevTools expect this structure; screen readers and search engines use the head for metadata. Giving every page a correct skeleton is the foundation for everything else in Phase 2 and for the CSS and JavaScript you will add later. If you use a static site generator, a template engine, or a framework, the output should still be valid HTML with DOCTYPE, html, head, and body. When you customize a template, ensure you do not remove or duplicate the head or the charset and title. The same principles apply: one root, one head, one body, charset first in the head, and a descriptive title. Whether you write the HTML by hand or generate it, the browser and the DOM expect this structure. Your homestead dashboards and status pages are just HTML documents; they benefit from the same skeleton as any other page on the web.

## 6) What Breaks When the Skeleton Is Wrong

Omitting the DOCTYPE can trigger quirks mode. Layout and parsing may differ from standards mode; margins, widths, and error recovery can be inconsistent across browsers. Always include the DOCTYPE at the very beginning of the file. Putting body content in the head or head content in the body is invalid; the browser may move nodes around to fix the tree, and the result may not match what you intended. Keep metadata and links in the head and visible content in the body. Omitting or delaying the meta charset can cause encoding bugs: the browser may guess wrong and show garbled text. Put the charset meta as the first child of head. Missing or duplicate title is less critical but hurts usability: use exactly one title per page and make it descriptive. Forgetting the viewport meta on a page that will be viewed on mobile often results in a zoomed-out, tiny layout. If your dashboard is used on phones or tablets, include the viewport meta. Invalid nesting (e.g. putting an html element inside body) breaks the tree and can confuse the parser. Stick to the standard order: DOCTYPE, html, head, body, with head and body as the only direct children of html. Validators (Chapter 2.23) will flag missing or misplaced structure. Fix the skeleton first; then add and debug the rest of your markup. Another common mistake is putting the charset meta in the body or after a lot of content in the head. The browser may have already started parsing and made encoding decisions. Always put charset as the first child of head. Similarly, putting multiple title elements is invalid; the document has one title. If you use a template or server-side includes, ensure you do not output the head (or the charset and title) more than once. For dynamic pages, the server should send a single, well-formed head with charset, title, and viewport set correctly for that page. The skeleton is small and simple, but getting it wrong causes subtle or obvious breakage. Take the time to set it up once per project and reuse it.

## 7) Minimal Document Checklist

A minimal valid HTML5 document has the following in order: the DOCTYPE declaration; the opening html tag (with lang if you know the language); the head element containing at least the meta charset (first) and the title; the body element (which can be empty); and the closing html tag. Optionally include the viewport meta in the head for mobile-friendly layout. That is the skeleton. Everything else—paragraphs, headings, lists, links, images, forms—goes inside the body. When you create a new page, start with this skeleton. Then add the charset and title and viewport in the head, and start adding body content. You can validate the document (Chapter 2.23) to confirm the structure is correct. Once the skeleton is valid, you can focus on semantics and content: which elements to use for which meaning, how to nest them, and how to link stylesheets and scripts from the head. The document structure is the same for a single status page and for a multi-page dashboard; only the title and body content change. Building the habit of always starting with a valid skeleton ensures that every page you ship has a correct DOCTYPE, encoding, title, and head/body split, which is the base for reliable parsing, layout, and accessibility. When you open an existing project, check that every HTML file has this structure; if one page is missing the DOCTYPE or the charset, fix it so all pages behave consistently. The skeleton is the same for every page; only the title and body content differ.

## Common Pitfalls

Putting visible content in the head: the head is for metadata and linked resources only. Anything that should appear on the page goes in the body.

Omitting the meta charset or putting it after other content in the head: the browser may misdecode the file. Place the charset meta first in the head.

Using a generic or empty title: "Untitled" or "Page 1" hurts bookmarks, tabs, and search. Use a short, descriptive title for each page.

Skipping the viewport meta on pages that will be viewed on mobile: without it, the page is often rendered at desktop width and scaled down, making it hard to use on a small screen.

Adding more than one head or body: the document has exactly one of each. Duplicates are invalid.

Forgetting the DOCTYPE: without it, the browser may use quirks mode and render or parse the page differently than you expect.

Putting charset late in the head or in the body: the browser needs it early to interpret the rest of the document. Keep it the first child of head.

Confusing title with the main heading: the title is in the head and appears in the tab and bookmarks; the heading is in the body and appears on the page. Both can be descriptive; they serve different roles.

## Summary

Every HTML document needs a DOCTYPE (for HTML5 use the short form), an html root element, a head, and a body. The head holds metadata and linked resources: meta charset (first, for UTF-8), title (one per page, descriptive), viewport meta (for responsive behavior on mobile), and optional description or other meta tags. The body holds the visible content. Character encoding must be declared early so the browser interprets text correctly; UTF-8 is the default. The title appears in tabs, bookmarks, and search results. The viewport meta enables proper scaling on small screens. Keep the skeleton valid and consistent across pages so parsing and layout are predictable. The head is where you declare identity (title), encoding (meta charset), and viewport behavior; the body is where you build the visible tree.
