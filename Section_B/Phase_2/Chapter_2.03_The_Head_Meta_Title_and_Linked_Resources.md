# Section B Phase 2 · Chapter 2.03: The Head — Meta, Title, and Linked Resources

The head holds metadata and linked resources that identify the page and configure how it is rendered. This chapter covers meta tags (charset, viewport, description, and others), the title element, how to link stylesheets and favicons, and how script in the head behaves so you can set up the head correctly for dashboards, status pages, and any HTML document.

## Learning Objectives

By the end of this chapter, you should be able to:
- Place meta charset and viewport correctly in the head and explain why order matters
- Use the title element for tabs, bookmarks, and search results
- Link external stylesheets and favicons with the link element and the right relationship (rel) values
- Understand the difference between head (metadata, linked resources) and body (visible content) and when to use script in the head

## Key Terms

- **meta tag**: An element in the head that provides metadata (e.g. charset, viewport, description); typically void, with name and content or charset attributes
- **rel**: The relationship attribute on link elements; indicates how the linked resource relates to the document (e.g. stylesheet, icon)
- **favicon**: A small icon associated with the page, shown in tabs and bookmarks; linked with link rel icon
- **blocking**: A script in the head that runs immediately and can delay parsing and rendering until it finishes (unless deferred or async)

## 1) Meta Charset and Viewport

Chapter 2.02 introduced the document skeleton and the head. The first thing that should appear inside the head is the meta charset declaration. It tells the browser which character encoding to use (almost always UTF-8) so that all text in the document is interpreted correctly. The HTML spec recommends that this declaration appear within the first 1024 bytes of the document. If it comes later, the browser may have already started parsing and made encoding decisions, which can lead to mojibake or inconsistent behavior. So the conventional order is: open head, then meta charset as the first child, then any other meta tags, then title, then link and script elements. The charset meta uses the charset attribute; it is a void element with no closing tag. Set it to UTF-8 unless you have a specific reason to use another encoding. UTF-8 covers virtually all characters you will need for English, symbols, accented text, and other scripts. For a homestead dashboard or status page, UTF-8 is the right default and avoids encoding bugs when you add degree symbols, unit characters, or non-ASCII labels.

Right after charset, many authors put the viewport meta tag. The viewport meta has a name attribute (viewport) and a content attribute that describes how the browser should size and scale the layout on small screens. A typical value sets the width to device width and the initial scale to one. That tells the browser to use the device width as the layout width instead of assuming a large desktop width and scaling down, which would make text tiny and layout awkward on phones. Without the viewport meta, mobile browsers often render the page at a default width (e.g. 980 pixels) and then scale it to fit the screen. With the viewport meta, responsive CSS and flexible layouts work as intended. So for any page that might be viewed on a phone or tablet—including your voltage dashboard or coop status when you check it from the barn—include the viewport meta in the head, usually right after the charset. Both are void elements; they have no content and no closing tag. Order matters for charset (first); viewport can follow immediately.

Other meta tags are optional and go after charset and viewport when you need them. The description meta tag has name description and a content attribute with a short, human-readable summary of the page. Search engines may use it for snippets in search results. Keep it concise and avoid keyword stuffing. The robots meta tag can hint to crawlers whether to index the page or follow links; use it when you have a specific need (e.g. noindex for a staging or internal page). There are also meta tags for Open Graph (social sharing) and Twitter cards when you want to control how the page appears when shared. For internal dashboards and status pages you often only need charset and viewport; add description and others when the page is public or when you care about search or sharing. The important habit is: charset first, then viewport, then title, then any other meta or link or script. That order keeps encoding and viewport behavior predictable and keeps the head organized. The meta tag is a void element: one tag, no closing tag. Some meta tags use the charset attribute (for encoding); others use name and content (for viewport, description, robots, etc.). You cannot mix them: the charset meta has no name or content, and a viewport meta has name and content but no charset. Each meta tag does one job. If you need both charset and viewport, use two meta elements: first the one with charset, then the one with name viewport and the appropriate content. Browsers and validators expect this pattern. For a minimal head you need at least charset and title; for any page that might be viewed on a phone or tablet, add the viewport meta. The rest (description, robots, Open Graph, etc.) you add when the use case demands it. Internal dashboards often stop at charset, viewport, and title; public or shared pages may add more meta tags for search and social. The head stays the same structure; you just add more elements when needed.

## 2) Title and Page Identity

The title element goes in the head and contains the document title: the text that identifies the page in the browser tab, in bookmarks, in history, and often in search results. There must be exactly one title per document. The content is plain text only; you do not put other elements inside title. Choose a short, descriptive phrase that tells the user (and search engines) what the page is: "Voltage dashboard," "Coop door status," "Solar production — January." Avoid generic labels like "Home" or "Page 1" when you can be more specific. The title is not displayed in the body; it appears in the browser chrome (the tab, the window title) and in bookmark names. So it is part of the page identity, not part of the visible content. If you omit the title, the browser may show the URL or a blank label, which hurts usability and looks unprofessional. For a multi-page dashboard, give each page a distinct title so that when users have several tabs open or look at their bookmarks, they can tell which page is which. The title can match or differ from the main heading in the body; often the title is slightly more general (e.g. "Voltage dashboard") and the main heading is more specific (e.g. "Battery and solar readings"). Both should be meaningful. Screen readers and assistive technology use the title to announce the page; search engines use it as the primary link text in results. So the title is a small but important part of the head: one element, plain text, descriptive, and unique per page. Avoid very long titles; tabs and search results often truncate them. The title can be longer than the main heading if that helps identity (e.g. "Voltage dashboard — Homestead monitoring") but avoid very long titles; tabs and search results often truncate them. If your site has a common prefix (e.g. the site name), you can use it in the title (e.g. "Coop status | Homestead") so that when users have many tabs open, they see both the site and the page. The title is not the same as the h1 in the body: the h1 is the main heading on the page and appears in the document outline; the title is metadata and appears in the browser chrome. Both matter, and they can match or complement each other. Just ensure every page has exactly one title and that it is meaningful. When you update a page, changing the title updates what users see in tabs and bookmarks; the title is part of the live document.

## 3) Linked Resources: Stylesheets and Icons

The head is also where you link external resources that affect how the document is rendered or identified. The link element is a void element: it has no content and no closing tag. It uses attributes to say what is being linked and how it relates to the document. The rel attribute (relationship) is required and indicates the role of the linked resource. For a stylesheet you use rel equals stylesheet. You also specify the URL of the CSS file with the href attribute. The browser then fetches that resource and applies it to the document. Multiple link elements with rel stylesheet are allowed; the browser loads and applies each one in order. So you can have a base stylesheet and a page-specific one, or a main theme and an override. Place link elements for CSS in the head so that styles are loaded before or as the body is rendered; that reduces flash of unstyled content. For a homestead dashboard you might have one stylesheet shared by all pages (e.g. layout and typography) and link it in the head of every page. The same head can also contain a link for a favicon: rel icon (or shortcut icon for legacy support), with href pointing to the icon file. The favicon is the small icon shown in the tab and in bookmarks. It is optional but helps users recognize the page when they have many tabs open. Use a small image (e.g. 32 by 32 or 16 by 16 pixels) in a format the browser supports (e.g. ICO or PNG). One link with rel icon is enough for most sites. If you have both a stylesheet and a favicon, list them in the head after the meta tags and title; order between multiple link elements matters for CSS (later stylesheets can override earlier ones) but not for the favicon. The link element is always empty: no content, no closing tag. It only references an external resource; the browser fetches and uses it according to the rel and other attributes. For stylesheets the browser parses the CSS and applies it to the document; for the favicon it displays the icon in the tab and bookmarks. You can also use link with rel preconnect to hint that the browser should connect early to another origin (e.g. for fonts or an API); that is an optimization you can add later when you have a concrete need. For now, stylesheet and icon are the main link relationships to know.

Other link relationships you may see include preconnect (to hint the browser to connect early to another origin, e.g. for fonts or APIs) and canonical (to indicate the preferred URL for the page when duplicate content exists). For now the main ones to know are stylesheet and icon. The important point is that the head is the place for resources that affect the document as a whole: encoding (meta charset), viewport (meta viewport), identity (title), appearance (link stylesheet), and branding (link icon). The body does not contain link elements for stylesheets or favicons; those belong in the head. When you add a new page to your dashboard, copy the head from an existing page (including the charset, viewport, title, and stylesheet link) and change the title and any page-specific links. That keeps encoding and viewport consistent and ensures every page gets the same base styles and icon. The link element does not display anything in the body; it only tells the browser to fetch and use the resource. Multiple stylesheets are applied in order: the first link stylesheet, then the second, and so on. Later rules can override earlier ones, so you can have a base stylesheet and then a page-specific one that overrides colors or layout for that page. The favicon is usually a single link with rel icon; some older browsers expected rel shortcut icon, so you can provide both with the same href if you want maximum compatibility. The href can be relative (e.g. to a file in the same directory as the HTML) or absolute. Use the same pattern across all pages so that the head is easy to maintain and the browser always finds the stylesheet and icon.

## 4) Script in Head vs Body

Scripts can appear in the head or in the body. A script element in the head is fetched and executed when the parser reaches it. By default, parsing of the document is blocked until the script has been downloaded and run. That means a large or slow script in the head can delay the rest of the page from rendering. For small configuration scripts or critical setup that must run before the body is displayed, putting script in the head is fine. For larger or non-critical scripts, placing the script at the end of the body (just before the closing body tag) lets the HTML and visible content parse and render first; then the script runs. That improves perceived load time: the user sees the page sooner. Alternatively, you can keep the script in the head but add the defer attribute. Defer tells the browser to fetch the script in parallel with parsing and to run it only after the document has been fully parsed. That way the script still executes in order with other deferred scripts and runs before the DOMContentLoaded event. The async attribute is different: the script runs as soon as it is downloaded, without waiting for the rest of the document. Use async when the script does not depend on the DOM or on other scripts and when order of execution does not matter. For most dashboard or status pages, either put the script at the end of the body or use defer in the head so that the page content appears first and the script runs when the DOM is ready. Scripts that must run before any content (e.g. some polyfills or critical configuration) can stay in the head without defer, but be aware they block parsing. We go deeper into script loading and the DOM in later phases; here the takeaway is that the head can contain script elements, that they block by default, and that defer or placement at the end of the body are common ways to avoid blocking. The head is for metadata and for linking or declaring resources that affect the document; script is one of those resources when it belongs in the head, and the body is an alternative when you want to delay execution until after the visible content is parsed. If you use an external script (with a src attribute), the browser fetches it from the URL you give. Without defer or async, parsing stops until the script is downloaded and executed. With defer, the script is fetched in parallel and runs after the document is parsed, in order with other deferred scripts. With async, the script runs as soon as it is downloaded, in no guaranteed order. For configuration or critical setup that must run before the body, a small script in the head without defer is acceptable. For larger or non-critical scripts, prefer defer in the head or a script at the end of the body so the page content appears first. The head is the right place for script when the script must run early; otherwise, the body is often simpler and avoids blocking.

## 5) Homestead Examples: Head Setup in Practice

Your voltage dashboard page has a head with meta charset (UTF-8), viewport meta, title ("Voltage dashboard" or "Homestead — Voltage"), a link to your main stylesheet, and optionally a favicon. The body holds the heading, the paragraph, and the list or table of readings. Your coop controller status page has the same head structure with a different title ("Coop door status") and the same stylesheet and favicon so all your pages look and behave consistently. Your solar production page, poultry net status page, and drip irrigation schedule page each have their own title in the head but the same charset, viewport, and stylesheet link. When you add a new sensor or a new section to your Pi or small server, you create a new HTML file with the same head skeleton and change only the title and the body content. That way encoding is always set, mobile viewport is always set, and every page shares the same CSS and icon. If you later add a second stylesheet (e.g. for print or for a dark theme), you add another link element in the head. If you add a script that must run before the page is shown (e.g. a check that redirects in some cases), you can put it in the head; if the script only enhances the page (e.g. live updates of readings), put it at the end of the body or use defer so the page renders first. The head is small and mostly the same from page to page; the body is where the content varies. Keeping the head consistent and correct makes maintenance easy and ensures that every page has proper identity, encoding, viewport, and styling. Your freezer temperature page, barn humidity page, and drip schedule page each have a head with the same charset, viewport, and stylesheet link; only the title changes (e.g. "Freezer temps," "Barn humidity," "Drip schedule"). If you add a print stylesheet later, you add a second link in the head with rel stylesheet and an appropriate media attribute (e.g. for print). The head grows slightly but stays in one place; the body holds all the visible content. When you validate your pages (Chapter 2.23), the validator will check that the head has the required structure (e.g. charset, title) and that link and script are used correctly. Fix any head errors first; then the body content can rely on correct encoding and linked resources.

## 6) What Breaks When the Head Is Wrong

Putting the charset meta late in the head or in the body can cause encoding errors: the browser may misdecode the file. Always put charset first in the head. Omitting the viewport meta on a page that is viewed on mobile often results in a zoomed-out, hard-to-use layout. Include it for any page that might be opened on a phone or tablet. Missing or duplicate title hurts usability and SEO; use exactly one title per page and make it descriptive. Putting visible content (e.g. a paragraph or a heading) in the head is invalid and confusing; the head is for metadata and linked resources only. Putting link or script in the body is valid for script (scripts are often at the end of the body) but stylesheet links belong in the head so styles apply before or as the body renders. A script in the head without defer or async blocks parsing; if the script is large or slow, the page will feel sluggish. Use defer or move the script to the end of the body when you do not need it to run before the document is parsed. Wrong or missing rel on a link can make the browser ignore the resource or treat it incorrectly; use rel stylesheet for CSS and rel icon for the favicon. Validators (Chapter 2.23) will report missing or invalid structure in the head. Fix the head first; then the rest of the document can rely on correct encoding, viewport, title, and linked resources. Another mistake is using the wrong rel value: for example rel stylesheet is required for CSS; if you misspell it or use something else, the browser may not apply the stylesheet. For the favicon, rel icon is standard; rel shortcut icon is a legacy variant. Double-check that the href on link elements points to a resource that exists and is served with the correct content type (e.g. text/css for stylesheets). If the stylesheet or favicon does not load, the head is the first place to look: correct rel, correct href, and the resource available at that URL. The head is small but critical; get it right and the rest of the page can build on it.

## 7) Head Order and Checklist

A typical head order is: meta charset (first), viewport meta (if the page may be viewed on mobile), other meta tags (description, robots, etc. when needed), title, then link elements (stylesheet, favicon, preconnect, etc.), then script elements if any. That order ensures the browser knows the encoding before parsing the rest of the head, sets the viewport early, has a title for identity, and then loads styles and icons. Scripts can go in the head or at the end of the body; if in the head, consider defer so they do not block parsing. When you create a new page, use this checklist: charset first, viewport if the page is mobile-friendly, one descriptive title, at least one link stylesheet if you use CSS, and optionally link icon for the favicon. Validate the document to confirm the head has no duplicate or invalid elements (e.g. only one title, only one charset meta). Once the head is correct, the body content can assume proper encoding, viewport, title, and styles. Chapter 2.02 covered the document skeleton (DOCTYPE, html, head, body); this chapter filled in the head. The next chapters cover what goes in the body: text, headings, links, lists, and so on. When you open an existing project, verify that every page has a proper head: charset first, viewport if needed, a unique title, and the same stylesheet and favicon links where you want consistent styling and branding. Missing or inconsistent heads lead to encoding bugs, poor mobile layout, or pages that do not share the same look. A small, consistent head template pays off across all your dashboard and status pages. If you use a template engine or static site generator, ensure the head is output once per page with the correct charset, viewport, title, and links; avoid duplicating or omitting the head when you reuse partials or layouts.

## Common Pitfalls

Putting meta charset after other content in the head: the browser may have already started parsing. Keep charset the first child of head.

Skipping the viewport meta on pages that will be viewed on mobile: without it, the page is often rendered at desktop width and scaled down, making it hard to use on a small screen.

Using a generic or empty title: "Untitled" or "Page" hurts tabs, bookmarks, and search. Use a short, descriptive title for each page.

Putting stylesheet link in the body: stylesheets should be in the head so they load and apply before or during body render. Script can go in the head or body depending on when you need it to run.

Blocking the parser with a large script in the head: use defer or put the script at the end of the body so the page content can render first.

Forgetting the favicon or using the wrong rel: use rel icon (and optionally shortcut icon) and point href to a small icon file. Not critical for internal dashboards but improves recognition in tabs and bookmarks.

Mixing up title and the main heading: the title is in the head and appears in the tab; the heading is in the body and appears on the page. Both should be descriptive but serve different roles.

## Summary

The head holds metadata and linked resources: meta charset (first, for UTF-8), viewport meta (for responsive behavior on mobile), optional description and other meta tags, the title (one per page, descriptive), link for stylesheets (rel stylesheet) and favicon (rel icon), and optionally script (with awareness of blocking and of defer or body placement). The body holds the visible content. Charset and viewport order matter; title identifies the page in tabs, bookmarks, and search; link brings in CSS and the favicon; script in the head runs early and can block parsing unless you use defer or move it to the body. Set up the head once per project and reuse it across pages, changing only the title and any page-specific links. The head defines identity (title), encoding (meta charset), viewport (meta viewport), styling (link stylesheet), and optional branding (link icon) and behavior (script). The body holds the visible tree. Order in the head matters for charset (first) and for the cascade of stylesheets (later links can override earlier ones); title and favicon order do not affect behavior.
