# Section B Phase 2 · Chapter 2.04: Text and Headings

Headings and paragraphs are the main building blocks for text in the body. This chapter covers heading levels (h1 through h6), paragraphs, line breaks and horizontal rules, and how heading hierarchy forms the document outline and supports accessibility so you can structure your dashboard and status pages clearly and consistently.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use h1 through h6 for heading hierarchy; use one h1 per page and keep a logical order
- Mark up blocks of text with the paragraph element and avoid using line breaks for paragraph spacing
- Use line break and horizontal rule only where they are semantically appropriate
- Relate heading hierarchy to the document outline and to screen reader navigation

## Key Terms

- **Heading**: An element (h1–h6) that labels a section and defines its level in the document hierarchy; not for styling alone
- **Document outline**: The structure of the page derived from heading levels; used by assistive technology and for SEO
- **Paragraph (p)**: A block-level element for a block of text; the default container for prose
- **Line break (br)**: A void element that forces a line break within flow (e.g. in an address or poem); use sparingly
- **Horizontal rule (hr)**: A void element that represents a thematic break between sections; often rendered as a horizontal line

## 1) Headings h1–h6

Headings label sections and define the hierarchy of the page. There are six heading levels: h1 (first level), h2 (second), h3 (third), and so on through h6. The h1 is the top-level heading: the main title of the page or of a major landmark (e.g. the main content area). There should be exactly one h1 per page, or one per major landmark if the page is split into distinct regions (e.g. a main and an aside that each have their own top-level heading). The h2 is for major sections under the h1; h3 is for subsections under h2; and so on. Do not skip levels: if you have an h1, the next heading in that section should be h2, not h3 or h4. Skipping from h2 to h4 confuses the outline and assistive technology, which use the sequence of heading levels to build the document structure. So the order is logical: h1, then h2, then h3 under a given h2, then h4 under that h3 if needed. You can have multiple h2s under one h1, multiple h3s under one h2, and so on. What matters is that the levels reflect the real structure of the content: the main title, then major sections, then subsections.

Headings are for structure and semantics, not for visual effect. Do not choose a heading level because you want big or small text; use CSS to control size and appearance. If something is the main title of the page, use h1. If it is a major section, use h2. If it is a subsection, use h3. Screen readers and other assistive technology use headings to let users jump between sections and to announce the document outline. Search engines use the heading hierarchy to understand the page. So the correct level is the one that matches the logical role of the content, not the one that looks right. You can style an h2 to look smaller than an h3 if your design demands it; the markup should still reflect the true hierarchy. For a dashboard page you might have an h1 such as "Voltage readings," then h2s for "Battery," "Solar," "Load," and under "Battery" an h3 for "Readings" or "History." The outline would be: one top-level (Voltage readings), then three major sections (Battery, Solar, Load), and under Battery a subsection. That structure is what assistive technology and the document outline use. Chapter 2.15 (Sections, Articles, and the Document Outline) goes deeper into how sections and headings work together; here the point is to use h1–h6 for real hierarchy and to avoid skipping levels or using headings for decoration. The heading elements have no required attributes; you can add a class or id for styling or linking. The content of a heading is usually plain text or inline elements (e.g. a link). Keep heading text concise: a short phrase that labels the section, not a long sentence. "Battery voltage" is a good heading; "Here we show the current battery voltage and some history" is better as a paragraph. Headings are signposts; paragraphs are the content. When you add a new section to your dashboard, add the heading first at the right level, then add the content. That keeps the outline and the visual structure in sync. In HTML5 the heading elements are h1, h2, h3, h4, h5, and h6. There is no h0 or h7; the range is fixed. Most pages use h1, h2, and sometimes h3; deeper levels (h4–h6) are for long documents with many nested subsections. A short status page might need only an h1 and one or two paragraphs; a full dashboard might need h1, several h2s, and a few h3s. Avoid going deeper than you need; a flat outline (h1 and h2 only) is easier to follow than one with many levels. The heading content is typically plain text; you can include a link or other inline element if the heading is also a link (e.g. to an anchor or another page). Keep the text short so the outline remains scannable.

## 2) Paragraphs

A paragraph is a block of text. In HTML you mark it up with the p element: an opening p tag, the text (and any inline elements such as links or emphasis), and a closing p tag. Each paragraph is one p element. Multiple paragraphs are multiple p elements in a row; you do not put one paragraph inside another. The p element is block-level: it starts on a new line and typically has space above and below it (from default browser styles or your CSS). So a short page might have an h1, then a paragraph of introduction, then an h2, then two or three paragraphs under that section, then another h2 and more paragraphs. The structure is clear: headings label sections, paragraphs hold the prose. Do not use multiple line breaks (br elements) to simulate paragraphs. That creates no real structure: the outline and screen readers see one block of text with line breaks, not separate paragraphs. Use one p per logical paragraph. Empty p elements are valid but usually unnecessary; they add no content and no structure. If you need visual spacing, use margins or padding in CSS, not extra br or empty p elements. Paragraphs can contain inline elements: links, emphasis, strong, and so on (covered in Chapter 2.05). They cannot contain block-level elements such as another p, a list, or a heading. So the content of a paragraph is text and inline markup only. For your coop status page you might have an h1 "Coop door status," then a paragraph that explains the current state, then an h2 "Recent events" and a list (not a paragraph) of events. The paragraph holds the explanatory text; the list holds the events. Use paragraphs for prose; use lists, headings, and other elements for their proper roles. A single sentence can be its own paragraph if it is a distinct thought; long blocks of text can be split into multiple paragraphs for readability. There is no fixed rule for length—only that each p should be one logical block. In a dashboard you might have one short paragraph under the h1 ("Current readings as of the last update.") and then under each h2 a paragraph of explanation followed by a list or table. The paragraph introduces; the list or table holds the data. Do not wrap the whole page in one giant paragraph; break it up so that the structure is clear and the outline (from headings) matches the flow of content. Browsers and assistive technology treat each p as a separate block. When a screen reader moves by paragraph, it jumps from one p to the next. When you style with CSS, you can target "the first paragraph in the section" or "all paragraphs in the main area" because the structure is explicit. So paragraphs are not just visual; they are structural. Use them for every distinct block of prose. If you have a single sentence that stands alone (e.g. a status message), it can be one paragraph. If you have a long explanation, split it into several paragraphs for readability and structure. The paragraph is the default container for prose in the body; headings label sections, and paragraphs (and lists, tables, etc.) hold the content of those sections.

## 3) Line Breaks and Horizontal Rules

Sometimes you need a line break within a single block of content without starting a new paragraph. For example, in an address you might want the street on one line, the city and state on the next, and the postal code on the next. Or in a poem or a recipe instruction you might want to control where lines break. The br element is a void element: one tag, no closing tag, no content. It forces a line break at that point. Use it sparingly. For most text, use paragraphs for separate blocks and let the browser wrap lines automatically. Reserve br for cases where the line break is part of the content (e.g. an address, a poem, a single-line list that you are not marking up as a list). Do not use a series of br elements to create vertical space between sections; use proper block elements (headings, paragraphs, sections) and CSS for spacing. Overuse of br makes the structure flat and hard to style or navigate.

The hr element represents a thematic break between sections: a shift in topic or scene. It is a void element. Visually it is often rendered as a horizontal line, but its meaning is semantic: a break in the flow of content. Use it between major sections when you want to signal "here the topic changes" without introducing a new heading. For example, you might have a paragraph of summary, then an hr, then a paragraph of details. Or you might use hr between distinct parts of a long page. Do not use hr purely as a decorative line; if you only want a visual separator, use a border or a line in CSS. Like br, hr should be used when the semantics fit. For many pages you will use headings to divide sections and rarely need hr; when you do, use it for a real thematic break. Both br and hr are void elements: no closing tag in HTML5. They are minimal and purposeful; use them when they add meaning, not for layout or spacing. In an address block you might have the street, then a br, then the city and state, then a br, then the postal code—all within one paragraph or within a single block. That way the line breaks are part of the content. In a poem or song lyric the line breaks are structural; br can mark them if you are not using a different element. For most prose, however, use paragraphs and let the browser wrap lines. Horizontal rules are less common in modern pages; many designs use spacing and headings alone to separate sections. When you do use hr, use it for a real break in topic or flow, not as a decorative line. CSS can style hr (e.g. color, thickness, or hide it and use it only for semantics). The key is to choose br and hr for their meaning, not for visual effect. If you are unsure whether to use a paragraph or a list, ask: is this a series of items or a continuous block of prose? Items get a list (Chapter 2.07); prose gets paragraphs. If you are unsure whether to use br or a new paragraph, ask: is this a new thought or just a new line within the same block? New thought gets a new p; same block with a required line break (e.g. address) gets br.

## 4) Semantic Hierarchy and Accessibility

The heading hierarchy forms the document outline. Assistive technology (e.g. screen readers) can list the headings and let the user jump from one to the next. That makes the page navigable by structure: "Heading level 1: Voltage readings. Heading level 2: Battery. Heading level 2: Solar." If you skip levels or use headings for big text instead of structure, the outline is wrong and navigation is confusing. A user who jumps by headings expects h1 then h2 then h3 in a logical order; random levels or multiple h1s break that expectation. So one h1 per page (or per major landmark), no skipped levels, and headings that match the real structure of the content. Good hierarchy also helps comprehension: readers scan headings to understand the page. Search engines use the outline to infer importance and topic. So headings are not just labels; they are the backbone of the page structure. When you write a dashboard page, plan the outline first: one main title (h1), then major sections (h2), then subsections (h3) where needed. Write the headings, then fill in the paragraphs and lists. That way the structure is correct from the start and you avoid having to fix heading levels later. Some pages have a single main content area with one h1; others have multiple regions (e.g. main and aside) where each region might have its own h1 if the content is independent. For a simple dashboard or status page, one h1 for the whole page is the norm. The outline is then a flat or shallow tree: one top-level heading and a few section headings. For a long page with many subsections, the outline deepens; keep the depth consistent with the actual structure of the content so that "heading level" always matches "section depth." Chapter 2.01 described the document as a tree; headings define the major branches of that tree in the body. Keep the hierarchy logical and consistent across pages so that every page in your dashboard or status site has a clear, navigable outline. Some authoring tools or frameworks generate headings automatically (e.g. from a table of contents). If you use such a tool, ensure it does not skip levels or produce multiple h1s unless the page structure warrants it. When you validate your document (Chapter 2.23), check that headings are in order and that no block-level content is nested inside a paragraph. The outline is not just for screen readers; it is the structural summary of the page. Getting headings and paragraphs right makes the rest of the document (lists, tables, forms) easier to integrate and style.

## 5) Homestead Examples: Text and Headings in Practice

Your voltage dashboard might have an h1 "Voltage readings," then a short paragraph explaining what the numbers mean, then an h2 "Battery" with a paragraph or a list of readings, then an h2 "Solar" with similar content, then an h2 "Load." Under "Battery" you might have an h3 "Last 24 hours" and a paragraph or table. The outline is clear: one main title, three major sections, and under Battery one subsection. Your coop door status page might have an h1 "Coop door status," a paragraph with the current state (open or closed, last change time), then an h2 "Recent events" and a list of events. No need for h3 unless you add subsections (e.g. "Today" and "Yesterday"). Your solar production page might have an h1 "Solar production," a paragraph of summary, then h2s for "Today," "This week," "This month," each with a paragraph or figure. Your drip irrigation schedule page might have an h1 "Drip schedule," a paragraph of instructions, then h2s for each zone or time block. In every case the pattern is the same: one h1, then h2s for major sections, then h3s only when you have subsections. Paragraphs hold the prose; lists and tables hold structured data. Avoid using br to separate paragraphs; use a new p for each block of text. Use hr only when you have a real thematic break (e.g. between a summary and a detailed section). Keeping heading levels logical and using paragraphs for prose makes the page easy to navigate and to style consistently. Your freezer temperature page might have an h1 "Freezer temperature," a paragraph with the current reading and status, then an h2 "Sensors" and a list of sensors with readings. Your poultry net voltage page might have an h1 "Fence voltage," a short paragraph, then h2s for "Main energizer" and "Zones" with paragraphs or lists under each. Your barn or coop humidity page might have an h1, a paragraph of summary, then h2s for "Current" and "History." In every case: one h1, then h2s for major sections, then h3s only when you have subsections. Paragraphs for explanatory text; lists or tables for data. No skipped levels, no headings for decoration, no br for paragraph spacing. That pattern scales from a single status page to a full dashboard with many sections. If you use a template or a static site generator, ensure that the template outputs correct heading levels (e.g. the page title as h1, then section titles as h2) and that you do not accidentally duplicate or skip levels when you compose content. The same outline rules apply whether you write HTML by hand or generate it: one h1, no skipped levels, paragraphs for prose, br and hr only when semantically appropriate.

## 6) What Breaks When Headings and Paragraphs Are Wrong

Using headings for size instead of structure (e.g. h4 because you want small text) breaks the outline and confuses screen reader users. Use the correct level for the real hierarchy; use CSS for appearance. Skipping levels (h1 then h4) makes the outline inconsistent and can break assistive technology that expects a strict hierarchy. Use h1, then h2, then h3 in order. Multiple h1s on a simple page can be confusing; use one h1 for the main title unless the page has distinct landmarks that each need their own top-level heading. Putting block-level content inside a paragraph (e.g. a list or another p) is invalid; paragraphs can contain only inline content. Fix by closing the paragraph before the list or by using a section and paragraphs and lists as siblings. Using many br elements instead of paragraphs creates a single block of text with no structure; screen readers and the outline do not see separate paragraphs. Replace with proper p elements. Using hr for decoration instead of a thematic break is semantically weak; prefer CSS for visual separators. Validators (Chapter 2.23) will report invalid nesting (e.g. p containing a heading or a list). Fix the structure so that headings and paragraphs and lists are used correctly and the document outline matches the content. Another mistake is using a heading when a styled span or div would do. If you want a line of text to look like a heading but it is not actually a section title (e.g. a label inside a card), use a class on a paragraph or a div and style it with CSS; do not use an h2 or h3 for something that is not a structural heading. That keeps the real outline accurate. Conversely, do not use a paragraph or a div when you need a heading. If it is the title of a section, use the appropriate heading level. The outline and assistive technology depend on real headings; fake headings (styled divs) do not appear in the outline and break navigation.

## 7) Outline and Heading Checklist

When you build a page, plan the outline before you write the body. Decide the main title (h1), then the major sections (h2), then any subsections (h3). Write the headings in order; then add paragraphs and other content under each. Check that you have not skipped a level: after h1 comes h2, after h2 comes h2 or h3, after h3 comes h3 or h4, and so on. Check that you have only one h1 unless the page has distinct landmarks (e.g. main and aside) that each need a top-level heading. Use paragraphs for every block of prose; do not use br to separate paragraphs. Use br only for line breaks within a single block (e.g. address); use hr only for thematic breaks. Once the outline is correct, styling and scripting can build on it. Chapter 2.05 (Paragraphs and Inline Text) continues with what goes inside paragraphs: emphasis, strong, and other inline semantics. With headings and paragraphs in place, the body has a clear text structure; the next step is to add inline meaning (emphasis, strong, links) and then lists, links, and other elements in later chapters. Revisit the outline when you add or remove sections: if you add a new major section, give it an h2; if you add a subsection under an h2, give it an h3. Do not reuse the same heading text for different sections unless they are clearly distinct; screen reader users may jump by heading and need unique labels to tell sections apart.

## Common Pitfalls

Using heading levels for visual size: pick the level that matches the real hierarchy (h1 for main title, h2 for sections, etc.); use CSS to change how headings look.

Skipping heading levels: do not go from h2 to h4; use h3 for the next level under h2. The outline expects a logical sequence.

Using multiple br elements to simulate paragraphs: use one p per paragraph. Br is for line breaks within a block (e.g. address), not for spacing between blocks.

Putting block elements inside a paragraph: p can contain only inline content. Put lists, headings, and other block elements outside the paragraph, as siblings or in parent sections.

Using many h1s on a single page: one h1 is the norm for the main title. Use h2 for major sections unless you have a good reason for multiple top-level headings.

Using hr or br for layout: use them for semantics (thematic break, line break in content). Use CSS for spacing and visual separators.

Using a styled div or span instead of a real heading: if it is a section title, use h1–h6 so the outline and assistive technology are correct. Do not use headings for non-structural "labels" that only look like headings.

## Summary

Use h1–h6 for real structure: one h1 per page (or per major landmark), then h2 for major sections, h3 for subsections, without skipping levels. Headings define the document outline and support accessibility and SEO; do not use them for styling alone. Use the p element for paragraphs: one p per block of text. Do not use multiple br for paragraph spacing; use proper paragraphs. Use br only for line breaks within flow (e.g. address, poem) and hr only for thematic breaks between sections. Keep the heading hierarchy logical so that the outline matches the content and assistive technology can navigate by structure. Plan the outline (h1, then h2s, then h3s where needed) before filling in paragraphs and lists.
