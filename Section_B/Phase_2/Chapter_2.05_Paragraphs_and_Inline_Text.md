# Section B Phase 2 · Chapter 2.05: Paragraphs and Inline Text

Inside paragraphs and other text, you add meaning with inline elements: strong for importance, em for emphasis, and others for highlights or side comments. This chapter covers when to use strong versus b, em versus i, and how phrasing content (inline elements) fits inside block-level flow so your prose is both readable and semantically clear for assistive technology and styling.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use the paragraph element for blocks of text and avoid using line breaks for visual spacing; reserve br for line breaks within flow (e.g. addresses)
- Use horizontal rule for thematic breaks between sections when appropriate
- Choose strong versus b and em versus i for emphasis and importance; prefer semantic inline elements for meaning, not only appearance
- Understand how block-level (e.g. paragraph) and inline (e.g. strong, em) elements affect document flow and nesting

## Key Terms

- **Phrasing content**: Inline content such as text, strong, em, and span; flows within a line and does not start a new block
- **Flow content**: Block-level or inline content that can appear in the body or in block containers; paragraphs and headings are flow content
- **strong**: An inline element that indicates strong importance or urgency for its contents
- **em**: An inline element that indicates emphasis (stress) for its contents
- **b**: An inline element for text that is stylistically offset (e.g. a keyword) without conveying extra importance
- **i**: An inline element for text that is in an alternate voice or mood (e.g. technical term, thought) without emphasis
- **span**: A generic inline container with no inherent meaning; use for styling or scripting when no semantic inline element fits

## 1) Paragraphs and Line Breaks Revisited

Chapter 2.04 introduced paragraphs and line breaks. Here we focus on how paragraphs contain inline content and when to use br. A paragraph holds one or more runs of text and inline elements. You do not put block-level elements (another paragraph, a list, a heading) inside a paragraph; you put only phrasing content: plain text, links, strong, em, and other inline elements. So a paragraph is a block; inside it the content flows inline. Line breaks (br) force a new line within that flow. Use br only when the line break is part of the content: for example in an address (street, then city and state, then postal code on separate lines), in a poem or lyric where line breaks are meaningful, or in a short label where you need a specific break. Do not use br to create space between paragraphs; use a new paragraph element for each block. Do not use multiple br to simulate vertical spacing; use CSS margins or padding. When you have a single block of text that must have internal line breaks (e.g. an address block), you can use one paragraph with br elements between the lines, or you can use a dedicated element or pattern for addresses if your markup has one. The key is: one paragraph per logical block, and br only where the break is semantic, not for layout or spacing. For your dashboard or status pages, most text will be in paragraphs with no br; only use br when you have something like an address or a short multi-line label that is not a list. The paragraph element has an opening and closing tag; the content between them is the paragraph. You can have multiple paragraphs in a row; each is a separate block. Screen readers can announce "paragraph" and move by paragraph; so can some assistive technology. So the structure you choose (one p per block, no br for spacing) directly affects how the page is navigated and understood. When you add inline elements (strong, em, links) inside a paragraph, they stay within that block. The paragraph is still one block; the inline elements just add meaning to parts of the text. We turn to those next.

## 2) Horizontal Rules and Thematic Breaks

The horizontal rule (hr) element represents a thematic break between content: a shift in topic, scene, or section. It is a void element: one tag, no closing tag, no content. Visually it is often shown as a horizontal line, but its meaning is semantic. Use it between major parts of a page when you want to signal "here the topic or flow changes" without adding a new heading. For example you might have a paragraph of summary, then an hr, then a longer paragraph of details. Or you might use hr between distinct sections of a long status page. Do not use hr purely as a decorative line; if you only want a visual separator, use a border or a line in CSS. Screen readers and other assistive technology can announce the presence of a thematic break, so using hr for real breaks helps structure. For many pages you will use headings to divide sections and rarely need hr; when you do, use it for a real thematic break. Styling can change how hr looks (color, thickness, or even hide it) while keeping the semantic break. So: hr for meaning, CSS for appearance. You can have multiple hr elements on a page if you have multiple thematic breaks. Do not use hr between every paragraph; that would suggest every paragraph is a separate "theme," which is usually not true. Use hr between major parts of the content (e.g. between a summary section and a details section, or between two distinct topics). For a short status page you may not need hr at all; headings and paragraphs may be enough. If you use a content management system or a template that outputs hr automatically between sections, ensure that those sections are actually thematically distinct; otherwise the hr adds noise. The same principle applies to br: only use it when the line break is part of the content structure (address, poem, label), not for visual spacing. When in doubt, use a new paragraph or a heading instead of hr, and use a new paragraph instead of br for a new block of text. For a long page with several distinct sections, hr can reinforce the break when a new heading would be too heavy. The choice is semantic: does the content have a real thematic break here? If yes, hr is appropriate; if not, use spacing or a heading instead.

## 3) Inline Text Semantics: strong, em, and Others

Inside a paragraph or other text container you often want to mark some words as important or emphasized. The strong element indicates strong importance or urgency. Use it when the content is more important than the surrounding text: for example a warning ("Do not open the door when the motor is running"), a key term in a definition, or a critical value in a status message. The em element indicates emphasis: stress on the word or phrase when read aloud. Use it when you want to emphasize a point: "The sensor is working, but the battery is low." Screen readers may change tone or pitch for strong and em, so use them for real meaning, not for decoration. Do not use strong or em just to make text bold or italic; use CSS for that. If you want bold or italic look without extra importance or emphasis, you have two options. The b element is for text that is stylistically offset (e.g. a product name, a keyword in a summary) without conveying strong importance. The i element is for text in an alternate voice or mood: a technical term, a foreign phrase, a thought, or a ship name. So: strong for importance, em for emphasis, b for offset without importance, i for alternate voice. Choose based on meaning; then use CSS to adjust appearance if needed. Other inline elements you may see include small for side comments or fine print (e.g. disclaimers, copyright), and mark for highlighted or marked text (e.g. search results or a reference). Use small when the content is legally or semantically secondary; use mark when the text is highlighted for reference. Like strong and em, these are semantic: they convey meaning to assistive technology and to scripts. Abbreviations can be marked with the abbr element (with an optional title for the full form); that helps screen readers and tools that expand abbreviations. For now the main set to know is strong, em, b, i, small, mark, and span. When you need a generic wrapper with no meaning, span is the fallback; when you need meaning, pick the semantic element that fits. The HTML spec defines the content model for each element: what it can contain and where it can appear. Paragraphs allow phrasing content; so do headings and many other elements. Block elements that contain flow content can contain both block and phrasing; paragraphs are more restrictive and allow only phrasing. That restriction is what keeps paragraphs from containing lists or other paragraphs and keeps the structure clean. Prefer semantic elements over bare span when the meaning fits; use span when you need a generic inline wrapper for styling or scripting without semantic meaning. Chapter 2.17 (Attributes) covers class and id for styling; here the point is that strong, em, b, i, small, and mark each have a defined meaning and should be chosen for that meaning, not for how they look by default. You can nest em inside strong or strong inside em when the content is both emphasized and important; use the inner element for the inner meaning. Do not overuse strong; if everything is strong, nothing stands out. Reserve strong for the key fact or warning. Em can be used more freely for stress in a sentence. The default rendering of strong is often bold and of em is often italic, but that is only the default; you can change it with CSS. The semantics stay the same: screen readers and other tools use the element name, not the visual style. So pick the element for meaning first; then style as needed. In some languages or contexts, emphasis can change the meaning of a sentence (e.g. "I did not say that" vs "I did not say that"). Using em for the stressed word helps convey that. Strong is for importance: something the user must notice (a warning, a key value, a critical state). B and i do not add that level of meaning; they are for stylistic offset and alternate voice. If you are migrating old HTML that used b and i for everything, consider whether some of those should be strong or em; update the markup so that importance and emphasis are correctly tagged. Validators do not enforce this choice, but assistive technology and future styling will benefit from correct semantics.

## 4) Flow Content and Phrasing Content

Block-level elements (e.g. paragraph, heading, list) create blocks and typically start on a new line. Phrasing content (inline elements and text) flows within a line and does not start a new block. Paragraphs can contain only phrasing content: text, strong, em, a (links), span, and other inline elements. They cannot contain another paragraph, a list, or a heading. So the nesting rule is: block contains block or phrasing; phrasing does not contain block. When you write a paragraph, you write text and inline elements inside it. When you need a new block (e.g. a new paragraph or a list), you close the current paragraph and start the new block as a sibling. That keeps the document tree valid and makes styling and scripting predictable. For example: a paragraph with a strong phrase and a link; then another paragraph; then a list. The strong and the link are inside the first paragraph; the second paragraph and the list are siblings of the first paragraph. Chapter 2.20 (Block and Inline) goes deeper into content models and which elements can contain which; here the takeaway is that paragraphs are blocks and hold phrasing content only, and that strong, em, b, i, and similar elements are inline and go inside paragraphs (or other elements that allow phrasing content). Do not wrap a paragraph in a span or put a div inside a paragraph; use the right structure so that block and inline nesting is valid. Some elements are both flow and phrasing: for example the a element (link) is phrasing content and can sit inside a paragraph. So a paragraph can contain text, strong, em, and a link; it cannot contain a div, another p, or a list. When you want to group a few inline elements or apply a class to a run of text without semantic meaning, use span. Span is a generic inline container; it has no meaning by itself. Use it when no semantic element (strong, em, b, i, small, mark) fits. When you want to group block-level content, use div (Chapter 2.16). The content model is strict for a reason: it keeps the tree valid and makes it clear what is a block and what is inline. Browsers and assistive technology rely on that structure. So: paragraphs and headings and lists are blocks; strong, em, b, i, span, and links are inline; blocks contain blocks or phrasing; phrasing does not contain blocks. Headings can also contain phrasing content (e.g. text and a link); they cannot contain block elements. Lists contain list items; list items can contain flow content (paragraphs, lists, etc.). So the content model varies by element. For paragraphs the rule is simple: only phrasing content inside. When you add a link (Chapter 2.06) inside a paragraph, the link is phrasing content and the paragraph remains valid. When you add a list, the list must be a sibling of the paragraph, not inside it. That keeps the tree consistent and avoids parser corrections that might change the structure you intended. Chapter 2.20 (Block and Inline) goes into more detail on which elements are block and which are inline and how they nest; here the takeaway is to respect the boundary so that your document is valid and predictable.

## 5) Homestead Examples: Inline Text in Practice

On your voltage dashboard you might have a paragraph that says "Battery voltage is currently 12.1 V, within normal range." If you want to stress the value, you could wrap "12.1 V" in strong: the number is the important part. If you want to emphasize "within normal range," you could use em. On your coop door status page you might have "The door is closed; last opened at 06:30." You could use strong for "closed" if that is the key fact, or for the time if that is what users care about most. On a warning or alert message you might use strong for the entire warning so screen readers announce it with urgency. For a technical term (e.g. "State of charge" or "SOC") you might use i to indicate it is a technical term. For a small-print disclaimer at the bottom of a page you might use small. For a search result or a highlighted snippet you might use mark. In every case choose the element that matches the meaning: strong for importance, em for emphasis, b for offset, i for alternate voice, small for side comment, mark for highlight. Do not use strong or em just to get bold or italic; use b or i when the meaning is offset or alternate voice, and use CSS when you only want a visual style. Your dashboard and status pages will be clearer and more accessible when inline semantics match the content. On a freezer temperature alert you might use strong for "Below threshold" so the critical message is announced with emphasis. On a drip schedule page you might use em for the time "06:00" to stress when the cycle runs. On a poultry net status page you might use strong for "Energized" or "Not energized" as the key state. For units or technical terms (e.g. "V" for volts, "SOC" for state of charge) you might use i to mark them as technical. For a copyright or "Last updated" line at the bottom you might use small. In every case the rule is the same: choose the element that matches the meaning. Avoid using strong or em for every other word; that dilutes their effect. Use them where they add real information for the reader or for assistive technology. A single paragraph can mix plain text with one or more inline elements; you do not need to wrap every word. Use strong or em only on the phrase that is important or emphasized. Your barn or coop humidity page might use strong for the current reading when it is outside the safe range, and plain text when it is normal. Your drip irrigation page might use em for the duration ("15 minutes") to stress how long the cycle runs. Your poultry net page might use strong for "OK" or "Fault" as the main status. Consistency across pages helps: if you use strong for critical alerts everywhere, users and assistive technology learn the pattern. Do not mix strong for one kind of thing on one page and something else on another without reason. Keep semantics consistent so that "strong means important" and "em means emphasis" throughout your site.

## 6) What Breaks When Inline Semantics Are Wrong

Using strong or em only for appearance (e.g. to make text bold or italic) misleads assistive technology: screen readers may announce the content with stronger tone or emphasis when you did not intend that. Use strong and em for real importance or emphasis; use b or i when the meaning is offset or alternate voice; use CSS for pure styling. Putting block-level content inside a paragraph (e.g. a list or another paragraph) is invalid; the parser may fix it in unexpected ways. Close the paragraph and start the list or next paragraph as a sibling. Using many br elements instead of paragraphs creates a single block with no structure; screen readers and the outline do not see separate paragraphs. Use one paragraph per block. Using hr for decoration without a thematic break is semantically weak; prefer CSS for visual separators. Using b or i when you mean importance or emphasis underuses the semantic elements; prefer strong and em when the meaning fits. Validators (Chapter 2.23) will report invalid nesting. Fix structure first: paragraphs contain only phrasing content; block-level elements are siblings, not children of paragraphs. Then fix inline semantics: choose strong, em, b, i, small, or mark based on meaning. When you copy content from a word processor or another page, it may have bold or italic styling that was used for appearance only. When you add that content to HTML, decide whether the bold or italic represents importance (strong), emphasis (em), offset (b), or alternate voice (i), and use the right element. If it was only for visual effect, you can use span with a class and style it with CSS, or leave it as plain text. Prefer semantic elements when the meaning fits. Another mistake is using only div and span for everything and never using strong or em. The page may look fine, but screen readers and other tools will not get the emphasis or importance you intended. Add semantic inline elements where they fit; use span when no semantic element applies. Over-nesting inline elements (e.g. strong inside em inside strong) can also be confusing; keep nesting simple and meaningful. Putting a div or a list inside a paragraph will cause the browser to close the paragraph implicitly before the block element; the resulting DOM may not match what you had in mind. Always close the paragraph explicitly and then open the block element as a sibling. That way the structure is clear in your source and in the DOM.

## 7) Choosing the Right Inline Element

When you want to mark part of a sentence, ask: is this more important than the rest (strong), or is it emphasized for tone (em)? If it is important or urgent, use strong. If it is stress or emphasis in reading, use em. If the text is offset without extra importance (e.g. a product name, a keyword), use b. If it is an alternate voice (technical term, foreign phrase, thought), use i. If it is fine print or a side comment, use small. If it is highlighted for reference (e.g. search hit), use mark. If none of these fit and you only need a hook for styling or scripting, use span with a class or id. Do not use strong or em "because I want it bold or italic"; use them for meaning. The default look can be overridden with CSS; the semantics cannot. This choice matters for accessibility and for maintainability: when you change the visual design later, the correct semantics will still be in place. Chapter 2.06 (Links and Anchors) adds the anchor element, which is also phrasing content and commonly used inside paragraphs to link to other pages or to fragments. When you have both a link and strong or em in the same phrase, you can nest them: for example strong around the link text if the link is the important part, or the link around strong text if the whole phrase is the link. Keep nesting to one or two levels when possible so the structure stays clear. The same "meaning first" rule applies: use the element that matches the content, then style with CSS.

## Common Pitfalls

Using strong or em only for bold or italic look: use them for importance and emphasis; use b or i for offset or alternate voice; use CSS for appearance alone.

Putting block elements inside a paragraph: paragraphs can contain only phrasing content. Close the paragraph before a list, heading, or another paragraph.

Using br for paragraph spacing: use a new paragraph for each block; use br only for line breaks within a single block (e.g. address).

Using hr as a decorative line: use hr for thematic breaks; use CSS for visual separators.

Choosing b or i when strong or em would be correct: if the content is more important or emphasized, use strong or em so assistive technology can convey that.

Ignoring nesting rules: phrasing content does not contain block content. Keep paragraphs and other blocks as siblings; put only inline elements inside paragraphs.

Using only span and div and never strong or em: the page may look right but assistive technology will not get emphasis or importance. Use semantic inline elements where they fit.

Overusing strong or em: if everything is marked important or emphasized, nothing stands out. Use them for the parts that really need it.

## Summary

Use paragraphs for blocks of text and avoid using br for spacing between blocks; use br only for line breaks within flow (e.g. addresses). Use hr for thematic breaks between sections, not for decoration. Prefer semantic inline elements: strong for importance, em for emphasis, b for stylistically offset text, i for alternate voice (e.g. technical term), small for side comments, mark for highlights. Use CSS for appearance when there is no semantic meaning. Paragraphs are block-level and contain only phrasing content; do not nest block elements inside paragraphs. Flow content and phrasing content rules determine valid nesting; Chapter 2.20 (Block and Inline) goes deeper. Choose inline elements for meaning so that assistive technology and styling can build on correct structure. Paragraphs hold blocks of text; inside them use strong, em, b, i, small, mark, or span as appropriate. Keep block and phrasing nesting valid: no block elements inside paragraphs. Use br only for line breaks within flow; use hr only for thematic breaks.
