# Section B Phase 2 · Chapter 2.09: Audio, Video, and Embedded Content

Audio and video let you add live streams, recordings, and sound to your dashboard; embed and object let you include external content such as PDFs or maps. This chapter covers the audio and video elements, source and track for format selection and captions, and embed and object (and when to use iframe) for embedded content. Getting media and embeds right improves accessibility, avoids autoplay problems, and keeps your page secure and performant. Chapter 2.08 covered static images; here we extend the same principles—alternative content, dimensions, and user control—to time-based and embedded media. Many dashboards include a live camera view or an embedded map; this chapter gives you the markup and accessibility patterns for those and for audio alerts or recorded clips. The same ideas as for images apply: provide alternative or fallback content, set dimensions to avoid layout shift, and keep the user in control (no autoplay with sound, visible controls).

## Learning Objectives

By the end of this chapter, you should be able to:
- Use the audio and video elements with source for multiple formats and track for captions or descriptions
- Choose when to use embed, object, or iframe for external content (PDFs, maps, other pages)
- Provide fallback content and accessible alternatives (captions, transcripts, text for embeds)
- Avoid autoplay with sound; use poster for video and controls so users stay in control
- Balance accessibility and performance for media and embedded content

## Key Terms

- **audio**: Element that embeds sound; can contain source and track children; supports controls, autoplay, muted, loop
- **video**: Element that embeds video; like audio but with visual track; supports poster, width, height, and the same playback attributes
- **source**: Child of audio or video; specifies src and type so the browser can pick a format (e.g. MP3, WebM, MP4)
- **track**: Child of audio or video; provides timed text (captions, subtitles, descriptions); uses kind, srclang, label, and src
- **embed**: Element that embeds external content (e.g. PDF, plugin content); no fallback content in the element; use with caution
- **object**: Element that embeds external content; can contain param elements and fallback content (e.g. text or a link) for when the object cannot be displayed
- **iframe**: Element that embeds another HTML document (e.g. a map, a widget, or another page); sandbox and other attributes control security
- **poster**: Attribute on video; URL of an image shown before playback starts (like a thumbnail)
- **captions**: Timed text that matches speech and sound (for deaf or hard-of-hearing users); provided via track with kind="captions"

Browsers and user preferences vary: some block autoplay, some restrict mixed content (HTTP media on an HTTPS page), and some do not support certain codecs. Providing multiple source formats and fallback content ensures that as many users as possible can access the media or a text alternative. For embeds, the same-origin policy and sandbox restrict what framed content can do; use them to keep your page secure while still embedding useful content like maps or widgets. Audio and video are flow content and can appear in the main content like images. They require user interaction or careful use of autoplay (muted only in most browsers) to avoid annoying or inaccessible auto-playing sound. Embedded content (embed, object, iframe) creates a boundary: content from another source runs in your page, so security and fallbacks matter. Validators will flag audio or video without a source (or src on the element) and may warn about missing track for accessibility; provide at least one source and consider captions or transcript for content media. ## 1) Audio and Video Elements

The audio element embeds sound. It can have one or more source elements as children, each with src and optionally type (the MIME type of the resource). The browser picks the first source it supports; if none are supported or no source is given, it can use the src attribute on the audio element itself as a fallback. After the source elements you can add track elements for captions or descriptions. Any content inside the audio element after the sources and tracks is fallback content: it is shown when the browser cannot play any of the sources. So you might put a paragraph with a link to download the audio or a transcript. The audio element has no visual display by default except when you add the controls attribute, which shows play, pause, volume, and optionally progress. Other boolean attributes: autoplay (start when the page loads; note that many browsers block autoplay with sound), muted (start muted), and loop (repeat). Use controls so users can start, stop, and adjust volume. Avoid autoplay with sound; if you use autoplay (e.g. for background ambience), use muted so the page is not intrusive and remains compliant with accessibility and browser policies. The playsinline attribute on video is useful on mobile so that video plays inline rather than forcing fullscreen. Without it, some mobile browsers may open the video in a separate player, which can disrupt the dashboard experience.

The video element works like audio but displays a visual track. It supports the same source and track children, the same controls, autoplay, muted, and loop, and adds width and height (or CSS) for layout and poster. The poster attribute is the URL of an image shown before the user plays the video; it acts like a thumbnail and helps avoid a blank or first-frame flash. Always set width and height (or aspect-ratio) for video so the page does not layout-shift when the video loads, just as with images in Chapter 2.08. Fallback content inside the video element is shown when the browser cannot play the video; provide a link to the file or a transcript so users are not left with nothing. Video is often the largest resource on a page; use appropriate resolution and format (e.g. WebM or MP4) and consider not autoplaying so that users on slow or metered connections can choose whether to load it. Both audio and video can have multiple source elements; the browser uses the first one it supports. If you have only one format, you can put src directly on the audio or video element. The preload attribute (none, metadata, or auto) hints how much data the browser should load before the user plays; use metadata or none to reduce initial load when you have many media elements on the page.

## 2) Source and Track

Source elements inside audio or video provide multiple formats. Each source has src (the URL of the media file) and optionally type (e.g. audio/mpeg, video/webm). The browser selects the first source it can play, so put preferred formats first (e.g. modern codecs) and a widely supported fallback last. If you have only one format, you can put src on the audio or video element and omit source; source is useful when you have more than one option. The order of source elements matters: the browser does not "pick the best" from the whole list but uses the first one it supports.

Track elements provide timed text. Each track has src (URL of a text file in a supported format, e.g. WebVTT), kind (e.g. captions, subtitles, descriptions), srclang (language code for captions/subtitles), and label (a human-readable label for the track, e.g. "English"). Kind captions is for dialogue and sound effects, typically for deaf or hard-of-hearing users; kind subtitles is for translation when the audio is in another language; kind descriptions is for audio description of the video content for blind users. Provide at least captions for speech and important sounds when the media is content (e.g. a how-to or status message). Multiple track elements are allowed; the user can choose which to show if the player supports it. If captions are not available, provide a transcript in the fallback content or nearby so that everyone can access the information. WebVTT (Web Video Text Tracks) is a common format for track src: plain text with time cues and optional styling. The file typically has a .vtt extension and must be served with the correct MIME type so the browser recognizes it. Track files must be served with the correct MIME type (e.g. text/vtt for WebVTT) and must be same-origin or CORS-enabled if the media is cross-origin. The default attribute on a track marks it as the default track when multiple tracks of the same kind exist. Screen readers and media players can expose track selection so users choose their preferred language or description. If you generate captions manually or with a tool, ensure they are synchronized with the audio and that speaker identification and sound effects are included where helpful. For short clips or alerts, a transcript in the fallback content may be enough; for longer or narrative content, proper captions via track are better.

## 3) Embed and Object

The embed element embeds external content: a PDF, a map, a plugin, or another type of resource. You give it a src (and optionally type and dimensions). Embed is a void element; it has no content, so there is no built-in fallback. If the browser cannot display the content, the user may see nothing or a broken icon. For accessibility and robustness, prefer object when you need fallback content: object can contain param elements (for plugin parameters) and then any flow content (e.g. a paragraph with a link to the PDF or an alternative summary) that is shown when the object cannot be displayed. So use object when you want a fallback (e.g. "Your browser cannot display this PDF; download it here"); use embed when you are okay with no fallback or when you provide alternative content elsewhere on the page.

Object can also embed images and other content; in practice it is often used for PDFs, legacy plugins, or external applications. Embed is simpler but has no fallback. Both can have security implications: embedded content from another origin may run scripts or behave in unexpected ways. Prefer same-origin or trusted sources; for third-party content (e.g. a map from another site), consider an iframe with sandbox and other restrictions (see below). Always set width and height (or CSS dimensions) so the embed or object does not cause layout shift. Some user agents or assistive technologies may not support certain embed types; the fallback inside object is then the only way users get the content, so make the fallback useful (e.g. a direct link to the resource and a short description).

The iframe element embeds another HTML document. It is commonly used for maps, videos from external sites, or widgets. You set src to the URL of the document. Important attributes: sandbox (restricts what the framed content can do; use a non-empty value to restrict scripts and forms unless you need them), allow (for feature policy, e.g. fullscreen), and loading (e.g. lazy to defer loading). If the iframe content is from another origin, it runs in a separate origin from your page; that isolates it but also means you cannot style or script it directly. Provide a title on the iframe that describes the content (e.g. "Embedded map of property") for accessibility. If the iframe is optional or supplementary, consider fallback content (e.g. a link to open the content in a new tab) for users whose browsers block iframes or when the source is unavailable. Chapter 2.08 and this chapter share the principle: provide alternative or fallback content so that when the primary content fails or is inaccessible, users still have a path forward. The allow attribute on iframe can restrict features (e.g. fullscreen, payment) that the framed page may request; use it to limit what the embed can do. The referrerpolicy attribute can control what referrer information is sent when the iframe loads a resource; use it when you want to limit referrer leakage to the embedded site.

## 4) Accessibility and Performance

**Accessibility.** For audio and video, provide captions (track with kind captions) when the media contains speech or important sound. Provide a transcript or summary in fallback content or adjacent text when captions are not available. Do not autoplay with sound: it is disorienting for many users and is blocked by many browsers; if you autoplay, use muted. Expose controls so users can pause, adjust volume, and turn captions on. For video, use a poster image so that the area has meaning before playback. For embed and object, provide a text alternative (e.g. in surrounding content or in fallback inside object) that describes what the embed is (e.g. "Map of the property") and any key information it conveys. For iframe, use the title attribute to describe the frame. Users who cannot hear or see the media, or who cannot use the embedded plugin, should still get the information via captions, transcript, or fallback text. Test with a screen reader and with media paused to ensure that labels, captions, and fallbacks are announced and available.

**Performance.** Media files are often large. Do not load every video on the page at once; rely on the browser’s default behavior (often to load metadata and a small amount of data until the user plays) or use preload="metadata" or preload="none" to limit loading. Use poster for video so the initial paint shows something useful without loading the full video. Use poster for video so the initial paint shows something useful without loading the full video. For iframes, use loading="lazy" when the iframe is below the fold so it does not block the main page. Prefer efficient formats (e.g. Opus for audio, WebM or H.264/MP4 for video) and appropriate resolutions; do not serve 4K video when the display is small. On a homestead dashboard, a single live stream or a few short clips are usually enough; avoid embedding many heavy media or iframes on one page so that mobile and slow connections remain usable. If you stream from an ESP32-CAM or similar, the stream may be MJPEG or another format; ensure the video element’s source type matches what the server sends so the browser can play it. For embedded third-party widgets (e.g. weather, map), prefer lazy loading and a clear title so the page stays responsive and understandable when the embed is slow or blocked. If you host your own stream (e.g. from a Pi or NAS), ensure the server sends the right CORS and MIME headers so the video element can load the stream; some streaming protocols may require a different approach (e.g. HLS via a library) which is beyond the scope of this chapter but follows the same accessibility and control principles.

## 5) When to Use What

Use audio for sound-only content (e.g. an alert tone, a recorded message). Use video for content with a visual track (e.g. coop cam, how-to clip). Use source inside audio or video when you have multiple formats; use track when you have captions or descriptions. Use object when you need fallback content (e.g. PDF with a download link as fallback); use embed when you do not need fallback or when the alternative is elsewhere. Use iframe when you are embedding another HTML page (e.g. map, widget, external dashboard); use sandbox and title for security and accessibility. Prefer not to autoplay; if you do, use muted. Always provide controls for audio and video. Provide captions or a transcript for meaningful speech or sound. When you have both audio and video versions of the same content (e.g. a narrated clip), use the video element with track for captions rather than separate audio and video so that one player controls both. Validators can check for missing sources and suggest accessibility improvements; use the checklist in section 8 when you add or update media. ## 6) Homestead Examples: Audio, Video, and Embedded Content in Practice

Your coop or barn camera might stream video to the dashboard. Use a video element with a poster (e.g. latest snapshot), controls, and a source (or multiple sources for format fallback). Add a track for captions if the stream includes speech (e.g. a narrated tour); otherwise provide a short text summary next to the video (e.g. "Live coop view; door closed"). Do not autoplay with sound; let the user press play. A poultry net or alarm might use an audio element for an alert tone; use a short, efficient file and controls or a "Play alert" button so the user triggers playback. A Pi or Home Assistant dashboard might embed a small iframe showing another view (e.g. weather widget or a second dashboard); give the iframe a title and consider loading="lazy" if it is below the fold. If you embed a PDF (e.g. a wiring diagram or manual), use object with a fallback link to download the PDF and a brief description so users without a PDF viewer can still get the document. A live webcam page might have one main video (no lazy load) and optional thumbnails that link to full video or other cameras; keep the main stream efficient and provide text labels for each camera. For any embedded map (e.g. property or sensor locations), use an iframe with a descriptive title and ensure the map provider allows embedding. Consistency in how you handle media (controls, no autoplay with sound, captions or transcript where needed) makes the dashboard predictable and accessible. If you add an audio alert (e.g. for poultry net fault or coop door left open), keep the file short and provide a visible text alert as well so users in quiet environments or who are deaf can still get the information. A drip or irrigation status page might embed a small video showing the current zone or a map of zones; use object with fallback text and dimensions so the layout is stable and fallback is available. When you add a new camera or stream to the dashboard, give the video a poster (e.g. latest snapshot URL), set dimensions, and add a short text label (e.g. "Coop camera") so the purpose is clear even before playback. For embedded dashboards (e.g. Home Assistant panel in an iframe), ensure the iframe has a title that describes the panel and that the parent page still has a way to navigate back or to other sections without relying only on the iframe content. If you offer recorded clips (e.g. "Last door open event"), use a short video with controls and a one-line transcript or caption so users can get the gist without watching the whole clip.

## 7) What Breaks When Audio, Video, or Embeds Are Wrong

Autoplay with sound: many browsers block it and it annoys users; use muted if you autoplay. Missing controls: users cannot pause or adjust volume; add the controls attribute. Missing captions or transcript for speech: deaf and hard-of-hearing users get no information; add track or fallback text. Missing poster on video: blank or flashing first frame and possible layout shift; add poster and dimensions. Missing width/height on video or iframe: layout shift when the resource loads; set dimensions or aspect-ratio. Embed with no fallback: when the content cannot be displayed, users see nothing; use object with fallback or provide alternative content on the page. Iframe without title: screen reader users do not know what the frame is; add a descriptive title. Unsandboxed iframe from untrusted source: security risk; use sandbox and allow only what you need. Broken src or wrong MIME type: media or embed fails to load; check URLs and server configuration. Track file wrong format or missing: captions do not show; use WebVTT or another supported format and correct MIME type. Fix media and embeds so that controls are present, autoplay is muted or off, captions or transcript are provided for content media, and fallbacks exist for embed and object. When you change media URLs or embed sources, verify that playback and embeds still work and that fallback content is still accurate. ## 8) Media and Embed Checklist

When you add audio or video, confirm: source (or src on the element) points to a valid file; controls are present; autoplay is not used with sound (use muted if autoplay). For video, set poster and width/height. Add track for captions when the media has speech or important sound, or provide a transcript in fallback or nearby. When you add embed or object, provide fallback or alternative text; set dimensions. When you add an iframe, set title and consider sandbox and loading="lazy" for below-the-fold embeds. Verify that media URLs and embed src values are correct and that fallback content is still accurate after any path or server changes. Test with media disabled or in a restricted profile to ensure fallbacks and text alternatives are sufficient. Re-run the checklist when you add new media or change sources so that controls, captions, and fallbacks stay correct. ## Common Pitfalls

Autoplay with sound: use muted if you autoplay, or avoid autoplay so users stay in control.

Omitting controls on audio or video: users need to pause and adjust volume; always add the controls attribute.

Skipping captions or transcript for media with speech: provide track or text alternative so everyone can access the content.

Missing poster on video: add a poster image and dimensions to avoid blank area and layout shift.

Using embed without any fallback: use object with fallback content or provide an alternative on the page.

Iframe without title: add a descriptive title for accessibility.

Trusting embedded content from other origins without sandbox: restrict iframes with sandbox to reduce security risk.

Serving very large media files without preload control: use preload="metadata" or "none" when you do not need immediate full load.

Missing fallback inside object: when the embed fails, users see nothing; add a link or description inside the object element.

Using iframe without considering sandbox: restrict capabilities with the sandbox attribute to limit what the embedded page can do.
