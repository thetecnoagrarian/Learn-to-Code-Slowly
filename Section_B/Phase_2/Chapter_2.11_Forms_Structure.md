# Section B Phase 2 · Chapter 2.11: Forms — Structure and Input Types

Forms collect input from the user and submit it to a server or handle it with script. This chapter covers the form element (action and method), how to associate labels with controls using for and id, and common input types: text, number, email, password, checkbox, and radio. Every form control needs a label and a name for submission; choosing the right input type and GET vs POST keeps your dashboard forms accessible and semantically correct. Chapter 2.10 covered tables for tabular data; forms often sit alongside tables (e.g. filters or settings) and use the same structural principles. Forms are a boundary where user input is collected and sent; labeling and naming controls correctly keeps that boundary clear and accessible. Chapter 2.12 continues with select, textarea, and buttons.

## Learning Objectives

By the end of this chapter, you should be able to:
- Create a form with action (submit URL) and method (GET or POST) and understand when to use each
- Associate a label with every form control using for and id (or by wrapping the control in the label)
- Use the name attribute on controls so submitted data has the right keys
- Choose appropriate input types (text, number, email, password, checkbox, radio) and use required, placeholder, and min/max where appropriate
- Ensure every control has a visible or screen-reader-only label; avoid using placeholder as the only label

## Key Terms

- **form**: The element that wraps form controls; has action (URL to submit to) and method (GET or POST)
- **action**: Attribute on form; the URL that receives the submitted data (or empty for same page)
- **method**: Attribute on form; GET (data in URL query string) or POST (data in request body)
- **label**: Element that describes a form control; use for with id on the control, or wrap the control inside the label
- **input**: Element for single-line text, number, email, password, checkbox, radio, and other types; has type, name, and optionally id, required, placeholder, min, max
- **name**: Attribute on form controls; the key under which the control’s value is submitted (required for submission)
- **id**: Attribute on a control; must match the for attribute on its label so clicking the label focuses the control
- **required**: Boolean attribute; the form will not submit until the control has a value (browser validation)
- **placeholder**: Attribute that shows hint text inside the control; not a substitute for a label

Forms are flow content. They create a boundary: user input is collected and sent somewhere (the action URL with the chosen method). Section A Phase 1 introduced boundaries and validation; the form is the boundary where user data enters the system, so correct labeling and naming help both users and servers. Validators can check for missing labels and duplicate ids; fix those before relying on client-side or server-side validation. Section A Phase 1 introduced HTTP and request/response; form submission triggers an HTTP request with the method and a body or query string built from the controls’ names and values. Every control that should be submitted must have a name. Buttons that submit the form (type="submit") do not need a name unless you have multiple submit buttons and need to know which was clicked; Chapter 2.12 covers that. Forms can contain other flow content (e.g. paragraphs, headings) to structure the form; keep the relationship between labels and controls clear so that users and assistive technology can move through the form in a logical order. Chapter 2.12 covers select, textarea, and submit/reset buttons so you can build complete forms.

## 1) form, action, method

The form element wraps the form controls (inputs, and later select, textarea, buttons). It has two important attributes: action and method. The action is the URL to which the form is submitted. It can be a relative path (e.g. "settings" or "/dashboard/save") or an absolute URL. If you omit action or set it to the empty string, the form submits to the current page URL, which is useful when you handle submission with script on the same page. The method is the HTTP method used for the request. Use method="get" when the submission is a read-only query: the form data is appended to the action URL as a query string (e.g. ?sensor=battery&from=2024-01-01). GET requests should not change state on the server; they are suitable for search, filters, and links that could be bookmarked or shared. Use method="post" when the submission changes state: the form data is sent in the request body, not in the URL. POST is for creating or updating data (e.g. saving settings, adding a record). Do not use GET for actions that change state; use POST so that reloading or sharing the URL does not resubmit the form.

The browser builds the submitted data from every form control that has a name and is not disabled. Each control contributes a name–value pair. For GET, these become query parameters; for POST, they go in the body (typically application/x-www-form-urlencoded or multipart/form-data for file uploads). The form element can have other attributes (e.g. enctype for POST body format, autocomplete for hints); the essentials are action, method, and ensuring every submit-relevant control has a name. Relative URLs in action are resolved against the current document (same as for links in Chapter 2.06); use relative paths for same-origin endpoints so the form works on any host. If the form is handled by client-side script (e.g. preventDefault and fetch), you may still set action and method so that the form is valid and works when script is disabled or unavailable; the script can then intercept submit and send the data itself. Chapter 2.10 (Tables) showed how to present data; forms are how users send data back. Keep the form structure clear: one form per logical submission (e.g. one "Filter" form, one "Save settings" form) so that the boundary between "user fills this" and "this gets submitted" is obvious. Do not nest a form inside another form; HTML does not allow it and the inner form is ignored. If you need multiple submission actions on the same page (e.g. filter and export), use two separate form elements or one form with multiple submit buttons that have different names and values (Chapter 2.12).

## 2) label and id

Every form control that accepts user input must have an associated label. The label tells the user (and assistive technology) what the control is for. There are two ways to associate a label with a control. First: give the control an id (e.g. id="voltage-min"), and give the label a for attribute with the same value (e.g. for="voltage-min"). When the user clicks the label, the browser focuses the control. That also increases the hit area (especially useful for checkboxes and radio buttons) and ensures screen readers announce the label when the user focuses the control. Second: wrap the control inside the label element. Then you do not need for or id for association; the label is implicitly associated with the single control inside it. Use one or the other consistently. Prefer for and id when the control and label are in different parts of the layout (e.g. label in one column, input in another) or when you need the id for other purposes (e.g. aria-describedby). Use wrapping when the label and control are adjacent and you want simpler markup.

There should be one label per control (or one control per label). Do not use the same id for two controls; id must be unique on the page (Chapter 2.17). If you have a group of controls (e.g. several checkboxes for "Notify for: voltage, coop, poultry net"), use a fieldset with a legend to describe the group (Chapter 2.12), and each checkbox still gets its own label. Never use placeholder as the only label: placeholder is a hint that may disappear when the user types and is not always announced by screen readers. Always provide a real label (visible or visually hidden with a class that keeps it available to screen readers). Visible labels are best when space allows; they make the form understandable at a glance and improve accessibility. If you must hide the label visually (e.g. when the placeholder or layout implies the purpose), use a class or technique that keeps the label in the DOM and available to screen readers (e.g. visually hidden text or aria-label on the control); do not remove the label entirely. The id on the control must be unique in the whole document, not just within the form; if you have multiple forms on the page (e.g. filter form and settings form), ensure input ids are unique (e.g. filter-date and settings-date).

## 3) input Types — text, number, email, password

The input element is a void element; it has a type attribute that determines its behavior and appearance. Use type="text" for a single line of text (e.g. sensor name, filter value). Use type="number" for numeric input; the browser may show a spinner and you can set min, max, and step to constrain values. Use type="email" for email addresses; the browser can validate format and suggest email autocomplete. Use type="password" for passwords; the value is masked so it is not visible on screen. Every input that participates in submission must have a name attribute; that name is the key in the submitted data. Give the input an id when you use a label with for so that the label is associated.

The required attribute (boolean) means the form will not submit until the control has a value; the browser shows a validation message when the user tries to submit empty. Use required for fields that are mandatory. The placeholder attribute shows hint text inside the field (e.g. "Enter minimum voltage"); it is not a label. Placeholder can supplement the label but must not replace it. Avoid long or critical instructions in placeholder only; put them in the label or in help text (e.g. aria-describedby). For number inputs, min and max set the allowed range; step sets the increment (e.g. step="0.1" for decimals). For text and email, you can use maxlength to limit the number of characters. Other useful types include type="search" for search boxes (some browsers style them with a clear button) and type="date" or type="datetime-local" for date and time; use these when the data is clearly a date or time so the browser can provide an appropriate picker. Type="url" and type="tel" are for URLs and phone numbers; they can improve mobile keyboard behavior. For this chapter the focus is on text, number, email, password, checkbox, and radio; the same principles (name, label, required when needed) apply to all input types. The value attribute sets the initial value; when the form is submitted, the current value (what the user typed or the initial value) is sent. Disabled controls are not submitted and are not focusable; use disabled when the control is not applicable in the current context. Readonly controls are submitted but cannot be edited by the user; use readonly when you show a value that is not user-editable in this form. The autocomplete attribute can suggest values (e.g. autocomplete="email" on an email input) so browsers and password managers can fill the form; use it when the field has a standard meaning. For number inputs, avoid very large ranges without step so that the spinner and validation stay useful; for voltage or temperature limits, min and max in a sensible range (e.g. 0–30 V) help prevent typos. Input types also affect mobile keyboards: number may show a numeric keypad, email may show a keypad with @, which improves usability on small screens.

## 4) checkbox and radio

Checkboxes and radio buttons are two more input types. Use type="checkbox" when the user can select zero, one, or more options from a set (e.g. "Notify for: voltage, coop, poultry net" — any combination). Use type="radio" when the user must select exactly one option from a set (e.g. "Units: V or A" — one choice). For radio buttons, all options in the same group share the same name attribute; each option has a different value. Only one radio in the group can be checked at a time; when the user selects one, the others are unchecked. You should set one radio as checked by default if there is a sensible default, or leave none checked if the user must make a choice. For checkboxes, set checked on those that are on by default (e.g. "Notify on low voltage" checked, "Notify on coop door" unchecked). The checked attribute is boolean; its presence means the control is checked. When the form is submitted, only checked checkboxes and the selected radio in each group contribute their name and value; unchecked checkboxes are omitted from the submission (unless you need to send "off" explicitly, in which case a hidden input or server-side default handles it). For checkboxes, each can have its own name (so each submits as a separate name–value pair) or several can share a name (then multiple values are submitted for that name, depending on server handling). Each checkbox and radio needs a value attribute so that when it is checked, that value is submitted; if you omit value, the value "on" is submitted for checkboxes.

Every checkbox and radio must have a label. Use for and id so that clicking the label toggles the checkbox or selects the radio; that makes the control easier to use, especially on touch devices. When you have a group of checkboxes or radios (e.g. "Choose one: A, B, C"), wrap them in a fieldset and use a legend to describe the group (e.g. "Unit"); that way screen readers announce "Unit, radio group, A selected" and the user understands the context. Chapter 2.12 covers fieldset and legend in more detail. Do not use radio or checkbox for a single on/off choice when a single checkbox is enough (e.g. "Enable notifications" — one checkbox with value="yes" or no value and check means "on"). Keep the group semantics clear: same name for radios in one group, and a legend that describes what the group is for. If you have a single checkbox (e.g. "I agree" or "Enable notifications"), one checkbox with a label is enough; no need for a second "Off" option. Checkboxes that share a name (e.g. name="notify" with values "voltage", "coop", "poultry") submit multiple name–value pairs with the same name when several are checked; server-side or client-side code must handle multiple values for that name. Radio buttons with the same name submit exactly one value (the value of the checked radio). Validators will flag form controls without associated labels when accessibility checks are enabled; fix by adding a label or aria-label so every control is identified.

## 5) When to Use What

Use GET for forms that only query or filter (e.g. "Filter by date," "Search"); the parameters appear in the URL and the request is safe to repeat. Use POST for forms that change state (e.g. "Save settings," "Add zone"). Use text for short free text, number for numeric values (with min/max/step if needed), email for email addresses, password for passwords. Use checkbox for zero-or-more choices and radio for exactly-one choice. Always give every control a name (for submission) and an associated label (for accessibility). Use required when the field is mandatory. Use placeholder only as a hint, not as the only label. If the form has many fields, group related ones in fieldsets (Chapter 2.12) and consider splitting into multiple forms or steps so the form does not overwhelm. Use autocomplete where it helps (e.g. email, username) so users can reuse saved values. Avoid putting interactive elements (e.g. links or buttons that are not submit/reset) inside a form if they trigger navigation or actions that could be confused with form submission; use type="button" for buttons that do not submit (Chapter 2.12). ## 6) Homestead Examples: Forms in Practice

Your dashboard might have a "Filter readings" form: method GET, action the same page or a readings URL, with inputs for date range (e.g. type date or text with a placeholder) and sensor (e.g. select or radio). Each control has a label and a name; submitting the form adds the parameters to the URL so the user can bookmark or share the filtered view. A "Settings" form might use method POST: action a save endpoint, with inputs for voltage min/max (type number, min and max), email for alerts (type email, required), and checkboxes for "Notify on: low voltage, coop door, poultry net fault." Each checkbox has a name and value; the labels use for and id so clicking the label toggles the checkbox. A login or API-key form would have email (or username) and password inputs, labels, and POST to an auth endpoint. A drip schedule form might have number inputs for zone duration and checkboxes for which days each zone runs; use fieldset and legend to group "Zone 1" and "Zone 2" so the form is clear. Keep form and table separate: use a table to display data (Chapter 2.10) and a form above or beside it to filter or submit; do not nest a table inside a form in a way that breaks the table structure, or put multiple forms inside one table row unless you intentionally have one form per row. An alert or notification preferences form might group "Email address" (type email, required), "Min voltage threshold" (type number, min/max), and "Alert types" (checkboxes for voltage, coop, poultry net, drip) in one POST form with a clear caption or heading (e.g. "Alert settings"). Use consistent naming: e.g. name="email" for the email field and name="alert_voltage", name="alert_coop" for checkboxes so the server can parse the submission unambiguously. When you add a new form, ensure every control has a label and a name and that the form has action and method; then add submit and reset buttons (Chapter 2.12). A voltage or solar threshold form might have number inputs for "Min voltage" and "Max voltage" with min and max set to a safe range (e.g. 10–15 V), each with a label and name. A coop or poultry net settings form might have checkboxes for "Alert on door open," "Alert on low voltage," and "Alert on fault," each with a distinct name and value so the server knows which options are enabled. Keep the form and its submission target (action) in sync: if you change the backend endpoint, update the form action so submissions still work.

## 7) What Breaks When Forms Are Wrong

Missing or wrong action: the form may submit to the wrong URL or nowhere; set action to the correct endpoint. Using GET for a state-changing action: reload or sharing the URL can resubmit and duplicate the action; use POST. Missing name on a control: the control’s value is not submitted; add a name to every control that should be sent. Missing label: users and screen readers do not know what the control is for; add a label (for/id or wrapping). Using placeholder as the only label: placeholder is not reliable for accessibility; add a real label. Duplicate id: two controls with the same id break label association and validity; ensure each id is unique. Missing value on radio or checkbox: the submitted value may be "on" or empty; set value explicitly. Required field with no label or unclear label: validation may fire but the user may not know which field to fix; pair required with a clear label. Multiple submit buttons without names: the server may not know which was clicked; give each submit button a name and value (Chapter 2.12). Fix forms so that action and method are correct, every control has a label and a name, and input types and required/placeholder are used appropriately. Form validation (required, type="email", min/max) runs on submit; ensure that error messages or inline validation (if you add it with script) are associated with the correct control (e.g. aria-describedby) so screen reader users know what to fix. Empty or incorrect action with POST can send data to the wrong URL or leave the user on the same page with no feedback; always set action and, if using script to submit, provide clear success or error feedback. ## 8) Form Checklist

When you add a form, confirm: the form has action and method (GET for query, POST for state change). Every control that should be submitted has a name. Every control has an associated label (for/id or wrapping); do not rely on placeholder alone. Use the appropriate input type (text, number, email, password, checkbox, radio) and add required, min, max, or step where needed. For radio groups, all options share the same name and each has a value; one can be checked by default. For checkboxes, each has a label and a value. Test by submitting the form (or with script disabled) to ensure the request goes to the right URL with the right method and that the names and values appear as expected. Test with a screen reader to ensure every control is announced with its label. When you add or remove form controls, update the checklist: new inputs need name and label; new radio groups need the same name and distinct values. If the form is generated from data (e.g. a list of sensors to choose from), ensure each generated input has a unique id and that labels are correctly associated. ## Common Pitfalls

Using GET for state-changing actions: use POST so that reload or share does not resubmit.

Omitting the label: every control needs an associated label for accessibility and usability.

Using placeholder as the only label: add a real label; use placeholder only as a hint.

Missing name on a control: the value will not be submitted; add name to every control that should be sent.

Duplicate id on controls: breaks label association; ensure each id is unique on the page.

Radio group with different names: each name creates a separate group; use the same name for all options in one group.

Checkbox or radio without a value: set value so the submitted data is meaningful.

Relying on placeholder for critical instructions: put important text in the label or in help text linked via aria-describedby.

Using the same id on multiple pages: if forms are in a template reused across pages, ensure ids are unique per page (e.g. prefix with form name or use dynamic ids).

## Summary

Use form with action and method; use GET for queries and POST for state changes. Associate every form control with a label using for and id or by wrapping the control in the label. Give every control that should be submitted a name. Choose the right input type: text, number, email, password, checkbox, radio. Use required for mandatory fields; use placeholder only as a hint, not as the only label. Use checkbox for zero-or-more choices and radio for exactly-one choice; use fieldset and legend for groups (Chapter 2.12). Run through the form checklist when you add or change forms. Use GET for filters and searches so the URL reflects the query and can be bookmarked; use POST for saving or updating so that reload does not resubmit.
