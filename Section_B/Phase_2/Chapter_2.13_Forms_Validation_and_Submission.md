# Section B Phase 2 · Chapter 2.13: Forms — Validation and Submission

This chapter ties together form validation and submission: how HTML5 validation attributes work, how form action and method determine where and how data is sent, how the name attribute shapes submitted data, and why server-side validation and security (HTTPS, CSRF awareness) are essential. Client-side validation improves UX but is not security; the server must always validate and sanitize. Chapters 2.11 and 2.12 covered form structure, inputs, select, textarea, and buttons; this chapter focuses on what happens when the user submits and how to handle validation and security. Chapter 2.14 (Semantic HTML and Landmarks) continues with document structure and accessibility.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use HTML5 validation attributes (required, pattern, min, max, minlength, maxlength) and understand that they improve UX but can be bypassed
- Set form action and method correctly and understand when to use GET vs POST for submission
- Explain how name attributes on controls become the keys in submitted data (query string for GET, body for POST) and how multiple values (checkboxes, multi-select) are sent
- Recognize that client-side validation is for UX only; the server must validate, sanitize, and authorize
- Be aware of HTTPS for form submission and CSRF and same-origin considerations

## Key Terms

- **Constraint validation**: The browser’s built-in checks (required, pattern, min, max, minlength, maxlength, type) that run on submit or on blur
- **Invalid state**: A control that fails validation is invalid; the browser can show a message and prevent submit
- **action**: The URL the form is submitted to (form attribute)
- **method**: GET (data in URL query string) or POST (data in request body)
- **name**: Attribute on form controls; the key under which the control’s value is submitted
- **CSRF (Cross-Site Request Forgery)**: An attack where a different site triggers a request from the user’s browser to your site with the user’s credentials; mitigation includes same-origin checks and CSRF tokens
- **Server-side validation**: Validation performed on the server after submission; required for security and correctness because client-side validation can be bypassed

Validation and submission form a boundary: the user enters data in the browser, and that data crosses into your system when the form is submitted. How you validate (what you accept) and how you secure the request (HTTPS, CSRF) determine whether the boundary is safe and reliable. User data enters the system when the form is submitted, so validation (what is accepted) and security (how the request is trusted) matter. ## 1) HTML5 Validation Attributes

HTML5 constraint validation lets the browser check controls before the form is submitted. The browser runs these checks when the user submits the form (or when you call checkValidity or reportValidity in script). The required attribute (boolean) means the control must have a value; an empty required text input, or an unchecked required checkbox, or a select with no selection (when required) will fail. The minlength and maxlength attributes set minimum and maximum character count for text inputs and textarea. The min, max, and step attributes constrain number and date-like inputs. The pattern attribute takes a regular expression that the value must match (for text inputs). Input types such as type="email" and type="number" bring their own validation (e.g. email format, numeric value). When the user submits the form, the browser runs these checks. If any control is invalid, the browser typically stops submission, focuses the first invalid control, and shows a default message (e.g. "Please fill out this field" or "Please match the requested format"). The control is then in an invalid state; the :invalid CSS pseudo-class can be used to style invalid controls, and the validity state is exposed to script via the constraint validation API: checkValidity() returns true or false for the form or a single control; setCustomValidity() sets a custom message the browser shows when the control is invalid; reportValidity() triggers validation and shows messages without submitting. ValidityMessage gives the browser’s or your custom message for the current invalid state.

Use validation attributes to give immediate feedback so users can correct errors without a round trip to the server. Do not rely on them for security: a user can disable JavaScript, alter the DOM, or send a direct HTTP request with arbitrary data, bypassing all client-side validation. So use required, minlength, pattern, and min/max to improve UX and reduce invalid submissions; always validate the same rules (and more) on the server. Custom error messages can be set with setCustomValidity so that when the control is invalid, the browser shows your message instead of the default; clear the custom message when the control becomes valid so the browser does not keep showing it. The reportValidity() method can be used to trigger validation and show messages without submitting (e.g. on blur or on a "Validate" button). Novalidate on the form disables browser validation for that form; use it when you handle validation entirely with script and want to control when and how messages appear. If you use novalidate, you must still validate on the server and can use reportValidity or your own checks to show errors before submit.

The pattern attribute expects a JavaScript regular expression. The value is checked against the full string, so you usually do not need ^ and $ unless you want to enforce that the whole value matches (many patterns work without them). Provide a title attribute that describes the expected format; some browsers show the title when validation fails, and it helps all users understand the rule. For number inputs, min and max are numeric; the browser will reject values outside the range. For date or datetime-local, min and max are date or datetime strings. Step controls the allowed increments (e.g. step="0.1" for one decimal place). If the user enters a value that does not match the step, the control may be invalid. Combining type, required, min, max, and pattern gives clear, immediate feedback; keep server-side checks in sync so the same constraints are enforced after submission.

## 2) Form Action and Method

The form’s action attribute is the URL to which the form is submitted. It can be relative (e.g. "save" or "/dashboard/settings") or absolute (e.g. "https://api.example.com/settings"). If action is missing or empty, the form submits to the current document URL, which is often used when the same page handles both display and form processing. The method attribute is the HTTP method: "get" or "post". With method="get", the form data is appended to the action URL as a query string (e.g. action="https://example.com/search" and inputs named q and type produce .../search?q=voltage&type=sensor). GET requests should be idempotent and not change state; use GET for search, filters, and anything that could be bookmarked or shared. With method="post", the form data is sent in the request body, not in the URL. Use POST for actions that change state (e.g. saving settings, creating a record, logging in). Never use GET for state-changing actions; otherwise reloading or sharing the URL could resubmit and duplicate the action.

The enctype attribute specifies how POST data is encoded. The default is application/x-www-form-urlencoded (name=value pairs). Use enctype="multipart/form-data" when the form includes file uploads (input type="file"); that encoding is required for files. For normal form data (text, numbers, checkboxes, select), the default is fine. When the form is submitted, the browser sends an HTTP request to the action URL with the given method; the server receives the data and must validate, sanitize, and process it. If the form is handled by client-side script (e.g. preventDefault on submit and then fetch to an API), you still set action and method so the form is valid and works when script is disabled; the script then intercepts submit and sends the data itself (e.g. as JSON in the body). Chapter 2.11 covered action and method in the context of form structure; here the focus is on how they affect the request and why GET vs POST matters for correctness and security.

On the homestead, a filter form for sensor logs (sensor id, date from, date to) should use GET so the URL contains the filter (e.g. /logs?sensor=coop&from=2025-01-01&to=2025-01-30). A form that saves voltage thresholds or alert settings should use POST so the URL does not contain sensitive or state-changing data and so reloading does not resubmit. A form that uploads a wiring diagram image must use POST and enctype="multipart/form-data". Choosing the right method and enctype keeps your URLs safe and your state changes explicit.

## 3) Name and Submitted Data

Every form control that should contribute to the submission must have a name attribute. The name is the key in the submitted data; the value is the control’s value (what the user entered for text/number/date, or the value attribute for checkboxes and radio, or the selected option’s value for select). The server receives a set of name–value pairs and uses the names to know which field each value belongs to. For GET, the name–value pairs become query parameters; for POST with the default enctype, they become body parameters. Controls that are disabled are not submitted; use disabled when a control is not applicable so its value is omitted. Controls without a name are not submitted. For checkboxes, only checked checkboxes are submitted; each sends its name and value. If multiple checkboxes share the same name, multiple name–value pairs with that name are sent (e.g. name="alert" value="voltage" and name="alert" value="coop"); the server must handle multiple values for the same key. For a multi-select (select with multiple), each selected option contributes a name–value pair with the select’s name and the option’s value. For radio buttons, only the selected radio in each group (same name) is submitted. So the shape of the submitted data is determined by the names and values of the controls and by which controls are enabled and (for checkboxes and multi-select) selected. When you build the server-side handler, you expect these keys and values; if you change a control’s name on the front end, you must update the server to match, or the data will be missing or misinterpreted.

Empty text inputs and textareas submit as an empty string for that name (unless required stops submit). Number inputs submit the numeric value as text. The format of the body or query string is standardized (application/x-www-form-urlencoded or multipart/form-data), so the server can parse it. When you use client-side script to submit (e.g. fetch with JSON), you are responsible for building the payload from the form controls (e.g. reading value from each named control and constructing a JSON object); the browser does not send JSON by default for form submission. Keep names consistent and predictable so that both client and server agree on the shape of the data.

If you rename a control on the front end (e.g. from "voltage_min" to "min_voltage"), the server must be updated to look for the new key; otherwise the value will be missing. Similarly, if the server expects an array for a multi-select or multiple checkboxes, it must read all values for that name, not just the first. Document the expected keys and value formats in your API or handler so that future changes stay in sync between HTML and server.

## 4) Security and Best Practices

Client-side validation is for user experience only. It can be bypassed by turning off JavaScript, editing the DOM, or sending a direct HTTP request (e.g. with curl or a script). Therefore the server must always validate and sanitize submitted data: check required fields, format (e.g. email, number range), length, and pattern. Reject invalid data and return clear error messages; do not trust the client. Sanitize input to prevent injection (e.g. SQL injection, XSS) when you store or display the data. Authorize: ensure the authenticated user is allowed to perform the action (e.g. saving settings for their own dashboard only).

Use HTTPS for forms that submit sensitive data (passwords, API keys, personal information). Without HTTPS, the request body can be read or modified in transit. For forms that only filter or search (GET), HTTPS is still recommended so the query string (which may contain search terms or filters) is not visible on the network. CSRF (Cross-Site Request Forgery) is an attack where a malicious site causes the user’s browser to send a request to your site (e.g. a form POST) using the user’s cookies or session. Mitigations include: same-origin policy (your form is on your origin, so a form on another origin cannot easily read the response), CSRF tokens (a token in the form that the server checks), and SameSite cookies so the browser does not send cookies on cross-site requests in some cases. For a dashboard that is only used on your own network or that does not use session cookies for form submission, the risk may be lower, but for any form that changes state and uses cookies or sessions, consider CSRF protection. Do not rely on client-side validation or on "secret" fields for security; the server is the authority.

Server-side validation should check types (e.g. number in range, email format), length (min/max), and business rules (e.g. end date after start date, sensor id exists). Return clear error messages (e.g. 400 Bad Request or 422 Unprocessable Entity with a list of field errors) so the client can show them next to the right controls. Sanitize and escape output when you display stored data to avoid XSS; use parameterized queries or an ORM to avoid SQL injection when you store form data. On the homestead, a sensor config form that posts to your Pi or to a cloud API should still be validated on the receiving side so a mistyped threshold or a malicious request does not corrupt your config.

## 5) When to Use What

Use GET for forms that only query or filter (search, date range, sensor filter); the URL reflects the query and can be bookmarked. Use POST for forms that change state (save settings, add record, login). Use HTML5 validation attributes (required, minlength, pattern, min, max) to give immediate feedback; pair them with server-side validation that enforces the same rules and more. Use clear, stable name values so the server can reliably parse the submission. Use HTTPS in production for any form that submits sensitive or state-changing data. For CSRF, use tokens or SameSite cookies when the form is used with session-based auth. When you display validation errors from the server (e.g. "Email is invalid"), associate them with the correct control (e.g. next to the field or via aria-describedby) so users know what to fix. If you use JavaScript to submit the form (e.g. fetch with JSON), you still need server-side validation; the client only prepares the request.

Choose validation attributes that match what the server will check: if the server rejects values outside 0–100, set min="0" and max="100" on the number input so the user sees the same rule. If the server requires a specific format (e.g. sensor id pattern), use a pattern that matches it and a title that explains it. Avoid validating only on submit if you can give feedback earlier (e.g. on blur) using reportValidity or your own checks; but remember the browser’s submit-time validation is the built-in safety net. ## 6) Homestead Examples: Validation and Submission in Practice

Your dashboard filter form (sensor, date range) should use GET so the filtered view can be bookmarked and shared; the server validates the query params (e.g. sensor id exists, date range is valid) and returns the filtered data. Your settings form (voltage thresholds, email, alert checkboxes) should use POST to a save endpoint; the server validates required fields, email format, and number ranges, then saves. If validation fails, the server returns error messages and the client can display them next to the fields (e.g. "Min voltage must be between 10 and 15"). Use required and min/max on the client so the user gets instant feedback; the server still checks the same and returns 400 or 422 with error details if someone bypasses the client. A login or API-key form must use POST and HTTPS; the server validates credentials and sets a session or returns a token; never send passwords in the URL (GET). A "Report issue" form with a textarea and select can use POST; the server validates minlength for the description and that the category is allowed, then stores the report. For a form that triggers an action on a Pi or device (e.g. "Run zone 1 now"), use POST so the action is not triggered by a stray GET (e.g. prefetch or link). Keep validation messages consistent: same rules on client and server, and clear messages so the user can fix the form and resubmit.

A drip schedule form (zone, duration, days) can use POST; the server checks that zone exists, duration is within limits, and days are valid, then updates the schedule. A freezer alert threshold form (min/max temperature) can use required and min/max on number inputs; the server must revalidate the range before saving so a tampered request cannot set an invalid threshold. When you show server errors (e.g. "Email already in use" or "Sensor not found"), associate each message with the correct field so screen reader users and sighted users know what to change. ## 7) What Breaks When Validation or Submission Is Wrong

Relying only on client-side validation: invalid data can be submitted; always validate on the server. Using GET for state-changing actions: reload or shared URL can resubmit; use POST. Missing name on a control: the value is not submitted; add name to every control that should be sent. Wrong or missing action: form submits to the wrong URL or nowhere; set action correctly. Server not validating: injection or invalid data can be stored or executed; validate and sanitize on the server. Submitting passwords or secrets over HTTP: data can be read in transit; use HTTPS. No CSRF protection when using sessions: attacker site can trigger requests with user’s session; add CSRF token or SameSite cookie. Custom validation message not cleared when control becomes valid: browser keeps showing the old message; call setCustomValidity("") when valid. Form with novalidate and no script validation: invalid data can be submitted; if you use novalidate, implement validation in script and still validate on the server. Mismatched name between HTML and server: the server looks for a key that is never sent or sends a different key; keep names in sync. Pattern or min/max only on client: a direct POST can send values outside the range; enforce the same constraints on the server. Submitting with wrong enctype (e.g. file upload without multipart/form-data): the file is not sent correctly; set enctype when the form has file inputs. Fix validation and submission so that client-side validation improves UX, server-side validation enforces rules, and action, method, and names are correct. ## 8) Validation and Submission Checklist

When you add or change a form, confirm: action points to the correct URL; method is GET for query-only and POST for state-changing. Every control that should be submitted has a name. Required fields have the required attribute (and server-side checks). Use minlength, maxlength, pattern, min, max where they help; validate the same on the server. If the form uses session cookies or auth, consider CSRF protection (token or SameSite). Use HTTPS for forms that submit sensitive or state-changing data. When the server returns validation errors, display them next to the relevant controls so the user can correct and resubmit. Test by submitting valid and invalid data; confirm the server rejects invalid data and returns clear errors. Test with client-side validation disabled or with a direct request to ensure the server does not accept bad data. For file uploads, set enctype="multipart/form-data". For custom validity messages, clear setCustomValidity when the control becomes valid. Document the expected request keys and value formats so front-end and back-end stay in sync. When the server returns a list of field errors (e.g. "min_voltage: must be between 10 and 15"), map each key to the correct form control and show the message next to that control so the user can fix and resubmit without guessing. ## Common Pitfalls

Relying on client-side validation for security: always validate and sanitize on the server. Anyone can send a direct request with arbitrary data; the server is the only authority.

Using GET for state-changing actions: use POST so reload or share does not resubmit. GET is for reading; POST is for writing.

Missing or wrong name on controls: add name so values are submitted under the expected keys. Without a name, the control’s value is never sent.

Skipping server-side validation: invalid or malicious data can reach your app; validate every submission. Reject invalid data and return clear field-level errors.

Sending sensitive form data over HTTP: use HTTPS so data is not visible or modifiable in transit. This includes passwords, API keys, and any state-changing form.

Ignoring CSRF when using sessions: add CSRF token or SameSite cookie for state-changing forms. Otherwise a malicious site can trigger a request with the user’s session.

Not showing server validation errors next to fields: users need to see what to fix; associate errors with controls (e.g. next to the field or via aria-describedby) so they can correct and resubmit.

Clearing custom validity message only on submit: clear setCustomValidity when the control becomes valid so messages update. If you set a custom message and do not clear it, the browser may keep showing it after the user fixes the value.
