# Section B Phase 2 · Chapter 2.14: Semantic HTML and Landmarks

This chapter introduces semantic HTML for page structure: header, main, footer, nav, aside, section, and article. These elements give the page meaning for assistive technology and layout. Landmarks (exposed by these elements) let screen-reader users jump by region; a logical document outline helps everyone navigate. Chapter 2.13 covered form validation and submission; here we focus on how to wrap your content and forms in a clear structure so that the main content, navigation, and side panels are clearly identified. Chapter 2.15 (Sections, Articles, and the Document Outline) goes deeper on section, article, and heading hierarchy.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use header, main, footer, nav, aside, section, and article to structure a page by meaning
- Understand how these elements expose landmarks (e.g. banner, main, contentinfo, navigation, complementary) for assistive technology
- Prefer one main per page and keep main outside header, footer, nav, aside, and article
- Use section and article to subdivide content, each with a heading when appropriate
- Relate structure to the document outline and screen-reader navigation

## Key Terms

- **header**: Element for introductory or navigational content of a page or a section (e.g. site header with logo and nav)
- **main**: Element for the primary content of the page; there should be one per page, and it should not sit inside article, aside, nav, header, or footer
- **footer**: Element for the end of a page or section (e.g. copyright, links, contact)
- **nav**: Element for a block of major navigation links (e.g. main menu, footer links); there can be more than one nav per page
- **aside**: Element for content that is tangentially related to the main content (e.g. sidebar, related links, ads)
- **section**: Element for a thematic grouping of content that typically has a heading
- **article**: Element for a self-contained composition (e.g. blog post, news item, product card) that could stand alone
- **landmark**: A named region exposed to assistive technology (e.g. role="main" for main); screen readers can list and jump to landmarks
- **document outline**: The logical structure formed by headings and sectioning elements; used for navigation and accessibility

These terms are used throughout the chapter. Semantic structure makes the page understandable to tools and users: screen readers can announce regions and let users skip to main content; CSS and scripts can target regions by meaning. Search engines and other tools can use the structure to understand the page. Section 2.15 expands on section, article, and the document outline.

## 1) header, main, footer

The header element wraps introductory or navigational content for the page or for a section. A typical page has one top-level header containing the site logo, main navigation, and perhaps a search form. The header is not the same as "heading" (h1–h6); a header is a container. You can have multiple headers on a page (e.g. one at the top and one per section), but usually the top-level header is the one that defines the banner landmark. The footer can also appear multiple times (e.g. one at the page bottom and one per article or section) when each block has its own end content. The main element wraps the primary content of the page. There should be only one main per document, and it should contain the content that is unique to that page (e.g. the dashboard widgets, the form, the article body). Main should not be placed inside article, aside, nav, header, or footer; the spec says main is the primary content of the body. If you have multiple logical "main" areas (e.g. a dashboard with several tabs), only one should be visible at a time and that visible content should be inside the single main; hide the others with CSS or replace content dynamically so the DOM still has one main. The footer element wraps the end of the page or of a section: copyright, legal links, contact info, or secondary navigation. A page often has one top-level footer at the bottom. You can put a nav inside the footer for footer links (e.g. "About", "Privacy", "API docs"); that gives a second navigation landmark so screen-reader users can jump to "Footer navigation" if they need those links. The footer does not have to be at the very bottom of the viewport; it is the logical end of the page content, and CSS can position it at the bottom of the layout. Using header, main, and footer gives the page a clear top, middle, and bottom and exposes the banner, main, and contentinfo landmarks to assistive technology so users can jump to the main content and skip repeated header and footer content. In HTML5, these elements are flow content and can contain other flow content (headings, paragraphs, lists, nav, etc.); the only restriction is that main must not be a descendant of article, aside, nav, header, or footer. A typical body structure is: header (with nav), main (primary content), footer. You can wrap all three in a div for layout (e.g. a flex or grid container) without changing the landmark roles.

If your page has no distinct header or footer (e.g. a minimal single-view app), you can still use main to wrap the primary content; header and footer are optional but recommended when the content fits. Avoid putting the only meaningful content inside header or footer; the main content belongs in main. On the homestead, a simple status page might have only a header with the site name and a main with the current readings; a full dashboard adds a nav in the header and a footer with links. Screen-reader users who land on the page can jump to main and hear the primary content first, then use the banner (header) and contentinfo (footer) landmarks to find navigation or legal links. ## 2) nav and aside

The nav element is for blocks of major navigation links. A page can have multiple nav regions: for example a main nav in the header (site menu) and a nav in the footer (footer links). Use nav when the primary purpose of the block is navigation; do not wrap every set of links in nav (e.g. a list of related articles in the main content might be just a list of links, not a nav). If you have both a main nav and a breadcrumb trail, you can use two nav elements (e.g. one in the header for the main menu and one for breadcrumbs); give the main nav an aria-label such as "Main navigation" and the breadcrumb nav "Breadcrumb" so screen-reader users can tell them apart when listing landmarks. Nav exposes the navigation landmark so screen-reader users can jump to it and skip it when moving by landmark. The aside element is for content that is tangentially related to the main content: sidebars, related links, pull quotes, or ads. Aside exposes the complementary landmark. If the sidebar contains navigation, you can put a nav inside the aside. Use aside only when the content is truly tangential; if it is primary content, put it in main. If the content is neither primary nor tangential (e.g. a generic wrapper for styling), prefer a div; do not use aside as a generic sidebar container when the content is not complementary. In some screen readers, the complementary landmark is announced as "complementary" or "sidebar"; the name can be customized with aria-label if you want a more specific label (e.g. "Active alerts" for an aside that shows alerts). Nav can also have an aria-label to distinguish multiple nav regions (e.g. "Main navigation" vs "Footer links").

On a dashboard, the main nav might live in the header (links to Dashboard, Sensors, Settings); an aside might hold a panel of recent alerts or quick links. Screen-reader users can move by landmark to reach main quickly and to find navigation and complementary content without reading the whole page. Do not use nav for a single link (e.g. "Back to dashboard"); use it for a group of navigation links. If the aside contains both navigation and other content (e.g. alerts and a "Quick links" list), you can put a nav inside the aside for the links and leave the alerts as plain content in the aside. ## 3) section and article

The section element represents a thematic grouping of content that typically has a heading. Use section when you are grouping related content and can give it a heading (e.g. "Sensor status", "Recent events"). Do not use section as a generic wrapper when you have no thematic grouping or heading; in that case use a div. A section does not have to have a heading for validity, but without a heading the outline may not show a clear label for that region; prefer adding an h2 or h3 (or a visually hidden heading for accessibility) so the outline is meaningful. Section is not a replacement for div when you only need a styling hook; use div for that. When the content is both thematic and self-contained (e.g. a blog post that is also a distinct section of the page), you can use article and give it a heading; the outline will reflect the article and its internal structure. The article element represents a self-contained composition that could be distributed or reused on its own: a blog post, a news item, a forum post, or a product card. Article can nest inside section (e.g. a "News" section containing several article items), and section can nest inside article (e.g. an article with sections "Introduction", "Methods", "Results"). When you have a list of similar items (e.g. sensor cards, device cards, event logs), each item that is self-contained can be an article inside a section; the section can have a heading like "Sensors" and each article can have a heading with the sensor name. That structure supports both the outline (section > headings) and semantics (each card is an article). Do not use article for every small block; use it when the block could stand alone (e.g. syndication, reuse on another page). Each section and article that is a direct child of a sectioning root (body, blockquote, details, fieldset, figure, td, or another section or article) can contribute to the document outline; give each a heading so the outline is meaningful. Do not use section or article just for styling; use them when the content has that semantic role. For example, a "Sensor list" area that is just a styled div with no thematic heading can stay a div; a "Battery status" block that groups voltage, state of charge, and last updated can be a section with an h2 "Battery status". Article is appropriate for each sensor card or device card that could be read or reused on its own (e.g. in an RSS feed or another page). ## 4) ARIA Landmarks and Document Outline

Semantic elements like header, main, footer, nav, and aside expose ARIA landmarks to assistive technology. The main element has an implicit role of main; header at the top level is often treated as banner; footer as contentinfo; nav as navigation; aside as complementary. Screen readers can list landmarks and let users jump by region (e.g. "Main", "Navigation"), which makes it easier to skip repeated content and reach the primary content. You do not need to add role attributes for these elements; the roles are implicit. Only add ARIA when you need to fix or extend semantics (e.g. role="main" on a div if you cannot use main for some reason). Prefer the native elements (main, nav, aside) over ARIA roles on divs so you get correct behavior and less maintenance. If you do use role="main", ensure the region has an accessible name if needed (e.g. aria-label or a heading that labels the region) so screen-reader users know what the region contains. The document outline is the structure formed by sectioning elements and headings. Headings (h1–h6) define the outline levels; section and article create sectioning boundaries. Avoid skipping heading levels (e.g. h1 then h4); start with h1 for the page or main topic and use h2, h3, etc. in order so the outline is logical. Screen readers that support "headings list" or "outline" navigation will let users jump by heading; a clear hierarchy (e.g. "Sensor dashboard" as h1, "Battery status" and "Solar production" as h2, sub-sections as h3) makes navigation predictable. Landmarks and headings work together: landmarks for big regions (main, nav, aside), headings for the content structure inside those regions. When you add a new section or article, ask whether it needs a heading for the outline; if it does, use the correct level (e.g. the first heading in main is often h1 or h2, and sections inside main use h2 or h3 depending on the hierarchy). Consistency across pages (e.g. always h1 for the page title, then h2 for main sections) makes the outline predictable for users who navigate by headings. Screen readers and other tools use the outline for navigation (e.g. "Heading, Sensor dashboard; Heading, Battery status"). A well-structured page has one main, clear landmarks, and a logical heading hierarchy so both sighted and screen-reader users can navigate quickly. You can inspect the accessibility tree in browser dev tools to see how landmarks and headings are exposed; that helps verify that main, nav, and aside are correctly identified. On the homestead, a dashboard that uses header (with nav), main (dashboard content), aside (alerts or quick links), and footer (links) gives a consistent skeleton that you can reuse across pages; each page only changes the content inside main while the landmarks stay the same. If you must use a div for the main content (e.g. in a legacy app that cannot change the DOM easily), you can add role="main" and an accessible name so the region is still announced; prefer using the main element when possible. ## 5) When to Use What

Use header for the top-of-page intro and nav (logo, main menu); use footer for the bottom (links, copyright). Use main once per page for the primary content; keep it outside header, footer, nav, aside, and article. Use nav for blocks of major navigation (main menu, footer nav); do not wrap every link list in nav. Use aside for tangential content (sidebar, related links); do not use it as a generic wrapper. Use section for thematic groups that have a heading; use article for self-contained compositions. Prefer div when you need a neutral container with no semantic meaning. Use one h1 per page (or per main content area) and keep heading levels in order (h2 after h1, then h3, etc.) so the document outline is clear. When you have multiple sections inside main, give each section a heading that describes its content (e.g. "Current readings", "History", "Settings"); that creates a useful outline and helps screen-reader users jump by heading. If a section has no visible heading but you want it in the outline, you can use a visually hidden heading (e.g. with a CSS class that moves it off-screen but keeps it for assistive tech) so the outline stays meaningful without changing the visual design. Landmarks do not replace headings; use both so users can navigate by region and by heading. A page with good landmarks but no headings (or skipped levels) is harder to navigate by outline; a page with good headings but no main or nav is harder to navigate by region. When in doubt, use the element that matches the meaning: if it is the main content, use main; if it is a navigation block, use nav; if it is tangential, use aside; if it is a thematic group, use section; if it is self-contained, use article. ## 6) Homestead Examples: Semantic HTML in Practice

A homestead dashboard page can use a header at the top with the site title and a nav for links (Dashboard, Sensors, Settings, Alerts). The main region holds the primary content: summary cards (battery voltage, solar production, coop door status), a table or list of recent sensor readings, and perhaps a form to filter by date or sensor. An aside can show a panel of active alerts or quick actions (e.g. "Open coop", "Run zone 1"). The footer can contain links to documentation, API status, or contact. Screen-reader users can jump to main to get to the dashboard content and use nav to move between sections. A sensor detail page can have the same header and footer; main contains the sensor name, current reading, a chart or table of history, and maybe a form to set thresholds. Each logical block (e.g. "Current reading", "History", "Settings") can be a section with a heading so the outline is clear. A settings page can use main for the form and aside for help text or related links. Use section and article where they fit: for example a "Devices" section with an article per device card.

A live stream or camera view page can use main for the video and controls, and aside for a list of other cameras or related links. A map view of sensors can have main for the map and key stats, with aside for a legend or filter panel. Keep the same header and footer across pages so users always know where to find the main nav and footer links. When you add a new page (e.g. "Drip schedule"), put the schedule content in main and reuse the same header nav and footer; the landmark structure stays consistent so assistive technology users can orient quickly. A log or history page can use main for the table or list of events, with sections for "Today", "This week", or filter results; each section can have an h2. Forms from Chapters 2.11–2.13 fit inside main (e.g. a section "Alert settings" with the form, or a section "Filter" with the filter form). ## 7) What Breaks When Semantic Structure Is Wrong

Structure errors make the page harder to navigate and can confuse assistive technology. More than one main per page: assistive technology may not know which is primary; use one main. Main inside header, footer, nav, or aside: invalid and confuses landmarks; keep main as a direct descendant of body (or of a wrapper div if needed). No main: screen-reader users may have to read through header and nav to find content; add main. Using section or article as a generic wrapper with no heading: the outline can be empty or confusing; add a heading or use div. Skipping heading levels (h1 to h4): outline and navigation are confusing; use sequential levels. Putting all content in header and footer: main content is not in main; move primary content into main. Using aside for primary content: the content is announced as complementary; put primary content in main. Too many nav elements for minor link groups: landmarks get noisy; reserve nav for major navigation. Header or footer inside main: valid but be consistent; usually the top-level header and footer are outside main. Empty main: ensure main has the primary content so the main landmark is useful. Using header or footer for the only content: put the primary content in main so the main landmark is not empty. Fix structure so the page has one main, clear landmarks, and a logical outline. ## 8) Semantic Structure Checklist

Use this list when you add a new page or change the layout so the structure stays accessible. When you build or refactor a page, confirm: the page has one main that wraps the primary content. Main is not inside header, footer, nav, aside, or article. Header wraps intro/nav at the top; footer wraps end content at the bottom. Nav is used for major navigation blocks only. Aside is used for tangential content (sidebar, related links), not for primary content. Section and article are used when content is thematic or self-contained; each has a heading where appropriate. Div is used for neutral wrappers with no semantics. Heading levels are in order (no skipping). Test with a screen reader or accessibility tree to verify landmarks (main, navigation, complementary, banner, contentinfo) and that "Main" takes the user to the right place. If you use a wrapper div around header, main, and footer (e.g. for layout), that is fine; the semantic elements inside still expose the correct landmarks. When you add a new dashboard page, follow the same skeleton: header with nav, main with the page-specific content (and optionally sections with headings), aside for side panels if needed, and footer. That keeps landmarks and outline consistent so users can orient quickly on every page. Ensure the first focusable or readable content in main is the start of the primary content so keyboard and screen-reader users land in the right spot. If you use a "Skip to main content" link (a link that targets the main element or an id at the start of main), it works best when main is the primary content region and the link is one of the first focusable elements on the page. ## Common Pitfalls

Using more than one main per page: use a single main for the primary content so assistive technology can identify it.

Putting main inside header, footer, nav, or aside: keep main as the primary content of the body so landmarks are correct.

Using section or article as a generic wrapper with no heading: add a heading for each section/article that contributes to the outline, or use div.

Skipping heading levels (e.g. h1 then h4): use sequential levels (h1, h2, h3) so the document outline is logical.

Putting primary content in header or aside: primary content belongs in main so it is exposed as the main landmark.

Using nav for every link list: use nav only for major navigation blocks so the navigation landmark is meaningful.

Using aside for any sidebar: use aside only when the content is tangentially related; otherwise use div.

Forgetting to test with a screen reader or accessibility tree: verify that landmarks and the outline match what you intend. Many browsers expose an accessibility tree in dev tools; use it to confirm main, nav, and aside are correctly identified and that the first focusable element in main is where you expect.

## Summary

Use header, main, footer, nav, aside, section, and article to give the page meaning and expose landmarks for accessibility. Prefer one main per page and keep it outside header, footer, nav, aside, and article. Use nav for major navigation and aside for tangential content. Use section for thematic groups and article for self-contained compositions; give each a heading when it contributes to the outline. Keep heading levels in order and avoid skipping. Testing with a screen reader or the accessibility tree in dev tools confirms that landmarks and headings are exposed as intended. Run through the semantic structure checklist (section 8) when you build or refactor a page so landmarks and outline stay correct. Reusing the same header, main, and footer pattern across dashboard pages keeps the experience consistent: users always find the main nav in the same place and can jump to main for the page-specific content. Use aria-label on multiple nav or aside elements so screen-reader users can distinguish them (e.g. "Main navigation", "Footer links", "Active alerts").
