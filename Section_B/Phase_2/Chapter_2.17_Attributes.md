# Section B Phase 2 · Chapter 2.17: Attributes — class, id, data-*

This chapter covers the class, id, and data-* attributes: how to name them, when to use each, and how they support styling, scripting, and custom data. It builds on Chapter 2.16 (Div and Span), where you used class and id with div and span; here we go deeper on valid values, multiple classes, the data-* pattern for custom data, and boolean attributes. Chapter 2.18 (ARIA and Accessibility) then covers aria-* attributes when semantics need to be exposed or improved for assistive technology.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use class and id correctly: class for reusable styling and scripting hooks (multiple elements, multiple classes per element); id for a unique identifier (one element per id; anchors, ARIA, script).
- Apply valid naming: letters, digits, hyphen, underscore; no spaces; descriptive, lowercase-with-hyphens; avoid presentational names.
- Use data-* attributes for custom data that JavaScript or CSS needs (e.g. sensor id, threshold, unit); understand that data-* adds no semantics and no built-in behavior.
- Recognize boolean attributes (e.g. disabled, readonly, required): presence means true; omit the attribute to mean false; do not use "false" as the value.

## Key Terms

- **class**: An attribute that assigns one or more space-separated tokens to an element; reusable (many elements can share the same class); used for CSS selectors and JavaScript targeting; multiple classes per element are allowed.
- **id**: An attribute that assigns a unique identifier to one element in the document; used for in-page anchors, ARIA relationships, and script when a single element must be found; must be unique per document.
- **data-* attribute**: A custom attribute whose name starts with "data-" followed by a lowercase name (hyphens allowed); used to store custom data for JavaScript or CSS; no built-in semantics or behavior; the part after "data-" is the custom name (e.g. data-sensor-id, data-unit).
- **boolean attribute**: An attribute whose presence means true and whose absence means false (e.g. disabled, readonly, required); in HTML5 you may write the attribute with no value or with the attribute name as the value; writing "false" does not make it false—omit the attribute to mean false.

## 1) class and id Recap and Rules

Class and id are global attributes: you can use them on almost any HTML element. Class is for grouping: many elements can share the same class so you can style or target them together. You can give one element multiple classes by listing them in the class attribute, separated by spaces. For example, a sensor card might have class "card sensor-card alert-critical" so it gets shared card styles, sensor-card styles, and critical-alert styles. Use class when you want to apply the same styling or behavior to multiple elements (e.g. all "reading-value" spans, all "sensor-card" articles). Id is for uniqueness: in a valid document, only one element has a given id. Use id when you need to point to exactly one element: an in-page link (href="#main-content"), an ARIA relationship (e.g. aria-labelledby="label-id"), or JavaScript that must find a single node (e.g. the main content container, the form, or the element that receives focus). Do not reuse the same id on multiple elements; if you need to target several elements the same way, use a class. In CSS, you target class with a dot (e.g. .sensor-card) and id with a hash (e.g. #main-content). In JavaScript, you can select by class (e.g. querySelectorAll(".reading-value")) or by id (e.g. getElementById("main-content")). The browser does not enforce uniqueness of id at parse time in all cases, but duplicate ids cause undefined behavior for getElementById, in-page links, and ARIA references, so treat id as unique by convention and validate your markup.

Valid values for class and id are constrained. They must not contain spaces (spaces separate multiple class names). For id, the value must be unique in the document and is typically a single token. Allowed characters are letters (a–z, A–Z), digits (0–9), hyphen (-), underscore (_), and in some contexts colon (:) and period (.) for specific uses; in practice, stick to letters, digits, and hyphen for portability and clarity. The first character should not be a digit. Use lowercase-with-hyphens for readability (e.g. "sensor-card", "battery-voltage", "main-content"). Avoid presentational names (e.g. "red-box", "big-text") because when the design changes, the name becomes misleading; prefer names that describe role or content (e.g. "alert-critical", "reading-value", "form-settings"). Browsers and assistive technology use id for in-page navigation (clicking a link with href="#main-content" scrolls to and can focus the element with that id), for ARIA relationships (e.g. aria-labelledby="heading-id" associates the label with the element that has that id), and for form labels (the for attribute on a label matches the id of the input). So id is not just for CSS or script; it is part of the document's identity and relationships. Keeping id unique and meaningful matters for accessibility as well as for correct behavior.

## 2) Multiple Classes and Naming Conventions

An element can have multiple classes. List them in the class attribute separated by spaces. The order of class names usually does not matter for CSS (selectors match any element that has the class); order can matter if you use it in JavaScript (e.g. classList). Combining classes lets you reuse styles: one class for layout (e.g. "card"), one for type (e.g. "sensor-card"), one for state (e.g. "alert-critical"). Then in CSS you can target .card for all cards, .sensor-card for sensor cards only, and .alert-critical for critical state. That keeps markup flexible and avoids duplicating style rules.

Naming conventions help over time. Use lowercase and hyphens (kebab-case) for both class and id. Be consistent across the project: if you use "sensor-card" in one place, do not use "sensorCard" or "SensorCard" elsewhere for the same idea. Descriptive names (e.g. "coop-temperature-value", "alert-list", "main-content") make the DOM easier to read and maintain. Avoid very long names; if a name gets long, it may be a sign you are over-specifying (e.g. "battery-voltage-reading-display" might be "reading-value" with context from the parent). Prefixes like "js-" or "is-" are sometimes used to distinguish classes used only by JavaScript or to indicate state (e.g. "is-active"); that is optional but can help separate styling from behavior. When you add a new component (e.g. a new card type or form section), reuse existing class names where they fit (e.g. "card", "reading-value") and add new ones only when the component has a distinct role (e.g. "zone-schedule-row"). That keeps the stylesheet and script from growing with one-off names and makes the design system easier to maintain.

## 3) data-* Attributes for Custom Data

The data-* attributes let you store custom data on an element without adding semantics or built-in behavior. The name must start with "data-" followed by at least one character after the hyphen; the rest of the name can use lowercase letters, digits, and hyphens. For example, data-sensor-id, data-value, data-unit, and data-threshold are valid. The browser does not interpret these attributes; they are for your JavaScript or, in limited ways, CSS. Use data-* when you need to pass configuration, state, or identifiers to script (e.g. which sensor this card represents, what unit to display, what threshold to compare against). Do not use data-* for large or structured data; keep values short (ids, numbers, short strings). For complex data, fetch it via script or embed it in a script or JSON payload rather than in many data attributes. The data-* pattern was introduced in HTML5 to give authors a standard, valid way to store custom data without using non-standard or invalid attributes. Before data-*, authors sometimes used custom attributes that could conflict with future HTML attributes or cause validation errors; data-* is the safe, forward-compatible option for custom data on elements. You can have several data attributes on one element (e.g. data-sensor-id, data-unit, data-threshold); script can read all of them from dataset. Keep the set small and purposeful so the markup stays readable and the script's expectations are clear.

In JavaScript, data-* attributes are exposed on the element's dataset property. The attribute data-sensor-id becomes element.dataset.sensorId (camelCase in JavaScript). The attribute data-value becomes element.dataset.value. Hyphens in the attribute name become camelCase in dataset. In CSS, you can read data attributes with the attr() function in some contexts (e.g. content: attr(data-unit)), but attr() for other properties has limited support; data-* is most useful for JavaScript. Data attributes are useful for dashboard and sensor UIs: for example, a card might have data-sensor-id so when you click "Refresh" the script knows which sensor to request; a reading span might have data-unit="V" so the script can format the value with the unit. They keep the DOM as the source of configuration for the script without putting logic in the attribute value. Do not store sensitive data in data-* (e.g. passwords, tokens); data attributes are visible in the DOM and in markup. Do not use data-* to duplicate information that is already in the content (e.g. the visible text of a reading); use it for metadata the script needs (id, unit, type) that is not necessarily displayed or that supplements the visible content.

## 4) When to Use class, id, or data-*

Use class when you need to style or target a group of elements the same way. Use id when you need to reference exactly one element (anchor, ARIA, or script). Use data-* when you need to attach custom data to an element for script (or limited CSS use). Do not use id where class would work (e.g. do not give every card the same id). Do not use data-* for something that is only a styling hook; use class instead. Do not use data-* for semantic or accessibility information that has a dedicated attribute or element (e.g. use label and for for form labels, not data-label). Prefer class for styling and for "all elements of this type"; prefer id for "this specific element"; prefer data-* for "this value or identifier for script."

If an element needs both a class for styling and a unique id for an anchor or ARIA, give it both. If an element needs a class and a data attribute (e.g. data-sensor-id), use both. You can combine class, id, and one or more data-* attributes on the same element. Keep id unique, use class for repeated patterns, and use data-* only for data that script (or occasionally CSS) needs; do not overload attributes with meaning they do not have (e.g. data-* does not change how assistive technology interprets the element unless you use it in ARIA or script to expose state). When you are unsure whether to use class or data-*, ask: is this for styling or for grouping behavior? Use class. Is this a value or identifier that script needs (id, unit, type)? Use data-*. Is this the one element that must be referenced by link, ARIA, or script? Use id (and ensure it is unique). Keeping this rule simple—class for groups, id for one, data-* for script data—avoids overloading attributes and keeps the markup clear.

## 5) Boolean Attributes

Boolean attributes are attributes whose presence means true and whose absence means false. Examples include disabled (on form controls), readonly (on inputs), required (on inputs), multiple (on select), and checked (on checkboxes and radio buttons). In HTML5, you can write the attribute with no value (e.g. disabled) or with the attribute name as the value (e.g. disabled="disabled"); both mean true. Writing disabled="false" does not make the control enabled; the presence of the attribute means disabled. To make the control enabled, omit the disabled attribute entirely. The same applies to other boolean attributes: omit the attribute to mean false; do not set the value to "false" or "0".

This matters for dynamic content and script. When you enable or disable a button or input via script, remove the attribute to enable and set the attribute (with no value or value equal to the name) to disable. When you add a "required" field dynamically, add the required attribute; when you make it optional, remove the attribute. Screen readers and browsers rely on the presence or absence of the attribute; they do not interpret the string "false" as false. So for boolean attributes, think "present or absent" rather than "value true or false." Other common boolean attributes include multiple (on select, for multi-select), checked (on checkbox and radio), selected (on option in some legacy use), and hidden (to hide an element from the accessibility tree and visually when supported). The same rule applies: presence is true, absence is false. In templating or server-rendered HTML, ensure your pipeline does not output disabled="false" or required="false"; omit the attribute instead so the browser and assistive technology interpret the state correctly. When you toggle a control from disabled to enabled via script, remove the disabled attribute from the DOM (e.g. element.removeAttribute("disabled")); do not set disabled="false". Screen readers announce the state based on the presence or absence of the attribute, so keeping the rule consistent (present means true) avoids bugs and keeps behavior predictable across browsers and assistive technology.

## 6) Homestead Examples: class, id, and data-* in Practice

On a homestead dashboard, the main content area might have id="main-content" for the "skip to main content" link. Each section (e.g. "Battery status", "Solar production") might have an id for in-page links (e.g. id="section-battery", id="section-solar"). Cards or widgets might have class "card" or "sensor-card"; a card that shows a critical alert might also have class "alert-critical" so it can be styled differently. The voltage or temperature value inside might be in a span with class "reading-value" and perhaps data-unit="V" or data-unit="°F" so the script can format the number with the unit when it updates. A list of sensors might have each item with class "sensor-item" and data-sensor-id="freezer-1" so when the user clicks "Refresh" the script knows which sensor id to request from the API. Using both class (for shared behavior and styling) and data-* (for per-item data) is a common pattern: class says "this is a sensor item" and data-sensor-id says "this one is freezer-1."

For a coop door control, the button might have id="btn-coop-door" for focus management or ARIA, and class "btn btn-primary". The status text might be in a span with class "door-status" and data-door-id="coop" so script can update that element when the door state changes. For drip irrigation zones, each zone row might have class "zone-row" and data-zone-id="zone-1" so the script can send the right zone id when the user changes the schedule. For a form (e.g. alert thresholds), the form might have id="form-alert-settings" so you can target it for submission or validation; each input might have a class like "input-threshold" and data-input-type="temperature" so script can validate or format by type. For a table of sensor history, each row might have class "history-row" and data-sensor-id and data-timestamp so the script can sort, filter, or link to details. For a list of zones (drip or garden), each zone might have class "zone-item" and data-zone-id and data-zone-name so the script can update the right zone when the user edits. Combining class (for shared styling and behavior) with data-* (for instance-specific data) keeps the markup clean and makes the script's job straightforward: find elements by class, read instance data from data-*. When you add a new page or component, decide which elements need a unique id (e.g. main content, primary form, skip target), which need shared classes (e.g. all cards, all readings), and which need data-* (e.g. sensor id, zone id, unit). That keeps the attribute set minimal and consistent across the project. Reusing the same class and data-* names across pages (e.g. "reading-value", "sensor-card", data-sensor-id) makes it easier to write shared CSS and JavaScript and to maintain the codebase as it grows.

For electric fence or energizer status, a status block might have class "fence-status" and data-energizer-id so the script can poll the right device. For soil moisture or garden sensors, each reading might have class "moisture-reading" and data-sensor-id and data-zone. The pattern is the same: use id for the one element that must be uniquely referenced (main content, form, key controls); use class for repeated styling and behavior (cards, readings, buttons); use data-* for identifiers and small configuration (sensor id, zone id, unit, type) that script needs. For a Raspberry Pi or ESP32 device list, each row might have class "device-row" and data-device-id and data-device-type so the script can refresh or filter by device. For a live webcam or stream, the container might have id="stream-main" and the controls data-stream-id so the script knows which stream to start or stop. For alert history, each row might have class "alert-row" and data-alert-id for linking or refreshing. ## 7) What Breaks When Attributes Are Misused

Duplicate ids are the most common mistake. More than one element with the same id breaks in-page links (only the first is found), ARIA references (e.g. aria-labelledby may point to the wrong element), and getElementById (returns only one element). Fix by ensuring each id is unique in the document; use class for elements that share the same role or styling. Using id where class would work (e.g. giving every card id="card") is invalid and causes the same problems; use class for the repeated pattern and reserve id for the single element that must be referenced. Using spaces or invalid characters in id or class can break selectors or script; stick to letters, digits, and hyphens. Fix by renaming to valid, lowercase-with-hyphens values.

Using boolean attributes incorrectly (e.g. disabled="false" to enable) does not work; the control stays disabled because the attribute is present. Fix by removing the attribute to mean false. Using data-* for large or complex data makes the DOM heavy and is not the intended use; fix by storing data in script (variables, fetch) and using data-* only for small identifiers or configuration. Using presentational class or id names (e.g. "blue", "left") ties markup to one design; when you change styles, names become misleading. Fix by using descriptive names (e.g. "alert-critical", "reading-value"). Overusing data-* when class would suffice (e.g. data-style="card" instead of class="card") is redundant; use class for styling hooks and data-* for data. Storing sensitive data in data-* (e.g. API keys, tokens) is a security risk because the DOM and markup are visible; keep secrets in script or server-side only. Testing with validation (e.g. W3C validator) and with a screen reader or accessibility tree helps catch duplicate ids and misuse of attributes. If a form or control is not behaving as expected (e.g. label not associated with input, "skip to main" not working), check that ids are unique and that the for and href values match the id values exactly, including case and spelling. Typos in id (e.g. "main-content" in the markup but "maincontent" in the link) break in-page links and ARIA; use consistent naming and consider a lint or validation step to catch mismatches. For data-*, ensure the script reads the correct attribute name: dataset converts data-sensor-id to sensorId, so the script must use the camelCase form when reading from dataset.

## 8) Checklist for class, id, and data-*

When you add or change attributes, use this list. Keep id unique: only one element per id in the document. Use class for reusable styling and scripting (multiple elements, multiple classes per element). Use data-* for custom data that script (or limited CSS) needs; keep values short (ids, numbers, units). Use valid names: letters, digits, hyphen; no spaces in id; spaces in class only to separate multiple class names. Use descriptive, lowercase-with-hyphens names; avoid presentational names. For boolean attributes (disabled, readonly, required, etc.), omit the attribute to mean false; do not set value to "false". When you have many similar elements (e.g. sensor cards), use class for the type and data-* for the instance data (e.g. data-sensor-id); reserve id for the single element that must be referenced (main content, form, key control). Verify with a validator that ids are unique and attribute names and values are valid. When you add a new id (e.g. for a new section or form), search the document for that id to avoid duplicates. When you use data-* for script, ensure the script reads the attribute (e.g. via dataset) and that the attribute name matches what the script expects (remember the hyphen-to-camelCase conversion in dataset). ## Common Pitfalls

Duplicate ids: Only one element per id; duplicate ids break in-page links, ARIA, and getElementById. Use class for repeated patterns.

Using id for repeated elements: If many elements share the same id, the document is invalid. Use class to target the group and id only for the one element that must be uniquely referenced.

Boolean attribute value "false": Writing disabled="false" does not enable the control; the attribute is still present. Omit the attribute to mean false.

Presentational names: Class or id names like "blue" or "left" break when design changes. Use descriptive names (e.g. "alert-critical", "reading-value").

data-* for styling only: If you only need a styling hook, use class. Reserve data-* for data that script or CSS needs (ids, units, configuration).

Invalid characters or spaces in id/class: Spaces in id are invalid; spaces in class separate multiple classes. Use letters, digits, hyphen; start with a letter. Avoid special characters that can break CSS selectors or script (e.g. dots or colons unless you know the context).

## Summary

Use class for reusable styling and scripting; many elements can share a class and one element can have multiple classes. Use id for a unique identifier (one element per id) for anchors, ARIA, and script. Use valid, descriptive names (lowercase-with-hyphens); avoid presentational names. Use data-* for custom data that JavaScript (or limited CSS) needs—sensor id, unit, threshold—and keep values short; do not store sensitive data in data-*. Boolean attributes (disabled, readonly, required, etc.) are true when present; omit them to mean false; do not use "false" as the value. Homestead UIs use id for main content and key controls, class for cards and readings, and data-* for sensor id, zone id, and units so script can update and format correctly. Use the checklist in section 8 when adding or changing attributes so ids stay unique, names stay valid, and data-* is used only for script-relevant data.
