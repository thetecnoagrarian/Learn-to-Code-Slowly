# Section B Phase 2 · Chapter 2.18: ARIA and Accessibility Attributes

This chapter covers when and how to use ARIA (Accessible Rich Internet Applications) attributes to expose roles, names, and state to assistive technology when native HTML is not enough. It builds on Chapter 2.17 (Attributes — class, id, data-*) and the semantic structure from Chapters 2.14–2.16; here we focus on aria-label, aria-labelledby, aria-describedby, roles, and live regions for dynamic content. Chapter 2.19 (Character Entities and Encoding) then covers how to represent special characters correctly in text and attributes.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use aria-label and aria-labelledby when visible text is missing or insufficient for a control or region so screen-reader users get a clear name.
- Use aria-describedby when additional description (beyond the label) is needed; understand the difference between label (name) and description (extra context).
- Use ARIA roles when native HTML does not convey the right semantics (e.g. custom widgets built with div and script).
- Understand live regions (aria-live) for dynamic content that updates without a full page reload; choose polite or assertive as appropriate.
- Prefer semantic HTML over ARIA when an element already exists; avoid redundant or conflicting ARIA.

## Key Terms

- **ARIA**: Accessible Rich Internet Applications; a set of attributes that supplement HTML so assistive technology can expose roles, names, state, and relationships when native semantics are missing or insufficient.
- **aria-label**: An attribute that provides a short text name for an element when there is no visible label (e.g. an icon button); the value is announced by screen readers as the element's accessible name.
- **aria-labelledby**: An attribute that references the id(s) of one or more elements that together form the accessible name for this element; used when the label exists elsewhere in the DOM.
- **aria-describedby**: An attribute that references the id(s) of one or more elements that provide additional description (not the name) for this element; screen readers may announce it after the name.
- **aria-live**: An attribute that marks a region as "live" so screen readers announce changes (e.g. new alerts, updated readings); values include "polite" (announce when idle) and "assertive" (announce soon). role="alert" implies assertive live; role="status" implies polite live.

## 1) When to Use ARIA

ARIA fills gaps when HTML has no element or attribute that conveys the right semantics or name. Use ARIA when you need to expose a role, name, or state that native HTML does not provide. For example, if you build a custom control with a div and JavaScript (e.g. a slider or a toggle that is not a native button or checkbox), you add an ARIA role and often an aria-label or aria-labelledby so assistive technology knows what it is and what it is called. If you have an icon-only button (e.g. refresh, close, menu) with no visible text, you add aria-label so screen-reader users hear a meaningful name instead of "button" or nothing. If you have a region that updates dynamically (e.g. a list of alerts or a live sensor value), you can use aria-live so the update is announced.

Prefer native HTML whenever it fits. Use button for buttons, nav for navigation, main for main content, label and for for form labels, and so on. Native elements get correct behavior, keyboard support, and semantics without extra attributes. Use ARIA when you cannot use the native element (e.g. a custom widget), when the native element has no visible label and needs a name (e.g. icon button), or when you need to expose dynamic updates (aria-live). For example, a div that looks and acts like a button but is not a button element needs role="button" and an accessible name, and it must be focusable and activatable with Enter and Space. A span or div that only shows an icon and is clicked to refresh data needs either a visible label (e.g. "Refresh") or aria-label="Refresh" so screen-reader users know what it does. A region that displays the latest sensor value and updates via script can have aria-live="polite" and an aria-label so when the value changes, the user hears the update in context. Do not use ARIA to override or duplicate semantics that the element already has; for example, do not put role="button" on a button element. That is redundant and can cause inconsistent behavior. Think of ARIA as a supplement: use it when HTML is not enough, not as a replacement for good structure. When you are unsure, ask: does this element already have the right role and name from HTML? If yes, do not add ARIA for that. If the element is custom (e.g. a div that behaves as a button), add the role and ensure it is keyboard operable and has an accessible name. If the element has no visible label (e.g. an icon), add aria-label. If content updates and users should hear the update, consider a live region. That keeps ARIA focused and avoids overuse.

## 2) Labeling: aria-label, aria-labelledby, aria-describedby

Assistive technology needs an accessible name for interactive elements and for landmarks or regions when they are listed. The accessible name is what screen readers announce (e.g. "Refresh button", "Main navigation"). When there is no visible text that serves as the label, or when the visible text is not programmatically associated, you provide a name via aria-label or aria-labelledby. aria-label gives a short string directly: for example, aria-label="Refresh sensor data" on a button that only shows an icon. Use it when the label is short and not visible (or not sufficient). aria-labelledby references the id of one or more elements (e.g. a heading or a label element) whose text should form the name. Use it when the label already exists in the page and you want to associate it with another element (e.g. a chart that is labeled by a heading with id="chart-heading" can have aria-labelledby="chart-heading"). Only one of aria-label or aria-labelledby should be used on an element; if both are present, aria-labelledby takes precedence in most cases. Give each control or region at most one accessible name; avoid duplicate or redundant labels. If the element has visible text that already serves as its label (e.g. a button that says "Submit"), you usually do not need aria-label; the visible text is the accessible name. Add aria-label only when the visible text is missing, insufficient, or not programmatically associated (e.g. the label is in a different part of the layout and not tied to the control via label and for or aria-labelledby).

aria-describedby provides additional description that is not the name. Screen readers typically announce the name first, then the description (e.g. "Refresh button. Fetches the latest readings from the sensor."). Use aria-describedby when you have help text, instructions, or context that is already in the DOM and you want it associated with the control or region. The referenced element(s) can be visible or visually hidden; what matters is that the content is in the DOM so assistive technology can read it. Do not put long blocks of text in aria-label; keep the label short. Use aria-describedby for longer or supplementary content. For form inputs, prefer the native label element with for; use aria-label or aria-labelledby when a visible label is not possible or when you need to reference a label that is not the standard label element. When you have multiple regions of the same type (e.g. two asides), give each an aria-label so screen-reader users can tell them apart when listing landmarks (e.g. "Active alerts" and "Quick links"). The same applies to multiple nav elements: use aria-label to distinguish "Main navigation" from "Footer links". Do not use aria-label to repeat visible text that is already the only content of the element; that can cause double announcement. Use it when the accessible name would otherwise be missing or wrong (e.g. an icon button where the icon has no text alternative).

## 3) Roles and Live Regions

The role attribute exposes the type of widget or structure to assistive technology (e.g. role="button", role="alert", role="status"). Use role when you have built a custom control (e.g. a div that acts as a button) and there is no native element; the role tells the screen reader how to treat it. You must then ensure keyboard behavior and state match the role (e.g. a role="button" must be activatable with Enter and Space and must not be used for navigation). Do not add a role to an element that already has that role (e.g. do not add role="button" to a button). Some roles are implied by HTML (e.g. main has role main); only add role when the element would not otherwise have the right one. For custom widgets, reference the ARIA authoring practices or similar guidance so the role, keyboard behavior, and any state attributes (e.g. aria-expanded, aria-pressed) are correct.

Live regions announce changes. When content updates without a full page reload (e.g. new alert, updated temperature, new item in a list), screen-reader users may not notice unless the region is marked as live. aria-live="polite" means the screen reader should announce the change when it is idle (not interrupting current speech). aria-live="assertive" means the announcement can interrupt. Use polite for most updates (e.g. "Battery voltage updated to 12.4 volts"). Use assertive for urgent alerts (e.g. "Critical: freezer temperature above threshold"). The role="alert" is a live region that is assertive and is announced as an alert. The role="status" is a live region that is polite and is for status updates. Use them when you have dynamic content that should be announced; avoid marking large or frequently updating regions as live if the announcements would be noisy. Give live regions an accessible name (aria-label or aria-labelledby) when it helps context (e.g. "Battery voltage" so the user knows what was updated). Not all screen readers announce the name with every update; some announce only the changed content. Still, providing a name helps when the user navigates to the region or when the reader does announce it. Avoid marking the entire main content as a live region; that would announce every change on the page and create noise. Limit live regions to specific containers (e.g. the alerts list, the battery status block, the sensor value that updates). Use aria-atomic="true" if the whole region should be re-announced when any part of it changes; use aria-atomic="false" (the default) so only the changed part is announced. For a single updating value (e.g. "12.4 V"), false is usually enough; for a list where new items are added, you may want the new item announced without re-reading the whole list.

## 4) When Not to Overuse ARIA

Do not add ARIA when native HTML already provides the semantics. Redundant ARIA (e.g. role="button" on a button, or aria-label on an element that already has a visible, associated label) can cause duplicate announcements or inconsistent behavior. Prefer semantic elements: use button, not div with role="button", unless you have a specific reason. Use main, nav, section, article, header, footer, and so on so that landmarks and structure come from the elements. Add ARIA only when the element does not have the right role or name.

Do not use ARIA to fix bad structure. If a form control has no label, the right fix is to add a label element (or visible text and aria-labelledby), not only aria-label, when a visible label is appropriate. If the page has no main landmark, use the main element rather than div with role="main". Use ARIA to supplement, not to substitute for, proper HTML. Avoid over-announcing: do not set aria-live on every changing region; reserve it for updates that users need to hear. Do not use role or aria-* to convey visual-only information (e.g. "red" or "left"); use it for semantics that assistive technology can use. Test with a screen reader or accessibility tree to confirm that the names and roles you expect are exposed and that nothing is redundant or confusing. Browsers expose an accessibility tree in dev tools; you can inspect an element to see its accessible name, role, and other properties. That helps verify that aria-label, aria-labelledby, and role are applied correctly before testing with a real screen reader. When you add a new control or region, run through the checklist: does it have a name? Does it have the right role (if it is custom)? If it updates dynamically, should it be a live region? If you use native HTML (button, main, nav, label), you often need no ARIA at all. When you copy a pattern from another page (e.g. an icon button or a status block), ensure the ARIA is appropriate for the new context: update the aria-label to match the new button's action or the new region's content, and do not leave placeholder or generic labels in place.

## 5) When to Use What

Use aria-label when an interactive element or region has no visible label and you need to give it a short name (e.g. icon button, icon-only link). Use aria-labelledby when the label exists elsewhere in the DOM and you want to reference it by id. Use aria-describedby when you have additional description (help text, instructions) that should be announced after the name. Use role when you have a custom widget (e.g. div that acts as a button) and no native element; then ensure keyboard and state match. Use aria-live (or role="alert" or role="status") when content updates dynamically and the update should be announced. Prefer native HTML (button, label, main, nav, etc.) when it fits; use ARIA only when semantics or name are missing or insufficient. Do not add ARIA that duplicates or conflicts with native semantics or with visible text.

## 6) Homestead Examples: ARIA in Practice

On a homestead dashboard, icon-only buttons are common: refresh, settings, open coop, close door. Each needs an aria-label (e.g. "Refresh battery data", "Open coop door") so screen-reader users know what the button does. A chart or graph that has no text caption can have aria-labelledby pointing to a heading (e.g. "Solar production") and optionally aria-describedby for a short summary. A status block that shows "Battery: 12.4 V" and updates when new data arrives can be a live region: use role="status" and aria-live="polite", and give it an aria-label such as "Battery voltage" so when the value updates, the user hears "Battery voltage: 12.4 volts" (or similar). An alert panel that shows critical messages (e.g. "Freezer temperature high") can use role="alert" so the message is announced immediately when it appears.

For a coop door control, the button that opens or closes the door should have a clear label (visible text or aria-label). If the control is a custom widget (e.g. a toggle switch built with a div), use role="switch" or the appropriate role and aria-label, and ensure it is keyboard operable and that aria-checked or state is updated. For sensor cards or device lists, each card can have an aria-label or aria-labelledby so when the user navigates by card they hear the sensor name. For a form (e.g. alert thresholds), use native label and for; if a field has additional help text, associate it with aria-describedby. For an aside that shows "Active alerts", give the aside an aria-label (e.g. "Active alerts") so when the user lists landmarks they get a meaningful name. For dynamic lists (e.g. recent events or alert history), consider whether the list or the container should be a live region so new items are announced; use polite for non-urgent updates. Avoid making the whole main content a live region; limit updates to the specific blocks that change (e.g. the battery status div, the alerts list). For drip irrigation or zone controls, a button that runs a zone might need aria-label if it is icon-only (e.g. "Run zone 1"). For electric fence or energizer status, a status block that updates when the voltage is polled can be role="status" with aria-live="polite" and aria-label="Fence voltage". For soil moisture or garden sensors, each reading that updates can live in a container with role="status" so updates are announced. For a Raspberry Pi or ESP32 device list, if the list is updated when devices come online or go offline, consider a live region on the list container with polite so new items are announced without interrupting. For forms (e.g. alert thresholds), use native label and for; if a field has validation messages that appear dynamically, you can use role="alert" on the message container so the error is announced when it appears. Consistency across the dashboard (e.g. all icon buttons have aria-label, all status blocks that update have role="status") makes the experience predictable for assistive technology users. ## 7) What Breaks When ARIA Is Wrong or Overused

Redundant ARIA (e.g. role="button" on a button) can cause duplicate or conflicting announcements. Fix by removing the redundant role or attribute. Missing labels when there is no visible text (e.g. icon button with no aria-label) leave screen-reader users with no name or a generic "button". Fix by adding aria-label (or visible text and aria-labelledby). Conflicting semantics (e.g. role="button" on a link, or aria-pressed on a non-button) can confuse assistive technology and users. Fix by using the correct native element or the correct role and keyboard behavior for the control. Overuse of aria-live (e.g. on a region that updates every second) can make the screen reader announce constantly and distract the user. Fix by reserving live regions for updates that matter and using polite for non-urgent updates. Incorrect or missing keyboard support for a custom widget with a role (e.g. role="button" but not activatable with Enter or Space) makes the control unusable for keyboard users. Fix by implementing the keyboard behavior that matches the role. Referencing a non-existent id in aria-labelledby or aria-describedby means the name or description is empty. Fix by ensuring the referenced id exists and is unique. Using role without implementing the behavior (e.g. role="tablist" without keyboard navigation between tabs) leaves keyboard and screen-reader users without a way to use the widget. Fix by either using the native element (e.g. buttons or links for tabs) or implementing the full keyboard and ARIA state pattern for the role. Testing with a screen reader or the accessibility tree in dev tools helps catch these issues before they affect users. When debugging "why doesn't the screen reader say X?", check the accessibility tree for the element's accessible name and role; often the issue is a missing aria-label, a wrong id in aria-labelledby, or redundant ARIA that overrides the expected name.

## 8) Checklist for ARIA and Accessibility

When you add or change controls or regions, use this list. Prefer native HTML (button, label, main, nav, etc.) when it fits. Use aria-label for icon-only buttons and controls with no visible label; use aria-labelledby when the label is elsewhere in the DOM. Use aria-describedby for extra description (help text) when needed. Use role only for custom widgets that have no native element; ensure keyboard and state match the role. Use aria-live (or role="alert" or role="status") only for dynamic content that should be announced; use polite for normal updates and assertive or alert for urgent ones. Do not add ARIA that duplicates native semantics or visible text. Ensure every interactive element and every landmark or region that is listed has an accessible name. Test with a screen reader or accessibility tree to verify names, roles, and live region behavior. When you add a new icon button, give it an aria-label before you consider the control done. When you add a new dynamic block (e.g. a status that updates), decide whether it should be a live region and add role="status" or role="alert" and aria-live as appropriate. When you add a new landmark (e.g. an aside or a nav), give it an aria-label if there are multiple of the same type so users can distinguish them. ## Common Pitfalls

Redundant ARIA: Do not add role="button" to a button or aria-label that repeats visible text. Remove redundant ARIA so announcements are not duplicated.

Icon-only controls without a name: An icon button or link with no visible text and no aria-label is announced as "button" or "link" with no context. Always add aria-label (or visible text) for icon-only controls.

Overusing aria-live: Marking every updating region as live causes constant announcements. Reserve live regions for updates that users need to hear; use polite for most.

Custom widget without keyboard support: Adding role="button" (or similar) without making the element keyboard activatable makes it unusable for keyboard users. Implement the keyboard behavior that matches the role.

Missing or wrong id in aria-labelledby/aria-describedby: If the referenced id does not exist or is wrong, the name or description is empty. Ensure the id is unique and correct.

Conflicting role and element: Do not use role="button" on a link or role="heading" on a button unless you have a specific, correct reason. Match the role to the element and behavior. Test with the accessibility tree in dev tools to confirm the exposed name and role match what you intend.

## Summary

Use ARIA when native HTML does not provide the right semantics or name. Use aria-label for short names when there is no visible label (e.g. icon buttons); use aria-labelledby to reference an existing label by id; use aria-describedby for additional description. Use role for custom widgets that have no native element; ensure keyboard and state match the role. Use aria-live (or role="alert" or role="status") for dynamic content that should be announced; prefer polite for most updates. Prefer semantic HTML over ARIA; avoid redundant or conflicting ARIA. Homestead dashboards use aria-label on icon buttons (refresh, door control, settings), live regions for status and alerts, and clear names for charts and regions. Test with a screen reader or accessibility tree to verify behavior. Use the checklist in section 8 when you add or change controls, regions, or dynamic content so names and roles stay correct and live regions are used only where they add value.
