# Section B Phase 2 · Chapter 2.19: Character Entities and Encoding

This chapter covers when and how to escape special characters in HTML using character entities (named and numeric), and how character encoding (UTF-8 and meta charset) ensures characters display correctly. It builds on Chapter 2.18 (ARIA and Accessibility) and the attribute and markup work in earlier chapters; here we focus on the characters that have special meaning in HTML and how to represent any character safely. Chapter 2.20 (Block and Inline) then covers how block-level and inline elements affect layout and nesting.

## Learning Objectives

By the end of this chapter, you should be able to:
- Escape reserved characters in HTML using named entities (ampersand, less-than, greater-than, quote, apostrophe) or numeric entities so they are not interpreted as markup.
- Know when to use entities in text content and in attribute values versus when you can type the character directly.
- Relate character encoding (UTF-8, meta charset) to correct display of characters and when entities are still required.

## Key Terms

- **character entity**: A way to represent a character in HTML that would otherwise be interpreted as markup or that is hard to type; named (e.g. &amp;, &lt;) or numeric (e.g. &#160;, &#x00A0;).
- **named entity**: An entity that uses a name between & and ; (e.g. &amp; for ampersand, &lt; for less-than, &quot; for double quote).
- **numeric entity**: An entity that uses a decimal (&#number;) or hexadecimal (&#xhex;) code point (e.g. &#169; or &#x00A9; for copyright). Use when there is no named entity or when you have the Unicode code point (e.g. from a character map or from script).
- **character encoding**: The mapping between bytes in a file and characters (e.g. UTF-8); the browser uses it to interpret the document; declared with meta charset or HTTP header. When the encoding is correct (e.g. UTF-8 file and UTF-8 declared), most characters can be typed directly; entities are still required for the five that have special meaning in HTML (ampersand, less-than, greater-than, and in attribute values quote and apostrophe when they would end the value).

## 1) Why Character Entities Exist

Some characters have special meaning in HTML. The less-than sign starts a tag; the greater-than sign can end it; the ampersand starts an entity. If you want to display those characters as text (e.g. "x &lt; y" or "Smith &amp; Sons"), you must escape them so the parser does not treat them as markup. Use the less-than entity for less-than, the greater-than entity for greater-than, and the ampersand entity for ampersand. In attribute values, the double quote that delimits the value is special: if the attribute value itself contains a double quote, you must escape it with the quote entity so the parser does not treat it as the end of the value. The apostrophe is less often a problem in double-quoted attributes; you can usually type it as-is. In single-quoted attribute values, the apostrophe would end the value, so you use the apostrophe entity there if the value contains an apostrophe.

When you forget to escape these characters, the page can break. A bare less-than in text may be interpreted as the start of a tag; the browser may then hide or misparse content until it finds a closing angle bracket or gives up. A bare ampersand can be interpreted as the start of an entity; if what follows is not a valid entity name or number, the result is undefined or a broken display. So in text content and in attribute values, always escape ampersand, less-than, and greater-than when you mean them as literal characters; escape double quote inside double-quoted attributes when the value contains a quote; escape apostrophe inside single-quoted attributes when the value contains an apostrophe. The same rule applies inside script or style elements when the content is HTML: if you are writing a string in JavaScript or CSS that will be output as HTML, any ampersand, less-than, or greater-than in that string that could be seen by the HTML parser must be escaped in the HTML source. When the content is in a separate file (e.g. an external script or stylesheet), that file has its own encoding and the HTML entity rules apply only when that content is inlined into the HTML document.

## 2) Named and Numeric Entities

Named entities use a short name between ampersand and semicolon. Common ones include the ampersand entity (for ampersand), the less-than entity (for less-than), the greater-than entity (for greater-than), the quote entity (for double quote), and the apostrophe entity (for apostrophe). Others include non-breaking space, copyright, and symbols like degree or trademark. Named entities are easy to read and remember for the most common characters. Numeric entities use a decimal or hexadecimal Unicode code point: &#decimal; or &#xhex;. For example, the copyright symbol can be written as a decimal entity or a hex entity. Numeric entities work for any Unicode character, even if there is no named entity. Use numeric when the character has no named entity or when the name is hard to remember; use named when the character has a well-known name (ampersand, less-than, greater-than, quote, apostrophe, non-breaking space, and a few others). The HTML standard defines a long list of named entities for symbols, accented letters, and special characters; for many of those, in a UTF-8 document you can type the character directly instead of the entity. The five that you must use when the character appears as content or in an attribute value are ampersand, less-than, greater-than, double quote (inside double-quoted attributes), and apostrophe (inside single-quoted attributes).

The semicolon terminates the entity. In HTML5, for many named entities the semicolon can be omitted in some contexts and the parser will still infer the end of the entity, but always including the semicolon avoids ambiguity and is good practice. For numeric entities, the semicolon is required. Entity names are case-sensitive in some legacy contexts; the standard named entities use lowercase names. When you need a character that is not on your keyboard or that would be ambiguous in HTML, look up its Unicode code point and use a numeric entity, or use a named entity if one exists. Reference documentation (e.g. MDN or the HTML spec) lists the full set of named entities; for day-to-day work, the five mandatory ones (ampersand, less-than, greater-than, quote, apostrophe) and optionally non-breaking space, copyright, and degree are the ones you will use most often. Numeric entities are useful when you need a character that has no name or when you are generating HTML programmatically and have a Unicode code point.

## 3) UTF-8 and meta charset

Character encoding determines how the browser interprets the bytes in the document. UTF-8 is an encoding that can represent every character in Unicode: ASCII characters (letters, digits, common symbols) use one byte; many other characters use two or more bytes. When the document is saved as UTF-8 and the browser is told to use UTF-8, you can type most characters directly (e.g. degree sign, accented letters, symbols, or characters from other scripts) and they will display correctly. You do not need an entity for those characters as long as the file is actually saved in UTF-8 and the encoding is declared. UTF-8 is the recommended encoding for web content: it is widely supported, avoids the need for entities for most characters, and matches what many editors and tools use by default. Older encodings (e.g. ISO-8859-1, Windows-1252) support only a limited set of characters; if your content includes symbols or characters outside that set, UTF-8 and the correct declaration are the way to get them to display reliably.

The browser needs to know the encoding. In HTML5, you declare it with a meta charset tag in the head: the meta element with charset set to UTF-8. That should be early in the head so the browser can interpret the rest of the document correctly. The server can also send the encoding in the HTTP Content-Type header (e.g. charset=utf-8); the header takes precedence if present. If the declared encoding does not match the actual file encoding (e.g. the file is in Latin-1 but the page says UTF-8), characters outside ASCII can display as mojibake (wrong or replacement characters). So save your HTML files as UTF-8 and declare UTF-8 in the meta charset; then you can use most characters directly and reserve entities for the few that have special meaning in HTML (ampersand, less-than, greater-than, and quote or apostrophe when needed in attributes). When you copy text from a web page or document into your HTML, check that the source encoding matches what you expect; pasted characters can sometimes be the wrong byte sequence for your file encoding. Using an editor that shows the current encoding and lets you save as UTF-8 helps avoid mismatches. For content delivered by a server (e.g. from a database or template), ensure the response is sent with the correct charset so the browser interprets it as UTF-8 or whatever encoding you use.

## 4) When to Use Entities vs When Not To

Use entities when the character has special meaning in HTML and you want it to display as text: ampersand, less-than, greater-than in content, and double quote or apostrophe when they would end an attribute value. Use entities when you cannot type the character (e.g. an old editor or system that does not support UTF-8) and you know the numeric or named entity. Use numeric entities when you need a character that has no named entity. Use named entities for the common special characters (ampersand, less-than, greater-than, quote, apostrophe, non-breaking space) so the markup stays readable.

Do not use entities when the character has no special meaning and the document is UTF-8: you can type the degree sign, accented letters, copyright, or other symbols directly if the file is saved as UTF-8 and the encoding is declared. Typing the character directly is often easier to read and maintain than a numeric entity. Do not over-escape: for example, do not use an entity for a regular space or for letters; use entities only when necessary. In JavaScript or CSS that is embedded in HTML (e.g. in a script or style element), the same rules apply for the string content: if a string contains a less-than or ampersand that the HTML parser will see, it must be escaped in the HTML source so the parser does not treat it as the start of a tag or entity. When the content is generated by script (e.g. textContent or innerText), the script uses the character directly; the DOM is not HTML at that point, so no HTML entities are needed there. If you build HTML strings in script (e.g. innerHTML or insertAdjacentHTML), you must escape the five special characters in the data you insert, or use a method that does not parse the string as HTML (e.g. textContent) so that user or sensor data cannot accidentally inject tags or entities. Escaping on the server or in the script before concatenating into HTML is the safe approach when the content comes from user input or external data.

## 5) When to Use What

For ampersand, less-than, and greater-than in text or attribute values: always use the named entities (or numeric equivalents) so they are not interpreted as markup. For double quote inside a double-quoted attribute value: use the quote entity. For apostrophe inside a single-quoted attribute value: use the apostrophe entity. For other characters in a UTF-8 document: type them directly if your editor and file encoding support it; use a numeric entity only if you cannot type the character or need to avoid encoding issues. For non-breaking space: use the named entity if you need it (e.g. to prevent a line break between a number and unit). For copyright, degree, or similar symbols in UTF-8: you can type the character or use the named or numeric entity; consistency is more important than which you choose. When in doubt, escape the five special characters (ampersand, less-than, greater-than, quote, apostrophe) where they appear as content or inside attribute values; for everything else in UTF-8, typing the character is usually fine. In titles (page title or heading), in alt text, in aria-label or placeholder, and in any attribute value that is shown to users, the same rules apply: if the value contains ampersand, less-than, or greater-than, use entities so the HTML is valid and the parser does not misread the value. For content that is purely in the body (e.g. a paragraph or list item), escape those three and any quote or apostrophe that would break an attribute if the same text were used in an attribute. Keeping the habit "escape ampersand, less-than, and greater-than in content and in attributes; escape quote and apostrophe when they would end an attribute value" covers almost all cases.

## 6) Homestead Examples: Character Entities and Encoding in Practice

On a homestead dashboard, labels and values often include symbols. A temperature reading might show "23 °C" or "75 °F": the degree symbol can be typed directly in a UTF-8 file or written as a named or numeric entity. A voltage reading might show "12.4 V": the "V" is plain text; no entity needed. If a label says "Battery voltage & state" you must escape the ampersand so it is not parsed as the start of an entity: use the ampersand entity between "voltage" and "state". If you display a comparison in text (e.g. "Alert when temp &lt; 10 °C"), the less-than must be escaped so the browser does not treat it as the start of a tag. Alert messages or form placeholders that contain quotes (e.g. "Enter \"coop\" or \"barn\"") need the inner quotes escaped if they are in an attribute value.

Sensor names, zone names, or dropdown options that contain special characters (e.g. "Smith &amp; Sons Farm", "Temp &lt; 0") require entities in the HTML where those strings appear in content or in attributes. For a page title or heading that includes ampersand, less-than, or greater-than, use entities so the parser does not treat them as markup. For table cells, list items, or any visible text that comes from data (e.g. sensor name, zone name, alert message), escape the data when you insert it as HTML; if you insert as text (e.g. via textContent), the browser will display the characters and you do not need HTML entities, but then you also cannot include raw HTML in that content. For copyright or unit symbols in a footer (e.g. "© 2025" or "°F"), UTF-8 and meta charset let you type the character directly. If you generate HTML from a script (e.g. from sensor data), you must escape any ampersand, less-than, greater-than, and relevant quotes in the data before inserting it into the HTML, or use a method that does not interpret the data as HTML (e.g. textContent) so the browser does not parse it as markup. For forms, placeholder or title attributes that contain quotes or ampersands must use entities so the attribute value is well-formed. Keeping the file in UTF-8 and declaring it with meta charset avoids encoding problems; escaping the five special characters where they appear keeps the markup valid and the display correct. For coop or barn labels, drip zone names, or alert text that might contain "&" or "less-than" (e.g. "Door & sensor" or "Temp &lt; threshold"), always escape in the HTML. For units and symbols (°, ©, Ω, V, °F), UTF-8 and meta charset are enough; type the character. For forms, any default value or placeholder that includes quotes or ampersands must use entities in the attribute value so the value is well-formed and the parser does not cut the value short. For electric fence or energizer status, labels like "Voltage &amp; status" need the ampersand escaped. For soil moisture or garden zones, "Zone 1 &amp; 2" or "Reading &lt; 10%" require entities. For solar or battery dashboards, "Charge &amp; voltage" or "Temp &lt; 5 °C" are typical; the degree symbol can be typed in UTF-8. For dropdowns or options built from data (sensor names, zone names), escape any ampersand or less-than when building the HTML. For alert history or log tables, escape each cell's message text on insert or insert as text so it is not parsed as HTML. ## 7) What Breaks When Entities or Encoding Are Wrong

Leaving ampersand, less-than, or greater-than unescaped in content or in attribute values can break the page. The HTML parser does not know that you meant them as text; it interprets them as the start of a tag or an entity. So the first rule is: always escape those three when they are literal content. Leaving them unescaped is one of the most common causes of "disappearing" content or broken layout when the content or data contains "&" or "&lt;". A bare less-than may be interpreted as the start of a tag; content after it may disappear or be misparsed until the parser finds a closing bracket or recovers. A bare ampersand may start an entity; if the following text is not a valid entity, the result may be a broken character or nothing. Fix by always escaping these three in text and in attribute values. Using the wrong entity (e.g. a typo in the entity name) can result in the entity being displayed literally (e.g. "&amp;" on screen) or in parse errors; fix by using the correct named or numeric entity and ending with a semicolon.

Declaring one encoding (e.g. UTF-8) while the file is saved in another (e.g. Windows-1252 or Latin-1) causes mojibake: characters outside ASCII display as wrong or replacement characters. Fix by saving the file as UTF-8 and declaring UTF-8 in meta charset (and ensuring the server does not send a conflicting charset). Omitting the meta charset tag can cause the browser to guess the encoding, which may be wrong for non-ASCII characters; include the meta charset early in the head. Putting a character that looks like a less-than or greater-than (e.g. from a word processor) instead of the actual ASCII character can confuse validators or parsers; use the real ASCII characters and escape them when they are content. In attribute values, an unescaped double quote inside a double-quoted value ends the value early and can break the element or the layout; escape the quote with the quote entity. When you use a templating system or server-side rendering, ensure that variables that are inserted into HTML are escaped for HTML (ampersand, less-than, greater-than, quote, apostrophe) so that user input or database content cannot break the structure or introduce unwanted tags. Many templating engines escape by default; if you disable escaping or mark content as "raw", you are responsible for ensuring the content is safe. Validating your HTML with a validator can catch some unescaped characters; manual review of any place where dynamic content is inserted is also important. When debugging "missing" or wrong text on the page, check whether the content contains an unescaped ampersand or less-than that the parser has interpreted as the start of a tag or entity; fixing the entities often resolves the issue.

## 8) Checklist for Character Entities and Encoding

When you add or edit text or attribute values in HTML, use this list. Escape ampersand, less-than, and greater-than whenever they appear as literal content or inside attribute values; use the named entities (or numeric) and end with a semicolon. Inside double-quoted attribute values, escape any double quote that is part of the value with the quote entity; inside single-quoted values, escape any apostrophe with the apostrophe entity. Save HTML files as UTF-8 and include the meta charset tag for UTF-8 early in the head so the browser interprets the file correctly. For other characters (degree, copyright, accented letters), in UTF-8 you can type them directly; use numeric entities only if you cannot type the character or need to avoid encoding issues. When you insert user-provided or sensor data into the page, escape it for HTML if it is inserted as markup, or use a safe method (e.g. textContent) so the data is not parsed as tags or entities. When you copy text from another source (e.g. a doc or web page), check that ampersands and angle brackets are escaped if they are meant to be displayed as text. Validate the document to catch unescaped special characters or encoding mismatches. When you add a new form, label, or dynamic section, decide whether the content is static (you control the HTML) or dynamic (user or sensor data); for dynamic content inserted as HTML, escape the five special characters or use a safe insertion method. ## Common Pitfalls

Unescaped less-than or ampersand in content: The parser treats them as the start of a tag or entity; content can disappear or break. Always use the less-than entity and ampersand entity when they are literal text.

Wrong or missing encoding: Declaring UTF-8 while the file is in another encoding (or vice versa) causes mojibake. Save as UTF-8 and declare UTF-8 in meta charset.

Unescaped quote in attribute value: A double quote inside a double-quoted value ends the value early. Use the quote entity for literal quotes in the value.

Forgetting the semicolon: Some entities are recognized without it, but omitting the semicolon can cause ambiguity. Always end entities with a semicolon.

Using entities when the character would do: In UTF-8 you can type degree, copyright, and accented letters directly; reserve entities for the five special characters (ampersand, less-than, greater-than, quote, apostrophe) where needed.

Inserting unescaped data into HTML: If you build HTML from data (e.g. sensor names, zone names, alert text), escape ampersand, less-than, greater-than, and quotes in the data before concatenating into HTML, or insert as text (e.g. textContent) so it is not parsed as markup. Unescaped user or sensor data can also create security or correctness issues (e.g. broken layout or unintended script execution) if the data is later interpreted as HTML.

## Summary

Use character entities to escape characters that have special meaning in HTML: ampersand, less-than, greater-than, and (in attribute values) double quote and apostrophe when they would end the value. Use named entities for these common characters; use numeric entities for any Unicode character when there is no named entity or when you need a specific code point. Save HTML files as UTF-8 and declare UTF-8 with meta charset so most characters can be typed directly; entities are still required for the five special characters when they appear as content or in attribute values. Homestead pages use entities for ampersand in labels (e.g. "Battery &amp; solar"), for less-than in comparisons (e.g. "temp &lt; 10"), and for quotes in attribute values; degree and other symbols can be typed directly in UTF-8. Use the checklist in section 8 when adding or editing text and attributes. When you add new labels, titles, placeholders, or dynamic content, check that the five special characters are escaped where they appear and that the file is saved as UTF-8 with meta charset declared.
