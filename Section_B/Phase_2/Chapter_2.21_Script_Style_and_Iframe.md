# Section B Phase 2 · Chapter 2.21: Script, Style, and Iframe

This chapter covers how JavaScript and CSS are included in an HTML document (script and style elements, link for stylesheets), how loading and execution order work (blocking, defer, async), and how iframe embeds another document. It builds on Chapter 2.20 (Block and Inline) and the structure from earlier chapters; here we focus on where script and style go, when to use external versus inline, and when iframe is appropriate. Chapter 2.22 (HTML and HTTP) then ties HTML delivery to the HTTP protocol.

## Learning Objectives

By the end of this chapter, you should be able to:
- Include scripts with the script element (src for external, or inline content); understand blocking, defer, and async and when to use each.
- Include styles with link rel="stylesheet" for external CSS or the style element for inline CSS; prefer external stylesheets for maintainability.
- Use iframe for embedding another document or page; understand sandbox, srcdoc, and same-origin; know when to avoid iframe for accessibility and performance.
- Relate script and style placement to Phase 3 (JavaScript) and Phase 7 (CSS), and iframe to security and embedding.

## Key Terms

- **script element**: An HTML element that includes JavaScript either via src (external file) or as inline content; by default script blocks parsing until it is loaded and executed unless defer or async is used.
- **defer**: A boolean attribute on script; the script is downloaded in parallel and executed after the document is parsed, in order relative to other deferred scripts.
- **async**: A boolean attribute on script; the script is downloaded in parallel and executed as soon as it is available, without waiting for document parse; order is not guaranteed relative to other async scripts.
- **style element**: An HTML element that contains CSS inline in the document; typically in the head. For main site styles, external stylesheets (link) are usually preferred.
- **iframe**: An HTML element that embeds another document (page or resource) in a rectangular region; the embedded content is in a separate browsing context and can be subject to same-origin and sandbox restrictions. Use a title attribute so assistive technology can describe the frame.

## 1) Including Scripts

The script element loads and runs JavaScript. With a src attribute, the browser fetches the external file and executes it. Without src, the content of the script element is inline JavaScript. By default, when the parser encounters a script, it stops parsing the document until the script is loaded (if external) and executed. That is called blocking: the page does not finish rendering until the script is done. For scripts that must run before the page is interactive or that depend on the DOM, placement and loading behavior matter.

To avoid blocking the initial render, you can place scripts at the end of the body so the rest of the document is parsed first, or you can use the defer attribute. With defer, the script is downloaded in parallel with parsing and is executed after the document is parsed, in the order in which the deferred scripts appear. That preserves order: if script A and script B both have defer, B runs after A. Use defer when your script depends on the DOM or on other scripts and you want to avoid blocking. With async, the script is downloaded in parallel and executed as soon as it is available, without waiting for the document to finish parsing. Order is not guaranteed: if you have two async scripts, whichever loads first runs first. Use async when the script is independent (e.g. an analytics or third-party widget that does not depend on your DOM or other scripts). Do not use async for scripts that must run in order or that depend on the DOM being ready unless you handle that in your code.

Scripts in the head with no defer or async block parsing until they are loaded and run. Scripts at the end of body run after the document is parsed, so the DOM is available. For a homestead dashboard that updates sensor data via JavaScript, you typically want the script to run after the DOM is ready so it can find elements (e.g. by id or class) and attach behavior or update values. So either put the script at the end of body or use defer with the script in the head. Prefer one approach consistently: defer in head or scripts at end of body. Avoid blocking scripts in the head for main application logic unless you have a specific reason. If you have multiple scripts that depend on each other (e.g. a library and then your code), list them in order and use defer for all so they execute in that order after the document is parsed. Type="text/javascript" is optional in HTML5 (script defaults to JavaScript); you can omit it. For non-JavaScript script types (e.g. module), use type="module"; modules are deferred by default and have their own loading behavior. Phase 3 (JavaScript) will cover the language and DOM APIs in depth; here the point is correct inclusion and loading order so your script runs when the DOM is ready.

## 2) Including Styles

CSS can be included with a link element (external stylesheet) or a style element (inline CSS in the document). The link element goes in the head: link with rel="stylesheet" and href pointing to the CSS file. The browser fetches the stylesheet and applies it to the document. External stylesheets are preferred for main site styles: they can be cached, shared across pages, and maintained in one place. Multiple link elements load multiple stylesheets; the order of link elements determines cascade when specificity is equal (later rules override earlier). So place your base or reset stylesheet first, then theme or component sheets, then page-specific overrides. The style element is also typically in the head; it can appear after or between link elements. Inline styles (the style attribute on an element) are for one-off overrides and have high specificity; avoid using them for general styling and prefer classes and external CSS. The style element contains CSS directly in the HTML. Use it for small amounts of page-specific or inline CSS that are not worth a separate file, or when you need to inject styles for a single page. Avoid putting all your site CSS in a large style block; use external files for maintainability.

Stylesheets are render-blocking by default: the browser may delay rendering until the CSS is loaded so that the page does not flash unstyled content. For critical above-the-fold styles, some authors inline a small amount of CSS in a style element so the first paint is styled even before the external sheet loads; that is an optimization and is optional. For a homestead dashboard, one or more external stylesheets (e.g. main.css, dashboard.css) linked in the head is a common pattern. The order of link and style elements matters: later rules can override earlier ones when specificity is equal, so the order of stylesheets determines cascade. Place your main stylesheet first, then any overrides or component-specific sheets. The style element is flow content and can appear in the head or, in some document structures, in the body, but placing it in the head keeps all presentational setup in one place. Phase 7 (CSS) will cover selectors, cascade, and layout in depth; here the point is that link is for external CSS and style is for inline CSS, and that both affect how the page looks and when it is ready to display. Media attributes (e.g. media="print" or media="(max-width: 600px)") on link allow you to load or apply styles conditionally (e.g. a print stylesheet or a mobile stylesheet); the browser will still download the sheet in many cases but may apply it only when the media condition matches. Scoped styles (style with a scoped attribute) were intended to limit style to the parent element and its descendants but are deprecated or limited in support; prefer external stylesheets and class-based styling for maintainability.

## 3) Iframe and Nested Documents

The iframe element embeds another document (a full page or a document that renders in a frame) inside the current page. The src attribute points to the URL of the embedded document. The iframe creates a separate browsing context: the embedded page has its own document, script, and style context. That can be useful for embedding a map, a video player, a third-party widget, or a dashboard widget that is served from another URL. It also has downsides: accessibility (screen readers may announce the iframe as a separate document, and keyboard users must tab into the frame), performance (another full document is loaded), and security (the embedded content can be from another origin and is subject to same-origin policy).

Use iframe when you genuinely need to embed another document or page (e.g. a live stream from another server, a map, or a widget you do not control). Do not use iframe when you could include the content in your own page (e.g. your own dashboard content should be in your document, not in an iframe of another page on your site, unless you have a specific reason). For accessibility, give the iframe a title attribute that describes what it contains (e.g. title="Live coop camera" or title="Sensor status widget") so screen-reader users know what the frame is. The sandbox attribute restricts what the embedded document can do (e.g. run scripts, submit forms, open new windows); use sandbox when you embed untrusted or third-party content to limit risk. The sandbox value can be empty (all restrictions) or a list of allowed features (e.g. allow-scripts) if you need to relax specific restrictions. srcdoc allows you to provide inline HTML for the iframe content instead of loading from src; it is useful for small, static embedded content that you control. If both src and srcdoc are present, srcdoc takes precedence in HTML5. The iframe dimensions (width and height attributes or CSS) determine the size of the embedded viewport; without dimensions the iframe may have zero or default size depending on the browser, so set width and height (or use CSS) for a visible embed. When you use iframe, consider whether the content could be in the main page instead; if it can, that is often simpler and more accessible. If you control both the parent and the embedded page (e.g. your dashboard embedding a widget you also built), you can use postMessage to pass data between them if needed; otherwise, treat the iframe as an isolated view. For embedding maps, videos, or third-party widgets, iframe is the standard approach; always add a title and consider sandbox. Empty or decorative iframes (e.g. for layout hacks) should be avoided; use CSS for layout. Some user agents and accessibility tools list iframes as landmarks or regions; a clear title helps users decide whether to enter the frame.

## 4) Security and Performance

Script and style can affect security and performance. Scripts from your own site are under your control; scripts from third-party sources (e.g. analytics, widgets) run with the same privileges as your page, so only include scripts from trusted sources. If a third-party script is compromised or malicious, it can read or modify your page, steal user input, or redirect; use only sources you trust and consider subresource integrity (integrity attribute) when you need to verify that the file has not changed. Styles from third parties can also affect layout and, in some cases, be used in creative attacks (e.g. probing); prefer linking to your own styles or to well-known CDNs you trust. If you load a script from another domain, ensure that domain is reputable and that the script is served over HTTPS. Styles from external sources can also affect your page; prefer linking to styles you control. For iframe, the embedded document is subject to same-origin policy: script in the parent page cannot access the iframe's DOM if the iframe is from a different origin, and vice versa. That isolation can be good (third-party content cannot reach your DOM) but it also means you cannot easily coordinate between parent and iframe unless you use postMessage or other allowed mechanisms. Sandboxing an iframe (sandbox attribute) restricts the embedded page (e.g. no scripts, no forms) and reduces risk when the content is not fully trusted.

Performance: blocking scripts in the head delay first paint and interaction. Use defer or place scripts at end of body so parsing and rendering can proceed. Multiple large stylesheets can also delay rendering; combine or split styles as needed for your project. Iframes add weight: each iframe is another document load. Use iframe only when embedding is required; avoid multiple iframes for content you could serve in the main page. For a homestead dashboard that embeds a sensor widget from another URL (e.g. a shared status widget), one iframe with a clear title and appropriate sandbox is reasonable; avoid embedding many separate pages in iframes if a single page with sections would suffice. If you use a CDN or external host for your own script or style (e.g. for caching or performance), ensure the URLs use HTTPS and that you trust the host; integrity attributes (e.g. subresource integrity) can verify that the file has not been tampered with. For local development, relative paths (e.g. "js/dashboard.js", "css/main.css") are fine; the browser resolves them relative to the document URL.

## 5) When to Use What

Use script with src for external JavaScript; use defer when the script depends on the DOM or on other scripts and you want to avoid blocking. Use async when the script is independent and order does not matter. Place scripts at the end of body if you prefer not to use defer. Use link rel="stylesheet" for external CSS; put it in the head. Use the style element for small, page-specific CSS when an external file is not needed. Prefer external stylesheets for main styles so they can be cached and maintained. Use iframe when you need to embed another document (another page, a widget from another URL); give it a title for accessibility and use sandbox when the content is not fully trusted. Do not use iframe for content that belongs in your own page. Do not use blocking scripts in the head for main application logic unless necessary. Do not load scripts or styles from untrusted origins without understanding the risk. For script: one or two deferred scripts (or end-of-body scripts) for your app is a common pattern; avoid many small inline scripts scattered in the page. For style: one or more external stylesheets in the head; reserve inline style for one-off overrides only when needed. For iframe: one per embedded document, with title and sandbox when appropriate; avoid stacking many iframes on one page.

## 6) Homestead Examples: Script, Style, and Iframe in Practice

On a homestead dashboard, the main page is HTML with sections for battery, solar, coop, and alerts. The JavaScript that fetches sensor data and updates the DOM (e.g. reading values, refreshing on a timer) is typically in one or more external script files. Include them with script and defer (or place them at the end of body) so the DOM is ready when the script runs. The script can then find elements by id or class and update spans or divs with new values. The CSS that lays out the dashboard (grid, cards, typography) is in an external stylesheet linked in the head with link rel="stylesheet". That keeps the HTML structure and the presentation separate and makes it easy to change styles without touching the markup.

If the dashboard embeds a live camera view from another server (e.g. an ESP32-CAM or a Pi stream), an iframe with the stream URL is a common approach. Give the iframe a title (e.g. "Live coop camera") so assistive technology can announce it. If you embed a small widget (e.g. a shared "system status" widget from another page on your site), iframe can isolate it; use sandbox if the widget is from a less trusted context. For forms (e.g. alert thresholds, drip schedule), the form is in the main document; the script that submits or validates can be in the same script file as the rest of the dashboard logic. Avoid putting all JavaScript inline in the page unless it is a tiny amount; external files are easier to maintain and can be cached. For a multi-page site (e.g. dashboard, sensors, settings), share one or more common stylesheets and one or more common script files so updates apply everywhere. If you use a third-party library (e.g. for charts or maps), load it with script and defer or async as the library recommends, and ensure you load your own script after it if your code depends on the library. For coop door control, drip schedule, or alert settings, the form and buttons are in the main document; the script that handles clicks and API calls can be in the same deferred script as the dashboard logic. For electric fence or energizer status, solar production, or battery history, the data can be fetched by script and inserted into the DOM (e.g. into spans or tables) without iframe; use iframe only if you are embedding a separate app or page. For a live webcam or stream, iframe is often the way to embed the player or stream URL; give it a title like "Live barn camera" so users know what they are entering. For multiple cameras or streams, multiple iframes (each with a distinct title) or a single page that switches the iframe src are both valid; prefer clear titles and avoid an excessive number of simultaneous iframes for performance.

## 7) What Breaks When Script, Style, or Iframe Are Wrong

Blocking scripts in the head that depend on the DOM can run before the document is parsed, so the script may not find the elements it expects (e.g. getElementById returns null). Fix by using defer or by placing the script at the end of body so the DOM is ready. Scripts that run too early can also cause errors if they assume the presence of elements that are defined later in the markup; keeping the script deferred or at end of body avoids that. If you must run a script in the head (e.g. for critical configuration), ensure it does not rely on DOM elements that are not yet parsed, or use an event such as DOMContentLoaded to run the DOM-dependent part when the document is ready. Scripts that depend on each other but are loaded with async may run in the wrong order; fix by using defer (which preserves order) or by loading the dependent script after the one it depends on without async. Missing or wrong src or href (e.g. typo in the path) means the script or stylesheet does not load; the page may have no behavior or no styles. Fix by checking the path and that the file exists. Stylesheet order can cause unexpected overrides; fix by ordering link and style elements so the intended cascade is correct.

Iframe without a title is poor for accessibility; screen-reader users may only hear "frame" with no context. Fix by adding a descriptive title. Embedding untrusted content in an iframe without sandbox can expose your page to risk if the embedded content is compromised. Fix by using the sandbox attribute when the content is not fully under your control. Using iframe for content that should be in the main page (e.g. your own dashboard sections) adds complexity and can hurt performance and accessibility; fix by putting the content in the main document. Loading scripts or styles from HTTP on an HTTPS page can cause mixed-content blocking or warnings; fix by using HTTPS URLs for all resources. Testing in different browsers and with the network throttled helps catch loading and ordering issues. If an iframe's src is from a different origin and that server does not send appropriate cross-origin or frame-allow headers, the browser may block or restrict the embed; fix by ensuring the embedded resource is intended to be embedded and that the server allows it. If your script or style path is wrong (e.g. typo or wrong folder), the browser will show a 404 in the network tab; fix the path and refresh. Document your script and style inclusion pattern (e.g. "all scripts at end of body with defer" or "one app.js with defer in head") so future changes stay consistent.

## 8) Checklist for Script, Style, and Iframe

When you add or change script, style, or iframe, use this list. Use script with defer (or scripts at end of body) for main application logic so the DOM is ready; use async only for independent scripts where order does not matter. Use link rel="stylesheet" in the head for external CSS; use style for small inline CSS only when appropriate. Prefer external files for both script and style so they can be cached and maintained. Use iframe only when you need to embed another document; give the iframe a title for accessibility; use sandbox when the content is not fully trusted. Do not load scripts or styles from untrusted origins. Do not use blocking scripts in the head for DOM-dependent code unless you have a specific reason. Check that script and stylesheet paths are correct and that resources load (e.g. in the network tab). When you add a new script or stylesheet, verify it loads (no 404) and that script order (if multiple) is correct. When you add an iframe, add a title and decide whether sandbox is needed. Use relative or absolute paths consistently (e.g. "js/app.js" or "/assets/css/main.css") and ensure the paths match your server's file layout. If you move a file, update the reference in the HTML so the resource still loads. ## Common Pitfalls

Blocking script in head that needs the DOM: The script runs before the body is parsed, so elements are missing. Use defer or put the script at end of body.

Using async for dependent scripts: Async does not preserve order; the dependent script may run before the one it needs. Use defer or load in order without async.

Iframe without title: Screen-reader users get no context. Always add a descriptive title attribute to iframe.

Using iframe for your own content: Embedding your own dashboard sections in iframes adds load and complexity. Put content in the main document when possible.

Wrong or broken paths for script or link: A typo in src or href means the resource does not load. Verify paths and that files exist.

Loading third-party script or style without review: Untrusted resources run with your page's privileges. Only include scripts and styles from trusted sources. Use HTTPS for all script and style URLs when the page is HTTPS to avoid mixed-content issues.

## Summary

Use the script element for JavaScript: src for external files, and defer (or placement at end of body) so the DOM is ready and parsing is not blocked. Use async only when the script is independent and order does not matter. Use link rel="stylesheet" in the head for external CSS; use the style element for small inline CSS. Prefer external stylesheets for main styles. Use iframe when you need to embed another document; give it a title for accessibility and use sandbox for untrusted content. Do not use iframe for content that belongs in your page. Homestead dashboards typically use external script (with defer) and external CSS (link in head), and iframe only for embedded streams or widgets. Use the checklist in section 8 when adding or changing script, style, or iframe. Keep script and style in external files for caching and maintainability; use iframe only when embedding another document is required.
