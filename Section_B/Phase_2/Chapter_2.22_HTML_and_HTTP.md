# Section B Phase 2 · Chapter 2.22: HTML and HTTP

This chapter ties the HTML you have been writing to the HTTP protocol: how the browser requests an HTML document, how the server sends it, and how headers like Content-Type and Cache-Control affect delivery and reuse. It builds on Chapter 2.21 (Script, Style, and Iframe) and on Section B Phase 1 (HTTP); here we focus on HTML as the body of an HTTP response and how that connects to caching, validation, and serving HTML from a server. Chapter 2.23 (Validation and Best Practices) then covers HTML validation and practical habits for writing and serving correct markup.

## Learning Objectives

By the end of this chapter, you should be able to:
- Describe how a browser requests HTML (GET request to a URL; response with status, headers, and body).
- Explain Content-Type: text/html and charset (e.g. charset=utf-8) and why they matter for correct interpretation.
- Relate caching (Cache-Control, ETag) and validation (If-None-Match, 304 Not Modified) to HTML delivery and when to allow or disable caching.
- Connect HTML delivery to Section B Phase 1 (HTTP) and to Phase 5 (Express) when serving HTML with res.sendFile or res.render.

## Key Terms

- **GET request**: The HTTP method used when the browser requests a resource by URL (e.g. when you navigate or click a link); the server responds with a status, headers, and a body (e.g. the HTML document).
- **Content-Type**: The HTTP response header that tells the client what kind of data the body is (e.g. text/html; charset=utf-8 for an HTML document in UTF-8). The browser uses it to decide how to parse and display the response.
- **Cache-Control**: A response (or request) header that directs caches (browser, proxies) on whether and how long the response can be stored and reused (e.g. max-age, no-cache, no-store).
- **ETag**: A response header that gives a validator (often a hash or version) for the resource; the client can send it back in If-None-Match to ask "has this changed?" and receive 304 Not Modified if the content is unchanged. Saves bandwidth when the document has not changed.

- **304 Not Modified**: An HTTP status code the server sends when the client has a cached copy and the server confirms (via ETag or Last-Modified) that the content is unchanged; the response typically has no body or a minimal one, and the client uses its cached copy.

## 1) Requesting HTML

When the user navigates to a URL (e.g. by typing it, clicking a link, or submitting a form with method GET), the browser sends an HTTP GET request to that URL. The server (or a proxy) responds with an HTTP response: a status code (e.g. 200 OK), headers (e.g. Content-Type, Cache-Control), and a body. For an HTML page, the body is the HTML document: the same markup you have been writing in Phase 2. The browser receives that body, sees Content-Type: text/html (or similar), and parses it as HTML: it builds the DOM, loads linked resources (CSS, script, images) by issuing further requests, and renders the page. So the HTML file you edit is exactly what the server can send as the response body; the only difference between "opening the file from disk" and "requesting it over HTTP" is that over HTTP the server sends headers and the body together, and the browser uses the headers to interpret the body correctly. The URL in the address bar is the request-URL for the HTML document; relative URLs in the document (e.g. in link href or script src) are resolved against that document URL. So if the HTML is served from https://homestead.local/dashboard, a relative link like "styles/main.css" becomes https://homestead.local/dashboard/styles/main.css. The server must be configured to serve that path (or to map it to the correct file or route) so that the browser gets 200 and the CSS (or script, or image) for each of those requests. Broken links or wrong base paths are a common cause of 404s for assets; double-check that your relative URLs match the actual file layout and server configuration.

Subsequent resources (stylesheets, scripts, images) referenced in the HTML (e.g. link href, script src, img src) cause additional GET requests. Each resource has its own URL, which may be absolute or relative to the document URL. The browser parses the HTML, discovers these URLs, and fetches them. So one "page load" can involve many HTTP requests: one for the HTML document and then one or more for each linked resource. The order and timing of those requests depend on where the resources appear in the document (e.g. link in head, script at end of body) and on attributes like defer and async. From the HTTP perspective, each request is a separate GET; the server does not automatically send the CSS or script with the HTML—it sends only what was requested (the HTML), and the browser then requests the rest. That is the same request-response model you learned in Phase 1: one request, one response per resource. Redirects (e.g. 301 or 302) can change the URL the client uses; if the server responds with 302 Found and a Location header pointing to another URL, the browser typically issues a second GET to that URL and then receives the HTML from there. So the "page" the user sees may be the result of one or more requests (redirects plus the final document plus all linked resources). For a homestead dashboard, the typical flow is: one GET to the dashboard URL, one 200 response with the HTML, then additional GETs for each link, script, and image in that HTML. The server only needs to respond to each request with the right resource; it does not bundle everything into one response.

## 2) Content-Type: text/html

The server must send a Content-Type header so the client knows how to interpret the body. For an HTML document, the correct type is text/html. Often the server also sends the charset, e.g. Content-Type: text/html; charset=utf-8. That tells the browser that the body is HTML and that the character encoding is UTF-8, which matches the meta charset in the document and ensures that characters outside ASCII are decoded correctly. If the server sends the wrong Content-Type (e.g. text/plain or application/octet-stream), the browser may not parse the body as HTML: it might display raw markup as text, or treat it as a download instead of rendering. So for HTML pages, the server should set Content-Type to text/html and optionally include charset=utf-8 (or the actual encoding) so the browser parses and displays the page correctly.

Wrong or missing Content-Type can also affect security or behavior. Some browsers use "sniffing" to guess the type when the header is missing or wrong; that can lead to inconsistent or insecure behavior. Sending the correct header avoids guesswork. When you serve HTML from a backend (e.g. Node and Express), the framework often sets Content-Type automatically when you use the right API (e.g. res.sendFile for a static file, or res.render for a template). If you send raw HTML with res.send, you may need to set the header yourself (e.g. res.set('Content-Type', 'text/html; charset=utf-8')). Static file servers (e.g. serving from a directory) typically map file extension to Content-Type (e.g. .html to text/html) and may read charset from the file or default to UTF-8. Check your server's behavior so HTML is always served with the correct Content-Type. When the charset is included in the header (e.g. charset=utf-8), it should match the actual encoding of the file and the meta charset in the document. Sending charset=utf-8 in the header while the file is saved in another encoding can still cause mojibake; sending no charset may leave the browser to guess (e.g. from meta charset in the HTML, but that requires parsing the beginning of the body). So for consistency: save HTML files as UTF-8, declare meta charset="UTF-8" in the document, and have the server send Content-Type: text/html; charset=utf-8. That way the browser knows the encoding before and during parse. Some servers (e.g. Express with static middleware) set Content-Type from the file extension and may not add charset by default; check the docs or set the header explicitly if needed.

## 3) Caching and Validation

Caching lets the browser or an intermediate cache store a response and reuse it for later requests without asking the server again. That can speed up repeat visits and reduce load on the server. The server controls caching with response headers. Cache-Control is the main one: it can say how long the response can be cached (e.g. max-age=3600 for one hour), or that it must not be cached (no-store), or that the client must revalidate before using a cached copy (no-cache). For HTML pages that are dynamic (e.g. a dashboard that shows live data or user-specific content), you often want no-cache or a short max-age so that returning users get a fresh page. For static HTML that rarely changes, a longer max-age can be acceptable. For linked assets (CSS, JS, images) that have versioned or hashed URLs, long cache times are common because a new URL means updated content.

Validation is the process of asking the server "I have a cached copy with this ETag (or Last-Modified); has it changed?" The client sends If-None-Match (with the ETag) or If-Modified-Since (with the date). If the content has not changed, the server responds with 304 Not Modified and no body; the client uses its cached copy. If the content has changed, the server responds with 200 and the full body. That saves bandwidth when the content is unchanged. ETag is a validator that the server sends with the response (e.g. a hash of the content or a version string); the client stores it and sends it back in If-None-Match on the next request. So for HTML delivery: the server can send Cache-Control to say how long the response can be reused, and ETag (or Last-Modified) to allow validation. Dynamic HTML (e.g. dashboard, settings) is often sent with Cache-Control: no-cache or max-age=0 so the browser revalidates each time, and the server can send 304 if the content is unchanged or 200 with new content if it changed. Static HTML (e.g. a landing page) might have a short max-age or no-cache depending on how often you update it. The difference between no-cache and no-store is subtle but important: no-cache means the client can store the response but must revalidate (send If-None-Match or If-Modified-Since) before using it; no-store means the client should not store the response at all. For a dashboard that might change (e.g. you fix a typo or add a link), no-cache with ETag is often a good choice: the browser can keep a copy and ask "has it changed?" and get 304 when it has not, saving bandwidth while still getting updates when you change the file. no-store is stricter and can be used when the content is sensitive or must never be reused. Private and public in Cache-Control control whether shared caches (e.g. a CDN or proxy) can cache the response; private means only the browser (private cache) can store it, which is common for user-specific or dynamic HTML.

## 4) Bridge to HTTP and Express

Everything you learned in Section B Phase 1 about HTTP applies to HTML delivery. The request has a method (GET for loading a page), a URL, and optional headers. The response has a status code (200 for success, 304 for not modified, 404 if the page is not found), headers (Content-Type, Cache-Control, ETag, etc.), and a body (the HTML). The same model applies whether the server is a static file server, a simple Node HTTP server, or a framework like Express. When you use Express to serve a dashboard, you might serve the HTML as a static file (express.static) so that GET / or GET /dashboard returns the contents of index.html or dashboard.html with the correct Content-Type set by Express. Or you might use a template engine (e.g. Handlebars, EJS) and res.render so the server builds the HTML from a template and data, then sends it with the right headers. In both cases, the client still sends GET, the server still responds with status, headers, and body; the only difference is whether the body is read from a file or generated by the application.

For a homestead dashboard, the flow is: user navigates to the dashboard URL; browser sends GET to that URL; server returns 200 with Content-Type: text/html and the HTML document as the body; browser parses the HTML, loads linked CSS and script, and runs the script to fetch sensor data (e.g. via more HTTP requests to an API). The HTML document is the first response; the rest (CSS, JS, API calls) are separate requests. When you deploy, you configure the server (e.g. Express, Nginx, or a static host) so that requests for the dashboard URL return the correct HTML and so that Content-Type and caching headers are set as you want. Phase 5 (Express) will cover serving static files, res.sendFile, res.render, and setting headers in detail; here the point is that HTML and HTTP are the same request-response model you already know, and that correct headers (Content-Type, Cache-Control) ensure the browser interprets and caches the response correctly. When you run a local development server (e.g. live-server, or a small Node server), it too sends GET responses with HTML; the same rules apply. The only difference in production is that you configure the real server (Express, Nginx, Apache, or a platform like Vercel or Netlify) to serve your HTML and set the headers you want. Many platforms set Content-Type and basic caching by default; read the docs to see how to override or tune them. For a homestead project that will run on a Pi or a small VPS, you might use Express or Nginx; in both cases, the HTML is the body of a GET response and the headers you send (or that the server sends by default) determine how the browser treats it.

## 5) When to Use What

Use GET for requesting HTML (and for other resources when you are only reading). The server should respond with 200 and the HTML body when the resource exists, and with Content-Type: text/html; charset=utf-8 so the browser parses it as HTML. Use Cache-Control to control caching: no-store or no-cache (or short max-age) for dynamic HTML that should not be reused without revalidation; longer max-age only for static HTML that you are comfortable serving from cache. Use ETag (or Last-Modified) when you want the client to be able to revalidate and get 304 when the content has not changed. When you serve HTML from a backend, use the framework's recommended way to set Content-Type (e.g. res.sendFile or res.render in Express) so you do not have to set it manually unless needed. When you serve static HTML from a directory, ensure the server is configured to send text/html for .html files and the correct charset. For a homestead dashboard that is the same for all users and updates only when you deploy, a short max-age or no-cache is often enough; for API-backed or user-specific HTML, prefer no-cache or max-age=0 so the browser revalidates and gets fresh content when needed. When you use a CDN or reverse proxy in front of your server, caching may happen at that layer too; configure Cache-Control and Vary (if needed) so that the right responses are cached and invalidated when you deploy or when content changes. For HTML that varies by user (e.g. "Welcome, Alice"), use Vary: Cookie or similar so that caches do not serve one user's HTML to another; and use private or no-store if the page must not be cached in shared caches.

## 6) Homestead Examples: HTML and HTTP in Practice

A homestead dashboard is typically one HTML document (e.g. index.html or dashboard.html) that the server sends when the user requests the root URL or /dashboard. The browser sends GET; the server responds with 200, Content-Type: text/html, and the HTML. That HTML includes link and script elements that point to CSS and JavaScript files; the browser then sends additional GET requests for those. If the dashboard is static (the same file for everyone), the server might send it with Cache-Control: no-cache so that when you update the file and redeploy, users who refresh get the new version (or with ETag so they get 304 if unchanged). If the dashboard is built by the server from a template (e.g. different nav or user name), the server generates the HTML per request and usually sends no-cache or a very short max-age so that each visit gets a fresh page. The sensor data (e.g. battery voltage, coop status) is often loaded by JavaScript after the page is rendered, via separate API requests (GET to /api/sensors or similar); those are separate from the HTML request. So the HTML request delivers the shell (structure, links, script tags); the script then fetches data and updates the DOM. An alerts or notifications page might be server-rendered (the server includes the list of alerts in the HTML) or client-rendered (the HTML is a shell and the script fetches alerts from an API). In the server-rendered case, each request for the alerts page returns HTML that already contains the current alerts; caching that page would show stale alerts, so the server typically sends no-cache or a very short max-age. In the client-rendered case, the HTML is the same for everyone and might be cached briefly; the fresh data comes from the API. Either way, the initial HTML is still delivered via GET and Content-Type: text/html.

For a multi-page site (e.g. dashboard, sensors, settings, alerts), each page is a separate HTML document (or a server-rendered response) at a different URL. Each navigation is a GET to that URL; the server returns the appropriate HTML. Caching can be configured per route or per file type: e.g. static assets (CSS, JS with hashed filenames) might have long max-age, while HTML might have no-cache. For a simple static setup (e.g. files in a folder served by Nginx or Apache), the server maps URLs to files and sends Content-Type: text/html for .html files. If you run the dashboard on a Raspberry Pi or an ESP32-based device that serves a small web interface, the same rules apply: the device responds to GET with status, headers, and the HTML body. Lightweight servers (e.g. serving from an ESP32 or a minimal Node script) may not set Cache-Control or ETag by default; for a local or low-traffic homestead UI, that is often acceptable, but if you want to avoid stale pages after updates, configure no-cache or a short max-age and ensure Content-Type: text/html is set so the browser always parses the response as HTML. For an Express app, you might use express.static for the folder containing your HTML and assets, and the default behavior sends the right Content-Type. When you add a new page (e.g. "Drip schedule" or "Fence status"), you add the HTML file or the route that renders it, and the server sends it when the user navigates to that URL. The same HTTP rules apply: GET, 200, Content-Type, Cache-Control, and body. Keeping the HTML valid and the headers correct ensures the browser always interprets and caches your pages as intended. For a coop or barn status page, a freezer monitor page, or a drip schedule page, each is a separate URL and a separate GET; the server returns the HTML for that page. If you use client-side routing (e.g. a single HTML file and JavaScript that changes what is displayed without a full reload), the initial load is still one GET for that HTML file; subsequent "navigations" may be handled in JS without a new request, or they may use history and trigger new GETs depending on your setup. For Phase 2 we focus on the traditional model: each page URL results in a GET and an HTML response body. The same principles apply when you later add client-side routing or single-page app patterns. If the dashboard is behind authentication (e.g. a login page), the server may send 401 Unauthorized or redirect to a login URL when the user is not logged in; the HTML for the dashboard is then sent only after the user is authenticated. That is still GET and response with HTML; the only difference is that the server checks credentials (e.g. via a cookie or session) before sending 200 and the body. For a public status page (e.g. a simple sensor readout that anyone can view), no auth is needed and GET to the URL returns the HTML directly. For API endpoints that return JSON (e.g. /api/sensors), the server sends Content-Type: application/json and a JSON body; that is a different resource type from the HTML page, and the browser or your script handles it accordingly. So the same server can send HTML for page URLs and JSON for API URLs; the Content-Type and body distinguish them.

## 7) What Breaks When HTML and HTTP Are Wrong

Wrong or missing Content-Type (e.g. the server sends HTML but with Content-Type: text/plain or no Content-Type) can cause the browser to display raw markup as text or to treat the response as a download. Fix by ensuring the server sends Content-Type: text/html; charset=utf-8 for HTML responses. Caching that is too aggressive (e.g. long max-age for a page that changes often) means users may see stale content until the cache expires. Fix by using no-cache or a short max-age for dynamic HTML, and by using cache-busting (e.g. versioned or hashed URLs) for assets when you update them. Sending 200 with the same HTML when the content has not changed (instead of 304 Not Modified) wastes bandwidth; fix by supporting ETag or Last-Modified and returning 304 when the validator matches. Sending 304 with a body (or wrong headers) can confuse caches; the 304 response should have no body (or a minimal one) and the appropriate headers so the client uses its cached copy.

If the server does not send the HTML at all (e.g. 404 for a missing file, or 500 for a server error), the browser shows an error page instead of your content. Fix by ensuring the route or file exists and that the server returns 200 with the HTML body. If linked resources (CSS, script) have wrong paths or return 404, the page may render without styles or behavior; fix the paths and ensure the server serves those files too. Mixed content (e.g. HTML served over HTTPS but the page references HTTP resources) can cause blocking or warnings; use HTTPS for the page and all resources. For a homestead dashboard, the most common issues are: wrong Content-Type when serving HTML from a custom server, and over-caching so that after you update the HTML users still see the old version until they force refresh. Set headers correctly and use conservative caching for HTML unless you have a clear reason to cache longer. If the server sends 500 Internal Server Error or crashes before sending the body, the user sees an error page; fix by ensuring the server handles the route and does not throw. If the server sends HTML but with a wrong or missing charset in the header, the browser may misinterpret non-ASCII characters; fix by sending charset=utf-8 (or the actual encoding) in Content-Type. If you use a reverse proxy or load balancer, ensure it forwards the correct headers from the origin and does not strip or modify Content-Type or Cache-Control unless intended. Testing with a browser's network tab (inspect the response headers for the HTML document) helps verify that Content-Type, Cache-Control, and ETag are what you expect. If the server sends a large HTML document, compression (e.g. gzip or Brotli) can reduce transfer size; the server sends Content-Encoding: gzip and the compressed body, and the browser decompresses it. That is transparent to the HTML itself; the document is still the same once decompressed. Many servers and platforms enable compression by default for text/html. If you use server-side rendering (e.g. templates that inject sensor data into the HTML before sending), each request may produce different HTML (e.g. different "last updated" time or user name); in that case you typically do not cache the HTML at all or use very short max-age, and you may not send ETag if the content is always considered fresh. For static HTML files that are the same for every request, ETag based on file content or modification time is useful so that returning visitors get 304 when you have not changed the file.

## 8) Checklist for HTML and HTTP

When you serve or deploy HTML, use this list. Ensure the server sends Content-Type: text/html; charset=utf-8 for HTML responses. Use GET for loading pages; the server responds with 200 and the HTML body when the resource exists. Set Cache-Control appropriately: no-cache or short max-age for dynamic or frequently updated HTML; consider ETag for validation so clients can get 304 when the content is unchanged. When using a framework (e.g. Express), use the recommended API (res.sendFile, res.render, or express.static) so Content-Type is set automatically. When you add a new page or route, verify that the URL returns 200 and the correct HTML and that linked resources (CSS, script) load (no 404). For static assets, use versioned or hashed URLs if you want long cache times without stale content after updates. When you deploy to a new environment (e.g. from local to a Pi or VPS), re-check that the server is configured to serve HTML with the correct Content-Type and that paths to resources (relative or absolute) still resolve correctly. Document your caching strategy (e.g. "HTML: no-cache; assets: max-age=1 year with hashed filenames") so that future changes stay consistent. ## Common Pitfalls

Missing or wrong Content-Type: The browser may not parse the body as HTML. Always send Content-Type: text/html (and charset when appropriate) for HTML responses.

Over-caching HTML: Long max-age for dynamic HTML causes users to see stale pages. Use no-cache or short max-age for HTML that changes.

Sending 200 instead of 304 when content is unchanged: Wastes bandwidth. Support ETag or Last-Modified and return 304 when the client's validator matches.

404 for the HTML document: The route or file is missing or misconfigured. Verify the server returns 200 for the page URL.

404 for linked resources: Wrong paths in link href or script src. Fix paths and ensure the server serves CSS and JS at those URLs.

Forgetting charset: Without charset in Content-Type or in the document (meta charset), the browser may guess wrong and display mojibake. Send charset=utf-8 in the header and use meta charset in the HTML.

## Summary

HTML is delivered as the body of an HTTP response. The browser sends GET to the page URL; the server responds with status (200), headers (Content-Type: text/html; charset=utf-8, Cache-Control, ETag), and the HTML body. Content-Type tells the browser to parse the body as HTML; caching headers control whether and how long the response can be reused; ETag allows validation and 304 Not Modified when the content is unchanged. The same HTTP model applies whether you serve static files or generate HTML from a backend. For a homestead dashboard, the server sends the HTML document for the page URL; the browser then loads linked CSS and script and runs the script to fetch data. Use the checklist in section 8 when you configure or deploy so Content-Type and caching are correct. The same HTTP you learned in Phase 1 (methods, status codes, headers, body) is what delivers every HTML page; treating HTML as "the body of a GET response" keeps the mental model simple and applies whether you serve static files or generate HTML on the server.
