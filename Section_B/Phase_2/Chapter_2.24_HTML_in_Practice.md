# Section B Phase 2 · Chapter 2.24: HTML in Practice

This chapter ties Phase 2 together: how to build a real page from valid, semantic HTML, how to check it with view source and DevTools, and how HTML fits as the structural foundation for CSS and JavaScript. It builds on Chapter 2.23 (Validation and Best Practices) and on all earlier Phase 2 topics; here we focus on assembling a complete page (e.g. a homestead dashboard skeleton), applying the accessibility and quality checklist, and bridging to Phase 3 (JavaScript) and Phase 7 (CSS). Section B Phase 2 ends with this consolidation; the next phase in the curriculum is Phase 3 (JavaScript Fundamentals).

## Learning Objectives

By the end of this chapter, you should be able to:
- Assemble a minimal, valid HTML page using the right elements for structure (landmarks, headings), text, links, forms, and media.
- Use browser view source and DevTools (Elements panel) to inspect the DOM and check structure and accessibility.
- Apply a short quality and accessibility checklist: DOCTYPE, charset, title, landmarks, heading hierarchy, form labels, alt text, and a bridge to contrast and focus (CSS).
- Understand HTML as the structural contract that CSS and JavaScript build on, and when to hand off to the next phase.

## Key Terms

- **view source**: The raw HTML as sent by the server (e.g. via "View Page Source" in the browser). Shows exactly what was delivered, before any DOM changes by script.

- **DevTools Elements panel**: The browser tool that shows the live DOM tree (after parsing and any script changes). Used to inspect structure, attributes, and computed styles, and to test accessibility.

- **structural contract**: The idea that HTML defines the document structure and semantics; CSS adds presentation (layout, colors, typography) and JavaScript adds behavior. Keeping structure clean in HTML makes styling and scripting predictable.

- **skeleton (page)**: The minimal structure of a page—DOCTYPE, head, body, landmarks (main, nav, header, footer), and optionally placeholders for content—before filling in text, forms, and media. Building the skeleton first keeps nesting and validity under control.

## 1) Building a Page from Scratch

When you build a page from scratch, work in order: structure first, then content, then forms and media. Start with the document shell: DOCTYPE, html with lang, head (charset, viewport if needed, title), and body. Then add landmarks: one main for the primary content, nav for navigation, and optionally header and footer. That gives you a skeleton that screen readers and assistive technology can use to jump by region. Next add the content inside main: one h1 for the page title, then h2 for major sections, then paragraphs, lists, and links as needed. Keep heading hierarchy logical (no skips from h1 to h3). Then add forms (with label for every control), images (with alt), and any tables (with th and scope or headers). For a homestead dashboard, the skeleton might be: header with site title and nav (links to Dashboard, Sensors, Settings, Alerts), main with h1 "Dashboard" and sections for Battery, Solar, Loads, each with its own heading and placeholder content (e.g. a list or a short paragraph), and footer with a copyright or link. Every form control (e.g. a threshold input or a schedule selector) gets a label; every image or icon gets alt. Once the structure is in place, you can validate (W3C Validator), then add CSS for layout and appearance and JavaScript for behavior (e.g. fetching sensor data and updating the DOM). Building in this order—structure, content, forms and media—keeps the document valid and accessible before you layer on presentation and interactivity. If you are building from a wireframe or sketch, map the regions to landmarks (e.g. top bar to header, sidebar to nav or aside, main area to main) and the text blocks to headings and paragraphs. Lists (ul, ol) go where you have repeated items (e.g. nav links, sensor names, alert list). Forms go where you have inputs; each field gets a label. Tables go where you have tabular data (e.g. sensor log, event history). Avoid using div or span for everything; prefer semantic elements (main, nav, section, article, header, footer) so the document outline and accessibility tree are meaningful. When you add a new section (e.g. a "Drip schedule" or "Freezer status" block), give it a heading and put it inside main (or inside a section with its own heading) so the structure stays clear. Re-run the validator after adding content to catch any unclosed tags or invalid nesting introduced by the new blocks. If you use a component or partial (e.g. a shared nav or footer that you include in every page), ensure that partial is valid in isolation and that when you combine it with the rest of the page you do not create duplicate ids or unclosed elements. For example, if the nav is a list of links inside a nav element, the opening and closing tags must match; if you copy that block into several pages, each page should still have exactly one main, one nav, and so on. Naming conventions (e.g. id="main-content", class="sensor-card") help you and your future scripts find the right elements; keep names consistent across pages so that shared CSS and JavaScript work everywhere.

## 2) View Source and DevTools

View source shows the raw HTML as the server sent it. Use it to verify that the document the browser received is what you expect: correct DOCTYPE, charset in head, landmarks, and no obvious typos or missing tags. View source does not show changes made by JavaScript; if your page is static, view source and the file you wrote should match. If the page is server-rendered, view source shows the generated HTML. DevTools (e.g. the Elements panel in Chrome or Firefox) shows the live DOM: the tree of nodes after the browser has parsed the HTML and after any scripts have run. So if JavaScript adds or removes nodes, you see the current state in DevTools, not in view source. Use the Elements panel to inspect the structure: expand and collapse nodes, check that landmarks (main, nav, header, footer) are where you expect, that headings are in order, and that form controls have associated labels. Many DevTools also offer an accessibility view or an accessibility tree that shows how assistive technology sees the page (roles, names, states). Use both: view source for what was sent, DevTools for what the page looks like structurally at any moment. The validator (W3C) checks the static markup (from view source or from the file you upload); DevTools helps you verify that the runtime structure is correct and that your HTML is not broken by invalid nesting or missing elements. For a homestead dashboard that later loads data via script, the initial HTML should still be valid and well-structured; DevTools lets you confirm that the skeleton is correct before and after the script runs. You can use DevTools to edit the DOM temporarily (e.g. change text or attributes) to test how the page would look with different content; those changes are lost on reload. For debugging layout or script issues, inspect the computed styles and the parent-child relationships in the Elements panel to see whether the structure matches what your CSS or JavaScript expects. If something does not style or behave as expected, often the cause is a missing wrapper, an extra nesting level, or an element that ended up in the wrong place because of invalid HTML; view source and the validator help you catch that. For accessibility, use the accessibility tree or audit tools in DevTools to see how assistive technology will expose the page (roles, names, and relationships). Fixing structure in HTML (headings, labels, landmarks) improves that tree before you add ARIA or custom widgets. If the accessibility tree shows "unnamed" for a control or image, that often means a missing label or alt; fix it in the HTML. If the heading hierarchy appears flat or wrong, adjust your h1–h6 order. View source and DevTools together give you the full picture: what was sent (view source), what the DOM looks like now (Elements), and how assistive technology sees it (accessibility tree). Use that feedback loop when building or debugging a page so that structure and semantics stay correct as you add or change content.

## 3) Accessibility and Quality Checklist

Apply a short checklist before considering a page done. Document: DOCTYPE html, html with lang (e.g. lang="en"), meta charset UTF-8, and a descriptive title in the head. Structure: one main landmark for primary content, nav for navigation, and heading hierarchy (one h1, then h2, then h3 as needed, no skips). Forms: every input, select, and textarea has an associated label (for/id or wrapping). Images: every img has alt (descriptive or "" for decorative). Tables: use th for headers and scope or headers as needed. Optional but recommended: skip link (e.g. "Skip to main content" that targets main) for keyboard users, and ensure that interactive elements (links, buttons) are focusable and in a logical order (keyboard navigation). Contrast and focus visibility are largely CSS (Phase 4/7); here the goal is to have the structure and semantics right so that when you add styles, the page is already navigable by heading, landmark, and label. Run the validator and fix errors; then run through this checklist. For a homestead dashboard, that means: one h1, sections with clear headings, nav with meaningful link text, form labels for any settings or thresholds, and alt for any status icons or images. Document your checklist (e.g. in a project README) so that every new page gets the same treatment. Contrast and focus visibility are largely CSS (Phase 4/7); here the goal is to have the structure and semantics right so that when you add styles, the page is already navigable by heading, landmark, and label. Skip links (e.g. "Skip to main content" at the top that links to the main element with an id) help keyboard users bypass repeated navigation; add one if your nav has many links. Keyboard navigation order follows the DOM order by default, so placing the main content after the nav in the HTML and using landmarks helps screen-reader and keyboard users reach content without tabbing through every link. The checklist is not a substitute for testing with a screen reader or keyboard-only use, but it gets the HTML layer right so that such testing is meaningful. For a homestead dashboard, that means: one h1, sections with clear headings, nav with meaningful link text (e.g. "Battery" not "Click here"), form labels for any settings or thresholds, and alt for any status icons or images.

## 4) Bridge to CSS and JavaScript

HTML is structure; CSS is presentation; JavaScript is behavior. Phase 2 has focused on HTML: elements, attributes, semantics, validation, and accessibility at the markup layer. Phase 4 (CSS) will add layout, typography, colors, and focus styles. Phase 3 (JavaScript) will add logic, DOM manipulation, and interactivity (e.g. fetching sensor data and updating the page). Keeping HTML clean—valid, semantic, with landmarks and headings and labels—makes both CSS and JavaScript easier. CSS selectors (e.g. main section, nav a) rely on the structure you build in HTML; if the structure is wrong or invalid, styling can be fragile or inconsistent. JavaScript that finds elements by tag, class, or id and that updates content or attributes depends on a predictable DOM; invalid HTML can lead to unexpected structure (e.g. elements in the wrong place because of implicit closing of tags). So the habit from Phase 2 is: build the page in HTML first, validate it, apply the accessibility checklist, then add CSS and JavaScript. For a homestead dashboard, the HTML might be a static skeleton (header, nav, main with sections, footer) with placeholder content; CSS will style it (grid, colors, responsive layout), and JavaScript will fetch data from an API and fill in the live values (battery voltage, coop status, etc.). The HTML does not need to change for that—the script finds the right elements (e.g. by id or class) and updates their text or attributes. Section B Phase 2 is complete when you can build such a page, validate it, and understand that the next steps are styling (CSS) and behavior (JavaScript). When you start Phase 3 (JavaScript), you will use the DOM API to select elements (e.g. by id, class, or tag), read and set their content or attributes, and listen for events (clicks, form submit). The HTML you wrote in Phase 2 defines those elements and their structure; valid, semantic markup with consistent ids and classes makes the script easier to write and maintain. When you add CSS (Phase 4 or 7), you will target elements by tag, class, or structure (e.g. main section, nav a); again, the HTML structure you built here is what those selectors match. So Phase 2 is not just "learning HTML tags"—it is establishing the contract that the rest of the stack relies on. For a homestead project, that contract might be: a main with sections that have predictable ids or classes (e.g. section id="battery", section id="solar") so that CSS can lay them out and JavaScript can find and update the right placeholders (e.g. a span with id="battery-voltage") when new data arrives. Keeping that contract in valid, accessible HTML is the goal of this chapter and of Phase 2 as a whole.

## 5) When to Use What

Use DOCTYPE html and meta charset in every page. Use landmarks (main, nav, header, footer) where they fit. Use one h1 and a logical heading hierarchy. Use label for every form control and alt for every image. Use the validator before you call a page done. Use view source to confirm what was sent; use DevTools to inspect the live DOM and accessibility. Use CSS for layout and appearance (Phase 4/7) and JavaScript for behavior (Phase 3); do not try to do layout or complex behavior in HTML alone. For a multi-page homestead site, repeat the same structure and checklist on each page so that navigation, headings, and forms are consistent. For a single-page dashboard that updates via script, the initial HTML is still the contract: the script expects certain ids or classes to exist; keep that contract in valid, semantic HTML.

## 6) Homestead Examples: HTML in Practice

A homestead dashboard page in practice is one HTML document: header with site name and nav (Dashboard, Sensors, Alerts, Settings), main with h1 "Dashboard" and sections for Battery, Solar, Coop, Freezer, Drip, or whatever you monitor. Each section has an h2 and a place for values (e.g. a list or a div with an id so JavaScript can update it). Footer might have a link to docs or a version. Forms (e.g. set low-voltage threshold, or configure drip schedule) live in main or in a dedicated section; every input and select has a label. Icons or status images have alt. You validate this document, run the accessibility checklist, then add CSS (e.g. a simple grid for the sections) and JavaScript (e.g. fetch /api/sensors and fill in the values). The same approach applies to a sensors-only page (list of sensors with headings and placeholders for readings), an alerts page (list or table of alerts, with form to add or edit rules), or a settings page (forms for user or system preferences). For a Raspberry Pi or ESP32 that serves a minimal status page, the HTML might be a single file with one main, one h1, and a few sections; still use the same checklist (DOCTYPE, charset, title, landmarks, headings, labels, alt). For a multi-page site, each page shares the same nav and footer pattern so that structure is consistent and users can move between pages with the same landmarks and heading structure. The goal is to have a real, valid, accessible page that is ready for CSS and JavaScript—not a mockup, but the actual structural foundation. If the dashboard has a "Last updated" timestamp, you can put it in the HTML as static text initially (e.g. "Last updated: —") and have JavaScript replace it when the page loads; the HTML just needs a container (e.g. a span with an id) so the script has a place to write the value. Same for sensor readings: the HTML might have "Voltage: —" with a span or element that the script will fill; the structure (heading, label, value placeholder) is in HTML, the live data is injected by script. For an alerts page that lists recent events, the HTML might have an empty list (ul with id="alerts") or a table body (tbody with id="alert-rows") that the script populates; the table header (th cells) stays in the HTML so the columns are defined and accessible. For a settings form, all fields and labels are in the HTML; the script may load current values from an API and fill the inputs, or handle submit. In every case, the HTML defines the structure and the placeholders; CSS and JavaScript build on that. Validate the HTML, run the checklist, then add the next layer. When you deploy (e.g. to a Pi or a small VPS), the same HTML file (or the same template output) is what the server sends; ensuring it is valid and accessible in development means it stays that way in production. If you later add a backend (e.g. Express) that serves this HTML or renders it from a template, the same checklist applies to the output: the HTML that the browser receives should still have DOCTYPE, charset, landmarks, headings, labels, and alt. Server-side rendering does not change the rules; it only changes who writes the HTML. So the habits you build in Phase 2—validate, checklist, structure first—apply whether you ship static files or server-generated pages.

## 7) What Breaks When HTML in Practice Is Skipped

If you skip the order of work (structure first, then content, then forms and media), you may end up with invalid nesting (e.g. block inside p), missing labels, or no landmarks, and then have to refactor later. If you skip validation, errors (unclosed tags, duplicate ids, wrong nesting) can cause the DOM to be different from what you expect, and CSS or JavaScript that assumes a certain structure will break or behave inconsistently. If you skip the accessibility checklist, the page may be hard to use with a screen reader or keyboard: no heading hierarchy, unlabeled form controls, or images without alt. If you mix structure with presentation (e.g. try to do layout only with HTML and inline styles), the document becomes hard to maintain and to style consistently with CSS later. If you add JavaScript before the HTML is valid and complete, the script may depend on elements that are in the wrong place or missing because of invalid markup. Building the HTML page first, validating it, and applying the checklist avoids these problems. For a homestead project that you or others will use on different devices and possibly with assistive technology, investing in valid, semantic HTML from the start pays off when you add styling and behavior and when you add more pages or features later. If you copy-paste HTML from another project or from a snippet, validate it in context; the pasted block might have been valid in its original document but introduce duplicate ids or invalid nesting in yours (e.g. an extra closing div that does not match your structure). If you use a template engine or server-side rendering, validate the rendered output (the final HTML that the server sends), not only the template in isolation; the template plus data might produce invalid or inconsistent markup (e.g. unclosed tags in a loop or missing alt when the image src is dynamic). Treat the HTML that the browser receives as the source of truth for validation and for the accessibility checklist. Once that is solid, CSS and JavaScript can assume a stable, predictable DOM. If the page is embedded in an iframe (e.g. a dashboard widget or a status panel on another site), the HTML you send for that frame is still subject to the same validation and checklist; the embedding context does not relax the rules. Similarly, if you build a small HTML fragment that is loaded via fetch and inserted into the page by script, that fragment should still be valid (e.g. a single section or a list of items) so that when it is injected into the DOM, the result is valid and the accessibility tree stays consistent. HTML in practice means treating every document or fragment you produce as part of the same contract: valid, semantic, and accessible.

## 8) Checklist for HTML in Practice

Before you consider a page or Phase 2 complete, use this list. Document shell: DOCTYPE html, html with lang, meta charset UTF-8, title. Landmarks: main for primary content, nav for navigation, header/footer as needed. Headings: one h1, then h2/h3 in order, no skips. Forms: every input, select, textarea has a label. Images: every img has alt. Tables: th and scope/headers if applicable. Run the W3C Validator and fix all errors. Check view source and DevTools: structure matches what you expect. Optionally: skip link, keyboard order. Then add CSS for presentation and JavaScript for behavior; keep HTML as the structural contract. Section B Phase 2 is complete; next is Phase 3 (JavaScript Fundamentals) or Phase 4/7 (CSS) per your learning path. When you add new pages (e.g. a dedicated "Coop" or "Drip" page), reuse the same document shell and checklist so that every page has DOCTYPE, charset, title, landmarks, and consistent nav; that keeps the site predictable for users and for your own CSS and script. If you later integrate a design system or component library, the HTML you wrote here (semantic elements, ids and classes) is what those tools will target or generate; starting with valid, accessible markup makes that integration easier.

## Common Pitfalls

Skipping structure and going straight to content: You may introduce invalid nesting or missing landmarks. Build the skeleton first (DOCTYPE, head, body, main, nav), then fill in content.

Ignoring view source: If you only look at the rendered page, you might miss that the server sent wrong or incomplete HTML. Check view source to see what was actually delivered.

Assuming DevTools shows the same as your file: After JavaScript runs, the DOM can change. For structure checks, either disable script or confirm that the initial HTML (view source) is correct before script runs.

Skipping the accessibility checklist: Unlabeled form controls and missing alt make the page harder for everyone and can fail accessibility audits. Apply the checklist on every page.

Adding CSS or JavaScript before HTML is valid: Invalid HTML leads to an unpredictable DOM; styling and scripting then become fragile. Validate and fix HTML first, then add presentation and behavior.

Treating HTML as "done" once it looks right: Looks are from CSS; structure and semantics are from HTML. A page can "look" fine but have wrong heading order or missing labels. Use the checklist and validator, not just visual inspection.

Forgetting to re-validate after edits: One new section or pasted block can introduce an unclosed tag or duplicate id. Re-run the validator after significant changes so errors do not accumulate.
