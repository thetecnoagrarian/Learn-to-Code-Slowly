# Section B Phase 3 · Chapter 3.01: What JavaScript Is

This chapter describes where JavaScript runs (browser and Node.js), how engines execute it, and how scripts differ from modules. It starts Section B Phase 3 and sets the mental model for the language; Chapter 3.02 (Variables and Declarations) then covers how to declare and use variables.

## Learning Objectives

By the end of this chapter, you should be able to:
- Name the two main environments where JavaScript runs: the browser and Node.js (server or command line).
- Explain that JavaScript is the language and that engines (e.g. V8) parse and execute it; same language, different host APIs.
- Distinguish classic script execution (top-to-bottom, global scope) from module execution (import and export, strict by default, deferred in the browser).
- Relate JavaScript to the program model you know from Section A: execution order, state, and boundaries.

## Key Terms

- **browser environment**: The host where JavaScript runs inside a web page; it provides the DOM, window, fetch, and other web APIs but no direct file system or Node APIs.
- **Node.js**: A host where JavaScript runs on the server or in the command line; it provides require or import, process, the file system, and other Node APIs but no DOM.
- **engine**: The program that parses and executes JavaScript (e.g. V8 in Chrome and Node); the same language can run in different engines. The host (browser or Node) embeds the engine and exposes APIs to your code.
- **script (classic)**: A JavaScript file or inline block run as a classic script: execution is top-to-bottom, scope can be global, and there is no import or export.
- **module**: A JavaScript file (or inline block in the browser) that uses import and export; it runs in module mode, is strict by default, and in the browser is deferred. Dependencies are declared with import; the host loads them before running the module.

## 1) Where JavaScript Runs

JavaScript is a programming language. It does not run by itself; it runs inside a host environment that provides the APIs and the runtime. The two main hosts you will use in this curriculum are the browser and Node.js.

In the browser, JavaScript runs in the context of a web page. The host gives you the DOM (to read and change the document), the window object, fetch (to make HTTP requests), timers, and other web APIs. The browser does not give you direct access to the file system or to Node-specific APIs such as require or process. Scripts are typically loaded via a script tag or as modules with type="module". The same language runs in every modern browser; the differences are in which APIs and which engine version each browser provides. When you open the developer tools and run code in the console, that code runs in the same browser context as the page; when you load a script from a file, that file runs in that context too. So "browser JavaScript" means any JavaScript that the browser engine executes for that page, whether inline, from a file, or from the console.

In Node.js, JavaScript runs on the server or in the command line. The host gives you process, the file system (e.g. reading and writing files), the ability to run HTTP servers, and either CommonJS (require and module.exports) or ES modules (import and export) depending on configuration. Node does not provide the DOM or window; there is no document to manipulate. Node is often used to build servers, tools, and scripts that run outside the browser. Chrome and Node can share the same engine (V8), so the language behavior is the same; only the available globals and APIs differ. You run Node by typing node and a filename (or node by itself for the REPL) in a terminal; the entry point is the file you pass. That file can require or import other files; the host resolves paths and runs your code in order. So "Node JavaScript" means any JavaScript that the Node engine executes, whether from a single file or a package of modules. Node can also run TypeScript or other languages via transpilers, but in this curriculum we stick to JavaScript that Node runs directly or via a simple build step.

So when you write JavaScript, you are writing in one language, but the environment (browser or Node) decides what you can do: in the browser you can change the page and call fetch; in Node you can read files and listen on a port. For a homestead dashboard, you might write JavaScript that runs in the browser to update the UI and call an API, and JavaScript that runs in Node (or another server) to serve the page and talk to sensors or a database. The same syntax (variables, functions, conditionals, loops) works in both; the difference is which built-in objects and functions exist. In the browser you get document.querySelector and fetch; in Node you get require or import and fs.readFile. If you move a snippet from a Node script into a browser page, you must remove or replace any Node-only APIs; if you move browser code to Node, you must remove or replace any DOM or window usage. The curriculum will use both environments: Phase 3 focuses on the language; Phase 4 (Node) and Phase 8 (DOM) focus on the host APIs. When you see "run this in Node" or "run this in the browser," that is a reminder of which host and which globals apply; the syntax and the core language are shared.

## 2) Engines and Execution

The host (browser or Node) uses an engine to run JavaScript. You do not need to install the engine separately when you use a browser or Node; the host bundles it. The engine parses the source code, compiles or interprets it, and executes it. V8 is the engine used in Chrome and in Node.js; other browsers use their own engines (e.g. SpiderMonkey in Firefox, JavaScriptCore in Safari). The language specification (ECMAScript) defines what JavaScript is; each engine implements that specification. So when we say "JavaScript does X," we mean the language as specified; in practice it is the engine in your host that does it. Engine differences are mostly in performance and in how recently they added a given feature; the curriculum uses features that are widely supported in modern browsers and in current Node versions. You do not need to memorize engine names; the point is that the same language runs in different hosts and that the host, not the engine, provides the environment (DOM, fetch, file system, and so on).

Execution is synchronous by default. The engine runs one statement after another, in order. When you call a function, the engine runs that function before continuing. If a function takes a long time, it blocks until it finishes. Asynchronous behavior (e.g. waiting for a network response or a timer) is handled by the host: the host provides APIs (e.g. fetch, setTimeout) that register work to be done later. When that work is ready, the host puts a task on the queue, and the engine runs it when it gets back to the event loop. So your code is either running or waiting; when it is waiting, it is not running, and the host can run other tasks (e.g. other tabs' scripts, or other requests in Node). That is the event loop: the engine repeatedly takes the next task from the queue, runs it to completion, then takes the next. No task is interrupted mid-run; that is why long synchronous work blocks everything else in that context. When you use fetch or setTimeout, you are asking the host to do something and to queue your callback when it is done; your current code then finishes, and later the host enqueues the callback so the engine runs it. That is how async is cooperative: you yield by returning from the current task, and the host decides what runs next. So JavaScript runs in a single thread per context; you do not get multiple threads of JavaScript running in parallel in the same context. That single-threaded, run-to-completion model is important for understanding when code runs and when async callbacks execute. If you start a loop that runs for ten seconds, nothing else in that context runs until the loop finishes; the page or the server appears frozen. So long-running work is usually done asynchronously: you ask the host to do something (e.g. fetch a URL or wait for a timer), and you provide a callback or a Promise that runs when the host is done. The engine then runs other code until the host queues your callback. Later chapters (async, Callbacks and Promises, async/await) will go deeper; here the point is that the engine runs your code step by step, and the host manages when async work runs. In the browser, each tab has its own context and its own thread; in Node, the main module and its imports share one thread unless you use worker threads or similar. For most homestead projects (a dashboard, a small server, a script that polls sensors), the single-threaded model is enough; you use async to avoid blocking. Worker threads (in Node or the browser) allow a separate thread for heavy work, but that is an advanced topic; for Phase 3 we stay with the single main thread and the event loop.

## 3) Scripts vs Modules

How your JavaScript is loaded determines whether it runs as a classic script or as a module. The differences affect scope, strict mode, and how dependencies are expressed.

A classic script is the traditional way to run JavaScript. The host loads the file (or the inline block) and runs it from top to bottom. Variables and functions declared at the top level can become properties of the global object (e.g. window in the browser), depending on how they are declared. There is no import or export; if you need code from another file, you load it with another script tag (in the browser) or with require (in Node, which is CommonJS). Classic scripts are easy to get started with but can lead to global namespace pollution and unclear dependencies. In the browser, multiple classic scripts share the same global scope; the order of script tags determines execution order and which variables exist when. In Node, each file is a module by default (CommonJS) unless you set "type": "module", so "classic script" in Node terms usually means a CommonJS module that uses require and module.exports rather than import and export.

A module is a file (or block) that uses import and export. In the browser, you load it with a script tag with type="module". In Node, you use it by setting "type": "module" in package.json or by using the .mjs extension. Modules are strict by default: you cannot use undeclared variables, duplicate parameters, or certain other constructs that are allowed in non-strict classic scripts. Each module has its own scope; top-level variables are not global. Dependencies are explicit: you import what you need and export what you provide. In the browser, module scripts are deferred: they run after the document is parsed, in order, and they do not block parsing. For new projects, modules are usually the better choice because they make dependencies clear and avoid accidental globals. When you load a module in the browser, the browser fetches it and any modules it imports; execution is deferred and in dependency order. In Node, ES modules are loaded asynchronously by the host but your top-level code runs synchronously once the module is loaded; the main difference from classic scripts is the scope and the strictness, not whether the host does async loading internally.

So when you write JavaScript for the browser, you can use a classic script (no type="module") for a simple page or a module (type="module") when you want import and export and stricter behavior. In Node, you choose between CommonJS (require, module.exports) and ES modules (import, export) via project configuration. If your Node project has "type": "module" in package.json, .js files are treated as ES modules and you use import and export; if not, they are CommonJS and you use require and module.exports. You can also use the .mjs extension for a module file and .cjs for a CommonJS file so the extension overrides the default. Phase 3 will use both where appropriate; the important thing is to know which mode you are in so you understand scope and execution order. Mixing modes in one file (e.g. import and require in the same file) is not supported; the whole file is either a module or a classic script. In the browser, a script tag without type="module" loads a classic script; with type="module" it loads a module. Modules can import other modules; classic scripts cannot use import or export at all.

## 4) When to Use What

Use the browser when your JavaScript must interact with the page: update the DOM, handle clicks, or call fetch from the user's device. Use Node when your JavaScript must run on a server or in the CLI: serve HTML, read files, or run build tools. Use classic scripts when you are adding a small inline script or a single file with no dependencies; use modules when you have multiple files and want explicit imports and exports and strict behavior. For a homestead dashboard, the page that the user sees runs in the browser (script or module); the server that sends that page and talks to sensors or a database often runs in Node. Same language, different host and APIs. When in doubt about host: if the code touches the document or runs in response to a page load or user action in a tab, it is browser code; if it runs without a browser (e.g. from the command line or as a server process), it is Node or another host. When in doubt about script vs module: if the file uses import or export, it must be loaded as a module; if it does not and you want to keep dependencies simple and global scope acceptable for a one-off, a classic script can be fine. For anything that will grow or be reused, prefer modules. In this phase we will write small examples that can run in either host where it makes sense; when an example is browser-only or Node-only, we will say so. The language itself (variables, types, functions, control flow) is the same in both.

## 5) Homestead Examples: Where JavaScript Fits

On a homestead you might have a web dashboard that shows battery voltage, coop status, or drip irrigation schedules. The HTML and the logic that updates the page (e.g. fetching sensor data and filling in values) run in the browser as JavaScript. That script might be a classic script in a single file or a module that imports helpers. The server that hosts the dashboard and that might aggregate data from ESP32s or a database runs in Node.js: same language, different environment. A small utility that reads a config file and generates a report runs in Node from the command line. Scripts that run on a Raspberry Pi to poll sensors or control a relay are also Node (or another runtime). So JavaScript appears both in the browser (user-facing dashboard, forms, live updates) and on the server or device (API, file access, sensor logic). Knowing where your code runs (browser vs Node) and whether it is a script or a module tells you which APIs and which execution rules apply. For example, a coop door controller might run on a Pi: Node (or Python) talks to hardware and keeps state; a browser-based admin page runs JavaScript in the browser to show status and send commands. The dashboard that displays freezer temps or poultry net voltage might be a static HTML page with a script that fetches JSON from an API; the API is served by Node or another backend. So the split is consistent: user interface and in-page behavior in the browser, server and device logic in Node or another host. You will write JavaScript for both sides in this curriculum. Soil moisture or drip irrigation data might be collected by an ESP32 or a Pi and then exposed via an HTTP API; the browser script fetches that data and updates the page. Electric fence or solar monitoring might be shown in a small dashboard: the numbers come from the server (Node or another backend), and the browser script only renders them and handles user input. In every case, the language is JavaScript (or another language on the device); the host (browser vs Node vs device) determines what APIs and what execution context you have.

## 6) What Breaks When You Ignore Environment and Mode

If you assume browser APIs in Node, your code will fail: there is no document, no window, no fetch in the same form. If you assume Node APIs in the browser, same problem: no require, no process.env, no file system. Always know your host. If you use module syntax (import or export) in a file that Node or the browser loads as a classic script, you will get a syntax error; the host must be told that the file is a module (type="module" or "type": "module"). If you rely on global variables across multiple classic scripts, the order of script tags matters and you can get name collisions; modules avoid that by keeping scope per file. If you forget that execution is single-threaded, you might block the UI or the server with a long synchronous loop; async patterns (covered later) keep the thread free. So: match your code to the host (browser vs Node), declare the right mode (script vs module), and remember that the engine runs one thing at a time unless the host schedules async work. Another common mistake is copying a snippet from a tutorial or from Node and pasting it into a browser script without removing Node-only calls (e.g. require or fs); the browser will throw a ReferenceError. Similarly, code that uses document or window will not run in Node. When you add a new file or a new script tag, decide up front: browser or Node, and script or module, so the rest of your choices (which APIs, how to load dependencies) stay consistent. If your Node project uses "type": "module" and you accidentally use require in a file, Node will throw; use import instead. If your browser page uses type="module" and you load a script that expects to be in the global scope and to run immediately before the DOM is ready, the deferred execution of modules may surprise you: the module runs after the document is parsed, so the DOM is available, but execution order relative to other scripts is different from a classic script. Knowing the host and the mode avoids these failures. Finally, if you run an older Node version or an older browser, some syntax or APIs might be missing; the curriculum assumes a modern environment (e.g. Node 18+ or current LTS, and evergreen browsers). Check your Node version with node --version and use a recent browser for development so that modules, async/await, and other features we use are available. If you must support an older environment, you may need a build step (e.g. a bundler or transpiler) to convert modern syntax to an older form; for learning, stick to a current Node and a current browser.

## 7) Relating to Section A (Programs and Python)

The mental models from Section A apply here. A program transforms input and state into output and new state; JavaScript does that in the browser (user input and DOM state) and in Node (requests and file state). Execution order matters: the engine runs your code in sequence, and async work is scheduled by the host. Boundaries matter: the browser cannot see the server's memory; the server cannot directly manipulate the user's DOM. You will use variables, functions, conditionals, and loops in JavaScript much as in Python or in the conceptual Phase 1 material; the syntax differs but the ideas (scope, return values, branching, iteration) are the same. So Phase 3 is not learning programming from scratch; it is learning the same concepts in a second language and in two main hosts. That is why we start with where JavaScript runs and how it is executed: once you know the host and the execution model, the rest (variables, types, functions, async) fits into that picture. Errors and failure (Section A) also apply: the host can throw or log errors; you will add try/catch and error handling in later chapters. Invariants and boundaries (what the program assumes, what it does not control) are as important in JavaScript as in any language; the host environment is one such boundary. You assume the host provides certain globals and APIs; you do not control when the host runs your code (e.g. on page load or when the user clicks). Keeping that in mind helps when debugging: if something is undefined, it might be a host difference (browser vs Node) or a timing issue (code running before the host has set something up).

## 8) Checklist

When you start a JavaScript project or add JavaScript to a page, confirm: (1) Where it runs—browser or Node. (2) How it is loaded—classic script or module. (3) What APIs you can use—DOM and fetch in the browser, process and file system in Node. (4) That you are not mixing host APIs: no document in Node, no require in the browser (use import for modules instead). (5) For the browser: script tag with or without type="module" and execution order relative to the DOM. (6) For Node: package.json "type" or file extension (.mjs / .cjs) so the loader treats the file correctly. If you open an existing project, check package.json and the script tags in HTML first so you know the intended host and module mode before adding or editing JavaScript. Chapter 3.02 (Variables and Declarations) builds on this by showing how to declare variables and how scope works in scripts and modules.

## Common Pitfalls

Assuming the same globals everywhere: The browser has window and document; Node has process and global. Do not use one host's globals in the other. Code that works in one host will not run unchanged in the other without replacing or polyfilling host APIs.

Using import/export in a classic script: Import and export are only valid in modules. Use type="module" in the browser or "type": "module" in Node (or .mjs) so the file is treated as a module. If you see a syntax error about unexpected token (e.g. import or export), check that the file is loaded as a module.

Blocking the thread: A long synchronous loop or a heavy computation blocks execution. Use async APIs (fetch, setTimeout, etc.) and later async/await so the host can run other work. In the browser, blocking freezes the page; in Node, blocking delays handling other requests or events.

Ignoring strict mode in modules: Modules are strict. Undeclared variables and duplicate parameters throw. Write with that in mind so your code works in both script and module contexts. If you plan to move code from a classic script to a module, fix any non-strict behavior first.

Treating script and module as interchangeable without changing load method: You cannot load a module with a plain script tag in the browser or run a file with import/export as CommonJS in Node. The load method (script tag type, or Node package.json type / file extension) must match the syntax.

## Summary

JavaScript is one language that runs in different hosts. In the browser it has the DOM and web APIs; in Node it has the file system and server APIs. Engines (e.g. V8) parse and execute the language; execution is synchronous and single-threaded unless the host schedules async work. Classic scripts run top-to-bottom and can use the global scope; modules use import and export, are strict by default, and have per-file scope. Know your host (browser vs Node) and your mode (script vs module) so you use the right APIs and avoid broken or brittle code. The same concepts (variables, functions, control flow) apply in both environments; only the available globals and the way you load and run code differ. Chapter 3.02 adds variables and scope on top of this foundation; from there we build types, operators, and control flow in the same two hosts.
