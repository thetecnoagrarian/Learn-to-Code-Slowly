# Section B Phase 3 · Chapter 3.02: Variables and Declarations

This chapter covers how to declare variables in JavaScript with let and const, how scope and the temporal dead zone work, and when to prefer each. It builds on Chapter 3.01 (What JavaScript Is); here we focus on binding names to values, block scope, and the difference between reassignment and mutation. Chapter 3.03 (Types and Values) then covers what kinds of values those variables can hold and how types affect behavior.

## Learning Objectives

By the end of this chapter, you should be able to:
- Declare variables with let and const and know when to use each.
- Understand block scope (let and const) and function scope (var); avoid var in new code.
- Explain the temporal dead zone for let and const and avoid accessing variables before declaration.
- Prefer const by default and use let when reassignment is needed; apply clear naming so state is easy to reason about.

## Key Terms

- **let**: A declaration that creates a block-scoped binding that can be reassigned. The variable is not usable until the declaration line runs (temporal dead zone).
- **const**: A declaration that creates a block-scoped binding that cannot be reassigned. The binding is immutable; the value (e.g. an object or array) may still be mutable. Also subject to the temporal dead zone.
- **block scope**: The region of code between a pair of curly braces (e.g. inside an if or for). Variables declared with let or const inside a block exist only within that block.
- **temporal dead zone (TDZ)**: The span from the start of a block (or script/module) until the line where a let or const variable is declared. Accessing the variable in that span throws a ReferenceError.
- **var**: A legacy declaration that is function-scoped (or global) and hoisted; avoid in new code in favor of let and const. Redeclaration in the same scope is allowed, which can cause bugs.

- **reassignment**: Giving a different value to an existing binding. Allowed for let; not allowed for const. The value (e.g. an object) can still be mutated when declared with const.

- **hoisting (var only)**: With var, the declaration is treated as if it were at the top of the function; the variable exists from the start of the function but is undefined until the assignment runs. let and const are not hoisted in this way; they are in the TDZ until the declaration line.

## 1) let and const

Variables in JavaScript hold values. You create a variable by declaring it with let or const followed by a name and optionally an initial value. The name is a binding: it refers to a value. With let, you can later assign a new value to that same binding (reassignment). With const, you cannot reassign; the binding is fixed once it is set. Both let and const are block-scoped: the variable exists only inside the block (the pair of curly braces) where it is declared. A function body is also a block; variables declared inside the function are not visible outside. So when you pass data between functions, you do it via arguments and return values (or via shared objects), not via variables that leak out of their scope. Block scope also means that two different blocks can declare variables with the same name without conflict; each block has its own binding. That is useful when you have a short-lived variable (e.g. a loop index) that you do not need outside the loop. The same name in an outer scope is then shadowed (hidden) by the inner declaration for the duration of the inner block; that is intentional and allows reuse of names like i or key in different blocks without conflict. Outside that block, the name is not defined or refers to a different variable from an outer scope. A block can be the body of an if, for, while, or a standalone pair of braces used to create a scope. The top level of a script or module is also a scope; variables declared there are in that script or module's scope and are not global unless the host attaches them (e.g. in a classic script without strict mode, top-level var becomes a property of the global object). In a module or in strict mode, top-level let and const are not added to the global object; they are just in the module or script scope.

Use const when the binding will not change. That does not mean the value itself is immutable. If the value is an object or an array, you can still change its properties or elements; you just cannot assign a different object or array to that variable. So const is ideal for references you do not plan to replace: a configuration object, a list of items, or a function. Use let when you need to reassign: a counter, a result that you update in a loop, or a value that changes over time. In practice, prefer const by default and switch to let only when you need to reassign. That keeps the number of changing bindings small and makes the code easier to follow. If you later discover that a const needs to be reassigned (e.g. you need to point it at a new object), change the declaration to let; that is a small, local edit. Starting with const and only relaxing to let when necessary keeps the default "this binding does not change" and makes reassignment visible in the declaration.

You must declare a variable before you use it in the same scope (or in an inner scope). JavaScript does not create implicit globals when you assign to an undeclared name in strict mode (and modules are strict by default). In non-strict classic scripts, assigning to an undeclared name creates a global property, which is error-prone; strict mode and modules avoid that. So the habit is: declare with let or const at the top of the block or at the point where you first need the variable, and do not use a name without declaring it. You can declare several variables in one statement (e.g. let a = 1, b = 2;) but often one declaration per line is clearer. You can also declare without an initial value (e.g. let x;) and assign later; the variable will be undefined until the first assignment. For const you must provide an initial value in the same statement, because you cannot assign to it later. If you need a const whose value is computed after some logic, use a block: declare let inside the block, compute the value, then use it; or use an IIFE (immediately invoked function expression) that returns the value and assign it to a const. For most cases, a single const with an initial value or a let that you assign once or a few times is enough.

## 2) var (Legacy) and Function Scope

Before let and const existed, JavaScript had var. Variables declared with var are function-scoped: they exist for the entire function (or the global scope if declared outside any function), not just the block where they appear. So a var declared inside an if or for is still visible after that block, anywhere in the same function. That is different from let and const, which are block-scoped. var is also hoisted: the declaration is treated as if it were at the top of the function, so you can use the variable before the line where it is written (it will be undefined until the assignment runs). You can also redeclare the same var in the same scope without error, which can lead to bugs when you think you are creating a new variable. In a classic script (non-strict), a top-level var becomes a property of the global object (window in the browser, global in Node); that can cause name collisions between scripts. In strict mode and in modules, var is still function-scoped and hoisted but the rest of the rules are unchanged; the main reason to avoid var is block scope and TDZ, which let and const give you.

In new code, avoid var. Use let when you need reassignment and const otherwise. Block scope makes it clear where a variable is valid, and the temporal dead zone prevents use before declaration. You will still see var in older code and in some tutorials; when you do, treat it as function-scoped and hoisted, and prefer rewriting to let or const when you touch that code. The curriculum uses let and const only unless we are explicitly describing legacy behavior. One more quirk of var: in a for loop, a var declared in the loop header is shared across all iterations and is still visible after the loop; a let in the loop header creates a new binding per iteration, so closures or async callbacks that capture the loop variable see the right value. That is another reason to use let (or const) for loops. When you work with setTimeout, fetch callbacks, or event handlers, the callback runs later; if it closes over a loop variable, let gives each callback its own value, while var would give all callbacks the same (final) value. So for any loop where the variable is used in a callback or closure, use let.

## 3) Temporal Dead Zone

For let and const, the variable is not available until the declaration is executed. The period from the start of the block (or script/module) up to the declaration line is called the temporal dead zone. If you try to read or use the variable in that zone, the engine throws a ReferenceError. So you cannot use a variable before it is declared, even if the declaration appears later in the same block. This is different from var, which is hoisted and would be undefined before the assignment. The TDZ applies even when the access is in a function that is called later: if the function closes over a variable that is still in the TDZ when the function is defined, and you call the function before the declaration runs, you still get a ReferenceError. So the rule is simple: the variable exists only from the declaration line to the end of its block; before that, any access is an error. That makes the order of declaration and use explicit and avoids the "undefined then later assigned" behavior of var. Some style guides recommend declaring all variables at the very top of the function or block so that the TDZ is never an issue and the reader sees all names in one place. Others allow declaration at the point of first use when the block is long. Either way, the rule is the same: do not read the variable before the line that declares it.

In practice, declare variables at the top of the block where they are used, or at least before any line that references them. That way you avoid the temporal dead zone and make the scope obvious. If you need a value that is not yet available (e.g. it is computed later in the block), use let and assign it when the value is ready; do not try to read the variable before that assignment. In a loop, a let declaration inside the loop header creates a new binding per iteration, which is what you usually want for loop variables. The TDZ exists so that the semantics are consistent: the variable is not initialized until the declaration runs, and the engine does not allow access in the gap. That avoids the confusion of var, where the variable exists but is undefined before the assignment. So treat "declare then use" as the rule, and you will avoid TDZ errors.

## 4) Naming and Reassignment

Names should be clear and meaningful. Common style is camelCase for variables and constants (e.g. batteryVoltage, sensorReadings). Some teams use UPPER_SNAKE_CASE for values that are truly constant (e.g. a fixed configuration key), but that is a convention, not a language rule. Avoid single letters except for very short-lived loop counters (e.g. i, j). Names that describe the meaning (threshold, lastUpdated, config) make the code easier to read and debug. Reserved words (e.g. let, const, if, function) cannot be used as variable names; the engine will report a syntax error. Names can contain letters, digits (but not as the first character), underscore, and dollar sign; avoid starting with underscore unless you have a convention for "private" or internal names. Consistency within a project matters more than any single rule; pick a style and stick to it so variable names are predictable across files.

Reassignment is when you give an existing binding a new value. With let, you can do that as often as you need. With const, you cannot reassign the binding at all. Prefer const so that the set of names that can change is small; use let only when the value must change. For a homestead dashboard, you might use const for the API base URL, the list of sensor IDs, or a reference to a DOM element that does not change, and let for the current reading, a counter, or a string you build up. That way the reader (and you) can see at a glance which bindings are stable and which change. If you find yourself reaching for let often, ask whether the logic could be restructured so more values are computed once (const) and fewer are updated in place. Sometimes a new const in a narrower block is clearer than a let that gets reassigned several times. For example, inside a loop you might compute a value and assign it to a const for that iteration, so the name is only valid inside the loop and the value is fixed for that iteration. That reduces the mental load: you know the const does not change until the next iteration, when a new const is created. So reassignment is not the only way to handle changing values; sometimes a smaller scope and a new binding per step is clearer.

## 5) When to Use What

Use const by default for any variable whose binding will not be reassigned. Use let when you need to reassign (e.g. a loop variable, an accumulator, or a value that is updated in response to events). Avoid var. Declare variables in the smallest scope that makes sense: at the top of the block where they are used, or at the point of first use if that is clearer. In a function, prefer declaring at the top of the function body so all variables are in one place, unless a variable is only used inside a conditional or loop and declaring it there makes the code clearer. Do not access a variable before its declaration (stay out of the temporal dead zone). In modules and strict mode, always declare with let or const so you never create accidental globals. When refactoring old code that uses var, replace it with let or const and fix the scope: if the variable was used only inside a block, declare it with let or const inside that block so the scope matches the use. When you are unsure whether a value will change, start with const; you can change it to let later if you need to reassign. That way the default is "stable binding" and reassignment is explicit. When you read code, the declaration tells you the scope; when you write code, keeping scope small reduces the chance that you reuse a name by accident or that a variable is still in use long after it is relevant.

## 6) Homestead Examples: Variables in Practice

In a script that fetches sensor data, you might use const for the API URL and for the element reference (e.g. the span that displays the voltage), and let for the last reading or the current error message so you can update them when new data arrives. The API URL and the DOM element reference do not change; the reading and the error message do. In a small utility that parses a config file, you might use const for the parsed config object (you do not replace the whole object) and let for a line counter or the current section name as you iterate. For a poultry net monitor, const might hold the list of check intervals and let might hold the last voltage reading or the last time the energizer was checked. The principle is the same across contexts: const for "this reference stays the same," let for "this value is updated." A coop door controller might use const for the pin numbers or the schedule config and let for the current state (open or closed) or the last time the door moved. A drip irrigation script might use const for the list of zone IDs and let for the active zone or the timer handle. In each case, const marks "this reference does not change" and let marks "this value is updated over time." That makes the data flow clear: what is fixed (config, DOM references, list of IDs) versus what is state (current reading, current zone, door state).

When you have many related values, you can group them in an object or array declared with const; the binding is fixed but you can mutate the object's properties or the array's elements. For example, const sensors = {} might hold sensor IDs as keys and latest readings as values; you do not reassign sensors, but you do update sensors["battery"] or sensors.battery when new data comes in. Same idea for a config object: const config = { threshold: 12 }; you might change config.threshold later but you do not replace the whole config. So const is still the right choice for the container; the mutability of the value inside is separate from the reassignment of the variable. A freezer monitor might keep const zones = ["freezer1", "freezer2"] and let currentTemp = null, then update currentTemp when a reading arrives. A drip controller might have const zoneIds and let activeZone = null or let schedule = getDefaultSchedule() and then reassign schedule when the user changes it. The pattern is the same: const for structure and fixed references, let for values that change over the life of the script. When you build a small CLI tool (e.g. a Node script that reads sensor log files), you might use const for the file path and the parsed options and let for the current line or the running total. When you add a new feature that needs state, ask: will this binding be reassigned? If yes, use let; if no, use const. Over time that habit keeps the number of mutable bindings low and makes the data flow in your homestead scripts and dashboards easier to follow.

## 7) What Breaks When Variables Are Misused

If you use a variable before it is declared (in the temporal dead zone), you get a ReferenceError. Fix by moving the declaration above the use or by restructuring so the value is available when needed. If you try to reassign a const, you get a TypeError. Fix by using let if the binding must change. If you use var and expect block scope, you will be wrong: the variable is visible for the whole function. Fix by switching to let or const. If you forget to declare a variable and assign to it in strict mode, you get a ReferenceError; in non-strict mode you might create a global, which can cause subtle bugs. Fix by always declaring with let or const. If you declare the same name with let or const twice in the same block (e.g. let x = 1; and later let x = 2; in the same block), you get a SyntaxError; the engine does not allow duplicate declarations in the same scope. If you have nested blocks and declare the same name in an inner block, that is shadowing and is allowed; the inner variable is separate from the outer one. If you are in a loop and you capture the loop variable in a callback or closure, use let so each iteration gets its own binding; with var all iterations share one binding and you may see the wrong value when the callback runs later. So the fixes are: declare before use, use let for reassignment, use let or const for block scope, and use let in loops when the variable is captured.

If you reuse the same variable name in nested blocks with let or const, the inner declaration shadows the outer one; that is intentional. If you do it with var, you have one variable for the whole function and may overwrite values unexpectedly. If you declare the same name twice with let or const in the same block, you get a SyntaxError; each declaration needs a distinct scope. So: declare once per scope, prefer const, use let only when reassigning, and avoid accessing variables before their declaration. In a function, parameters are also bindings (they behave like let in that scope); you cannot redeclare them with let or const in the same function body. When you move from script to script or module to module, each file has its own top-level scope; variables declared in one file are not visible in another unless you export and import them (covered in the Modules chapter). So variables are always scoped to a block, function, script, or module; there is no "global" variable unless you explicitly attach something to the global object (e.g. window in the browser or global in Node), which is rarely needed and best avoided. When debugging "variable is not defined" or "variable is undefined," check: (1) Is the variable declared? (2) Is it declared in a scope that includes this line? (3) Are you accessing it before the declaration (TDZ)? (4) Did you mean a different variable (e.g. a typo or a shadowed name)? Those four checks cover most variable-related errors.

## 8) Checklist

When you add or edit variables: (1) Prefer const; use let only when you need to reassign. (2) Declare at the top of the block or before first use; never use a variable before its declaration. (3) Use clear, meaningful names (camelCase). (4) Do not use var in new code. (5) In modules or strict mode, every binding is declared with let or const. (6) For loop variables, use let (or const if the value does not change in the loop). (7) When you have a container (object or array) that you will mutate but not replace, use const for the container. (8) When debugging variable errors, check declaration, scope, TDZ, and name (typo or shadowing). Chapter 3.03 (Types and Values) covers what kinds of values you can assign to these variables.

## Common Pitfalls

Reassigning a const: The binding is read-only. Use let if you need to assign a new value to the same name.

Using a variable before declaration: Puts you in the temporal dead zone and throws ReferenceError. Declare first, then use.

Assuming var is block-scoped: It is function-scoped. Prefer let and const so scope matches the block structure.

Creating globals by accident: In non-strict scripts, assigning to an undeclared name creates a global. Use strict mode or modules and always declare with let or const.

Confusing "const means immutable": const means the binding cannot be reassigned. Objects and arrays declared with const can still be mutated (properties and elements changed). Use const for the reference; if you need an immutable value, you need a different approach (e.g. Object.freeze or immutable data structures).

Declaring in the wrong scope: A variable that is only used inside a loop or an if block should be declared there with let or const, not outside. That keeps the scope minimal and avoids leaking the variable into other code. If you need the value after the block, declare it before the block with let and assign inside the block. That way the variable is available where it is needed and the scope is still clear.

## Summary

Use let and const to declare variables; prefer const and use let only when you need reassignment. Both are block-scoped and subject to the temporal dead zone (no use before declaration). Avoid var; it is function-scoped and hoisted and makes scope harder to reason about. Good naming and minimal reassignment make state clearer. Const means the binding cannot be reassigned; it does not make the value immutable, so objects and arrays declared with const can still be mutated. Scope is determined by where you declare (block, function, script, or module), not by where you use; and the temporal dead zone ensures you never read a variable before it is initialized. Apply these rules in every script and module so that variable behavior is consistent and predictable across the curriculum and in your own projects.
