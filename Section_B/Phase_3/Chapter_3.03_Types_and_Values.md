# Section B Phase 3 · Chapter 3.03: Types and Values

This chapter covers JavaScript's type system: primitive types (number, string, boolean, undefined, null, symbol, bigint), how to inspect types with typeof, and common pitfalls around type coercion and truthiness. It builds on Chapter 3.02 (Variables and Declarations); variables hold values, and here we define what those values are and how they behave. Chapter 3.04 (Operators and Expressions) then uses these types in expressions and comparisons.

## Learning Objectives

By the end of this chapter, you should be able to:
- List JavaScript's primitive types and describe each briefly (number, string, boolean, undefined, null, symbol, bigint).
- Use typeof to inspect types and understand its quirks (e.g. typeof null is "object").
- Avoid common type-coercion pitfalls: prefer strict equality (===), be careful with + and string concatenation, and know falsy values.
- Relate types to boundaries and validation: use explicit checks and consistent types at boundaries to reduce bugs.

## Key Terms

- **primitive**: A value that is not an object: number, string, boolean, undefined, null, symbol, or bigint. Primitives are immutable and are compared by value.
- **typeof**: An operator that returns a string describing the type of a value (e.g. "number", "string", "boolean", "undefined", "object", "function", "symbol", "bigint"). typeof null is "object" (a historic quirk).
- **type coercion**: Automatic conversion of a value from one type to another (e.g. when using == or when + is used with a string). Can lead to surprising results; prefer explicit conversion and strict equality.
- **falsy**: Values that behave as false in a boolean context: false, 0, -0, "", null, undefined, NaN, and (in some contexts) 0n (BigInt). All other values are truthy.
- **strict equality (===)**: Compares value and type; no coercion. Use === and !== for predictable comparisons.

- **NaN**: "Not a Number"; the result of invalid numeric operations (e.g. 0/0, Number("abc")). NaN is not equal to itself; use Number.isNaN(x) to detect it.

## 1) Primitives

JavaScript values are either primitives or objects. Primitives are the built-in value types that are not objects. They are immutable: you cannot change a primitive value; you can only assign a new value to a variable. When you compare two primitives, they are compared by value (with the important exception of NaN, which is not equal to itself).

The primitive types are: number, string, boolean, undefined, null, symbol, and bigint. Number represents numeric values, including integers, decimals, NaN (not a number, the result of invalid math like 0/0), and Infinity (and -Infinity). All numeric values are 64-bit floating point; there is no separate integer type, but whole numbers within the safe integer range behave as you expect for counting and indexing. String is text: a sequence of characters; strings are immutable, so methods that "change" a string return a new string. Boolean is true or false; there are only these two boolean values. Undefined means "no value": a variable that has been declared but not assigned, or an optional parameter that was not passed, or a missing property. Null is an intentional "no value" or "empty" that you assign; it is not the same as undefined, though both are falsy. Symbol is a unique value used mainly for object property keys and for well-known symbols; you will see it less often in everyday code. BigInt is for arbitrarily large integers when number's precision is not enough; you create it with a literal suffix n or with BigInt(). You cannot mix number and bigint in arithmetic without converting; use BigInt() or Number() as needed. For most homestead and web code, number, string, boolean, undefined, and null are the ones you use daily; symbol and bigint appear in more specialized cases.

Everything that is not a primitive is an object. That includes plain objects, arrays, functions, dates, and other built-in or custom objects. Objects are compared by reference: two objects with the same contents are not equal unless they are the same reference. Primitives are compared by value: two numbers or two strings with the same value are equal. So the type of a value determines how it is stored, how it is compared, and what you can do with it. When you assign a primitive to a variable, the value is copied; when you assign an object, the reference is copied, so two variables can point to the same object. When you pass a primitive to a function, the function gets a copy; when you pass an object, the function gets a reference, so mutations inside the function affect the original. That is why types matter for both comparison and mutation: primitives are safe to pass around without side effects on the value itself, while objects are shared by reference. For a homestead dashboard, you will often work with numbers (sensor readings, thresholds), strings (labels, units, API responses), booleans (on/off, valid/invalid), and objects (config, parsed JSON). Understanding primitives versus objects helps you choose the right checks and avoid bugs when comparing or converting values. Numbers in JavaScript are always double-precision floating point; there is no separate integer type, but integers within the safe range (up to about 2^53) behave as expected. NaN is the only value that is not equal to itself (NaN !== NaN is true); use Number.isNaN(x) to test for NaN. Strings are immutable; any "change" creates a new string. Undefined typically means "not yet assigned" or "optional and missing"; null is an intentional empty value that you or an API might return. Choosing between undefined and null is often a matter of convention; the important thing is to check for both when a value might be missing, unless you intentionally treat them the same (e.g. value == null).

## 2) typeof Operator

The typeof operator returns a string that names the type of its operand. For primitives you get: "number", "string", "boolean", "undefined", "symbol", or "bigint". For null you get "object"; that is a historic bug in the language, so if you need to detect null you must check explicitly (e.g. value === null). For objects you get "object", and for functions you get "function" (functions are objects, but typeof treats them specially). So typeof is useful for a quick check, but it does not distinguish between different kinds of objects (e.g. array vs plain object) and it does not correctly identify null. You can use typeof as a function: typeof value or typeof(value); both work. The result is always a string, so you compare with "number", "string", etc. When you are building a helper that accepts different types (e.g. a formatter that handles number or string), typeof lets you branch on the input type and handle each case safely. When you receive external data, a single typeof check can reject obviously wrong types (e.g. if you expect a number and get typeof x === "object", you might need to check for null or for an object that has a numeric property) before you proceed.

Use typeof at boundaries when you need to validate or branch on type: for example, when you receive data from an API or from user input and you want to ensure it is a number before doing arithmetic, or a string before calling string methods. Combine with explicit null checks when the value might be null. For arrays, typeof returns "object"; to check for an array, use Array.isArray(value). For other object types you may need constructor checks, instanceof, or duck typing depending on the situation. In homestead code, you might use typeof to verify that a sensor reading is a number before comparing it to a threshold, or that a config property is a string before using it in a label. Defensive checks at boundaries (where data enters your code) reduce the chance of type errors later. If you are building a function that accepts a config object, you might check that config is an object (typeof config === "object" && config !== null) before reading properties, so that you do not try to read properties of undefined or null. When you log or debug, typeof helps you quickly see what kind of value you have; when you validate, it helps you reject invalid input before it propagates. The goal is to establish a type contract at the boundary and then rely on that contract inside your logic.

## 3) Type Coercion and When to Avoid It

JavaScript can automatically convert values between types in certain contexts. That is type coercion. It happens with the loose equality operator (==): if the two sides have different types, the engine may convert one or both before comparing. For example, the number 1 and the string "1" are equal with == but not with ===. Loose inequality (!=) does the same. To avoid surprises, prefer strict equality (===) and strict inequality (!=): they compare value and type and do not coerce. So 1 === "1" is false, and null === undefined is false (they are different types). The only common exception is when you intentionally want to treat null and undefined as the same; then you might use value == null, which is true for both null and undefined. In general, default to === and !==.

The + operator also involves coercion. When one operand is a string, the other is coerced to string and the result is string concatenation. So 1 + "2" yields the string "12", not the number 3. If you want numeric addition, convert explicitly with Number() or ensure both operands are numbers. Similarly, when you mix types in other arithmetic or comparisons, the rules can be subtle. Prefer explicit conversion: Number(x), String(x), Boolean(x) (or !!x for boolean), so that the intent is clear and the behavior is predictable. For a threshold check, ensure the reading and the threshold are both numbers (e.g. after parsing from JSON or form input) before comparing; otherwise you may get string comparison or NaN. When you build strings for display or for API payloads, convert numbers to strings explicitly (String(n) or n.toString()) so you control the format; when you read numbers from strings, use Number() or parseFloat/parseInt and handle NaN. Other arithmetic operators (e.g. -, *, /) coerce to number when possible, so "10" - 3 is 7, but "10" + 3 is "103" because + prefers string concatenation when either side is a string. That asymmetry is a common source of bugs: a value that was a number becomes a string (e.g. after reading from a form), and then + concatenates instead of adding. Parse early and keep numeric values as numbers throughout your logic.

Truthiness is another form of coercion. In a boolean context (if, while, &&, ||, ternary), values are coerced to true or false. The falsy values are: false, 0, -0, "" (empty string), null, undefined, NaN, and (in modern JS) 0n (BigInt zero). Everything else is truthy, including the string "0", empty arrays [], and empty objects {}. So if (value) treats 0 and "" as false, which can be surprising when 0 is a valid sensor reading or "" is a valid string. When you need to distinguish "missing" from "zero" or "empty string", check explicitly: value === undefined, value === null, value === 0, or use Number.isNaN(value) for NaN. Relying on truthiness is fine when you truly want "any non-falsy value," but at boundaries (e.g. user input or API data) explicit checks are safer. For optional parameters or optional properties, you might use value == null to catch both null and undefined in one check, or value === undefined || value === null if you prefer to be explicit. When you use logical operators for short-circuit evaluation (e.g. value || default), remember that 0 and "" will trigger the default; use value ?? default (nullish coalescing) if you only want to substitute for null or undefined. That way zero and empty string are preserved when they are valid.

## 4) When to Use What

Use typeof when you need to branch on type or validate at a boundary; remember to check for null explicitly and use Array.isArray for arrays. Use strict equality (=== and !==) for comparisons; use == only when you intentionally want null and undefined to be equal. Use explicit conversion (Number(), String(), Boolean()) when you need a specific type; avoid relying on implicit coercion in arithmetic or concatenation. Use explicit checks for falsy edge cases when 0, "", or NaN are valid values in your domain. For numbers from external input (API, form, file), parse and validate (e.g. Number() or parseFloat(), then check for NaN or range) before using them in calculations or comparisons. For a homestead dashboard, sensor readings are often numbers; ensure they stay numbers through parsing and avoid accidentally turning them into strings (e.g. by concatenating with ""). Config values (thresholds, labels) may be numbers or strings; decide the type at the boundary and stick to it. When you read from the DOM (e.g. input.value), you always get a string; convert to number with Number() or parseFloat if you need a number. When you write to the DOM (e.g. element.textContent = reading), the value is coerced to string automatically; that is usually fine for display, but if you need a specific format (e.g. fixed decimal places), use String() or a formatting helper with the number first, then assign the result. So the rule is: at the boundary where data enters (API, form, DOM, file), parse and validate types; in the middle of your logic, work with known types; at the boundary where data leaves (DOM, API, storage), ensure you send or display the right type. That keeps type issues localized and predictable. Types and values are the foundation for everything that follows: operators, conditionals, loops, and functions all work on values of these types, so getting the types right at the start (variables in Chapter 3.02 and types here) makes the rest of the phase easier to reason about and debug. Apply the checklist in section 7 whenever you add a new boundary (new API, new form, new config source) so types are established and validated there. With types and values clear, the next chapter adds operators and expressions that combine them.

## 5) Homestead Examples: Types in Practice

A battery voltage reading is a number. When you receive it from an API or a sensor, it may arrive as a string (e.g. from JSON or a form). Parse it to a number (e.g. Number(reading) or parseFloat(reading)) and check for NaN before comparing to a threshold. If you leave it as a string, a comparison like reading > 12 might do string comparison and give wrong results. A coop door state might be a boolean (open/closed) or a string ("open", "closed"); pick one representation and use it consistently, and use strict equality when comparing. A list of sensor IDs might be an array of strings; use Array.isArray to confirm before iterating. A config object might have threshold as a number and unit as a string; use typeof or explicit checks when reading config so you do not accidentally treat a string threshold as a number. When you get data from fetch and parse JSON, the result is plain objects and arrays with primitive values; property types depend on what the API sent. If the API sends numbers as strings (e.g. "12.5" for voltage), you must parse them before numeric comparison or arithmetic. If the API sends booleans as strings ("true", "false"), you may need to normalize to actual booleans or compare with the string. Establishing a small set of types for your domain (e.g. "voltage is always a number", "status is always one of these strings") and enforcing them at the boundary keeps the rest of the code simple and type-safe in practice.

When you display values in the UI, numbers and booleans are often converted to strings for display; that is fine. When you send data to an API or save it, ensure the types match what the server or schema expects (e.g. numbers as numbers, not strings, in JSON). When you read from localStorage or from a form, everything comes back as strings unless you parse it; use Number() or JSON.parse as appropriate. So the flow is: data enters (often as string or raw JSON), you parse and validate types at the boundary, then you work with known types inside your logic. That keeps type coercion and falsy surprises at the edges where you handle them explicitly. A drip schedule might store zone IDs as an array of strings and durations as numbers; when you load from config or JSON, ensure the array is an array and the durations are numbers. A freezer alarm might compare currentTemp (a number) to minTemp (a number); if either came from a form or API as a string, parse first and reject or correct NaN. A poultry net monitor might receive a voltage value that could be a number or a string depending on the source; normalize to number at the boundary so the rest of the code can assume number. Consistent types inside your functions and modules make the code predictable and easier to test.

## 6) What Breaks When Types Are Wrong or Unchecked

If you assume a value is a number but it is a string (e.g. from user input or JSON), arithmetic or comparison can be wrong: "10" + 5 is "105", and "10" > 5 can be true or false depending on how the engine coerces. Fix by parsing to number and checking for NaN at the boundary. If you use == and mix types, you can get unexpected equality: 0 == false is true, "" == false is true. Fix by using === and explicit checks. If you rely on truthiness and 0 or "" is a valid value, you will treat valid data as missing. Fix by checking for null/undefined explicitly and allowing 0 and "" when they are valid. If you forget that typeof null is "object", you may treat null as an object and try to read properties. Fix by checking value === null (or value == null if you want to catch undefined too) before object access.

If you compare objects with ===, two objects with the same contents are not equal because they are different references. Fix by comparing properties you care about, or by using a deep-equality helper if needed. If you pass the wrong type to a function (e.g. a string where a number is expected), the function may produce NaN or wrong results. Fix by validating types at the function boundary or at the call site. If you use parseFloat or parseInt, they return NaN for invalid input (e.g. parseFloat("abc")); they also stop at the first invalid character, so parseFloat("12.5 volts") returns 12.5. Check for NaN after parsing. If you use Number(""), you get 0, not NaN; so empty string to number can be 0, which may or may not be what you want. Define how you handle empty or invalid input at the boundary (e.g. reject, return 0, or return NaN) and document it so callers know what to expect. If you serialize data to JSON and back, undefined and functions are dropped, and dates become strings; so types can change across the boundary. Fix by defining a clear contract for your data (e.g. "sensor reading is always a number") and enforcing it when data enters your code. So: parse and validate at boundaries, use === and explicit conversion, and know the falsy list and the typeof null quirk. If you use optional chaining (value?.property), the result is undefined when value is null or undefined; that is safe, but the type of the result may be undefined, so handle that in your logic. If you use default parameters or default values (e.g. function f(x = 0)), the default is used when the argument is undefined, not when it is null; so if you pass null explicitly, the default is not used. Being explicit about "missing" (undefined vs null) and about "zero" vs "absent" avoids a lot of type-related bugs in homestead automation code where sensor readings and config often cross boundaries (API, form, storage, DOM). In summary: primitives give you value semantics and predictable comparison; objects give you reference semantics and shared state. The type system does not stop you from mixing types or from coercion, so the discipline of checking types at boundaries and using === and explicit conversion is something you apply yourself. Once that habit is in place, the rest of your code can assume the types it works with and avoid the large class of bugs that come from wrong or unexpected types.

## 7) Checklist

When you work with values: (1) Know whether you have a primitive or an object; use typeof and Array.isArray as needed. (2) Check for null explicitly when it might occur. (3) Use === and !== for comparisons unless you intentionally want coercion. (4) Parse external input (API, form, file) to the right type and validate (e.g. NaN check for numbers). (5) Avoid relying on truthiness when 0, "", or NaN are valid. (6) At boundaries, document or enforce the expected types so the rest of the code can assume them. (7) Use Number.isNaN(x) for NaN checks; do not use x === NaN (it is always false). (8) For optional or missing values, decide whether you use undefined, null, or both and check consistently. (9) When reading from DOM or form, remember values are strings; convert to number when needed and handle NaN. (10) When sending data (API, JSON), use the correct types (numbers as numbers, not strings) so the receiver gets what it expects. Chapter 3.04 (Operators and Expressions) uses these types in expressions and in more comparison and arithmetic.

## Common Pitfalls

Using == and mixing types: Coercion can make 1 == "1" true. Prefer === so type and value both match.

Assuming typeof distinguishes all types: typeof null is "object". Check for null explicitly. Use Array.isArray for arrays.

Relying on truthiness when 0 or "" is valid: if (reading) fails when reading is 0. Use explicit checks (e.g. reading !== undefined && reading !== null) or Number.isNaN checks.

Adding number and string: 1 + "2" is "12". Use Number() or parseFloat() so both operands are numbers when you want addition.

Forgetting that objects are compared by reference: two objects with the same contents are not ===. Compare by property or use a deep-equality utility.

Ignoring NaN: Math and parsing can produce NaN. Use Number.isNaN(value) to detect it; NaN !== NaN.

Using x === NaN: NaN is the only value not equal to itself. Always use Number.isNaN(x). global isNaN(x) coerces first (e.g. isNaN("hello") is true) which can be useful but is not the same as Number.isNaN; for strict "is this the NaN value," use Number.isNaN.

## Summary

JavaScript has primitive types (number, string, boolean, undefined, null, symbol, bigint) and objects. Primitives are immutable and compared by value; objects are compared by reference. Use typeof to inspect types, but check for null explicitly and use Array.isArray for arrays. Prefer strict equality (===) and explicit conversion to avoid coercion pitfalls. Know the falsy values and use explicit checks when 0, "", or NaN are valid. Validate types at boundaries (API, form, config) so the rest of your code works with known types. Relating to Section A: types categorize data and give it meaning; the same idea applies in JavaScript. Variables hold values; the type of the value determines what you can do with it and how it compares. At boundaries (input, output, storage), explicit type checks and conversion reduce the class of bugs that come from wrong or unexpected types.
