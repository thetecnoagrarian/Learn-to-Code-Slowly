# Section B Phase 3 · Chapter 3.04: Operators and Expressions

This chapter covers JavaScript operators: arithmetic, comparison, logical, and the use of strict equality, short-circuit evaluation, optional chaining, and nullish coalescing. It builds on Chapter 3.03 (Types and Values); operators combine values and produce new values, and type and evaluation order matter. Chapter 3.05 (Conditions and Branching) then uses these operators in conditionals.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use arithmetic operators (+, -, *, /, %, **), comparison operators (===, !==, <, >, <=, >=), and logical operators (&&, ||, !).
- Prefer strict equality (=== and !==) over loose equality to avoid type coercion in comparisons.
- Use short-circuit evaluation for defaults and guards (e.g. value || default, obj && obj.property).
- Use optional chaining (?.) for safe property and method access and nullish coalescing (??) for defaults when null or undefined should trigger the fallback but 0 or "" should not.

## Key Terms

- **expression**: A piece of syntax that produces a value when evaluated. Operators are used in expressions (e.g. a + b, x === 0).
- **operator**: A symbol or keyword that performs an operation on one or more operands and returns a value (e.g. +, ===, &&).
- **strict equality (===)**: Compares value and type; no coercion. Use for predictable comparison. !== is strict inequality.
- **short-circuit evaluation**: For &&, if the left operand is falsy, the right is not evaluated and the left is returned. For ||, if the left is truthy, the right is not evaluated and the left is returned.
- **optional chaining (?.)**: If the value before ?. is null or undefined, the expression short-circuits and returns undefined instead of throwing. Used for safe property and method access.
- **nullish coalescing (??)**: Returns the right operand only when the left is null or undefined. Unlike ||, it does not replace 0 or "".

- **operand**: A value that an operator acts on. In a + b, a and b are operands. In !x, x is the operand.

## 1) Arithmetic and Comparison Operators

Arithmetic operators work on numbers and produce a number (or NaN). Addition (+), subtraction (-), multiplication (*), division (/), remainder (%), and exponentiation (**) are the main ones. When one operand is not a number, the engine may coerce it; if the result is not a valid number, you get NaN. As in Chapter 3.03, + is special: when either operand is a string, the other is coerced to string and the result is string concatenation. So 1 + 2 is 3, but 1 + "2" is "12". For numeric addition, ensure both operands are numbers (e.g. Number(x) + Number(y)). Division by zero produces Infinity (or -Infinity for negative zero); 0/0 produces NaN. NaN propagates: any arithmetic with NaN yields NaN. So when you do math with values that might be NaN (e.g. after parsing), check with Number.isNaN before relying on the result. The assignment operators (=, +=, -=, *=, /=, %=, **=) combine assignment with an operation; for example, x += 1 is equivalent to x = x + 1. They return the assigned value. For comparisons, the result is always a boolean when you use ===, !==, <, >, <=, >=; that boolean is what you use in if and while. The ternary operator (condition ? a : b) evaluates condition, then returns a if truthy or b if falsy; it is an expression, so you can use it anywhere a value is expected (e.g. const label = isOpen ? "Open" : "Closed"). We will cover conditionals and ternary in more detail in Chapter 3.05; here the point is that operators build expressions that produce values, and those values (including booleans) drive the next chapter's branching logic.

Comparison operators compare two values and return a boolean. Strict equality (===) and strict inequality (!==) compare value and type with no coercion. Use them by default so that 5 === "5" is false and you avoid surprises. Loose equality (==) and loose inequality (!=) coerce types before comparing; they can make 0 == false and "" == false true, which is rarely what you want in conditionals. The relational operators <, >, <=, >= compare values; if the types differ, coercion may occur (e.g. string and number), which can give counterintuitive results. So prefer to ensure both sides are the same type (e.g. both numbers) before using < or >. For a homestead threshold check (e.g. reading < threshold), ensure reading and threshold are numbers so the comparison is numeric. For strings, < and > do lexicographic (dictionary) order, which is useful for sorting but not for numeric comparison. The remainder operator (%) gives the remainder of division (e.g. 7 % 3 is 1); it is useful for wrapping indices or for "every N times" logic. Exponent (**) raises to a power (e.g. 2 ** 10 is 1024). Unary plus (+) can coerce a value to number (e.g. +"42" is 42), but Number() is clearer. Unary minus (-) negates. Increment (++) and decrement (--) change a variable by one; they can be prefix (++x) or postfix (x++); the difference is the value returned (before or after the increment). For most expressions, explicit x = x + 1 or x += 1 is clear enough. Operator precedence determines the order of evaluation when multiple operators appear in one expression; when in doubt, use parentheses so the order is obvious (e.g. (a + b) * c instead of relying on * having higher precedence than +).

## 2) Logical Operators and Short-Circuit Evaluation

The logical operators are && (and), || (or), and ! (not). They are often used in conditionals, but they do not always return a boolean. The ! operator returns a boolean: it coerces the operand to boolean and negates it. The && and || operators use short-circuit evaluation and return one of the operands (not necessarily a boolean). For a && b: if a is falsy, the expression returns a and b is not evaluated; if a is truthy, the expression returns b. For a || b: if a is truthy, the expression returns a and b is not evaluated; if a is falsy, the expression returns b. So you can use them for defaults: name = input || "anonymous" means "use input if it is truthy, otherwise use the string." You can use them for guards: user && user.name means "if user is truthy, return user.name; otherwise return user (falsy)." That avoids reading a property of null or undefined when user might be null.

The caveat is that || treats 0 and "" as falsy, so value || default replaces 0 and "" with default. If 0 or "" is a valid value, use nullish coalescing (??) instead: value ?? default replaces only null and undefined. Short-circuit evaluation also means that if the right operand has side effects (e.g. a function call), it may not run when the left operand short-circuits. So use && for "only do this if that is truthy" (e.g. config && config.threshold) and || for "use this or that as fallback when this is falsy." For conditionals in if or while, the expression is evaluated and then coerced to boolean for the branch; so truthiness and falsiness (from Chapter 3.03) apply. When you need an explicit boolean, use Boolean(x) or !!x; when you want the actual value or a default, use || or ?? as appropriate. Multiple conditions can be combined: (a > 0 && a < 100) for "a in range," or (status === "open" || status === "opening") for "one of these values." The ! operator has high precedence, so !x && y means (!x) && y. Use parentheses when combining ! with && or || so the logic is clear. For "not null and not undefined" you can use value != null (loose equality is one of the few cases where == is sometimes used intentionally, since null == undefined is true), or value !== null && value !== undefined. Many style guides prefer the explicit checks for readability.

## 3) Optional Chaining (?.)

Optional chaining (?.) lets you read a property or call a method when the value before ?. might be null or undefined. If the value is null or undefined, the whole expression short-circuits and returns undefined instead of throwing. So obj?.prop is equivalent to "if obj is null or undefined, undefined; else obj.prop." You can chain: obj?.a?.b?.c returns undefined if any part of the chain is null or undefined. You can use it for method calls: obj?.method?.() calls method only if obj and method exist. You can use it for indexing: arr?.[0] returns the first element only if arr is not null or undefined. That avoids "Cannot read property of undefined" or "Cannot read property of null" when you are not sure the object or the property exists (e.g. when data comes from an API or from user input).

Use optional chaining when you are traversing a structure that might be incomplete: for example, response?.data?.sensors?.battery when the API might omit data or sensors. Use it when you are not sure a property exists (e.g. config?.threshold when config might be missing). Do not overuse it to hide bugs: if obj should always exist at that point, using obj?.prop can mask the fact that obj is unexpectedly null. So optional chaining is for "this might be missing" cases, not for "this must exist and if it does not we have a bug" cases. For a homestead dashboard, you might use reading?.value when the reading object might not exist yet (e.g. before the first API response), or sensor?.name when iterating over a list that might have holes or missing entries. Optional chaining works with bracket notation too: obj?.[key] when key is a variable. It also works with function calls: fn?.() calls fn only if fn is not null or undefined; useful when a callback might be optional. The result of any ?. chain that short-circuits is undefined; so you can combine with ?? to provide a default: obj?.prop ?? 0 so that missing obj or prop gives 0 instead of undefined.

## 4) Nullish Coalescing (??)

The nullish coalescing operator (??) returns the right operand only when the left is null or undefined. So value ?? default is "use value unless it is null or undefined, in which case use default." That is different from value || default, which uses default when value is any falsy value (false, 0, "", null, undefined, NaN). So 0 ?? 10 is 0, and "" ?? "default" is "". Only null and undefined trigger the fallback. Use ?? when you want to preserve 0 and empty string as valid values. For example, count ?? 10 means "use count if it is a number (including 0), otherwise 10." With count || 10, a count of 0 would be replaced by 10. For thresholds, limits, or counts where zero is meaningful, ?? is the right choice for a default.

You can combine ?? with optional chaining: value = obj?.prop ?? default means "get obj.prop if obj exists, and if that result is null or undefined (or if obj was null/undefined), use default." So you get safe access and a sensible fallback in one expression. Do not mix ?? with || or && in the same expression without parentheses; the precedence rules can be surprising. Use parentheses to make the order clear: (a ?? b) || c or a ?? (b || c) depending on what you want. For homestead config, you might have threshold = config?.threshold ?? 12 so that if config or config.threshold is missing you get 12, but if threshold is explicitly set to 0 you keep 0. That keeps defaults and "missing" distinct from "zero." Nullish coalescing only considers null and undefined; it does not treat NaN, 0, or "" as "missing." So for numeric defaults where 0 is valid, ?? is correct; for string defaults where "" might mean "use default," you might still use ||. Choose based on your domain: "missing" (null/undefined) vs "empty or zero" (0, ""). When you document your config or API contract, state which values mean "use default" so that ?? and || are used consistently.

## 5) When to Use What

Use === and !== for all comparisons unless you intentionally want null and undefined to be equal (value == null). Use arithmetic operators only when operands are numbers; parse and validate first so you do not get string concatenation or NaN. Use && for guards (only access if previous value is truthy) and for conditional execution. Use || for defaults when any falsy value should trigger the fallback (e.g. display name || "Anonymous"). Use ?? for defaults when only null and undefined should trigger the fallback (e.g. count ?? 10, threshold ?? 12). Use ?. when the object or property might be missing and you want to avoid a throw. Use ! when you need an explicit boolean negation. In conditionals (if, while, ternary), the expression is evaluated and then coerced to boolean; so ensure the expression and the types you use are what you expect (e.g. do not use value || default when value can be 0 and 0 is valid). For homestead code: threshold and reading comparisons use === and numeric operands; optional config and API responses use ?. and ??; display names and labels use || when empty string should get a default. When you have a chain of conditions (e.g. "only run if config exists and threshold is a number and reading is below threshold"), combine with && so that the first falsy value short-circuits and the rest are not evaluated; that is efficient and reads clearly. When you have "any of these" conditions (e.g. "alert if low battery or high temp or door open"), combine with ||. When you need to negate a condition, use ! with parentheses if the condition is compound: !(a && b) is "not (a and b)," which is different from !a && b. De Morgan's laws: !(a && b) is equivalent to !a || !b, and !(a || b) is equivalent to !a && !b; use them when simplifying or when you need the opposite of a compound condition.

## 6) Homestead Examples: Operators in Practice

A battery voltage check might be: if (reading !== undefined && reading !== null && !Number.isNaN(reading) && reading < threshold) then trigger a low-voltage alert. Here you use strict equality and explicit checks so that 0 is not treated as missing, and you ensure reading and threshold are numbers before comparing. A coop door controller might use config?.openTime ?? 6 and config?.closeTime ?? 18 so that missing config gives defaults but explicit 0 (e.g. "open at midnight") is preserved. A sensor list might be displayed with sensor?.name ?? "Unknown" so that missing names get a label but empty string is not replaced. When you build a string for display, use + with strings (e.g. "Voltage: " + reading) or template literals (covered later); ensure reading is converted to string if it is a number so you do not accidentally do numeric addition. When you compute a total or average from an array of readings, use + only after ensuring each element is a number (or use reduce with Number() and NaN checks).

For optional API response shape, use response?.data?.sensors?.map(s => s.value) so that if the response or any part of the path is missing, you get undefined instead of a throw. Then you can use ?? [] to default to an empty array for iteration. For form input, input?.value ?? "" gives you the value or empty string; then you might parse to number with Number() and check for NaN before using in arithmetic or comparison. For a multi-zone drip system, you might have zones?.length ?? 0 so that missing zones gives 0 and you can loop safely; if you used || 0, an empty array (which is truthy) would be kept, but null or undefined would become 0. For a sensor reading that might be { value: number } or null, use (reading?.value ?? 0) so that missing reading or missing value gives 0 for display. When you validate "all required fields present," you might use Boolean(name && email && threshold) or name !== "" && email !== "" && threshold != null; the choice depends on whether empty string is allowed. When you compute "at least one alert active," use alerts?.some(a => a.active) ?? false so that missing alerts is treated as false. These patterns (?. for safe access, ?? for defaults, === for comparison) recur across homestead and web code; internalizing them makes both reading and writing expressions easier. So the pattern is: use ?. for safe traversal, ?? for null/undefined defaults, === for comparison, and explicit number conversion before arithmetic. That keeps operator behavior predictable and avoids coercion and missing-property errors in homestead dashboards and automation scripts. When you aggregate readings (e.g. sum or average), use a loop or reduce with + only after ensuring each item is a number; filter out or skip NaN so the aggregate is valid. When you compare dates or timestamps, ensure both are numbers (e.g. Date.getTime()) so < and > give chronological order. When you build a condition for an alert (e.g. "low battery or high temp"), combine with && and || and use parentheses so the logic is unambiguous: (reading < lowThreshold || reading > highThreshold) && enabled. Operators are the building blocks of expressions; the next chapter uses those expressions in if and else to control the flow of your program.

## 7) What Breaks When Operators Are Misused

If you use == and mix types, you get coercion and unexpected equality (0 == false, "" == false). Fix by using ===. If you use + with a string and a number, you get concatenation instead of addition. Fix by converting both to numbers (Number(x) + Number(y)) when you want addition. If you use value || default when value can be 0 or "", you replace valid values with the default. Fix by using value ?? default when only null/undefined should trigger the fallback. If you access obj.prop when obj might be null or undefined, you get a runtime error. Fix by using obj?.prop or by checking obj before access. If you use ?? with || or && in the same expression without parentheses, precedence may not match your intent. Fix by adding parentheses. If you use < or > with a string and a number, coercion can give wrong order (e.g. "10" < 9 can be true because string comparison). Fix by ensuring both operands are numbers for numeric comparison. If you rely on short-circuit side effects (e.g. call a function in the right operand of &&), remember that the right side is not evaluated when the left short-circuits; that is usually fine but be aware. If you use ! and expect a truthy value to become false, remember that ! returns a boolean; for "value or default" you want || or ??, not !. If you use optional chaining on something that is not null/undefined but is not an object (e.g. a number), the engine will try to read a property and you may get undefined or an error depending on the case; ?. is defined for null and undefined, and for other values it proceeds normally (e.g. (42).toString() works, 42?.toString?.() would call toString). So ?. is mainly for null/undefined in the chain. If you use ** or % with non-numbers, the operands are coerced to number; NaN propagates. So: prefer ===, parse numbers before arithmetic, use ?? when 0 or "" is valid, use ?. for safe access, and use parentheses when mixing ?? with || or &&. When an expression does not behave as you expect, check the types of the operands (typeof, or log them) and the operator semantics (short-circuit, precedence, coercion) so you can fix the expression or add explicit conversion. If you see undefined or NaN in a place you expected a number, trace back: was an operand undefined? Did + concatenate because one was a string? Did you use || when you meant ??? If you see "Cannot read property of undefined," you accessed a property on a value that was null or undefined; add ?. or a guard (obj && obj.prop) or an explicit check before access. If a condition always evaluates the same way (e.g. always true or always false), check the types: maybe you are comparing a string to a number (e.g. "0" === 0 is false) or the value is always undefined. Fix by normalizing types at the boundary and using the right operator (===, ??, or ?.) for the intended meaning.

## 8) Checklist

When you write expressions: (1) Use === and !== for comparisons. (2) Ensure operands are numbers before arithmetic (+, -, *, /, %, **); watch for + with string. (3) Use || for defaults when any falsy value should trigger fallback; use ?? when only null/undefined should. (4) Use ?. when the object or property might be missing. (5) Use && for guards (e.g. obj && obj.prop). (6) Use parentheses when mixing ?? with || or &&. (7) For threshold or numeric comparison, ensure both sides are numbers. (8) Check for NaN after arithmetic or parsing before using the result. (9) Use parentheses when combining ! with && or || so the logic is clear. (10) For optional API or config shapes, use ?. and ?? together (e.g. config?.threshold ?? 12). Chapter 3.05 (Conditions and Branching) uses these operators in if, else, and ternary.

## Common Pitfalls

Using == instead of ===: Coercion can make 0 == false and "" == false. Use === so type and value both match. Use == only when you intentionally want null and undefined to be equal (e.g. value == null).

Using || when 0 or "" is valid: value || default replaces 0 and "". Use value ?? default when you only want to replace null/undefined.

Forgetting + concatenates with string: 1 + "2" is "12". Use Number() on both operands for numeric addition.

Accessing property on possibly null/undefined: obj.prop throws if obj is null or undefined. Use obj?.prop.

Mixing ?? with || or && without parentheses: Precedence can surprise. Use (a ?? b) || c or a ?? (b || c) explicitly.

Using < or > with mixed types: String and number comparison can be wrong. Convert to numbers first for numeric order.

Assuming && or || return boolean: They return one of the operands. Use Boolean() or !! if you need a boolean. In conditionals (if, while), the expression is coerced to boolean anyway, so the truthiness of the returned operand is what matters.

## Summary

Use arithmetic operators with numbers; watch for + and string concatenation and for NaN. Use strict equality (=== and !==) for comparisons. Use logical operators with short-circuit behavior: && for guards, || for defaults when any falsy triggers fallback, and ?? for defaults when only null/undefined triggers. Use optional chaining (?.) for safe property and method access when the value might be missing. Use nullish coalescing (??) to preserve 0 and "" as valid values. Operators produce values; understand type and short-circuit behavior to avoid bugs. Prefer ===, use ?. for safe access and ?? for null/undefined defaults when 0 or "" is valid, and ensure numeric operands for arithmetic and numeric comparison.
