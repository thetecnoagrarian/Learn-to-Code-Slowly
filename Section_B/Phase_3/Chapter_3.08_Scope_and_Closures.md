# Section B Phase 3 · Chapter 3.08: Scope and Closures

This chapter covers where variables are visible (lexical scope and block scope) and how functions retain access to the scope where they were created (closures). It builds on Chapter 3.07 (Functions): when you define a function, it "sees" the variables in the scope where it was written, and when you return or store that function, it keeps that access. Chapter 3.09 (Objects) then adds properties and methods and how this and object scope interact. Understanding scope and closures explains why the createZoneHandler(zoneId) pattern from the previous chapter works: the returned function remembers zoneId from the outer scope. Scope controls where variables are visible; closures let functions keep using those variables after the scope that created them has finished, which is how event handlers and factories get the right configuration.

## Learning Objectives

By the end of this chapter, you should be able to:
- Explain lexical scope: visibility is determined by where the code is written (nesting), not where it is called.
- Use block scope (let and const inside curly braces) to limit variable visibility to a block.
- Define a closure: a function together with its "remembered" outer environment; the function keeps access to variables from the scope where it was created even after that scope has finished.
- Use an IIFE (immediately invoked function expression) or a block with let/const when you need a one-off scope to avoid polluting the surrounding scope.

## Key Terms

- **scope**: The region of the program where a variable or binding is visible. A variable declared in a function is in that function's scope; a variable declared in a block is in that block's scope.
- **lexical scope**: Scope is determined by the structure of the source code (where the declaration appears, which blocks or functions contain it), not by when or where the code runs. Inner scopes can see outer scopes; outer scopes cannot see inner scopes.
- **block scope**: A scope created by a block (curly braces). Variables declared with let or const inside a block are visible only inside that block. Useful in loops, conditionals, or to hide temporary variables.
- **closure**: A function that "closes over" or retains access to variables from an outer scope where it was defined, even after that outer scope has finished executing. The function plus its captured environment together form a closure.
- **IIFE**: Immediately Invoked Function Expression. A function expression that is defined and called in one go, creating a one-off scope. Historically used to avoid polluting the global scope; in modern code, blocks with let/const or modules often replace it.

When you reference a variable inside a function, the engine looks for it in that function's scope, then in the enclosing scope, and so on until the global scope. That lookup is fixed by where the function was defined (lexically), not by where it is called. So a function defined at the top level can only see global variables and its own parameters and locals; a function defined inside another function can see the outer function's variables too.

## 1) Lexical Scope

Scope in JavaScript is lexical: it is determined by where the code is written in the source, not by where the function is called. When you declare a variable with let, const, or var inside a function, that variable is in the function's scope. It is visible everywhere inside that function (including inside nested functions defined in the same function). It is not visible outside the function. When you declare a variable inside a block (curly braces) with let or const, the variable is visible only inside that block. So the "nesting" of your code—which function or block contains the declaration—determines where the variable can be used. Inner scopes can read variables from outer scopes. The opposite is not true: an outer scope cannot read variables declared inside an inner scope, because those variables do not exist until the inner scope runs and are not visible outside the block or function.

The global scope is the top-level scope: variables declared there (or that are implicitly global in non-strict mode) are visible everywhere, which is why they can cause naming collisions when scripts are combined. In a browser, the global scope is often the window object; in Node.js it is a different object. Reducing the number of globals makes it less likely that your code will conflict with libraries or other scripts. Prefer modules or an IIFE to keep most variables out of the global scope. Function scope: a variable declared with var inside a function is visible throughout the entire function (var is function-scoped, not block-scoped). Block scope: a variable declared with let or const inside a block (e.g. inside an if or for) is visible only inside that block. So prefer let and const so that variables are limited to the smallest scope they need; that reduces bugs and makes it clear where a variable is used. Two functions defined in the same scope cannot see each other's local variables; they can only see shared outer scope. That is why passing arguments or returning values is how functions communicate—they do not share inner scope. For a homestead example: a variable sensorId declared at the top of a function that fetches a reading is visible in the whole function; a variable temp declared inside an if block that checks the reading is visible only in that block, so you can reuse the name temp in another block if needed without conflict. A helper function defined inside getBatteryReading can see the parameters of getBatteryReading but not the locals of another helper defined in the same function; they are siblings in the same scope.

## 2) Block Scope

A block is a pair of curly braces. Variables declared with let or const inside a block exist only inside that block. Once execution leaves the block, those variables are no longer in scope. That is block scope. Use it to limit the lifetime and visibility of variables. In a for loop, when you write for (let i = 0; i < n; i++), the variable i is block-scoped to the loop: it is visible only in the loop header and body. Each iteration gets its own binding for i (in the sense that a closure capturing i in the loop would see the value for that iteration). When you use var in a for loop, the variable is function-scoped (or global), so there is only one binding shared by all iterations; if you create a callback inside the loop that uses that variable, all callbacks may see the same final value. So in loops, prefer let so each iteration has its own loop variable. In an if or else block, you can declare let or const variables that are only needed for that branch; they do not leak into the rest of the function. You can also use a bare block { let x = computeSomething(); use(x); } to create a scope for a temporary variable x so the rest of the function does not see it. That keeps the scope small and avoids accidental reuse of the name.

For a homestead example: inside a function that processes zones, use a block to compute a temporary list of active zones and then use it; the temporary variable is not visible after the block. In a loop over sensors, use let so that a callback registered for each sensor (e.g. a click handler) captures the correct sensor id for that iteration. Block scope and lexical scope together tell you exactly where each variable is visible and for how long. If you use const in a for...of loop, each iteration gets a new binding for the loop variable (e.g. for (const id of ids)), so closures created inside the loop each capture a different id. That is the preferred pattern when you are creating one handler per item in a collection.

## 3) Closures

A closure is formed when a function retains access to variables from the scope where it was defined, even after that scope has finished running. When you define a function inside another function and return it (or pass it to someone else, or store it), the inner function "remembers" the variables of the outer function that were in scope at the time the inner function was created. So when the inner function is later called, it can read and update those variables. The inner function closes over the outer scope; that combination of function plus captured environment is a closure. You do not have to do anything special to create a closure—whenever a function uses a variable from an outer scope and that function outlives the outer scope (e.g. it is returned or stored), you have a closure. The closure "holds" a reference to the outer scope's environment, so the variables are not garbage-collected as long as the closure is reachable. That is why closing over large data can increase memory use: the data stays alive as long as the closure does. Closures are useful for factory functions: a function that takes some configuration (e.g. a zone id or a threshold) and returns a new function that uses that configuration when it runs. The returned function "remembers" the configuration because it closed over the parameter. They are also useful for private state: variables in the outer function are not directly accessible from outside, but the inner function can read and update them, so you can expose only the inner function and keep the state encapsulated.

For a homestead example: createZoneHandler(zoneId) that returns a function; when the returned function is called (e.g. on a button click), it uses zoneId from the outer scope to know which zone to start. Each call to createZoneHandler("zone1"), createZoneHandler("zone2") produces a different function, each with its own remembered zoneId. Another example: a function that returns a "get reading" function for a given sensor id; the returned function closes over the sensor id and can be passed to a UI component that will call it when it needs the latest value. Or a function that creates a debounced version of another function: it closes over the original function and a timer so that repeated calls are coalesced into one call after a delay. Closures are everywhere in JavaScript: event handlers, timers, array method callbacks, and factory functions all rely on the same mechanism. Closures are why the "function that returns a function" pattern from Chapter 3.07 works: the returned function retains access to the outer function's parameters and variables. Be aware that if you close over a variable that changes (e.g. a loop variable), the closure sees the current value when it runs, not the value at the time the closure was created—unless you use let in a loop, which gives each iteration its own binding so each closure captures the right value. Multiple closures can share the same outer variable; if one closure updates it, the other closures see the update when they run. That can be useful for shared state (e.g. a counter) or a source of bugs if you did not intend shared mutable state. When in doubt, close over parameters or const bindings so the captured value does not change.

## 4) IIFEs and One-Off Scope

An IIFE (immediately invoked function expression) is a function expression that is defined and called in the same statement. You write (function() { ... })(); the parentheses around the function make it an expression, and the trailing () invoke it. The function runs once and creates a scope: variables declared inside with var are in that function's scope, not in the global scope. So an IIFE was historically used to avoid adding variables to the global scope when you had a script that needed temporary variables or that wanted to keep a private helper. In modern JavaScript, you have better options: use a block with let or const to create a one-off scope, or use modules (each module has its own scope and exports only what it chooses). So you might see IIFEs in older code or in contexts where modules are not available; in new code, prefer a block { let x = ...; ... } or a module. When you do need a one-off scope and a block is enough (e.g. to hide a temporary variable), use the block. When you need to run a function once for its side effects and keep everything inside that function's scope, an IIFE still works. The idea is the same: limit visibility so that only the code that needs a variable can see it, and avoid polluting the outer scope. You can pass arguments into an IIFE: (function(config) { ... })(myConfig); that way the IIFE receives values from outside without closing over them, which can make dependencies explicit. For a homestead script that runs in a context without modules, an IIFE could wrap the whole script so that all variables are local to the IIFE and only one or two values are attached to the global object if needed. In a module or bundler environment, the file is already scoped, so an IIFE is usually unnecessary. Prefer blocks and modules; use IIFEs when you encounter legacy code or a non-module environment.

## 5) When to Use What

Use lexical scope to your advantage: put declarations in the smallest scope that needs them so that the rest of the code cannot accidentally use or overwrite them. Use block scope (let and const inside blocks) in loops so each iteration has its own binding; use block scope in if/else to keep branch-local variables from leaking; use a bare block when you need a temporary variable for a short computation. Use closures when you need a function to remember values from its creation context: factory functions that return configured handlers, callbacks that need to "capture" a value (e.g. zone id, sensor id), or helpers that maintain private state. Use an IIFE only when you need a one-off function scope and blocks or modules are not available; otherwise prefer a block with let/const or a module. When you need a "snapshot" of a value for each closure in a loop (e.g. each handler should see the value at the time the handler was created), capture it in a const inside the loop: for (const id of ids) { const currentId = id; handlers.push(() => use(currentId)); }. Then each closure has its own currentId. For homestead code: createZoneHandler(zoneId) returns a closure that remembers zoneId; loop over sensors with for (let id of ids) or for (const id of ids) and pass a callback that uses id so each callback gets the right id; use blocks to limit the scope of temporary variables in formatting or validation logic.

## 6) Homestead Examples: Scope and Closures in Practice

A factory createZoneHandler(zoneId) that returns a function; the returned function is the click handler and uses zoneId from the closure. Each zone button gets a handler created by passing that zone's id; the handler remembers its zone. A function that takes a threshold and returns a "check" function; the check function closes over the threshold and can be called with a reading to see if it is below threshold. That way you can create different checkers for different thresholds and pass them around. A loop over sensor ids with for (const id of ids) that registers a callback for each sensor; because id is block-scoped (and const in a for...of gives a fresh binding per iteration), each callback captures the correct id. If you had used var or a single shared variable, all callbacks might see the last id. A function that maintains a private counter (variable in the outer function) and returns an object with methods that increment or read the counter; the counter is not accessible from outside, but the methods close over it. A function that returns a "formatter" for a given unit (e.g. "V" or "°C"); the returned function closes over the unit and formats any number with that unit when called. That way you can create formatters once per unit and pass them to display logic. For retry logic, a function that takes maxAttempts and returns a "try once" wrapper; the wrapper closes over the attempt count so each call to the wrapper can increment and check the count. For config validation, use a block to hold temporary variables (e.g. the current key being validated) so they do not leak into the rest of the function. For a dashboard that attaches one handler per row, create the handler in a loop with let or for...of so each handler closes over the right row id or sensor. A "make checker" factory that takes a threshold and returns a function that takes a reading and returns true if the reading is below threshold; use it to create different checkers for battery, freezer, and soil without duplicating the comparison logic. A function that builds a list of zone handlers (one per zone) and returns them; each handler closes over its zone so when the user clicks, the right zone is started. Scope and closures tie together variables (3.02), functions (3.07), and the structure of your code so that data is visible only where it is needed and callbacks remember the right context. ## 7) What Breaks When Scope and Closures Are Wrong

If you use var in a for loop and create a callback inside the loop that uses the loop variable, all callbacks may see the same value (the value after the loop ends). Fix by using let in the for loop so each iteration has its own binding. If you close over a variable that you later reassign, the closure sees the updated value when it runs; that can be what you want, but if you expected a "snapshot" you need to capture the value in a new variable (e.g. const currentId = id) inside the loop so each closure gets its own copy. If you forget that outer scopes cannot see inner variables, you might try to use a variable from inside a block or function outside it and get a reference error. Fix by declaring the variable in a scope that includes both the place where it is set and the place where it is read. If you have a closure that holds a reference to a large object, that object cannot be garbage-collected as long as the closure is reachable; that can cause memory pressure if you create many closures each holding a large value. Be aware of what you close over. If you use an IIFE and expect to use variables from outside, remember the IIFE creates a new scope—you need to pass values in as parameters if the IIFE should use them, or the IIFE can read outer variables (it closes over them). So: use let in loops when creating callbacks, capture loop values in a local constant if you need a per-iteration snapshot, declare variables in the right scope, and be mindful of what closures retain. If you use a variable before it is declared (in the same block), let and const are in the "temporal dead zone" until the declaration runs, so you get a reference error. That encourages you to declare at the top of the scope or at least before use. Function declarations are hoisted, so you can call a function before the line where it is declared; the scope is still the function or script, but the binding exists from the start of the scope.

## 8) Checklist

When you work with scope and closures: (1) Prefer let and const so variables are block-scoped and limited to the smallest scope they need. (2) In for loops where you create callbacks or closures, use let (or for...of with const) so each iteration gets its own binding. (3) Use a closure when a function must remember values from its creation context (factory functions, handlers that need an id). (4) Keep closures minimal: close over only what is needed so you do not accidentally retain large data or stale references. (5) Use a block with let/const for one-off scope when you need to hide temporary variables; use an IIFE only when a function scope is required and modules are not available. (6) Remember that lexical scope is determined by where the code is written; inner functions see outer variables, not the other way around. (7) When creating many closures (e.g. one per row or sensor), close over only the identifier or small value needed so you do not retain large objects. ## Common Pitfalls

Loop variable in closure: Using var in a for loop and creating a callback that uses the loop variable—all callbacks see the final value. Use let (or for...of) so each iteration has its own binding.

Expecting a snapshot: A closure sees the current value of a variable when the closure runs, not when it was created. If the variable is reassigned, the closure sees the update. Capture in a local const inside the loop if you need a per-iteration value.

Outer scope cannot see inner: Variables declared inside a block or function are not visible outside. Declare in a scope that includes all uses, or return/pass the value out.

Closing over large data: A closure keeps references to everything it uses from the outer scope. If you close over a large object or array, it stays in memory as long as the closure is reachable. Close over only what you need.

IIFE when block would do: In modern code, a block with let/const is simpler than an IIFE for one-off scope. Use an IIFE only when you need function scope (e.g. for var) or when modules are not available.

Temporal dead zone: Using a let or const variable before its declaration in the same block throws. Declare at the top of the block or ensure you do not reference before declaration.

Shared mutable state in closures: Multiple closures that close over the same variable all see the same value; if one updates it, the others see the update. Intended for shared counters or caches; unintended when you expected independent copies.

## Summary

Lexical scope means visibility is determined by where the code is written: inner scopes see outer scopes, not vice versa. Block scope (let and const inside blocks) limits variables to the block. A closure is a function that retains access to variables from the scope where it was defined; use closures for factory functions, configured handlers, and private state. Use blocks or modules for encapsulation; use an IIFE only when you need a one-off function scope. Lexical scope and closures are the same mechanism: the function was defined in a scope, so it has access to that scope's variables whenever it runs.
