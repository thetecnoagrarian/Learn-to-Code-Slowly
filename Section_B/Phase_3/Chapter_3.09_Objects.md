# Section B Phase 3 · Chapter 3.09: Objects

This chapter covers object literals, properties, methods, spread, and destructuring. It builds on Chapter 3.08 (Scope and Closures): objects group related data and behavior, and methods are functions that receive the object as this when called. Chapter 3.10 (Arrays) then covers ordered collections that are a special kind of object. Objects are the main way you represent structured data (a sensor with id and reading, a zone with name and status) and key-value configuration; optional chaining and nullish coalescing from Chapter 3.04 work with object properties to handle missing keys safely. In earlier phases you saw key-value or dictionary-style data; in JavaScript, objects are the primary construct for that, with properties as keys and dot or bracket access for values.

## Learning Objectives

By the end of this chapter, you should be able to:
- Create objects with literals and access properties with dot notation and bracket notation.
- Add, update, and delete properties; use methods (functions as object properties) and understand how this is bound when methods are called.
- Use spread to copy or merge objects and to create updated copies immutably.
- Use destructuring to extract properties into variables and to assign defaults when a property is missing.

## Key Terms

- **object literal**: A value written as { key: value, ... }. Keys are strings (or symbols); values can be any type. The literal creates a new object each time it is evaluated.
- **property**: A key-value pair on an object. You read and write properties with dot notation (obj.key) or bracket notation (obj["key"] or obj[variable]).
- **method**: A function stored as a property. When you call it as obj.method(), the function receives the object as this inside the call.
- **spread (object)**: ...obj in an object literal copies the enumerable own properties of obj into the new object. Used for shallow copy and merge; later properties override earlier ones.
- **destructuring**: A syntax that extracts properties from an object into variables: const { a, b } = obj; assigns obj.a and obj.b to variables a and b. Supports defaults and renaming.

All keys are strings (or symbols); when you write a bare word as a key in a literal, it is coerced to a string. So { id: 1 } and { "id": 1 } are the same. The order of properties in an object is generally preserved for string keys in insertion order in modern JavaScript; when you iterate with for...in or Object.keys, the order matches the order in which properties were added (with some engine-specific rules for numeric-looking keys). That can matter when you build an object step by step or merge with spread.

## 1) Literals and Properties

An object literal is written with curly braces and a list of key-value pairs. Each key is followed by a colon and a value; pairs are separated by commas. Keys are strings. If the key is a valid identifier, you can omit quotes (e.g. name: "sensor1"); if the key contains a hyphen, a space, or starts with a number, you must use quotes (e.g. "sensor-id": 1). You can also use a computed property name with square brackets in the literal so the key is the result of an expression. The value can be any type: number, string, boolean, null, undefined, another object, an array, or a function. So an object can hold both data (properties) and behavior (methods, which are properties whose value is a function). Two object literals in the same scope create two distinct objects; they are equal only by reference (same object), not by content. So {} === {} is false. To compare by content you would need to compare each property or use a library. When you assign an object to a variable, the variable holds a reference to the object; assigning that variable to another variable copies the reference, not the object, so both variables point to the same object.

You access a property with dot notation: obj.key. That works when the key is a valid identifier. You access a property with bracket notation: obj["key"] or obj[variable]. Bracket notation is required when the key is not a valid identifier (e.g. "key-with-dash") or when the key is in a variable. So obj[key] uses the value of key as the property name. You can add a property by assigning: obj.newKey = value. You can update a property by assigning to an existing key. You can delete a property with delete obj.key; the property is removed. Setting obj.key = undefined leaves the property present with value undefined; delete removes the property. If you read a property that does not exist, you get undefined. So missing keys and explicitly set undefined both yield undefined when read; use optional chaining (obj?.key) and nullish coalescing (obj?.key ?? default) from Chapter 3.04 to handle missing or nullish values safely. When you iterate over an object's keys with for...in or Object.keys, you get only the object's own enumerable properties, not inherited ones; that is usually what you want for config or data objects. To copy only certain properties into a new object, you can build the object explicitly or use destructuring with rest and then build a new object from the rest; spread is simpler when you want most or all properties. For a homestead example: an object { id: "sensor1", reading: 12.3, unit: "V" } for a sensor; access with sensor.reading or sensor["unit"]; add a timestamp with sensor.timestamp = Date.now(). When the key comes from a variable (e.g. the name of a setting), use bracket notation: config[settingName]. You can check whether a property exists with "key" in obj (returns true or false); that is useful when you need to distinguish "missing" from "present with value undefined". To list all own enumerable keys, use Object.keys(obj); you get an array of key names that you can loop over with for...of (Chapter 3.06).

## 2) Methods and this

A method is a function that is a property of an object. You define it in the literal as key: function() { } or with the method shorthand: key() { }. When you call the method as obj.method(), the function runs with this set to obj. So inside the method you can use this to refer to the object and access other properties (e.g. this.reading, this.id). That is how methods get access to the object's data. If you call the function without the object context (e.g. assign the method to a variable and call it as fn()), this is undefined in strict mode or the global object in non-strict mode, so the method loses its connection to the object. To pass a method as a callback and keep the object as this, you can wrap it: () => obj.method() so that when the callback runs, it calls the method on the object. Or use bind (covered in later chapters) to create a function that has this fixed. Do not use an arrow function as an object method if the method needs this to refer to the object: arrow functions do not have their own this and inherit it from the enclosing scope, so this would not be the object. Use a regular function for methods. For a homestead example: an object that represents a zone with properties name and enabled and a method start() that uses this.name to know which zone to start; call as zone.start() so this is zone. If the object is created in a loop or factory, each object gets its own copy of the method (or they share the same function reference; in either case, when you call obj.method(), this is that object). Methods are still just functions; the only special thing is how this is set when the function is called as a method. You can assign a method to another variable and call it: const start = zone.start; start(); but then this is not zone (it is undefined in strict mode), so the method usually fails. Keeping the call as zone.start() preserves the receiver.

You can have multiple methods on the same object; they can call each other via this. Methods can read and update the object's properties; that is how objects encapsulate state and behavior together. When you pass an object to a function, the function receives a reference to the object, so if the function mutates the object's properties, the caller sees the changes. That is the same as in Chapter 3.07: objects are passed by reference. The method shorthand in object literals (key() { }) is equivalent to key: function() { } but is shorter and keeps the same this behavior. Use it when defining methods in literals. For a homestead example: an object that represents a drip zone with properties id, name, enabled and methods start() and stop() that use this.id to send commands; the UI holds a reference to the object and calls zone.start() when the user clicks.

## 3) Spread and Copying

The spread operator applied to an object in an object literal copies the enumerable own properties of that object into the new object. You write { ...obj }. The result is a new object with the same properties as obj (shallow copy). "Shallow" means only the top level is copied; if a property value is itself an object or array, the new object holds a reference to that same value, not a copy. So nested objects are shared between the original and the copy. You can merge objects by spreading multiple objects: { ...defaults, ...overrides }. Properties from later objects override earlier ones when keys match. So you can build a config object from defaults and then overlay user overrides. You can add or override a single property while copying: { ...obj, key: newValue }. That gives you a new object that is like obj but with key set to newValue; the original obj is unchanged. That pattern is useful for immutable updates: instead of mutating obj.key = newValue, you create a new object so that other code holding a reference to the old object is unaffected. For a homestead example: copy a sensor object to avoid mutating the original; merge default config with user config so user values win; update one property immutably when the reading changes so the UI can compare old and new. When you spread the same object twice in one literal (e.g. { ...obj, a: 1, ...obj }), the second spread overwrites the first for overlapping keys, so the result has a: 1 and then all of obj again; usually you spread once or spread different objects. To remove a property in an immutable way, you destructure to omit it: const { keyToRemove, ...rest } = obj; then rest is the object without that property.

Spread only copies enumerable own properties. It does not copy inherited properties or non-enumerable properties. So for a plain object created with a literal, spread copies what you see. For objects that have a prototype (e.g. from a class or constructor), only the object's own properties are copied. If you need a deep copy (nested objects and arrays also copied), you need a different approach (e.g. a library or a recursive function); shallow copy is the common case and is enough when you are not mutating nested values. The order of spread matters when keys overlap: { ...a, ...b } means properties from b override those from a for the same key. So put defaults first and overrides last. For a homestead config: { ...defaultConfig, ...userConfig } so user values win; then you can add one more override with { ...merged, threshold: 11 } if you need to force a value.

## 4) Destructuring

Destructuring extracts properties from an object into variables. You write const { a, b } = obj; that declares a and b and assigns them the values of obj.a and obj.b. You can give a default when the property is missing: const { a = 0 } = obj; so if obj.a is undefined, a is 0. You can rename: const { a: alias } = obj; so the property a is assigned to a variable named alias. You can combine: const { a: x = 0 } = obj; rename to x and default to 0. You can use rest in destructuring: const { a, ...rest } = obj; so a gets obj.a and rest is an object with all other own enumerable properties. That is useful when you want to pull out one or a few properties and keep the rest in another object. Destructuring works in function parameters: function f({ id, reading }) { } so the function expects an object and uses id and reading inside; you can add defaults for the whole parameter or for each property. For a homestead example: const { id, reading, unit } = sensor; then use id, reading, unit as variables. In a function that receives a config object, destructure the keys you need and give defaults: { threshold = 11, unit = "V" } so the function works even when the caller omits those keys. Destructuring is syntactic sugar for reading properties; it does not copy nested objects, so if you destructure an object property that is an object, you get a reference to that object.

You can destructure in assignment (not just declaration): ({ a, b } = obj); the parentheses are needed when the destructuring is not part of a declaration. You can nest: const { sensor: { reading } } = data; to get data.sensor.reading into reading. Use optional chaining in the source if the path might be missing: the destructuring pattern itself does not short-circuit, so if data.sensor is undefined, destructuring data.sensor.reading would throw; get the object first and then destructure, or use optional chaining when reading. You can provide a default for the whole destructured object in a function parameter: function f({ threshold = 11 } = {}) so that if the caller passes nothing, the parameter is {} and threshold is 11. That way the function works with no arguments, one argument, or an argument with some properties missing. When destructuring in a loop (e.g. for (const { id, reading } of sensors)), each iteration gets id and reading from that element; the element must be an object. If an element might be null or undefined, use optional chaining or a guard so you do not destructure null.

## 5) When to Use What

Use object literals when you need to group related data (a sensor with id, reading, unit) or to pass named options (config with threshold, unit). Use dot notation when the key is a fixed identifier; use bracket notation when the key is in a variable or is not a valid identifier. Use methods when the behavior belongs to the object and needs to use this to read or update the object; use regular functions (not arrows) for methods. Use spread to copy an object when you do not want to mutate the original, to merge defaults with overrides, or to create an updated copy with one or more properties changed. Use destructuring when you want to pull several properties into variables or when you want to declare function parameters that expect an object and use its properties by name. Use optional chaining (obj?.key) when the object or a path might be null or undefined; use nullish coalescing (obj?.key ?? default) when you want a default for missing or nullish values. When a function has more than two or three parameters, consider passing a single options object and destructuring it; that way callers can omit optional arguments and pass them by name, which is easier to read than positional arguments. For homestead code: sensor and zone objects with properties and methods; config objects merged with spread; destructuring in function parameters for options; optional chaining when reading from API or config. Use "key" in obj when you need to know whether a property exists (e.g. to skip undefined vs missing); use obj?.key ?? default when you just want a value to use.

## 6) Homestead Examples: Objects in Practice

A sensor object with id, reading, unit, and maybe timestamp; read with sensor.reading, update with sensor.reading = newValue. A zone object with name, enabled, and a start() method that uses this.name. A config object built from defaults and user overrides with spread: { ...defaultConfig, ...userConfig }. A function that takes an options object and destructures: { threshold = 11, unit = "V" } so the body uses threshold and unit. A reading object copied before sending to the UI so the original is not mutated: { ...reading, timestamp: Date.now() }. An object that holds formatters per unit: { V: formatVoltage, "°C": formatTemp }; access with formatters[unit] when unit is in a variable. A sensor summary built from several properties: destructure { id, reading, unit } from the sensor and build a string. A response or API result that is an object; use optional chaining to read nested keys (e.g. response?.data?.readings) and ?? for defaults. A lookup object that maps status codes or names to display strings or handlers: const statusLabels = { ok: "OK", low: "Low", unknown: "—" }; then statusLabels[status] ?? "—". An options object passed to a function that builds a dashboard: destructure { title, refreshInterval = 5000, sensors } and use them in the body. Freezer or coop state as an object with temp, minTemp, maxTemp, and a method checkAlarm() that uses this.temp and the thresholds. A single object holding multiple related formatters or validators keyed by type or unit. Objects tie together variables (3.02), types (3.03), operators (3.04), and functions (3.07) and scope (3.08): you store data in objects, pass them to functions, and use methods that close over or receive this. Chapter 3.10 (Arrays) covers ordered lists, which are objects with numeric indices and a length property and special methods for iteration and transformation.

## 7) What Breaks When Objects Are Wrong

If you use dot notation with a key that is in a variable, you get the wrong result: obj.key looks for the property named "key", not the value of the variable key. Use bracket notation obj[key] when the key is in a variable. If you mutate an object after passing it to a function, the caller sees the mutation; that can be intended or a bug. If you want to avoid side effects, copy the object first (e.g. with spread) or document that the function may mutate. If you use spread for a "copy" but then mutate a nested object, the original and the copy share that nested object, so both see the change. Fix by copying nested levels too when you need independence, or avoid mutating nested values. If you destructure a property that does not exist, you get undefined (or your default). If the property exists but is null or undefined, the default in destructuring is used only for undefined; null is not replaced by the default. Use nullish coalescing after destructuring if you want to treat null the same as undefined. If you use an arrow function as a method and refer to this, this is not the object. Fix by using a regular function for the method. If you call a method without the object context (e.g. pass it as a callback and call it later), this is lost. Fix by wrapping: () => obj.method() or by binding. So: use bracket notation for variable keys, be aware of shallow copy and mutation, use regular functions for methods, and preserve this when passing methods as callbacks. If you destructure and the right-hand side is null or undefined, you get an error; the destructuring source must be an object (or something that can be destructured). Guard with a default: const { a } = obj ?? {} so that if obj is null or undefined, you destructure an empty object and a is undefined (or use a default in the pattern). When building an object dynamically, make sure the key you set is the one you intend; using a typo or wrong variable as the key creates a property with the wrong name and leaves the one you wanted missing. If you use Object.keys or for...in and then mutate the object (add or delete properties) during the loop, behavior can be engine-dependent and confusing; prefer iterating over a snapshot of the keys (e.g. Object.keys(obj)) and not mutating obj inside that loop, or collect changes and apply them after.

## 8) Checklist

When you work with objects: (1) Use literals for structured data and options; use dot notation for fixed keys and bracket notation when the key is in a variable. (2) Use methods (regular functions) when the behavior needs this to refer to the object; do not use arrow functions for such methods. (3) Use spread to copy or merge; remember spread is shallow. (4) Use destructuring to extract properties and to declare function parameters that take an options object; use defaults in destructuring when properties may be missing. (5) Use optional chaining and nullish coalescing when reading paths that might be missing. (6) Prefer immutable updates ({ ...obj, key: value }) when you do not want to mutate the original. (7) Use "key" in obj to test for property existence when you need to distinguish missing from undefined. (8) Guard destructuring when the source might be null or undefined (e.g. obj ?? {}). Chapter 3.10 (Arrays) introduces array literals, length, and array methods that work with ordered data.

## Common Pitfalls

Dot vs bracket: obj.key uses the literal "key"; obj[variable] uses the value of variable. Use bracket notation when the key is in a variable.

Arrow function as method: Arrow functions do not have their own this. Use a regular function so this is the object when the method is called.

Shallow copy: Spread copies only the top level. Nested objects are shared; mutating them affects both the original and the copy.

Losing this when passing method: If you pass obj.method as a callback, the receiver calls it without the object, so this is wrong. Wrap: () => obj.method() or use bind.

Destructuring default and null: Defaults in destructuring apply when the property is undefined, not when it is null. Use ?? after destructuring if you want to treat null as missing.

Destructuring null/undefined source: Destructuring null or undefined throws. Use a default for the source: obj ?? {}.

Mutating object while iterating: Adding or deleting properties while iterating with for...in or Object.keys can lead to unpredictable behavior. Iterate over a copy of the keys or apply changes after the loop.

## Summary

Objects group data and behavior with literals, properties, and methods. Use dot and bracket notation for access; use spread for shallow copy and merge and for immutable updates; use destructuring to extract properties and to define options parameters. Methods need regular functions so this is the object; use optional chaining and nullish coalescing for safe access. Prefer options objects and destructuring for functions with many parameters, and guard destructuring when the source might be null or undefined.
