# Section B Phase 3 · Chapter 3.13: Async — Callbacks and Promises

This chapter covers the event loop, callbacks, and Promises: how JavaScript schedules work that finishes later (I/O, timers, network) without blocking the single thread, how callbacks report completion or failure, and how Promises represent an eventual value or rejection so you can chain .then, .catch, and .finally. It builds on Chapter 3.12 (Error Handling): rejections are the async form of thrown errors, and you handle them with .catch or with try/catch around await in Chapter 3.14. Understanding callbacks and Promises gives you the foundation for async/await and for writing reliable homestead dashboards that fetch sensor data, start zones, or run timers without freezing the UI.

## Learning Objectives

By the end of this chapter, you should be able to:
- Explain that JavaScript is single-threaded and that async work is scheduled via the event loop; long or I/O work is offloaded or deferred, and callbacks run when that work completes.
- Use callbacks for async completion (e.g. Node-style err-first (err, data)); recognize how nested callbacks become hard to read and maintain (callback hell).
- Create and consume Promises: new Promise with resolve and reject; .then, .catch, .finally; chain multiple .then steps and handle rejections in one .catch.
- Use Promise.all to wait for all of several promises and Promise.race to react to the first that settles (fulfill or reject).

## Key Terms

- **event loop**: The mechanism that runs JavaScript. One thread executes your code; when an async operation (timer, network, file) is started, it is handed off. When it completes, a callback (or promise reaction) is queued and run by the event loop. So the main thread is never blocked by waiting; it keeps processing other work until the callback runs.
- **callback**: A function you pass to another function to be invoked when an operation completes (or fails). In Node-style APIs the convention is (err, data): if err is truthy, the operation failed; otherwise data holds the result. Callbacks are the older pattern for async; Promises and async/await build on or replace them.
- **Promise**: An object representing the eventual result of an async operation. A promise is in one of three states: pending (not yet settled), fulfilled (success, with a value), or rejected (failure, with a reason). You cannot read the value directly; you register handlers with .then, .catch, and .finally, which run when the promise settles.
- **then, catch, finally**: .then(onFulfilled, onRejected?) runs when the promise fulfills (and optionally when it rejects). .catch(onRejected) is shorthand for .then(null, onRejected). .finally(cleanup) runs when the promise settles (fulfill or reject) and is used for cleanup (e.g. hiding a loading spinner). Each of these methods returns a new promise, so you can chain.
- **Promise.all**: A static method that takes an array (or iterable) of promises and returns a promise that fulfills with an array of results when all input promises fulfill, or rejects with the first rejection. Use it to run several async operations in parallel and wait for all of them.
- **Promise.race**: A static method that takes an array of promises and returns a promise that settles (fulfill or reject) when the first input promise settles. Use it for timeouts (race a real operation against a timer) or to take the first of several sources.

## 1) Event Loop and Callbacks

JavaScript runs in a single thread. Only one piece of your code runs at a time. When you start work that takes time—a network request, reading a file, or a timer—that work is not done by your thread; the engine or the environment (browser, Node) performs it. When it finishes, the environment queues a callback (or a promise reaction), and the event loop eventually runs it. So your code does not sit and wait; it continues, and later the callback runs with the result or an error. That is why async APIs take a callback or return a promise: they cannot return the result immediately. If they blocked until the result was ready, the whole program would freeze; no clicks, no timers, no other requests. So the design is: start the operation, pass a function that will be called when it completes, and keep going. The callback runs in the same thread as the rest of your code, so you still do not have two pieces of your script running at once; you just have work scheduled for later. Timers (setTimeout, setInterval), network requests (fetch, XMLHttpRequest), and file or database access in Node are all implemented this way: your code registers interest in a result, and when the system has it, your callback is queued and run. That is why you cannot assign the result of a fetch to a variable and use it on the next line; the result is not there yet. You must use the value inside the callback or inside a .then that runs when the promise fulfills.

The classic async pattern is the callback. You call a function that starts an operation and pass a function that will be invoked with the result. In Node.js and many Node-style APIs, the convention is err-first: the callback receives (err, data). If the operation failed, err is an error object (or truthy value) and data may be undefined. If it succeeded, err is null or undefined and data holds the result. So inside the callback you first check err: if (err) { handle error; return; } then use data. That way you handle both success and failure in one place. The downside of callbacks appears when you need to do several async steps in sequence: get the config, then get a reading, then update the UI. You end up calling the next step inside the callback of the previous one. Each step adds a level of nesting. Three or four steps produce deeply nested code that is hard to read and to maintain. That structure is often called callback hell. Promises (and later async/await) were introduced to flatten this: you chain .then steps or use await in a linear-looking way, so the flow is easier to follow and errors can be handled in one .catch or try/catch. For a homestead example: reading config from a file might use a callback (err, config); inside the callback you check err and if there is none you might then fetch a sensor reading, again with a callback. The nesting grows with each async step. Understanding the event loop and callbacks explains why your code does not block and why many older APIs pass a function to be called when the work is done. When you read Node or browser documentation and see "callback" or "callback-based," that means the function you pass will be invoked later, possibly with an error and a result. Designing your own callback-based API is rare in new code; returning a promise is preferred so callers can chain and await. But you will still call into callback-based APIs (Node fs, some database drivers, legacy code), so recognizing the pattern and knowing how to promisify it or nest it carefully is useful.

## 2) Promises — then, catch, finally

A Promise is an object that represents a value (or a rejection) that will be available in the future. You do not read the value synchronously; you call .then and pass a function that will receive the value when the promise fulfills. .then(onFulfilled) returns a new promise: that new promise resolves with the return value of onFulfilled, or rejects if onFulfilled throws. So you can chain: firstPromise.then(result => process(result)).then(nextResult => use(nextResult)). Each .then produces another promise, so the chain can continue. If any step throws or returns a rejected promise, the rest of the chain is skipped until a .catch is reached. .catch(onRejected) is equivalent to .then(null, onRejected): it runs when the promise rejects and receives the rejection reason (often an Error). After .catch, you can still chain .then if the catch handler does not rethrow; the chain continues from the value returned by the catch. So a typical pattern is: start an async operation (e.g. fetch), then .then to parse or transform the result, then .then to use it, and a single .catch at the end to handle any rejection in the chain. Rejections propagate down the chain until a handler catches them; if none does, you get an unhandled rejection (which can log a warning or terminate the process in some environments). .finally(cleanup) registers a function that runs when the promise settles, whether it fulfilled or rejected. It is for side effects that must run in both cases: hide a loading spinner, close a connection, or reset state. .finally does not change the outcome: it passes through the fulfillment value or the rejection. So the full pattern is: promise.then(handleSuccess).catch(handleError).finally(cleanup). In a homestead dashboard you might fetch a list of zones, then .then to parse JSON, then .then to render the list, and .catch to show "Failed to load zones" and log the error; .finally to hide the loading indicator. Chapter 3.12 already established that you must handle rejections; this chapter gives you the tools to structure the chain so one .catch can handle errors from any step. You can pass two functions to .then: .then(onFulfilled, onRejected). The second runs when the promise rejects; it is equivalent to .then(onFulfilled).catch(onRejected) for that step only. Usually a single .catch at the end of the chain is clearer so all errors are handled in one place. If you return a value from .catch, the next .then in the chain receives that value and the chain continues as if the rejection was "recovered"; if you rethrow (throw e) inside .catch, the chain rejects again and a later .catch can handle it. So you can use .catch to log and rethrow, or to return a default value and continue.

## 3) Creating Promises

You create a new promise with new Promise(executor). The executor is a function that receives two arguments, conventionally named resolve and reject. When the async work completes successfully, you call resolve(value); when it fails, you call reject(reason). The promise transitions from pending to fulfilled or rejected; once settled, it cannot change. You typically wrap a callback-based API: inside the executor you start the operation and in its callback you call resolve(data) or reject(err). So the caller gets a promise and uses .then and .catch instead of passing a callback. You can also wrap a value that is already known: Promise.resolve(x) creates a promise that is already fulfilled with x; Promise.reject(e) creates one that is already rejected with e. That is useful when you need to return a promise from a function that sometimes has the value immediately (return Promise.resolve(cached)) or when you want to start a chain with a rejection (Promise.reject(new Error("invalid"))). Many environments and libraries provide a promisify utility that turns a Node-style (err, data) callback API into a function that returns a promise; use that when available instead of writing the wrapper by hand. When you do write an executor, be careful to call resolve or reject only once; calling both or calling one twice has no effect after the first settlement, but the code can be confusing. Also, if you throw inside the executor (before any async work), the promise will reject with that thrown value; so you can validate arguments at the start and reject by throwing. For a homestead example: you might wrap "read config file" in a promise: inside the executor you call the file API with a callback that calls resolve(config) or reject(err). The rest of your code then uses that promise with .then and .catch instead of nesting callbacks. If the API can throw synchronously (e.g. invalid arguments), that throw will reject the promise because the executor runs immediately when the promise is constructed. So the promise can reject either from an explicit reject(err) in the callback or from a synchronous throw in the executor. Callers only need to .catch once to handle both. When you use Promise.resolve or Promise.reject, you are creating an already-settled promise; that is useful in tests (e.g. mock a function that returns Promise.resolve(mockData)) or when a function sometimes has a value in hand and sometimes needs to do async work—return Promise.resolve(value) in the synchronous case so the caller always gets a promise and can .then or await uniformly.

## 4) Promise.all and Promise.race

When you need to run several async operations and wait for all of them, use Promise.all([p1, p2, p3]). It returns a promise that fulfills with an array of results in the same order as the input promises when every input fulfills. If any input promise rejects, Promise.all rejects immediately with that rejection reason; the other operations may still be running but their results are ignored. So Promise.all is "wait for all, fail fast on first error." Use it when you need several independent results before proceeding: for example fetch readings for multiple sensors in parallel, then display all of them, or fetch zone list and config in parallel, then combine them. That is faster than doing them one after the other. When you want to react as soon as the first of several operations completes, use Promise.race([p1, p2, ...]). The returned promise settles (fulfill or reject) when the first input promise settles, with that result or reason. The other promises keep running but their outcomes are ignored. A common use is a timeout: race your real operation (e.g. fetch) against a promise that rejects after a delay (e.g. new Promise((_, reject) => setTimeout(() => reject(new Error("timeout")), 5000))). If the fetch wins, you get the data; if the timer wins, you get a timeout error. Another use is "first response wins": for example race requests to several mirrors or fallback endpoints. For a homestead dashboard you might use Promise.all to fetch temperatures for freezer, coop, and barn in parallel and then render all three; or use Promise.race to enforce a maximum wait time for a zone-start request so the UI does not hang if the server is slow. Promise.allSettled (if available in your environment) is a variant that waits for all promises to settle and gives you an array of status objects (fulfilled or rejected) so you can see which succeeded and which failed instead of failing the whole batch on first rejection; that is useful when you want to try all sensors and show which are unavailable. Promise.all and Promise.race both take iterables (e.g. arrays); if you pass an empty array to Promise.all, it fulfills immediately with an empty array; if you pass an empty array to Promise.race, the returned promise never settles because no input ever does. So when building the array dynamically (e.g. from a list of sensor ids), ensure the list is not empty if you need the race to settle, or handle the empty case before calling Promise.race.

## 5) When to Use What

Use callbacks when you are calling an API that only supports callbacks (many Node built-in modules and older libraries). Follow the err-first convention: check err first, then use data. If you need to sequence several callback-based operations, consider wrapping each in a promise (or using a promisify helper) so you can chain .then instead of nesting callbacks. Use promises when you have or can get a promise-returning API: fetch in the browser, many modern libraries, or your own wrapped code. Prefer .then and .catch for a clear chain: one or more .then for the happy path and a single .catch for errors. Use .finally for cleanup that must run whether the promise fulfills or rejects. Use Promise.all when you have several independent async tasks and need all results before continuing; use Promise.race when you need the first result (or a timeout). When you create async behavior yourself, prefer returning a promise from your function so callers can chain or await; that is easier to compose than passing callbacks through. If you wrap a callback API in a promise, call resolve or reject exactly once from the callback and handle both success and error cases. Do not leave promise chains without a .catch (or a try/catch when you use async/await in Chapter 3.14); unhandled rejections are a common source of silent failures. For a homestead app: use promises for fetch (sensor data, zone control); use Promise.all to load multiple readings or config and zone list in parallel; use Promise.race with a timeout when calling a slow or unreliable endpoint so the UI can show "timed out" instead of hanging.

## 6) Homestead Examples

Fetching sensor readings: the dashboard calls an API that returns a promise (e.g. fetch then .then(r => r.json())). You chain .then to extract the reading and update the UI, and .catch to show "Sensor unavailable" and log the error. No callback nesting; one linear chain. Loading config and zones in parallel: Promise.all([fetchConfig(), fetchZones()]).then(([config, zones]) => { use both to render the page }).catch(e => showError(e.message)). You get both results before rendering; if either request fails, the catch runs. Starting a zone with a timeout: Promise.race([startZone(id), timeout(5000)]).then(result => { if result is from startZone, show success; else treat as timeout }).catch(e => show("Could not start zone")). The timeout promise rejects after five seconds so the user is not left waiting forever. Reading a config file in Node: if the API is callback-based, wrap it in a promise so the rest of your startup code can do await loadConfig() or loadConfig().then(config => ...). Inside the wrapper you call the file API and in its callback you call resolve(config) or reject(err). A simple timer for a coop door: setTimeout is callback-based; you can wrap it in a promise (new Promise(resolve => setTimeout(resolve, ms)) then .then(() => runNextStep())) so you can chain "wait N seconds then do X" without nesting. Displaying a loading state: before the fetch you set loading true; in .finally you set loading false so the spinner hides whether the request succeeded or failed. Fetching multiple sensors for a summary: Promise.all(sensorIds.map(id => fetchReading(id))) gives you an array of readings in order; .then to compute an average or show all; .catch to show "Some sensors failed" and optionally log which ones. Each of these patterns avoids callback hell and centralizes error handling in .catch. If one sensor fails, Promise.all rejects and you do not get the others; if you need partial results (e.g. show readings for all that succeeded and "unavailable" for the rest), use Promise.allSettled and then map over the results to separate fulfilled and rejected, or fetch each sensor in a loop and push successes and errors into separate arrays. For a coop door timer: wrap setTimeout in a promise so you can do "wait 30 seconds then close the door" with a single .then instead of a nested callback; that keeps the sequence readable when you add more steps (e.g. log, then wait, then close, then notify).

## 7) What Breaks When Async or Promises Are Wrong

If you forget to handle rejections—no .catch on a chain and no try/catch around await—you get unhandled rejections. The promise fails and nothing in your code runs to log or show the error; the environment may log a warning or exit. Always add .catch or handle the promise in a caller that uses try/catch. If you nest callbacks deeply instead of chaining promises, the code becomes hard to read and to change; refactor to promises (or async/await) so the flow is linear. If you call resolve or reject more than once in an executor, only the first call matters; the rest are ignored, but doing it by mistake can mask bugs. If you use Promise.all and one promise rejects, the whole result is rejected and you do not get partial results; if you need "try all and see which failed," use Promise.allSettled or handle each promise separately. If you use Promise.race for a timeout but the losing promises keep running, remember they still consume resources (e.g. the fetch continues); race only ignores their outcome. If you throw inside a .then handler instead of returning a rejected promise, the next .catch will still receive it; but if you forget to return a value from .then, the next .then receives undefined. If you mix callbacks and promises (e.g. pass a callback to a function that also returns a promise), you may get duplicate handling or confusing behavior; pick one style per API. If you do long synchronous work inside a .then (e.g. a heavy loop), you block the event loop and the UI or server stalls; offload or break up the work. If you create a promise and never call resolve or reject (e.g. you forget to call them in a callback), the promise stays pending forever and any .then never runs; ensure every path in your executor leads to resolve or reject. So: always handle rejections, prefer chaining over nesting, call resolve/reject once, and use Promise.all or Promise.race for the right pattern (all results vs first or timeout).

## 8) Checklist

When you work with async code and promises: (1) Understand that the event loop runs one thing at a time; async work is scheduled and callbacks or promise handlers run when it completes. (2) Use callbacks for APIs that require them; follow err-first (err, data) and check err first. (3) Prefer promises when available; chain .then for steps and .catch for errors. (4) Add .finally for cleanup (e.g. hide loading) that must run on success or failure. (5) Create promises with new Promise(resolve, reject) and call resolve or reject exactly once from the async path. (6) Use Promise.all to wait for several promises and get all results; use Promise.race for first result or timeout. (7) Never leave a promise chain without .catch (or equivalent handling). (8) Avoid deep callback nesting; wrap in promises or use async/await. (9) For timeouts, race the real operation against a timer promise. (10) In homestead code, use promises for fetch and parallel loads (Promise.all) so the UI stays responsive and errors are handled in one place. Chapter 3.14 (Async — async/await) will let you write the same logic with await and try/catch for a more linear style.

## Common Pitfalls

Unhandled rejection: A promise rejects and no .catch or try/catch handles it. Add .catch to the chain or handle the returned promise in the caller.

Callback hell: Nesting callbacks for sequential async steps. Refactor to promises (or async/await) and chain .then so the flow is readable.

Calling resolve/reject twice: Only the first call settles the promise. Ensure only one path runs (e.g. in a callback, call resolve(data) in success branch and reject(err) in error branch).

Forgetting to return from .then: If the next .then needs the result of a computation, return it from the previous .then; otherwise the next step receives undefined.

Using Promise.race for "first success": Promise.race settles when the first promise settles; if the first one rejects, the race rejects. For "first successful result" you need a pattern that ignores rejections until one fulfills (or use a library).

Blocking the event loop in a handler: Doing heavy synchronous work inside .then blocks the thread. Keep handlers short or defer work (e.g. setTimeout, worker, or chunking).

Mixing callbacks and promises: Using both a callback and the returned promise for the same operation can double-invoke or confuse flow. Stick to one style per function.

## Summary

JavaScript is single-threaded; the event loop runs your code and runs callbacks or promise handlers when async work completes. Callbacks use the err-first (err, data) pattern; nesting them leads to hard-to-read code. Promises represent an eventual value or rejection: use .then for the next step, .catch for errors, .finally for cleanup. Chain promises for a linear flow; handle rejections so you do not get unhandled rejections. Create promises with new Promise(resolve, reject) and call resolve or reject once. Use Promise.all to wait for all of several promises; use Promise.race for the first to settle (e.g. timeouts). Homestead dashboards use promises for fetch, Promise.all for parallel loads, and .catch to show and log errors. Chapter 3.14 (Async — async/await) builds on this by letting you write async code with await and try/catch for a more readable style.
