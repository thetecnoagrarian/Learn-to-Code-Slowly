# Section B Phase 3 · Chapter 3.14: Async — async/await

This chapter covers the async and await keywords: how to declare async functions that always return a promise, how await pauses the function until a promise settles and gives you the value, and how to handle errors with try/catch so that rejections become thrown exceptions. It builds on Chapter 3.13 (Async — Callbacks and Promises): await consumes promises; the same promise chains and rejection semantics apply, but the code reads in a linear, synchronous-looking style. You will see when to run independent awaits in parallel with Promise.all versus one after another, and when to prefer async/await over raw .then. Chapter 3.15 (Modules) then introduces how to organize code into files and import/export; async functions and modules work together when you load config or fetch data at startup.

## Learning Objectives

By the end of this chapter, you should be able to:
- Declare async functions and use await to wait for a promise; understand that an async function always returns a promise (fulfilled with the return value or rejected if the function throws).
- Handle errors with try/catch around await; a rejected promise becomes a thrown exception that catch receives; use finally for cleanup.
- Run independent async operations in parallel with Promise.all and await the result, or run them sequentially by awaiting one after another when the next step depends on the previous.
- Prefer async/await over raw .then when the flow is linear and readability matters; use .then when composing or when you need fine-grained control.

## Key Terms

- **async function**: A function declared with the async keyword. When called, it returns a promise. If the function returns a value, that promise fulfills with that value; if the function throws (or an awaited promise rejects and is not caught), the returned promise rejects. Inside an async function you can use await.
- **await**: An operator used inside an async function (or at top level in a module in modern environments). await promise pauses the function until the promise settles. If it fulfills, the expression evaluates to the fulfillment value; if it rejects, the rejection is thrown as an exception and can be caught by try/catch in that function. If you await a non-promise value, it is used as-is with no wait.
- **sequential await**: Awaiting one async operation, then awaiting the next on the following line. The second does not start until the first completes. Use when the next step needs the result of the previous (e.g. get config then use config to fetch data).
- **parallel await**: Starting several async operations without awaiting them immediately, then awaiting Promise.all([...]) so they run in parallel and you get all results. Use when operations do not depend on each other (e.g. fetch several sensors at once).

- **top-level await**: In ES modules, await can be used at the top level of a module (not inside a function). The module load is then asynchronous; the runtime waits for that await to settle before the module is considered loaded. Not all environments support it; in scripts or older setups you must wrap await in an async function and call it.

## 1) async and await

An async function is declared by placing the async keyword before the function keyword (or before the parameter list in an arrow function). When you call an async function, it returns a promise immediately; that promise is not the final value but the promise that will settle when the function completes. If the function returns a normal value, the returned promise fulfills with that value (as if you had returned Promise.resolve(value)). If the function throws an error—either by an explicit throw or because an awaited promise rejected and the rejection was not caught—the returned promise rejects with that error. So from the caller's perspective, an async function is a function that returns a promise; you can .then or .catch that promise, or you can await it from another async function.

Inside an async function you can use await. await is followed by an expression that is usually a promise. When execution hits await promise, the function pauses: it does not block the rest of the program, but no further code in that function runs until the promise settles. When the promise fulfills, the await expression evaluates to the fulfillment value and execution continues. When the promise rejects, the rejection is turned into a thrown exception in that function; if there is a try/catch around the await, the catch runs; if not, the exception propagates and the promise returned by the async function rejects. So await gives you synchronous-looking code: you write "get the value, then use it" in order, and the engine handles the waiting. You can only use await inside an async function (or at the top level of an ES module in environments that support top-level await). If you try to use await in a normal function, you get a syntax error. For a homestead example: an async function that loads the dashboard might await fetch(configUrl), then await the response's .json(), then await a second fetch for zones using the config; each line runs after the previous completes, so the code reads in order. The caller of that function gets a promise and can await it or .then it.

If you await something that is not a promise (e.g. a number or a plain object), the engine treats it as an already-fulfilled promise and continues immediately with that value. That is useful when a function sometimes returns a value and sometimes returns a promise: the caller can always await, and either gets the value right away or waits for the promise. So you do not need to wrap synchronous results in Promise.resolve when using await; the language does that for you. Arrow functions can be async too: const load = async () => { const data = await fetch(url); return data; }; the same rules apply—load returns a promise, and inside it await pauses until fetch's promise settles. When you have multiple async functions calling each other, each can await the other; the chain of promises propagates until the top-level caller awaits or attaches .catch. So you can structure your app as many small async functions that await each other, with one top-level entry (e.g. main() or an event handler) that awaits the top function and uses try/catch to handle any failure along the way.

## 2) Error Handling with try/catch and finally

Because await turns a rejection into a thrown exception, you can use the same try/catch/finally pattern from Chapter 3.12 for async code. Wrap the awaited call in try: try { const data = await fetchAndParse(url); use(data); } catch (e) { showError(e.message); }. If the promise returned by fetchAndParse fulfills, data is set and use(data) runs. If it rejects, the catch block runs with the rejection reason (usually an Error). So you handle async errors exactly like synchronous ones: one try, one catch, and optionally finally for cleanup. If you do not catch, the exception propagates: the async function throws, so the promise it returned rejects, and the caller must handle that (with .catch or another try/await). So unhandled rejections inside an async function become rejected promises that propagate to whoever called the function; they do not disappear. Always ensure that either you catch inside the async function or the caller handles the returned promise.

Use finally when you need to run cleanup whether the try succeeded or the catch ran: hide a loading spinner, close a connection, or reset state. The same rules as in Chapter 3.12 apply: do not return or throw from finally if you can avoid it, because that can override the result of try or catch. You can rethrow in catch (throw e;) so the caller of the async function still sees the rejection; that is useful when you log or show a message in catch but want the error to propagate so a higher-level handler can also react. You can also return a fallback value from catch so the rest of the function continues with that value instead of failing; then the async function's returned promise fulfills with whatever the function eventually returns. Choose based on the contract you want: either the function reports failure by rejecting (and the caller must handle it) or it recovers and returns a value (e.g. null or a default) so the caller gets a fulfilled promise. Mixing both in the same function (sometimes rethrowing, sometimes returning) can be confusing; prefer one strategy per function. For a homestead example: before fetching sensor data you set loading true; in a try you await fetchReading(sensorId) and update the UI; in catch you show "Sensor unavailable" and log the error; in finally you set loading false. The spinner is hidden whether the request succeeded or failed. You can have multiple await calls in one try; the first rejection jumps to catch. If you want to handle errors per step (e.g. try sensor A, catch and log, then try sensor B), put each await in its own try/catch or use separate async helpers and combine the results.

## 3) Sequential vs Parallel

When you write two await lines in a row, the second does not start until the first has settled. That is sequential execution: first await getConfig(), then await fetchZones(config.apiUrl). You need that when the second call depends on the first (e.g. you need the config to know the API URL). Sequential is the default when you just list awaits one after another.

When you have several independent operations—fetch reading for sensor 1, sensor 2, and sensor 3—you do not need to wait for one to finish before starting the next. If you write const a = await getA(); const b = await getB(); const c = await getC(); then getB does not start until getA completes, and getC waits for getB. That is slower than necessary if getA, getB, and getC do not depend on each other. To run them in parallel, start all of them (without awaiting yet), then await Promise.all: const [a, b, c] = await Promise.all([getA(), getB(), getC()]). The three calls start immediately; Promise.all returns a promise that fulfills with an array of results when all fulfill, or rejects when the first rejects. So you get the same results, but in the time of the slowest call instead of the sum of all three. Use parallel when the operations are independent; use sequential when one step needs the result of the previous. For a homestead dashboard: loading config and then zones that depend on config is sequential; loading readings for freezer, coop, and barn in one screen is parallel—await Promise.all([fetchReading('freezer'), fetchReading('coop'), fetchReading('barn')]) then render all three. If you await in a loop (for (const id of ids) { results.push(await fetch(id)); }), each iteration waits for the previous; that is sequential. To do the same work in parallel, use Promise.all(ids.map(id => fetch(id))) then await that. Sometimes you need a mix: run the first step, then based on its result run several steps in parallel. For example: const config = await loadConfig(); const [zones, readings] = await Promise.all([fetchZones(config), fetchReadings(config.sensorIds)]); the first await is sequential (you need config), then the two fetches run in parallel because they only depend on config. So you can combine sequential and parallel in one async function by ordering your awaits and grouping independent ones in Promise.all.

## 4) When to Use async/await vs .then

Prefer async/await when the flow is linear: do A, then B, then C, with error handling in one try/catch. The code reads like synchronous code and is easier to follow. Use .then when you are composing small steps (e.g. returning a chain from a function), when you need to return a promise without awaiting it (e.g. fire-and-forget with .catch), or when you are inside a callback that is not an async function and you want to chain one or two steps. You can mix: an async function can await a promise that was built with .then, and you can .then the result of calling an async function. The important rule is to always handle rejections: either try/catch around await or .catch on the promise. Do not leave the promise returned by an async function unhandled.

Avoid using await inside a loop when the iterations are independent. A for loop with await in the body runs one iteration at a time; use Promise.all with a map instead so all operations run at once. When you need the first of several results (or a timeout), use Promise.race and await that; Chapter 3.13 covered race. When you have a value that might be a promise or might be plain, awaiting it is safe: if it is a promise you wait; if it is not, you get the value immediately. So conditional async (e.g. if (useCache) return cached; else return fetch(...)) works well with await at the caller: they always await and get either the cached value or the fetched one. When you call an async function without await (e.g. startRefresh() instead of await startRefresh()), you start the operation but do not wait for it; the function runs in the background and its returned promise settles later. That is useful for fire-and-forget (e.g. log an event to the server without blocking the UI), but then you must attach .catch to the returned promise so rejections are not unhandled. So either await the call (and handle in try/catch) or assign the return value and add .catch(...) to it; do not ignore the promise.

## 5) When to Use What

Use async/await for the main flow of an app or a feature: load data, validate, update UI, handle errors in one place. Use sequential await when step B needs the result of step A. Use Promise.all and await when you have several independent async operations and need all results before continuing. Use try/catch around the whole sequence so one catch handles any failure; use finally for cleanup (loading state, closing resources). Use .then when you are inside a non-async callback and need one or two steps (e.g. fetch(url).then(r => r.json()).then(data => use(data)).catch(...)), or when you explicitly want to return a promise for the caller to chain. When you write a function that does async work, making it async and using await inside is usually the clearest; the function returns a promise so callers can await it or .then it. For a homestead app: make your "load dashboard" or "refresh readings" logic an async function; await fetch and parse; use Promise.all to load multiple sensors or zones in parallel; wrap in try/catch to show errors and use finally to clear loading state. When calling an API that returns a promise, await it in an async function unless you specifically want to start the operation and attach .then/.catch without waiting in that function. In environments that support top-level await (e.g. ES modules in modern browsers or Node), you can use await at the top level of a module without wrapping it in an async function; the module load becomes async and the module system waits for the top-level await to settle before considering the module loaded. That is useful for initialization (e.g. load config once when the module loads). In older or non-module scripts you must wrap any await in an async function and call that function (and handle its promise) so that the entry point is valid. Many codebases use an async main or init function that is called once (e.g. on page load or when the app starts) and that awaits the initial load sequence; any failure is caught there so the app can show an error screen or fallback instead of failing silently.

## 6) Homestead Examples

Loading the dashboard: an async function loadDashboard() awaits fetch(configUrl), then response.json(), then stores config. It then awaits Promise.all([fetchZones(), fetchReadings(sensorIds)]) to get zones and readings in parallel. It uses the results to render the page. In catch it shows "Failed to load dashboard" and logs the error; in finally it sets loading false. Refreshing a single sensor: async function refreshSensor(id) { setLoading(true); try { const reading = await fetchReading(id); updateDisplay(id, reading); } catch (e) { showError(id, e.message); } finally { setLoading(false); } }. Starting a zone with a timeout: const result = await Promise.race([startZone(id), timeout(5000)]); then check result to see if it was success or timeout and show the right message. Reading config then zones (sequential): const config = await loadConfig(); const zones = await fetchZones(config.apiUrl); the second await uses config so it must come after the first. Loading three temperatures in parallel: const [freezer, coop, barn] = await Promise.all([fetchReading('freezer'), fetchReading('coop'), fetchReading('barn')]); then display all three. Wrapping a callback-based timer: function delay(ms) { return new Promise(resolve => setTimeout(resolve, ms)); } then in an async function await delay(3000) before running the next step (e.g. close coop door after delay). Each of these keeps the flow linear and uses try/catch and finally for errors and cleanup. When you need to call async code from an event handler (e.g. button click), the handler can be an async function so you can await inside the handler; wrap in try/catch so errors are shown and the returned promise is handled (the event system typically does not await the handler's promise, so if you do not catch inside, rejections can become unhandled). For a "Save settings" flow: async function saveSettings() { setSaving(true); try { await validateForm(); await postSettings(getFormData()); showToast('Saved'); } catch (e) { showError(e.message); } finally { setSaving(false); } } so validation and post run in sequence, and the button or UI reflects saving state until done. For batch operations (e.g. "start all zones in a list"), you can await Promise.all(zoneIds.map(id => startZone(id))) to start all in parallel and wait for all to complete, or run them one by one with a for loop and await if the system requires sequential execution. Choosing parallel vs sequential in homestead automation depends on whether the hardware or API can handle concurrent requests and whether you need to report each result separately.

## 7) What Breaks When async/await Is Wrong

If you use await outside an async function (or outside top-level in a module), you get a syntax error. Make the function async. If you forget to handle rejections—no try/catch and the caller does not .catch the returned promise—you get an unhandled rejection when the async function throws or an awaited promise rejects. Always wrap in try/catch or ensure the caller handles the promise. If you run independent operations sequentially by accident (await getA(); await getB(); when getB does not need A), the total time is the sum of both; switch to Promise.all([getA(), getB()]) and await that for parallel execution. If you use await inside a loop when the iterations are independent, you serialize the work; use Promise.all(ids.map(id => fetch(id))) instead. If you return a value from an async function and expect the caller to get that value directly, remember the caller gets a promise; they must await it or .then it to get the value. If you mix async and callback styles in a way that leaves one path not returning or not handling the promise, rejections can be dropped; keep one consistent style per function. If you do heavy synchronous work between awaits (e.g. a long loop), you block the event loop and the UI or server stalls; break up the work or run it in a worker. If you await the same promise twice in one function, both awaits get the same result (the promise is already settled); that is fine. If you create a promise and await it, the function pauses until it settles; if you never await and never .catch, and the promise rejects, you get an unhandled rejection. So: use async when you use await; handle errors with try/catch or .catch; use Promise.all for independent parallel work; and ensure the promise returned by an async function is always handled by the caller. If you forget to await a promise inside an async function and instead return or use it later, you might pass the promise itself (the object) instead of its value; the next line that uses it would see a promise, not the resolved data. So always await (or .then) when you need the value. If you have nested async functions and the inner one throws, the outer one's try/catch only catches it if the outer one awaited the inner one; so await innerAsync() in the outer function so that when innerAsync throws, the outer catch runs. Propagating errors up through several layers of async functions is done by not catching (or by rethrowing in catch) so the top-level caller can handle once.

## 8) Checklist

When you work with async/await: (1) Declare the function with async if it uses await. (2) Use try/catch around await so rejections become caught exceptions. (3) Use finally for cleanup that must run on success or failure. (4) Prefer sequential await when step B needs the result of step A. (5) Use Promise.all and await for independent operations so they run in parallel. (6) Avoid await in a loop when iterations are independent; use Promise.all with map. (7) Remember that an async function always returns a promise; callers must await or .then it. (8) Do not leave the returned promise unhandled; the caller should catch or await in try/catch. (9) Use await for conditional async (e.g. cached vs fetch); awaiting a non-promise is safe and returns the value. (10) In homestead code, use async for load and refresh flows, Promise.all for multiple sensors or zones, and try/catch/finally for errors and loading state. Chapter 3.15 (Modules) will show how to put these functions in separate files and import/export them.

## Common Pitfalls

await outside async: await is only valid inside an async function (or top-level in a module). Add async to the function.

Unhandled rejection from async function: The promise returned by an async function rejects if the function throws. The caller must .catch or await in try/catch.

Sequential by accident: Writing await a(); await b(); when a and b are independent runs them one after the other. Use await Promise.all([a(), b()]) for parallel.

await in a loop for independent work: for (const id of ids) { await fetch(id); } runs one at a time. Use await Promise.all(ids.map(id => fetch(id))) for parallel.

Forgetting that async function returns a promise: The caller gets a promise, not the return value. They must await or .then to get the value.

Blocking between awaits: Heavy synchronous work between await calls blocks the event loop. Keep work between awaits short or defer it.

Calling async function without handling its promise: If you call loadData() and do not await or .catch, rejections from loadData are unhandled. Either await loadData() in try/catch or loadData().catch(...).

## Summary

async functions always return a promise; inside them await pauses until a promise settles and gives you the value, or throws if it rejects. Use try/catch around await to handle errors; use finally for cleanup. Run independent operations in parallel with Promise.all and await the result; run sequentially by awaiting one after another when the next step depends on the previous. Prefer async/await for linear async flow; use .then when composing or when you need to return a promise without awaiting. Homestead dashboards use async for load and refresh, Promise.all for multiple sensors or zones, and try/catch/finally for errors and loading state.
