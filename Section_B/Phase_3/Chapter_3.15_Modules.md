# Section B Phase 3 · Chapter 3.15: Modules

This chapter covers how to split JavaScript into multiple files using modules: CommonJS (require and module.exports) in Node and ES modules (import and export) in Node and the browser. You will see how to expose values from one file and use them in another, the difference between default and named exports, and how Node and browsers decide which system to use. It builds on Chapter 3.14 (Async — async/await): async functions that load config or fetch data often live in modules that are imported by the main script. Chapter 3.16 (JSON in JavaScript) then covers parsing and producing JSON; modules are where you typically import config or export data structures that will be serialized as JSON. Organizing code into modules supports separation of concerns and clear dependencies, as in Section A Phase 1's view of program structure.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use CommonJS in Node: require a file or package, and assign module.exports (or exports) to expose values from a module.
- Use ES modules: import named or default exports from a path or package, and export values with export or export default; understand that a module can have one default and many named exports.
- Know how Node chooses module system: "type": "module" in package.json or .mjs extension for ES modules; .cjs for CommonJS; otherwise .js is CommonJS by default.
- Relate modules to program structure: split code by responsibility, keep dependencies explicit, and avoid loading the same logic in multiple places.

## Key Terms

- **CommonJS**: The module system historically used by Node.js. You load a module with require("path-or-package"); the result is whatever that module assigned to module.exports. Modules are loaded synchronously and cached by path so the same require returns the same object. File extension .js (when not in a package with "type": "module") is treated as CommonJS.
- **ES modules (ESM)**: The standard JavaScript module system using import and export. You export values with export or export default; you import them with import ... from "...". ES modules are the same in Node (when enabled) and in browsers with script type="module". Loading can be asynchronous; dependencies are resolved before the module runs.
- **require**: The CommonJS function that loads a module. You pass a path (relative with ./ or ../) or a package name; it returns the value of module.exports from that module. Called synchronously.
- **import / export**: ES module syntax. import { name } from "./file" brings in named exports; import Thing from "./file" brings in the default export. export const name = ... or export function f() {} exposes named exports; export default ... exposes the single default export.
- **default export**: A single primary value a module exposes. There can be only one per module. Imported with import X from "./file" (any name). Used when the module has one main thing (e.g. a class or a single function).
- **named export**: One of possibly many exports from a module. Each has a name; the importer uses the same name (or renames with as). Imported with import { a, b } from "./file". Used when the module exposes several values (e.g. several functions or constants).

- **dynamic import**: import() is a function-like form that takes a path and returns a promise that resolves to the module's namespace. Used when you need to load a module conditionally or at runtime (e.g. load a plugin). Works in ES modules; the loaded module is cached like static imports.

## 1) CommonJS (Node)

In Node.js, the traditional module system is CommonJS. To use code from another file, you call require and pass a path or a package name. The path is relative to the current file: ./ means the same directory, ../ means the parent. The result of require is whatever that other file assigned to module.exports. So one file assigns module.exports = something (a function, an object, a number), and any file that require-s it gets that value. A module can instead assign properties to exports: exports.foo = 1; exports.bar = function() {}; then the whole module's export is an object with foo and bar. In that case require returns that object. CommonJS loads modules synchronously: when require runs, Node loads and executes the target file (if not already loaded) and returns the export. The same path is cached: requiring the same path again returns the same object without re-running the file. That is why side effects (e.g. connecting to a database) in a module run only once. In Node, .js files are treated as CommonJS unless the package has "type": "module" in package.json or the file has the .mjs extension. So most older Node code and many tutorials use require and module.exports. For a homestead example: a file that reads config from disk might export a function getConfig that returns a promise; the main script would require that module and call getConfig() when starting the app. Another file might export an object of API helpers (fetchZones, fetchReading) so the main script can require the helpers module and call those functions without putting all the fetch logic in one file. When you require a package name (e.g. require("fs") or require("lodash")), Node looks in node_modules: first in the same directory as the current file, then in the parent directory, and so on. So installed packages are required by name, and your own files are required by relative path. The path you pass to require is resolved once and cached; changing the value of module.exports after the first require does not change what earlier require-ers already received—they have the cached object. So modules are singletons by path: one load per path per process.

## 2) ES Modules — import and export

ES modules use the import and export keywords. To expose a value from a file, you write export before a declaration (e.g. export const API_URL = "..."; export function fetchZones() { ... }) or export default expression at the end. A file can have many named exports and at most one default export. To use another module, you write import and the binding you want. import { fetchZones, fetchReading } from "./api.js" brings in the named exports with those names. You can rename with as: import { fetchZones as getZones } from "./api.js". import Api from "./api.js" brings in the default export; the name Api is up to you. import * as api from "./api.js" brings in all exports as properties of the object api (api.fetchZones, api.default, etc.). In ES modules, the path usually includes the file extension (e.g. .js); some tools allow omitting it but Node with ESM typically requires it. Imports are hoisted and resolved before the module body runs; you cannot conditionally or dynamically import with the static import syntax (there is import() for dynamic loads, which returns a promise). ES modules are the same in the browser (with script type="module") and in Node when you enable them. They support top-level await (Chapter 3.14) and have a clear static structure so tools can analyze dependencies. For a homestead dashboard, you might have a module that exports fetchZones and fetchReading, and a main script that imports those and calls them from an async loadDashboard function. The UI code stays in one file and the API logic in another, so you can test or change the API layer without touching the UI. In ES modules, exports are live bindings for named exports: if the exporting module changes the value of a variable it exported, the importing module sees the new value when it reads the binding. That is different from CommonJS, where require returns a copy of the exported object at load time. For default exports and for primitive values the distinction rarely matters in practice. Export default can be followed by any expression: a function, a class, an object literal, or a constant. You can only have one default per file. Named exports can be declared inline (export const x = 1;) or listed at the end (export { a, b, c };). The latter is useful when you want to export things that were defined with different names (export { fetchZones as getZones };).

## 3) Default vs Named Exports

A default export is the single main value a module provides. The importer chooses the name: import loadConfig from "./config.js" or import anything from "./config.js". Use a default when the module has one primary thing—a single class, a single function, or one config object. Named exports let you expose several values with fixed names. The importer must use those names (or rename with as). Use named exports when the module has multiple related values (e.g. several helper functions or constants). You can mix: one default and several named exports in the same file. Re-exporting is when a module imports from another and then exports the same bindings: export { foo, bar } from "./other.js" so that consumers can get foo and bar from this module without knowing they come from other.js. That is useful for creating a single entry point that re-exports from several internal modules. In bundlers and modern tooling, named exports can be tree-shaken: if the consumer only imports one name, the bundler may omit the rest of the module's code that is not used. Default exports are a single value so the whole export is often included. For that reason some codebases prefer named exports for libraries so that only the used parts are included. For application code (e.g. a homestead dashboard), either style is fine; choose default when there is one clear main export and named when there are several. When re-exporting, you can also do export default from "./other.js" in environments that support it, so this module has no local default but re-exposes the default from other.js. That keeps a single public entry (e.g. an index.js) that re-exports from several internal modules so consumers only need to import from one path. Barrel files are modules that only re-export from others; they are convenient for organizing many small modules under one import path but can affect tree-shaking and load time if the bundler loads the whole barrel.

## 4) Node and Browser

In Node, you opt into ES modules in one of two ways: set "type": "module" in package.json so that all .js files in that package are ESM, or use the .mjs extension for a file so that file is ESM regardless of package.json. Files with .cjs are always CommonJS. So in a package with "type": "module", you use import and export in .js files and you must use the .js extension in import paths. In a package without "type": "module", .js is CommonJS and you use require and module.exports. You cannot mix require and import in the same file in a straightforward way: a CommonJS file cannot use import (it is a syntax error), and an ESM file cannot use require unless you create an async context and use dynamic import() for a CommonJS module in some setups. So pick one system per project or per file and stick to it. In the browser, scripts without type="module" are classic scripts: they do not use import/export and run in the global scope. Adding type="module" to the script tag makes the script an ES module: you can use import and export, the script is deferred by default, and it runs in strict mode. Module scripts are subject to CORS: if you load a script from another origin, the server must send appropriate CORS headers. For local development, serving files from a server (even a simple one) avoids some restrictions that file:// has with modules. When Node runs an ESM file, it follows the import paths and loads dependencies; the same caching idea applies but the resolution rules differ (e.g. you need to specify file extensions). When the browser loads a script type="module", it fetches that script and then fetches each import in order; the module graph is loaded before any module body runs. So with ES modules in the browser, you get deferred execution and dependency order is guaranteed. Classic scripts (without type="module") run in order and share the global scope; module scripts have their own scope and do not pollute the global object with top-level variables. That reduces accidental name collisions and makes dependencies explicit. For a homestead app that runs in Node (e.g. a small server or a script that processes sensor data), you might use "type": "module" and put API helpers and config loaders in separate .js files. For a browser-based dashboard, you use script type="module" for the main script and import from relative paths to your other modules.

## 5) When to Use What

Use CommonJS when you are in a Node project that has not adopted "type": "module" and you are not using .mjs. Many existing Node codebases and tutorials use require and module.exports. Use ES modules when you want the standard syntax that works in Node and the browser, when you want top-level await, or when you are starting a new project and prefer import/export. In Node, set "type": "module" in package.json or use .mjs for ESM. In the browser, use script type="module". Prefer one module system per project so you do not have to mix require and import. Use default export when a module has one main value (e.g. a single async function that loads the app). Use named exports when a module has several values (e.g. fetchZones, fetchReading, API_URL). When you create a module, decide what the public API is: export only what other files need and keep the rest private (not exported). That keeps dependencies clear and makes refactoring easier. If you need to load a module conditionally or at runtime (e.g. load a plugin based on config), use dynamic import(): const mod = await import("./plugin.js"); then use mod.default or mod.someExport. Dynamic import returns a promise and works in ES modules; the loaded module is cached. In CommonJS you would use require inside the conditional, but require is synchronous so you cannot await it; in ESM, dynamic import is the way to load on demand. For a homestead app that might load different "drivers" or "adapters" (e.g. one API implementation for production and one for mock data), you could have a module that exports getAdapter and inside it does await import(adapterPath) based on config, then returns the adapter. The rest of the app just calls getAdapter() and uses the result without knowing which file was loaded. For homestead code: put config loading in one module, API calls in another, and UI or main flow in the entry script; import the helpers and call them from the entry script. Chapter 3.16 will show how to parse and produce JSON; config and API responses are often JSON, and modules are where you import or export that data. When working with a team or a larger codebase, agree on conventions: one default export per module or prefer named exports, where to put barrel files, and how to name modules (e.g. api.js vs apiHelpers.js). Consistency makes it easier to find and refactor code. When you use a bundler (e.g. for a production build), it will resolve your import paths and bundle the modules into one or a few files; the source code still uses the same module syntax, and the bundler handles extension resolution and sometimes different path aliases. Development without a bundler (plain script type="module" in the browser or Node with ESM) is enough to learn and run small apps; bundlers become useful when you have many modules or need to support older browsers or optimize load time.

## 6) Homestead Examples

A config module: a file that reads config from a file or environment and exports a function getConfig or a promise config. The main script imports getConfig and awaits it at startup so the rest of the app has config. An API module: a file that exports fetchZones, fetchReading, and startZone. Each function returns a promise. The dashboard script imports those functions and calls them from event handlers or from an async loadDashboard function. That way all HTTP logic lives in one place and can be tested or swapped (e.g. mock for tests). A constants module: export const API_BASE = "..."; export const SENSOR_IDS = [...]. The main script or other modules import what they need so the base URL and sensor list are defined once. A main entry point: the script that the browser or Node runs (e.g. index.js or main.js). It imports the config and API modules, calls async load or init, and attaches event listeners or renders the UI. If the entry point is an async function that is called once, any failure in loading config or initial data can be caught there and shown to the user. Splitting by layer: one module for "read config from disk or env," one for "talk to the API," one for "render UI" (or for "update DOM"). The main script wires them together. That matches the idea from Section A Phase 1 of separating concerns: each module has a clear job and explicit inputs and outputs. When you add a new feature (e.g. a new sensor type), you add a function in the API module and export it, then import and use it in the UI or main script. You do not paste the same fetch logic in multiple files. A validation module might export validateConfig and validateReading; the config loader and the API layer import those and call them at boundaries so invalid data is caught before it spreads. A small "constants" or "config schema" module can hold only exports (API_BASE, SENSOR_IDS, DEFAULT_TIMEOUT); any module that needs those values imports them, so you change the base URL or sensor list in one place. For a Node script that runs on a schedule (e.g. "check coop door every hour"), the entry file might be the only one that runs; it imports a function runCheck from a module that contains the logic (fetch state, compare to rules, send command). That way the logic is testable in isolation and the entry file stays short. The same idea applies in the browser: the HTML loads one main script as type="module", that script imports from dashboard, api, and config modules, and the main script only wires them together and handles the initial load or user events.

## 7) What Breaks When Modules Are Wrong

If you use import in a Node .js file that is not ESM (no "type": "module" and not .mjs), you get a syntax error. Enable ESM or use require. If you use require in an ES module file, it is not defined (unless you use a polyfill or createRequire). Use import instead. If you forget to export a value, other files cannot import it; they get an error or undefined. Export what you intend to expose. If you use the wrong path (e.g. typo or wrong extension), Node or the browser cannot resolve the module. In Node ESM you usually need the .js extension in the path. If you have a circular dependency (A imports B, B imports A), behavior can differ between CommonJS and ESM; in CommonJS, one of the modules might see a partially initialized export. Prefer to break cycles by moving shared code to a third module or by restructuring so one side does not depend on the other at load time. If you mix default and named import syntax incorrectly (e.g. import { default as X } when the module has export default X), you get undefined or a wrong shape. Match the export style: default export is imported as import X from "..."; named exports are imported as import { a, b } from "...". If you run a script that uses import in the browser without type="module", the browser treats import as a syntax error. Add type="module" to the script tag. If you serve the app from the file system (file://) with modules, some browsers block or restrict cross-origin module loads; use a local server for development. So: use one module system per project, export what others need, use correct paths and extensions, avoid circular dependencies, and in the browser use script type="module" and a proper server when needed. If you rename or move a file that others import, update all import paths or you get broken references. Tools and IDEs can help find usages. If you export a value that is undefined at load time (e.g. a variable that is assigned later), consumers that import it immediately see undefined; in ESM they might see the updated value later because of live bindings, but relying on that can be subtle. Prefer exporting functions or objects that are fully initialized so the contract is clear. If your module has side effects (e.g. registering a handler or connecting to a service), be aware that in ESM the module runs once when first imported and the side effect happens then; in CommonJS the same holds when the module is first required. So the order in which modules are loaded matters if side effects depend on each other; prefer explicit initialization (e.g. an init() function that the entry script calls) over side effects at load time when possible.

## 8) Checklist

When you work with modules: (1) Decide the module system (CommonJS or ESM) per project and stick to it. (2) In Node ESM, set "type": "module" or use .mjs and include .js in import paths. (3) Export only the values other files need; keep the rest private. (4) Use default export for one main value, named exports for several. (5) Import with the correct syntax: default with import X from "...", named with import { a, b } from "...". (6) Avoid circular dependencies; extract shared code or restructure. (7) In the browser, use script type="module" for any script that uses import/export. (8) Put config, API, and UI logic in separate modules and wire them in the entry script. (9) Use relative paths (./ or ../) for your own modules and package names for installed packages. (10) Chapter 3.16 (JSON in JavaScript) will cover the data format you often load in config modules or receive from API modules.

## Common Pitfalls

Using import in a CommonJS file: import is only valid in ES modules. Use require or switch the file to ESM.

Using require in an ESM file: require is not available. Use import or dynamic import() if you need to load something at runtime.

Wrong path or missing extension: In Node ESM, import paths often need the .js extension. Typos or wrong paths cause "cannot find module" errors.

Circular dependency: Module A imports B, B imports A. One module may see incomplete exports. Restructure to remove the cycle.

Forgetting to export: A value that is not exported cannot be imported elsewhere. Add export (or export default) for the public API.

Script without type="module" in browser: If the script uses import/export but the tag does not have type="module", the browser throws a syntax error.

Mixing default and named import wrongly: import { X } expects a named export named X; import X from "..." expects a default export. Match the export style.

Side effects at load time: If a module connects to a DB or registers a handler when loaded, that runs at first import. Order of imports can matter; prefer explicit init() called by the entry script when possible.

## Summary

CommonJS uses require to load modules and module.exports (or exports) to expose values; it is Node's default for .js without "type": "module". ES modules use import and export, work in Node (with "type": "module" or .mjs) and in the browser (script type="module"). Use default export for one main value per module and named exports for several. Node chooses ESM via package.json "type": "module" or .mjs; .cjs forces CommonJS. In the browser, use type="module" for scripts that use import/export. Split code by responsibility (config, API, UI) and keep dependencies explicit. Modules give you a clear boundary: what is exported is the public API; what is not stays internal. That makes it easier to change implementation details without breaking other files. Chapter 3.16 (JSON in JavaScript) covers the format you often load in config modules or receive from APIs.
