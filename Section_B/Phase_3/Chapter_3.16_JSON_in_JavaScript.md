# Section B Phase 3 · Chapter 3.16: JSON in JavaScript

This chapter covers how to turn JavaScript values into JSON strings (JSON.stringify) and how to parse JSON strings back into values (JSON.parse). You will see when JSON is used—API request and response bodies, config files, and storage—and how to handle values that JSON cannot represent (undefined, functions, dates) and how to handle parse errors safely. It builds on Chapter 3.15 (Modules): config and API layers often read or produce JSON, and your modules will call JSON.parse on file contents or response bodies. Chapter 3.17 (Array Methods and Iteration) then covers array methods that you use to transform or filter data; that data is often the result of parsing JSON from an API or config. Knowing JSON's limits and validating after parse keeps your app safe when data comes from outside your code.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use JSON.stringify to serialize objects and arrays to a JSON string; use the optional replacer (array of keys or function) and space (indent) arguments when needed.
- Use JSON.parse to turn a JSON string into a JavaScript value; use the optional reviver function to transform values (e.g. restore dates) during parse; wrap parse in try/catch when the input is untrusted.
- Handle non-JSON-serializable values (undefined, functions, symbols) and circular references; know that stringify omits or skips them and that circular refs throw unless handled.
- Use JSON for HTTP bodies (fetch, Express), config files, and storage (localStorage); know that Content-Type application/json is the convention for request and response bodies.

## Key Terms

- **JSON (JavaScript Object Notation)**: A text format for data: objects with string keys and values that are strings, numbers, booleans, null, arrays, or nested objects. No functions, undefined, symbols, or comments. Keys must be double-quoted. Used for APIs, config, and storage because it is simple and language-neutral.
- **JSON.stringify**: A built-in function that takes a value and returns a JSON string. Optional second argument: replacer (array of property names to include, or a function (key, value) that returns the value to include or undefined to omit). Optional third: space (number or string) for indentation. Throws if the value contains a circular reference unless the replacer handles it.
- **JSON.parse**: A built-in function that takes a JSON string and returns the corresponding JavaScript value. Optional second argument: reviver (key, value) called for each key-value pair so you can transform or filter values (e.g. turn date strings back into Date objects). Throws if the string is not valid JSON.
- **replacer**: The second argument to JSON.stringify. An array of keys limits output to those keys; a function (key, value) can omit properties (return undefined), transform values, or handle special types before they would cause an error.
- **reviver**: The second argument to JSON.parse. A function (key, value) that runs for each parsed key-value pair; you can return a transformed value (e.g. new Date(value) for date strings) or the original value. Runs in a specific order (innermost to outermost) so you can reconstruct nested structures.

## 1) JSON.stringify

JSON.stringify takes a JavaScript value and returns a string that represents it in JSON format. Objects become {...}, arrays become [...], strings are double-quoted, numbers and booleans and null are written as-is. Values that JSON does not support are handled in specific ways: undefined, functions, and symbols are omitted when they appear as property values (the property is left out of the output); in arrays they are replaced by null so the array length and positions are preserved. NaN, Infinity, and -Infinity are serialized as null. Date objects are serialized as ISO date strings (the same as date.toISOString()) because JSON has no date type. If the value or any nested value contains a circular reference (an object that references itself directly or through another object), JSON.stringify throws a TypeError; you must either remove the cycle or use a replacer that tracks seen objects and returns a placeholder or skips. The replacer argument lets you control what gets serialized: pass an array of property names to include only those keys (useful for whitelisting), or pass a function (key, value) that receives each key and value during serialization; return the value to include it (possibly transformed), or return undefined to omit that property. The replacer is called recursively, so you can transform nested values. The third argument, space, is a number (number of spaces to indent each level) or a string (e.g. a tab); it only affects readability and does not change the logical structure. For a homestead example: you might stringify a config object before saving to a file or before sending in a POST body; if the object has a lastUpdated Date, it becomes an ISO string in JSON. If the object has a function (e.g. a callback), that property is omitted. If you have an array of sensor readings with undefined for "no reading," those slots become null in the JSON array. When you need to serialize a value that would otherwise cause an error (e.g. a circular reference), you can pass a replacer function that keeps a Set or WeakSet of seen objects and returns undefined (or a placeholder string) when it sees the same object again, so the serializer skips it and does not throw. Libraries exist for "safe" or "circular" JSON stringification if you need it often. For numbers, JSON does not distinguish integers from floats; very large integers (beyond the safe integer range) can lose precision when parsed because JSON numbers are interpreted as floating point. If you need exact large integers, represent them as strings in JSON and parse them back to a big-int type or string in JavaScript.

## 2) JSON.parse

JSON.parse takes a string that should be valid JSON and returns the corresponding JavaScript value. The string must use double quotes for keys and strings, and the structure must be valid (matching braces and brackets, no trailing commas, no comments). If the string is not valid JSON, JSON.parse throws a SyntaxError. So when the string comes from the network, a file, or user input, you should wrap the parse in try/catch: try { const data = JSON.parse(responseText); use(data); } catch (e) { handleParseError(e); }. In the catch you can log the error, show a message to the user, or use a default value. The optional reviver argument is a function (key, value) that is called for each key-value pair in the parsed result. It is called from the innermost values outward, so when the reviver runs for a parent object, the child values are already the result of their own reviver calls. You can use the reviver to turn date strings back into Date objects: if the key is "createdAt" and the value looks like an ISO string, return new Date(value); otherwise return the value. You can also use it to filter out or transform values. JSON does not have a type for dates, undefined, or functions; so when you parse, you get strings where you had dates and those properties are just strings until you convert them. The reviver is the place to do that conversion so the rest of your code receives proper Date objects or other types. For a homestead example: after fetch(response).then(r => r.text()) you get a string; you JSON.parse that string to get the response body as an object. If the API returns a reading with a timestamp string, you can use a reviver to convert that key to a Date so the rest of the app can format or compare it. If the response is malformed (e.g. truncated or not JSON), the catch block runs and you can show "Invalid response" and log the error. The reviver runs in a specific order: it is called with the key and value for each property, and for nested objects it is called from the leaves upward. So when the reviver runs for a parent key, the child values have already been through the reviver. That allows you to reconstruct nested structures: for example if you have an object with a "nested" property that is an object with a "date" property, the reviver is first called with key "date" and the date string, then with key "nested" and the object (with date already converted). If you return undefined from the reviver for a property, that property is removed from the result; so you can filter out unwanted keys during parse. JSON.parse does not execute code; it only parses data. So even if a string contained something that looked like a function call, it would be parsed as a string value, not executed. The security concern with "JSON with code" applies to the deprecated JSON.parse subset that allowed expressions; the standard JSON.parse only parses data and is safe from code execution from the string itself. The main safety steps are validating the shape of the parsed data and not passing it blindly to code that might use it in unsafe ways (e.g. innerHTML).

## 3) When JSON Is Used

JSON is the common format for data sent and received over HTTP. When you call fetch and get a response, the response body might be JSON; you often do response.json() which reads the body and returns the result of JSON.parse for you. When you send a POST or PUT body, you typically build an object and pass it to fetch as body: JSON.stringify(payload), with headers that include Content-Type: application/json so the server knows how to interpret the body. Servers (e.g. Express in Section B Phase 5) read the body, parse it as JSON, and send back JSON responses. So request and response bodies are a primary use of JSON in web apps. Config files are often JSON: package.json, tsconfig.json, and custom config files like config.json. You read the file (e.g. with fs in Node or by fetching it) and then JSON.parse the contents to get a config object. The config module from Chapter 3.15 might do exactly that: read config.json and return the parsed object. Storage in the browser (localStorage, sessionStorage) only stores strings; to save an object you JSON.stringify it and to load it you JSON.parse the string. So you might save user preferences or the last-loaded sensor list as JSON in localStorage so the next visit can restore state. In a homestead dashboard, API responses (zones, readings) are usually JSON; the config file (sensor IDs, API base URL) might be JSON; and any client-side persistence uses JSON.stringify and JSON.parse. Section B Phase 4 covers Node and file system in more depth; Phase 5 covers Express and request/response bodies. This chapter gives you the JavaScript side: how to produce and consume the strings. When you use response.json() in fetch, the browser or environment reads the response body as text and then runs JSON.parse for you; if the body is not valid JSON, that method rejects the promise (or throws when you await it), so you still need to handle the error in try/catch or .catch. Some APIs return non-JSON (e.g. plain text or HTML) with a 200 status; in that case response.json() will fail when you call it, and you might use response.text() instead and then decide whether to parse or not. Checking the Content-Type header of the response (e.g. response.headers.get("Content-Type")) can tell you whether the server intended to send JSON, but the only way to know if the body is valid JSON is to try to parse it.

## 4) Limits and Safety

JSON has a fixed set of types: objects, arrays, strings (double-quoted), numbers (decimal), booleans, and null. It does not support undefined, functions, symbols, or comments. Numbers are decimal only; binary data or very large integers may need to be represented as strings or handled elsewhere. Keys in objects must be double-quoted. So when you stringify, anything outside that set is either omitted (undefined, functions, symbols in object values), replaced by null (in arrays, or NaN/Infinity), or converted to a string (dates). When you parse, you get plain objects and arrays—no Date instances, no functions—unless you use a reviver to recreate them. When parsing untrusted data (anything from the network, a file you did not create, or user input), do not assume the shape is correct. Parse can throw (invalid syntax), and even valid JSON can have unexpected structure (missing keys, wrong types, huge arrays). So after parsing, validate: check that required properties exist and have the expected types before using them. In very old JavaScript environments there were concerns about prototype pollution (parsed JSON with a "__proto__" key affecting the object); in modern practice, validate and use the parsed data in a controlled way rather than passing it blindly to code that assumes a schema. For large documents, JSON.parse loads the whole string into memory and builds the whole object; if the input is huge, consider streaming or chunked parsing (covered in Node/streams contexts) or splitting the data. For most config and API responses, the size is small enough that parse is fine. When you validate after parse, you can do simple checks: typeof obj.zoneId === "number", Array.isArray(obj.readings), obj.updatedAt !== undefined. For more complex configs you might walk the object and check each required key and type, or use a validation library or schema (covered in later phases). The goal is to fail fast at the boundary (right after parse) with a clear message ("Config missing sensorIds array") rather than failing later when some code assumes zones[0].id exists and gets undefined. When you stringify for storage or for sending, be aware that the string can be large if the object is large; localStorage has a size limit per origin (typically a few megabytes), so storing huge state objects may throw or be truncated. For very large payloads sent over HTTP, the server and client may have body size limits; stringify itself has no built-in size limit but the resulting string uses memory.

## 5) When to Use What

Use JSON.stringify when you need to send an object in an HTTP body (body: JSON.stringify(payload)), when you save to localStorage (localStorage.setItem("key", JSON.stringify(obj))), or when you write a config or data file as text. Use the replacer when you want to limit which keys are serialized (e.g. only id and name) or when you need to transform or omit values (e.g. skip internal fields). Use the space argument when the output is for humans (logs, config files) so it is readable. Use JSON.parse when you receive a JSON string: from response.text() or response.json(), from reading a file, or from localStorage.getItem. Always use try/catch when the source is untrusted or external so parse errors are handled. Use a reviver when the JSON contains date strings (or other custom formats) that you want to turn back into Date objects or other types so the rest of your code does not have to convert everywhere. For API responses, response.json() already does parse for you and throws on invalid JSON, so you still need try/catch around the fetch/await if you want to handle parse failures. For config files you read as text, you do JSON.parse(text) yourself and catch to throw a clearer error (e.g. "Invalid config file: ..."). For homestead code: stringify before POST/PUT and when saving to storage; parse after fetch or file read and validate the shape before using; use reviver for timestamp or date fields so the rest of the app works with Date objects.

## 6) Homestead Examples

Loading config: the config module reads a file or fetches config.json and gets a string. It does JSON.parse(string) in try/catch; on success it returns the config object, on failure it throws a clear error (e.g. "Invalid config JSON") so the caller knows the file was malformed. The config might have sensorIds (array), apiBase (string), and timeout (number); after parse you validate that those exist and have the right types before using them. API response: after await fetch(url) and response.ok check, you do const data = await response.json(). That is parse under the hood. The API might return { zones: [...], updatedAt: "2025-02-24T12:00:00Z" }. You use the zones array; if you need updatedAt as a Date, you can pass a reviver when you parse response.text() instead of using response.json(), or convert the string to a Date where you use it. Saving preferences: the user toggles a setting; you have an object prefs; you do localStorage.setItem("prefs", JSON.stringify(prefs)). On load you do const prefs = JSON.parse(localStorage.getItem("prefs") || "{}") so missing or invalid data becomes an empty object. Sending a zone command: you build an object { zoneId: 1, action: "start" } and send it with fetch(url, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify(payload) }). The server receives the body and parses it as JSON. Logging state: for debugging you might do console.log(JSON.stringify(state, null, 2)) so the object is printed in a readable form with indentation. If state has a Date, it appears as an ISO string in the log. If state has circular references, stringify throws unless you use a replacer that detects cycles and returns a placeholder. Each of these patterns—parse after read, stringify before send or save, validate after parse, reviver for dates—keeps your homestead app consistent and safe when dealing with JSON. When building a request body for an API that expects JSON, construct a plain object (no functions, no undefined in places that matter) and stringify it; if you need to send a date, use an ISO string (date.toISOString()) so the server can parse it. When you receive a list of zones or readings, the result of parse (or response.json()) is an array or an object with an array property; you can then use array methods (Chapter 3.17) to map, filter, or sort that data for display. When reading a config file in Node, you typically get a Buffer or string from the file API; if the file is UTF-8, you pass the string to JSON.parse. If the file does not exist or is not valid JSON, your config module should throw with a message that includes the file path and the parse error so the user or logs know what to fix. When persisting user choices (e.g. which sensors to show, sort order), store only the minimal data needed (ids and flags) as JSON so the string stays small and you do not hit storage limits.

## 7) What Breaks When JSON Is Wrong

If you pass an object with circular references to JSON.stringify without a replacer that handles them, it throws. Remove the cycle or use a custom replacer (or a library that supports cycles) if you must serialize such structures. If you forget to wrap JSON.parse in try/catch when the string is from the network or a file, invalid JSON will throw and can crash the app or leave it in a bad state. Always catch and handle parse errors. If you assume the parsed object has a certain shape (e.g. data.zones.length) without checking, malformed or unexpected API responses can cause runtime errors (e.g. data.zones is undefined). Validate after parse: check that required keys exist and are the right type before using them. If you store or send sensitive data (tokens, passwords) in JSON in localStorage or in request bodies, ensure the channel is secure (HTTPS) and that you do not log the stringified value. If you use the parsed object to set innerHTML or to construct HTML without escaping, you risk injection; JSON.parse does not sanitize for HTML. If you expect dates but the API sends strings and you do not convert them, comparisons or formatting may be wrong; use a reviver or convert at the boundary. If the JSON string is very large, parsing it all at once can use a lot of memory; for huge payloads consider streaming or pagination. If you stringify an object that includes functions or undefined and then parse it back, those are lost (omitted or null); do not rely on round-tripping non-JSON types without custom replacer/reviver. So: handle parse errors, validate shape after parse, use reviver for dates when needed, and avoid circular refs or handle them explicitly when stringifying. If you parse the same string multiple times, you get a new object each time; JSON.parse does not cache. So if you need to use the same parsed result in several places, parse once and pass the object around. If you stringify the same object twice without changing it, you get the same string (property order in objects may vary in theory but in practice modern engines preserve insertion order for string keys). If the object has properties that are not enumerable or are inherited, those may not appear in the JSON output; stringify only serializes own enumerable properties. So for "plain data" objects that you build for JSON, this is straightforward; for objects with prototype methods or getters, only the enumerable own data properties are included, and getters are evaluated so their return value is what gets serialized.

## 8) Checklist

When you work with JSON: (1) Use JSON.stringify to turn values into strings for HTTP bodies, storage, or files; use a replacer to limit or transform, and space for readability when useful. (2) Use JSON.parse to turn JSON strings into values; wrap in try/catch when the source is external or untrusted. (3) Validate the parsed result: check that required properties exist and have the expected types before using. (4) Use a reviver to convert date strings (or other formats) to Date objects or other types so the rest of the code has consistent types. (5) For HTTP, set Content-Type: application/json when sending JSON and use response.json() or response.text() plus parse when receiving. (6) For localStorage, stringify before setItem and parse after getItem; provide a fallback (e.g. "{}") when the key is missing. (7) Do not assume parsed data has a fixed shape; validate at the boundary. (8) Avoid stringifying objects with circular references unless you handle them with a replacer. (9) For config files, parse in the config module and throw a clear error on failure. (10) Chapter 3.17 (Array Methods and Iteration) will give you tools to transform and filter arrays; those arrays are often the result of parsing JSON from an API or config.

## Common Pitfalls

Parse without try/catch: Invalid JSON throws. When the string is from the network, file, or user, always catch and handle.

Assuming shape after parse: The API or file might return different keys or types. Validate required fields and types before use.

Circular reference in stringify: Objects that reference themselves (or each other) cause stringify to throw. Remove cycles or use a custom replacer.

Forgetting Content-Type: When sending JSON in a request body, set Content-Type: application/json so the server parses it correctly.

Dates as strings: JSON has no date type. After parse you get strings; use a reviver or convert where you use them so comparisons and formatting work.

Loss of undefined/functions: stringify omits undefined and functions; parse cannot bring them back. Do not rely on round-tripping those values without custom logic.

## Summary

Use JSON.stringify to serialize values to JSON strings; use a replacer to filter or transform and space for readable output. Use JSON.parse to parse JSON strings into values; use try/catch for untrusted input and a reviver to restore dates or other types. JSON supports objects, arrays, strings, numbers, booleans, and null; undefined, functions, and symbols are omitted or become null when stringified; circular references cause stringify to throw. JSON is used for HTTP bodies (request and response), config files, and storage (localStorage). Validate parsed data before use and handle parse errors. Chapter 3.17 (Array Methods and Iteration) covers methods you will use on arrays that often come from parsed JSON.
