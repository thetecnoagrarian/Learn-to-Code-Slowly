# Section B Phase 3 · Chapter 3.18: Template Literals and Interpolation

This chapter goes deeper into template literals: backtick-delimited strings, interpolation with ${expression}, multiline strings without escape sequences, and how to escape backticks and dollar-brace inside a template. It builds on Chapter 3.11 (Strings and Template Literals), which introduced string methods and the basics of template literals. Here the focus is on when and how to use template literals for readable embedded values, multiline text, and formatting; when to prefer concatenation or a helper; and a brief look at tagged template literals for custom processing. Chapter 3.19 (Throwing and Custom Errors) then covers error objects and messages; you will often build error messages with template literals so the message includes context (e.g. sensor id or expected value). Using template literals well keeps log messages, UI text, and URLs readable and avoids missing spaces or quotes that concatenation can introduce.

## Learning Objectives

By the end of this chapter, you should be able to:
- Write strings with template literals (backticks) and embed expressions with ${expression}; know that the expression is evaluated and coerced to string.
- Use multiline template literals and understand that newlines and indentation are preserved; use trim or line arrays when you need to control leading whitespace.
- Escape a literal backtick or ${ in the output with backslash; know when to use template literals vs concatenation vs String() or a formatter.
- Understand tagged template literals at a high level (tag function receives string parts and interpolated values) and when they are used (e.g. sanitization, i18n).

## Key Terms

- **template literal**: A string literal delimited by backticks. It can span multiple lines and can contain ${expression} placeholders. Each expression is evaluated and its result is converted to a string and inserted in place. Used for interpolation and multiline strings without \n.
- **interpolation**: Embedding the result of an expression inside a string. In template literals you write ${expression}. The expression can be a variable, property access, function call, or any expression that produces a value; the value is coerced to string (toString, or "null"/"undefined" for null/undefined).
- **tagged template literal**: A template literal preceded by a function name (the tag): tag`string ${expr} more`. The tag function is called with an array of string parts (the static text between interpolations) and the interpolated values. The tag can return any value (often a string). Used for custom parsing, sanitization, or internationalization.
- **multiline template literal**: A template literal that contains actual newline characters. The newline and any spaces or tabs between the backticks are part of the string. Indentation in your source is preserved in the output unless you trim or build the string differently.

- **escaping in template literals**: Inside a template literal, \` produces a literal backtick and \${ produces literal dollar-brace so they are not interpreted as the end of the literal or as interpolation. Other escape sequences (e.g. \n, \t) work as in normal strings.

## 1) Template Literals and Interpolation

A template literal is written with backticks. Inside it, ${expression} is an interpolation: the expression is evaluated when the template literal is evaluated, and the result is converted to a string and inserted. So instead of "Sensor " + id + ": " + value you write `Sensor ${id}: ${value}`. The expression can be any valid JavaScript expression: a variable, obj.property, a function call, or a ternary. For example you can write `Status: ${reading >= threshold ? "OK" : "Low"}` so the string reflects a condition. The conversion to string uses the same rules as String(value): numbers become their string form, booleans become "true" or "false", null and undefined become "null" and "undefined", and objects become "[object Object]" unless they have a custom toString. So for display you usually interpolate primitives or specific properties (e.g. `${reading.toFixed(1)}` for a number with one decimal) rather than a whole object. You can nest template literals: inside ${} you can use another backtick string, so `` `Outer ${`inner ${x}`}` `` is valid and produces "Outer inner " plus the value of x. Keep expressions inside ${} short; if the logic is complex, compute the value in a variable first and then interpolate the variable so the template stays readable. For a homestead example: a status line `Battery: ${reading.toFixed(1)}%` or `Zone ${zoneId}: ${status}`; a message that includes a threshold: `Temperature above ${maxTemp}°C`; or a log line with several values: `[${new Date().toISOString()}] Sensor ${id} = ${value}`. Template literals are evaluated where they appear; if the expression has side effects (e.g. a function call that updates state), that runs at evaluation time. So use expressions that are pure or that you intend to run when building the string. When you need to include a newline in a single-quoted or double-quoted string, you use \n; in a template literal you can type a real newline or use \n. Both produce the same character. When you build a string that will be parsed later (e.g. JSON or a URL), the interpolated value becomes part of the string; if the value contains quotes or special characters, the result might be invalid JSON or a broken URL unless you escape or encode. So for JSON, use JSON.stringify on the value and then interpolate that string (which will have escaped quotes); for URL parameters use encodeURIComponent so special characters are encoded. When you have a long expression inside ${}, consider moving it to a variable: const label = getLabel(reading); then `Status: ${label}`. That way the template stays a single line of placeholders and the logic is named and testable. When you interpolate the result of a function call, the function runs when the template is evaluated; so `${getCurrentReading()}` calls the function at that moment. If the template is inside a loop, the function is called every iteration; if that is expensive, call once before the loop and interpolate the stored result.

## 2) Multiline Strings and Escaping

Template literals can contain real newlines. You type Enter and the newline is part of the string; you do not need \n. That is useful for blocks of text: a multi-line log message, an email body, or help text. The catch is that every character between the opening and closing backtick is in the string, including spaces and tabs used to indent your code. So if you indent the second line of the template to align with your code, that indentation appears in the output. To avoid that you can: put the opening backtick and the first character of the string at the start of the line (so the template is not indented), which can look uneven in the source; or build the string from an array of lines and join with newline; or call trim() on the result to remove leading and trailing whitespace (but that does not remove indentation in the middle of the string). For a short message of two or three lines, leaving some indentation in the output is often acceptable; for longer blocks or when the format must be exact, building from lines and joining gives you control. To include a literal backtick in the output, escape it: \`. To include literal ${ in the output (e.g. you are building a string that will be used as a template or shown as code), escape the dollar sign: \${. So the string `` `Cost: \${amount}` `` contains the characters dollar, brace, "amount", brace—not the value of a variable named amount. For a homestead example: a multiline status report with embedded values, each reading on its own line; or a log block that spans several lines with timestamps and sensor ids. If you need to include a backtick inside an interpolation (inside ${}), you can use a backtick string there and the outer template still ends at the next unescaped backtick, so nesting and escaping can get tricky; for complex cases, build the string in steps or use a variable for the inner part. When you build a string from an array of lines (e.g. lines.map(line => line.trim()).join("\n")), you have full control over each line and can trim or pad as needed. When the template is inside a function that returns a string, the template is evaluated when the function is called, so the interpolated values are those at call time. When the template is in an object literal (e.g. a property value), it is evaluated when the object is created. So the timing of interpolation is the same as for any expression: when that line or expression is executed. When you pass a template literal to a function (e.g. log(`Message: ${x}`)), the template is evaluated first and the resulting string is passed to the function; the function receives only the final string, not the parts and values. Only a tagged template passes the parts and values to the tag function.

## 3) When to Use Template Literals vs Concatenation

Use template literals when you have one or more values to embed and the result is easier to read than concatenation. For a single value in a short string, both "Hello, " + name and `Hello, ${name}` are fine; many developers prefer template literals for consistency. For several values or a longer string, template literals reduce the chance of forgetting a space or a plus. For example `Sensor ${id}: ${value} ${unit}` is clearer than "Sensor " + id + ": " + value + " " + unit. Use concatenation when you are building a string in a loop by appending small pieces; in that case you might push segments onto an array and join("") so you do not create many intermediate strings, and the pieces might be variables or the result of conditions. When the string has no variables (a constant), use single or double quotes; backticks are for when you need interpolation or newlines. When you need to include many literal backticks or ${} in the output, escaping each one can be noisy; consider building the string from parts or using a different approach. When formatting numbers, do the formatting in the expression: `${reading.toFixed(1)}` or `${(value * 100).toFixed(0)}%` so the template stays clean. When the interpolated value might be null or undefined, you get "null" or "undefined" in the string; if you want a different fallback, use nullish coalescing in the expression: `${value ?? "—"}` so missing values show as a dash. When building URLs or JSON, do not interpolate raw user input without validation or encoding; template literals do not escape for you, so dangerous characters in the value can break the URL or inject content. When you concatenate with + and one operand is not a string, it is coerced to string (e.g. "x" + 1 is "x1"); in a template literal the same coercion happens inside ${}. So `${1 + 2}` produces "3" and `${"a" + "b"}` produces "ab". When you need to repeat a pattern (e.g. a row of a table), you often map over an array and return a template literal for each item, then join the results; the template is evaluated once per item. When the string is built from many small parts and the logic is complex (e.g. different separators or conditional segments), an array of parts with join can be clearer than one long template with many ternaries. When you want to defer the evaluation of the template (e.g. build a template once and fill in values later), you cannot do that with a single template literal—the literal is evaluated immediately. You would use a function that takes parameters and returns the template string, or a tagged template that stores the parts and merges values when called. For most use cases, building the string when you have the values is enough. For display text (labels, messages, logs), template literals with variables and simple expressions are ideal. For a homestead dashboard: status text, error messages that include sensor id or reading, log lines with timestamp and values, and multiline reports are all good uses of template literals. When you refactor from concatenation to template literals, the behavior is the same as long as the expressions produce the same values; the main gain is readability and fewer opportunities to miss a space or quote. When you have a mix of static text and many variables, one template literal with many ${} placeholders is usually easier to maintain than a long chain of +. When the string is constructed conditionally (e.g. different messages for different cases), you can use a ternary or an if/else that assigns different template literals to a variable; or build an array of parts and join. When you need to localize or translate strings later, having the string in one place (a template or a function that returns it) makes it easier to replace with a lookup; tagged templates are one way to hook into that. For now, focus on clear interpolation and consistent formatting; i18n can be added when the app grows.

## 4) Tagged Template Literals

A tagged template literal is written as a function name followed by a template literal: tag`Hello, ${name}`. The parser splits the template into an array of string parts (the static text between the interpolations) and the interpolated values. The tag function is called with (strings, ...values): the first argument is an array of strings (one more than the number of interpolations), and the rest are the evaluated values. The tag can return any value; often it returns a string that might be processed (e.g. escaped for HTML, or looked up in a translation table). So tagged templates are used when you need custom behavior: sanitizing user input before inserting into HTML, building a query with escaped parameters, or doing internationalization (the tag looks up each string part and value and returns the translated result). You will see tagged templates in libraries (e.g. for styled components or i18n); you do not need to write a tag function for normal interpolation. For normal use, plain backticks and ${} are enough. If you encounter a tag in documentation or code, remember that the tag receives the static parts and the values separately and can transform or combine them. For a homestead app, you might use a tag provided by a library for safe HTML or for translations; writing your own tag is optional and only needed when you have a specific transformation in mind. The string parts array has a special property that some tags use: it can include a raw property (strings.raw) that contains the string parts without processing escape sequences (e.g. \n as backslash-n rather than newline). Most tags use the normal strings array. A simple tag that just concatenates parts and values in order would return strings.flatMap((s, i) => [s, values[i] ?? ""]).join(""), which reproduces the default behavior; real tags do something more (escape values, look up translations, etc.). You do not need to implement a tag unless you are building a library or have a clear need for custom processing. For logging or display in a homestead dashboard, plain template literals are sufficient.

## 5) Homestead Examples

Build a status line for a sensor: `Sensor ${id}: ${reading.toFixed(1)} ${unit}` so the UI shows "Sensor freezer: 12.3 °C". Build an error message that includes context: `Failed to load zone ${zoneId}: ${error.message}` so the log or user sees which zone failed and why. Build a multiline log entry: a template that spans two or three lines with a timestamp, sensor id, and reading on separate lines, with values interpolated. Build a URL with a query parameter: `` `${apiBase}/readings?id=${sensorId}` `` so the base and id are clear; ensure sensorId is validated or encoded if it comes from user input. Build a list of zone names for display: zones.map(z => z.name).join(", ") gives a single string; if you want a label per zone use zones.map(z => `Zone: ${z.name}`).join("\n"). Build a short report: a template literal with several lines, each line including a reading or threshold, so the whole block is one string you can send to a log or display. Format a number with unit: `${value.toFixed(1)} ${unit}` for temperature or percentage. Use a ternary inside the template: `Status: ${value >= threshold ? "OK" : "Low"}` so the message reflects the condition. Build a message with a fallback for missing data: `Reading: ${reading ?? "—"}` so null or undefined shows as a dash. When you have an array of items to format (e.g. readings), map each to a string with a template literal and then join with newline or comma: readings.map(r => `${r.id}: ${r.value}`).join("\n"). When building a string that will be shown as code or config (e.g. an example that includes ${}), escape the dollar sign so the output contains the literal characters. When the string is long and you want to trim accidental indentation, call .trim() on the result or build from an array of lines. Each of these uses keeps the intent clear and avoids concatenation errors. When you format a date for display, get the string from the Date (e.g. toISOString or a locale formatter) and then interpolate: `Last updated: ${lastUpdate.toISOString()}`. When you build a CSV-like line from an array of values, use join(",") and interpolate the result if it is part of a larger template: `Row: ${values.join(",")}`. When you have optional segments (e.g. a suffix only when a condition holds), you can use a ternary in the template: `${value}${unit ? " " + unit : ""}` or build the string in steps. When the same value appears in several places in the template, the expression is not re-evaluated for each occurrence—each ${} is independent, so `${x} and ${x}` evaluates x twice (which matters if x is a getter or function call). When you need to include a backtick in an interpolated expression, the inner template can use backticks: `` `Outer \` and inner ${`nested ${x}`}` ``; the escaping and nesting can get hard to read, so a variable for the inner part is often clearer.

## 6) What Breaks When Template Literals Are Wrong

If you forget to escape a backtick inside the template, the parser thinks the template ends there and the rest of the line is invalid. Escape with \` when you need a literal backtick. If you want literal ${ in the output and do not escape it, the parser tries to interpret it as an interpolation and you get "undefined" or a wrong value; use \${. If you interpolate an object directly (e.g. `${config}`), you get "[object Object]" because that is the default toString for objects; interpolate specific properties or use JSON.stringify when you need the structure. If you interpolate a value that is null or undefined, you get the string "null" or "undefined"; if that is not what you want, use a fallback in the expression: `${x ?? "—"}`. If the expression inside ${} throws (e.g. a property access on undefined), the whole template literal evaluation throws; guard the expression or ensure the value exists. If you build HTML or a URL by interpolating user input without escaping, you risk injection; use a sanitization library or encode the value. If you use a multiline template and forget that indentation is preserved, the output has extra spaces; trim or build from lines. If you nest template literals deeply, the backtick and brace matching can be hard to read; prefer a variable for the inner part. If you use a tagged template but pass the wrong number of arguments or expect a different shape, the tag function may behave incorrectly; the first argument is always the array of string parts, and the rest are the values in order. So: escape backticks and ${ when literal, handle null/undefined and objects, validate or escape user input, and be aware of indentation in multiline templates. When the expression is expensive (e.g. a heavy computation), it runs every time the template is evaluated; if the template is in a loop, consider computing once outside the loop and interpolating the result. When you compare strings built with template literals, they are normal strings; === works. When you store the result in a variable and use it in several places, the string is built once when the variable is assigned. When you pass the template as an argument to a function, the template is evaluated before the function runs, so the function receives the final string. When you use a template literal as the message for an Error (e.g. throw new Error(`Invalid id: ${id}`)), the message is built at throw time and includes the current value of id; that is a common and recommended pattern for error messages (Chapter 3.19). When the interpolated value is an array, it is coerced to string by joining with commas (Array.prototype.toString); so `${[1,2,3]}` gives "1,2,3". If you want a different separator, use arr.join(" ") or similar in the expression. When the value is a number with many decimal places, interpolating directly can produce a long string (e.g. 0.1 + 0.2); use toFixed or toPrecision in the expression so the display is controlled. So: escape and validate as needed, handle null/undefined and objects, and be aware of when and how often the expression runs.

## 7) Checklist

When you work with template literals: (1) Use backticks for strings that need interpolation or multiline content. (2) Use ${expression} to embed values; the expression is evaluated and coerced to string. (3) Keep expressions short; use a variable for complex logic and interpolate the variable. (4) For numbers, format in the expression (e.g. toFixed(1)) before interpolating. (5) For null/undefined, use ?? in the expression to provide a fallback (e.g. `${x ?? "—"}`). (6) Escape literal \` and \${ when needed. (7) Remember that multiline templates preserve newlines and indentation; use trim or line arrays if you need to control whitespace. (8) Do not interpolate unsanitized user input into URLs, HTML, or shell commands. (9) Prefer template literals over concatenation when embedding several values or when the string spans lines. (10) Tagged templates (tag`...`) are for custom processing; use plain template literals for normal interpolation. ## Common Pitfalls

Unescaped backtick: A backtick inside the template ends the literal. Use \` for a literal backtick.

Literal ${ in output: Without escaping, ${ is treated as interpolation. Use \${ for literal dollar-brace.

Interpolating an object: Objects become "[object Object]". Interpolate properties or use JSON.stringify.

Null/undefined in output: They become the strings "null" and "undefined". Use `${x ?? "fallback"}` for a friendly display.

Indentation in multiline: Spaces and tabs between backticks are part of the string. Trim or build from lines if needed.

User input in URL/HTML: Interpolating raw input can cause injection. Validate or encode/sanitize.

## Summary

Template literals are backtick-delimited strings that can contain ${expression} for interpolation and can span multiple lines. The expression is evaluated and coerced to string. Use template literals when you embed one or more values or need multiline text; they are often clearer than concatenation. Escape \` and \${ when you need those characters in the output. Multiline templates preserve newlines and indentation; use trim or build from lines to control whitespace. Tagged template literals (tag`...`) pass string parts and values to a function for custom processing (e.g. sanitization, i18n). For display text, logs, and messages with embedded values, template literals keep the format readable.
