# Section B Phase 3 · Chapter 3.19: Throwing and Custom Errors

This chapter goes deeper into throwing errors: how throw works, how to create and use custom Error subclasses so callers can distinguish error types, and when to throw versus return an error value. It builds on Chapter 3.12 (Error Handling), which covered try/catch/finally and the basics of throw and Error types. Here the focus is on designing throwable errors with clear messages (using template literals from Chapter 3.18), defining domain-specific error classes (e.g. ConfigError, ValidationError), and rethrowing or wrapping errors so context is preserved without losing the original stack. Chapter 3.20 (Strict Mode and Robust Code) then covers strict mode and writing defensive code; throwing on invalid input is one way to make the program fail fast instead of continuing with bad state. Using custom errors and consistent throw/catch boundaries makes debugging and user feedback much clearer.

## Learning Objectives

By the end of this chapter, you should be able to:
- Throw errors with throw new Error(message) and build messages with template literals so they include variable context (e.g. id, expected type).
- Define custom error classes by extending Error; set name and message and optionally use the cause option to wrap an original error.
- Decide when to throw (precondition violations, invalid state, failed operations that the caller must handle) versus when to return a value or null for expected cases (e.g. not found).
- Rethrow after logging or wrap with a new error that has a cause, so the stack and chain of errors are preserved; avoid swallowing errors.

## Key Terms

- **throw**: A statement that throws a value and transfers control to the nearest enclosing catch (or terminates if none). Conventionally you throw an Error or a subclass so the value has message, name, and stack. Execution of the current function stops immediately.
- **Error (built-in)**: The standard constructor for error objects. new Error("message") creates an object with message, name "Error", and a stack property (the call stack at creation time). Subclasses (TypeError, RangeError, custom) inherit these and add a distinct name.
- **custom error class**: A class that extends Error. You define it so that catch blocks can check e.name or e.constructor and handle domain-specific errors (e.g. ConfigError, SensorNotFoundError) differently from generic errors. Set this.name in the constructor so it appears in the stack and in logs.
- **cause**: An optional property on Error (and subclasses) that can hold the original error when you wrap it. When you catch an error and throw a new one with more context, pass the original as cause: new Error("Failed to load config", { cause: e }). The chain is preserved for debugging.
- **rethrow**: In a catch block, throwing the same error again (throw e) so that a higher-level caller can handle it. Use after logging or adding context. Do not swallow the error without rethrowing or returning a documented result.

## 1) Throwing Errors

You throw with throw value;. The value can be any type, but you should throw an Error or a subclass so that message, name, and stack are available. Write throw new Error("description of what went wrong");. The message is the string that appears in e.message when the error is caught; make it clear and actionable. Use template literals (Chapter 3.18) to include variable context: throw new Error(`Sensor ${id} not found`); or throw new Error(`Expected string, got ${typeof value}`); so that logs and debugging show which id or what type caused the failure. When you throw, the current function stops and the error propagates up the call stack until a catch handles it or the program exits. Nothing after the throw in that function runs. So throw when you detect a precondition violation (e.g. missing required argument, invalid config), when an invariant is broken (e.g. state that should never happen), or when an operation fails and the caller should decide how to respond (e.g. network failure, parse failure). Do not throw for expected control flow: if "item not found" is a normal outcome of a lookup, return null or a result object instead so the caller can branch without try/catch. Reserve throw for exceptional or invalid cases. You can throw built-in types: throw new TypeError("expected string") when the type is wrong, throw new RangeError("index out of range") when a number is out of bounds. Catch blocks can then check e.name to handle type errors differently from range errors. For most application-level failures (sensor not found, config invalid, API failed), plain Error with a clear message is enough; use the message or a custom class when you need callers to distinguish cases. Avoid putting sensitive data (passwords, tokens) in error messages; they may end up in logs or in the UI. The stack property is set when the error is created; it shows where the throw happened and the call stack, which helps when debugging. So: throw Error objects with clear, contextual messages; use template literals for variable parts; and throw for exceptional or invalid cases, not for normal "not found" or "empty" outcomes. When you throw from inside a function that was called from a try block, the exception propagates to that try's catch. When you throw from inside a callback (e.g. passed to map or forEach), the throw happens when the callback runs; if the callback was invoked by code in a try, the catch can receive it only if the callback runs synchronously. If the callback runs later (e.g. after a promise resolves), the try has already finished and the throw becomes an unhandled exception or rejection. So in async or callback-based code, throw inside the callback or reject the promise so that the caller can catch via .catch or try/await. When you have multiple validation checks in one function, you can throw on the first failure (so the message is about that one thing) or collect all failures and throw once with a message that lists them (e.g. "Config invalid: missing sensorIds; apiBase must be a string"). The first approach is simpler; the second gives the user a full list of fixes in one go. When the same kind of error can occur in several places (e.g. "sensor not found"), use the same message pattern or the same custom error class so that callers can handle them uniformly.

## 2) Custom Error Classes

You can define a class that extends Error so that errors from a specific domain have a distinct name and optionally extra properties. Define a class and call super(message) in the constructor; set this.name to the class name so that e.name and the stack trace show it. Callers can then use if (e instanceof MyError) or if (e.name === "ConfigError") to handle that error type differently (e.g. show a config-specific message or retry logic). Custom errors are useful when you have several failure modes and want to handle them in different layers: for example ConfigError when config is invalid (caught at startup to show "Fix config"), NetworkError when fetch fails (caught to show "Check connection"), ValidationError when user input is invalid (caught to highlight the field). Each class can have additional properties (e.g. ValidationError might have a field property). In the constructor, after super(message), set this.name = "ValidationError" (or this.constructor.name) so that the name is correct; in some environments the name is not inherited correctly from the class name without this assignment. Custom errors still have message and stack; they are just tagged with a name and optionally extra data. You do not need a custom class for every function; use them when you have a family of errors that callers will branch on. For a homestead app, ConfigError, SensorNotFoundError, or ApiError might be enough; inside catch you check e.name or e.constructor and show the right message or take the right action. If you do not need to distinguish, plain Error with a good message is fine. When you add properties to a custom error (e.g. field or code), set them in the constructor after the super call. The caller can then read e.field or e.code in the catch block to decide what to do. When you subclass Error, the instance is an object that has message, name, and stack (and any custom properties); instanceof MyError works so you can catch (e) { if (e instanceof ConfigError) { ... } }. When you have a hierarchy (e.g. ApiError extends Error, and NetworkError extends ApiError), callers can catch the base type to handle all API errors or the subtype to handle only network failures. For a small app, one or two custom classes (e.g. ValidationError, ConfigError) are often enough; add more when you have distinct handling for different failure modes. When you throw a custom error, pass a message that is useful in logs and optionally user-facing; the custom class gives you the type, and the message gives the context.

## 3) Wrapping Errors and the cause Option

When you catch an error and throw a new one to add context (e.g. "Failed to load config" instead of the raw "Unexpected token" from JSON.parse), you can pass the original error as the cause. In supported environments, new Error("Failed to load config", { cause: e }) stores the original error in the new error's cause property. When you log or inspect the new error, you can follow cause to see the chain; stack traces and error reporting tools can show both. So when you wrap, use cause so the original error and stack are not lost. When you rethrow without wrapping (throw e), the same error and stack propagate; use that when you only need to log and then let the caller handle the same error. When you wrap, the caller sees your message and can still access the underlying cause for details. Do not wrap and then lose the original: avoid throw new Error("Something failed") in catch without passing the caught error as cause or logging it. In the catch block you can log e.message and e.stack, then rethrow (throw e) or wrap (throw new Error("Context", { cause: e })). Either way, do not leave the catch empty or with only a comment; at least log or rethrow so the failure is visible. When you wrap, the new error's stack shows where you threw the wrapper; the cause's stack shows where the original error came from. In development you can log both (e.stack and e.cause?.stack) so you see the full chain. When you rethrow the same error (throw e), the stack is unchanged and points to where the error was first created; that is useful when you only need to log and let the error bubble up. When you catch in a top-level handler (e.g. in main or in an event handler that runs user code), log the error with message and stack and optionally cause, then show a generic message to the user so they know something failed without exposing internal details. When you have several layers (e.g. API layer, business logic, UI), each layer can catch, log or add context, and rethrow so that the error is handled at the right level: API layer might wrap with "Request failed", business logic might wrap with "Could not start zone", and UI catches and shows "Action failed; try again."

## 4) When to Throw and When Not

Throw when a precondition is violated: the function cannot do its job (e.g. required argument is null, config is missing a key). Throw when an operation fails and the caller must be informed (e.g. network request failed, file not found and the file was required). Throw when you detect an invariant violation (state that should never occur if the program is correct). Do not throw for expected outcomes: when a lookup returns nothing and that is normal (e.g. findUser(id) when the user might not exist), return null or a result object so the caller can branch. Do not throw for control flow (e.g. using throw to break out of a loop is possible but confusing; use break or return). Do not throw when you can handle the failure locally and return a fallback or a documented error value; reserve throw for when the caller needs to know and possibly handle. At boundaries (where data enters your program—API response, config file, user input), validate and throw with a clear message if the data is invalid; that way the rest of the code can assume valid data. Inside internal logic, you may assume preconditions already hold because the boundary validated; if you discover otherwise (e.g. a bug), throwing is appropriate. When you design a function, document whether it throws on failure or returns null/error value so callers know whether to use try/catch or to check the return value. Mixing both in the same function (sometimes throwing, sometimes returning an error) is confusing; pick one contract per function. For a homestead example: throw when config.sensorIds is missing or not an array; throw when fetchReading is called with an invalid id and the id was required; return null when getOptionalSetting("theme") is not set and that is optional. When in doubt, throw with a clear message so failures are visible; you can always catch and convert to a return value at a higher layer if needed. When a function is documented as "throws when X", callers must use try/catch or ensure the promise is caught when the function is async. When a function is documented as "returns null when not found", callers should check for null and not wrap the call in try/catch for the not-found case. When you call a library that throws, check its docs for which errors it throws and under what conditions; then you can catch and either handle (e.g. retry for network errors) or wrap with your own message and rethrow. When you have a result type (e.g. { ok: true, data } or { ok: false, error }), you return that instead of throwing for expected failures; the caller branches on ok. That pattern is common in some codebases and languages; in JavaScript throwing is idiomatic for exceptional cases and returning null or a result object for expected ones. Choose one style per function and stick to it so callers know what to expect.

## 5) Rethrowing and Error Boundaries

When you catch an error, you can handle it and then rethrow so that a higher-level caller can also react. For example: catch (e) { logger.error(e); throw e; }. The error is logged and then propagates unchanged. The caller might show a generic "Something went wrong" and the log has the details. When you wrap with a new error, use cause: catch (e) { throw new Error(`Failed to load zone ${zoneId}`, { cause: e }); }. The caller sees your message and can inspect cause for the original. Do not swallow: avoid catch (e) { } with an empty body. At least log; or rethrow; or return a documented fallback and make it clear in the code that the error was handled. The term "error boundary" in UI frameworks means a component that catches errors in its subtree and shows a fallback UI instead of crashing the whole app; the same idea applies in any layered design: have a place (a boundary) where errors are caught, logged, and either handled or rethrown so that one layer does not have to know every possible error from below. In async code, ensure that when you catch in an async function and rethrow, the caller of that function (which gets a promise) still has to .catch or await in try/catch; rethrowing inside async propagates the rejection to the returned promise. So the chain of responsibility is preserved: inner code throws or rejects, middle layer logs or wraps and rethrows, top layer (e.g. main or event handler) catches and shows the user or exits. For a homestead dashboard, the top-level catch might show "Could not load dashboard" and log the full error; inner functions throw with context (sensor id, zone id) so the log is actionable.

## 6) Homestead Examples

Validate config at startup: if (!config || !config.sensorIds || !Array.isArray(config.sensorIds)) throw new Error("config.sensorIds must be a non-empty array"); so the rest of the app can assume sensorIds exists. When loading config from a file, catch JSON.parse errors and throw a new Error with context: catch (e) { throw new Error(`Invalid config file: ${e.message}`, { cause: e }); } so the user sees "Invalid config file" and the cause holds the parse error. When fetchReading(sensorId) is called with a missing or invalid id, throw new Error(`Sensor not found: ${sensorId}`) so logs show which id failed. When the API returns an error status, throw new Error(`API error ${response.status}: ${await response.text()}`) or a custom ApiError so the caller can catch and show "Service unavailable." When validating user input (e.g. zone name), if the value is invalid throw new ValidationError("Zone name cannot be empty") or throw new Error("Zone name cannot be empty") so the form layer can catch and show the message next to the field. When starting a zone fails, the function that calls the API can throw; the event handler catches and shows "Could not start zone" and logs the error. When you have a custom ConfigError class, at startup catch (e) { if (e.name === "ConfigError") { showConfigError(e.message); } else { throw e; } } so config errors get a specific UI and other errors propagate. When rethrowing after log: catch (e) { console.error("Fetch failed", e); throw e; }. When wrapping: throw new Error(`Failed to load zones`, { cause: e }); so the message is friendly and the cause has the original stack. When a function is designed to return null for "not found," do not throw for that case; throw only when the absence of the value is an error (e.g. required config missing). Each of these patterns keeps errors visible and contextual. When you validate user input in a form, throw or return a list of field errors so the UI can show messages next to each field; if you throw, use a ValidationError with a field property so the catcher can map errors to fields. When the API returns 404 for a resource, the function that fetches it can throw new Error(`Not found: ${resourceId}`) so the caller can catch and show "Not found" or return null if the API is designed to use null for missing resources. When a required environment variable is missing at startup, throw immediately with a message that names the variable so the deploy fails fast with a clear fix. When you parse a file and the format is wrong, throw with the file path and the parse error message so the user knows which file to fix. When you have a retry loop (e.g. for a flaky network), catch the error, log it, and retry up to N times; after N failures throw or return a failure result so the caller knows the operation did not succeed. When multiple operations can fail (e.g. loading several sensors), you can collect errors (e.g. push to an array) and at the end throw one error whose message lists all failures, or return a result object that contains both successes and failures; that way the user sees a complete picture instead of only the first failure.

## 7) What Breaks When Throwing or Custom Errors Are Wrong

If you throw a string (throw "error") or a number, the thrown value has no .message or .stack; catch blocks that expect an Error may break. Prefer throw new Error("message"). If you throw inside a callback that runs later (e.g. in a promise or setTimeout), the try that wrapped the code that started the callback does not catch it; the throw runs in a different turn. So catch inside the callback or use .catch on the promise. If you wrap an error but do not set cause, the original stack is hard to find; use { cause: e } when wrapping. If you define a custom error class but forget to set this.name in the constructor, e.name might be "Error" and instanceof or name checks fail; set this.name = this.constructor.name or the string you want. If you swallow an error (empty catch or catch that only returns without documenting), the program continues and callers do not know something failed; at least log or rethrow. If you throw for "not found" when the API design says the function returns null for that case, callers that expect null get an exception instead; reserve throw for exceptional cases. If your message has no context (e.g. "Invalid id"), debugging is harder; include the id or the expected type in the message. If you put secrets in the message, they can leak in logs or UI; avoid. If you throw in finally, that throw can replace the one from try or catch; avoid throwing in finally. If you rethrow a different error without passing the original as cause, you lose the stack; use throw e to rethrow the same error or wrap with cause. So: throw Error objects with clear messages, use cause when wrapping, set name on custom classes, do not swallow, and reserve throw for exceptional or invalid cases. When you catch and want to add context without wrapping (e.g. add a property to the error), you can mutate the error object (e.context = { zoneId }) and rethrow; that way the same error propagates with extra info. Prefer wrapping with cause when you want a new message and to keep the original error distinct. When you have a global or process-level error handler (e.g. window.onerror or process.on("uncaughtException")), it receives the error that was not caught; log it and optionally report it, then decide whether to exit or continue. Unhandled promise rejections are similar: they occur when a promise rejects and no .catch or try/await handles it; in Node you can use process.on("unhandledRejection") to log and optionally exit. Ensuring that every throw is eventually caught (or that every promise has a .catch) keeps errors visible and prevents silent failures. When you write tests, you can assert that a function throws: the test framework may provide expect(() => fn()).toThrow() or similar; the important thing is that the code under test throws when it should and that the message or error type is as expected.

## 8) Checklist

When you work with throwing and custom errors: (1) Throw new Error("message") or a subclass; use template literals to include variable context in the message. (2) Define custom error classes (extends Error) when callers need to distinguish error types; set this.name in the constructor. (3) When wrapping an error, pass the original as cause: new Error("Context", { cause: e }). (4) Rethrow (throw e) after logging when the caller should still handle the error; do not swallow. (5) Throw for precondition violations and operation failures that the caller must handle; return null or a result for expected "not found" or optional outcomes. (6) Document whether your function throws or returns an error value so callers know how to handle. (7) Validate at boundaries and throw with a clear message so the rest of the code can assume valid data. (8) Do not put sensitive data in error messages. (9) In catch, at least log or rethrow; avoid empty catch. (10) Chapter 3.20 (Strict Mode and Robust Code) builds on this by making the program fail fast on more kinds of invalid code and state.

## Common Pitfalls

Throwing non-Error: throw "error" has no .message or .stack. Use throw new Error("message").

Swallowing errors: Empty catch or catch that only returns without logging. Log or rethrow so failures are visible.

Wrapping without cause: throw new Error("Failed") in catch loses the original error. Use { cause: e }.

Forgetting this.name on custom errors: e.name may be "Error". Set this.name in the constructor.

Throwing for expected "not found": Use return null or a result object when absence is normal; reserve throw for exceptional cases.

Throw in finally: Replaces the throw from try/catch. Avoid throwing in finally.

Sensitive data in message: Messages may end up in logs or UI. Do not include passwords or tokens.

## Summary

Throw with throw new Error(message); use template literals so messages include variable context. Define custom error classes (extends Error) when callers need to distinguish error types; set name and optionally extra properties. When wrapping an error, use the cause option so the original error and stack are preserved. Rethrow after logging or wrap with cause; do not swallow errors. Throw for precondition violations and operation failures; return null or a result for expected outcomes like "not found." Validate at boundaries and throw with clear messages.
