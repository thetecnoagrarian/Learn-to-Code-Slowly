# Section B Phase 3 · Chapter 3.20: Strict Mode and Robust Code

This chapter covers strict mode ("use strict"): what it changes in JavaScript, how to enable it, and why ES modules and class bodies are strict by default. It also covers habits for robust, predictable code: preferring const and let over var, avoiding accidental globals, validating at boundaries, and failing fast when assumptions are violated. It builds on Chapter 3.19 (Throwing and Custom Errors), where you throw on invalid input; strict mode adds another layer by turning certain silent mistakes into errors (e.g. assigning to an undeclared variable). Chapter 3.21 (Debugging and the Console) then covers how to inspect and debug your program; strict mode and clear error messages make debugging easier because failures are visible instead of hidden. Using strict mode and consistent robust habits reduces bugs and makes the program easier to reason about.

## Learning Objectives

By the end of this chapter, you should be able to:
- Enable strict mode with "use strict" at the top of a file or function, and know that ES modules and class bodies are strict by default.
- Understand what strict mode disallows or changes: undeclared variables become errors, duplicate parameter names are errors, delete of plain identifiers is an error, and certain other behaviors are tightened.
- Apply habits for robust code: prefer const (and let when reassignment is needed), avoid var; declare variables in the smallest scope; validate inputs at boundaries and fail fast with throw when invalid.

## Key Terms

- **strict mode**: A mode of JavaScript that disallows or changes several loose or legacy behaviors. Enabled by "use strict" at the top of a script or function, or automatically in ES modules and class bodies. Assigning to an undeclared variable throws instead of creating a global; duplicate parameter names and other patterns throw or are disallowed.
- **"use strict"**: A directive (a string literal at the beginning of a script or function) that enables strict mode for that scope. Must appear before any other statements. In a function, it enables strict mode only for that function. In a script, it applies to the whole script.
- **accidental global**: In non-strict mode, assigning to a variable that was never declared (e.g. typo in a variable name) creates a new property on the global object instead of throwing. Strict mode makes this an error so typos and missing declarations are caught.
- **const and let**: Block-scoped declarations introduced in ES2015. const cannot be reassigned after initialization; let can. Prefer const by default and use let only when you need to reassign. Both are block-scoped (visible only within the enclosing block), unlike var which is function-scoped.

## 1) What Strict Mode Does

Strict mode is enabled by placing the string "use strict" (or 'use strict') at the very beginning of a script or at the beginning of a function body. No other statements can appear before it in that scope. When strict mode is on, several behaviors change. First, assigning to an undeclared variable throws a ReferenceError instead of creating a global. So if you typo a variable name (e.g. sensroId instead of sensorId) and assign to it, you get an error immediately instead of creating a mysterious global that can cause bugs elsewhere. Second, duplicate parameter names in a function (e.g. function f(a, a) {}) are a syntax error in strict mode; in non-strict they were allowed and the second one "won." Third, delete followed by a plain variable or argument name (e.g. delete x) is a syntax error in strict mode; delete is only for object properties. Fourth, with statements (with (obj) { ... }) are not allowed in strict mode; they are disallowed because they make scope hard to reason about. Fifth, in strict mode the value of this in a function that is not a method and not called with new is undefined instead of the global object; that avoids accidentally using or mutating the global when you meant to use a different this. Sixth, certain other edge cases (e.g. octal literals like 0123, assigning to read-only properties) throw or are disallowed. The goal is to catch common mistakes and to make the language behavior more predictable. For a homestead script, enabling strict mode at the top of the file (or using ES modules so it is automatic) means that a typo in a variable name or a missing declaration will fail fast with a clear error instead of silently creating a global or behaving oddly. Strict mode is lexically scoped: if you enable it at the top of a function, only that function is strict; any function it calls that is defined in a non-strict script runs in non-strict mode. So the strictness of a piece of code depends on where it is defined, not where it is called. When you nest functions, the inner function inherits the strictness of the outer scope. When you eval a string in strict mode, the evaluated code is also strict; in non-strict mode, eval can introduce subtle scope and behavior issues, so many codebases avoid eval entirely. When you use "use strict" in a script that is concatenated with others (e.g. by a build tool), the directive applies only to that script's content; so each file that should be strict needs its own directive or should be a module. Some tools and transpilers add "use strict" automatically when targeting strict-capable environments; check your setup so you know whether you need to write it explicitly.

## 2) Modules and Class Bodies Are Strict by Default

ES modules (files with import or export, or "type": "module" in Node) are always in strict mode; you do not need to write "use strict". The same applies to the body of a class: the code inside class methods and field initializers runs in strict mode. So if you are already using ES modules (Chapter 3.15) or writing classes, you are already in strict mode for that code. In Node, when you use "type": "module" in package.json, every .js file in that package is treated as an ES module and is strict. In the browser, a script with type="module" is strict. So for new projects that use modules, strict mode is the default. For legacy scripts (no modules, no class), adding "use strict" at the top of the file is a good idea so you get the same protections. You can also enable strict mode for a single function by putting "use strict" at the start of the function body; that is useful when you are gradually converting a large file and want one function to be strict while the rest is not yet. In practice, prefer making the whole file strict or using modules so the entire scope is consistent. When you run a script in Node without "type": "module", the file is not a module and is not strict unless you add "use strict". When you run the same logic as an ES module (e.g. rename to .mjs or set "type": "module"), the file is strict automatically. So migrating to modules gives you strict mode and the benefits of import/export. When you write a class, the constructor and method bodies are strict; you do not need to add "use strict" inside them. When you use arrow functions, they inherit the strictness of the scope where they are defined; so an arrow function defined in a strict script is strict.

## 3) Writing Robust Code: Declarations and Scope

Prefer const for every binding that you do not need to reassign. Use let when you must reassign (e.g. a loop counter, or accumulating a value in a loop). Avoid var; it is function-scoped and has hoisting behavior that can be surprising, and const/let make scope and reassignment explicit. When you use const with an object or array, the binding cannot be reassigned but the object or array itself can be mutated (you can push to the array or set properties on the object). So const means "this variable will not point to a different value," not "the value is immutable." When you need a variable that really does not change, const is the right choice; when you need to reassign the variable itself (e.g. let result = null; ... result = compute()), use let. Declare variables in the smallest scope that needs them: inside the block where they are used (e.g. inside a loop or inside an if block) so that you do not leak names to outer scopes and so the intent is clear. Avoid declaring many variables at the top of a long function; declare near use when possible. Do not rely on hoisting for let or const: the temporal dead zone means you cannot use the variable before its declaration in the block, which helps catch ordering bugs. For a homestead example: const config = loadConfig(); at the top of a function, then use config inside; const sensorIds = config.sensorIds; when you need a shorter name in a block. Use let only when you are reassigning, e.g. in a loop that accumulates or when you need to replace a value. This keeps the code predictable and makes it obvious which bindings are meant to change. When you destructure (e.g. const { sensorIds, apiBase } = config), you are still declaring constants; each destructured name is a const in that block. When you need a default in destructuring (e.g. const { timeout = 5000 } = config), that applies when the property is undefined; it does not replace validation when the whole config or a required field is missing. When you have a loop that only reads from a collection (e.g. for (const item of items)), use const for the loop variable; when you need to mutate a variable across iterations (e.g. let sum = 0; for (...) { sum += x; }), use let. When you have nested blocks, a variable declared in an inner block shadows the outer one; use different names or structure the code so the intent is clear. When you refactor and introduce const/let, you may find that you can make more things const than you thought; that reduces the number of bindings that can change and makes reasoning easier. When a linter or teammate suggests "prefer const," they mean: if you are not reassigning, use const. It is a small habit that pays off in clarity and in catching accidental reassignment.

## 4) Writing Robust Code: Validation and Fail Fast

Validate data at the boundaries where it enters your program: when you read config, when you receive an API response, when you get user input. Check that required fields exist and have the expected types; if not, throw with a clear message (Chapter 3.19) so the failure is visible and the rest of the code can assume valid data. Do not let invalid data propagate; fail fast at the boundary. For config: if the app requires config.sensorIds to be an array of strings, check that at startup and throw if it is missing or wrong. For API responses: after parsing JSON, validate the shape (e.g. that the response has a zones array) before using it; throw or return an error result so callers do not see undefined or wrong types later. For user input: validate before using (e.g. trim and check length, or check format); throw or return a validation error so the UI can show a message. When you call a function that might throw, either catch and handle (or rethrow) or document that your function propagates the error; do not ignore the possibility. When you write a function that takes arguments, document the contract (required, types, meaning) and throw when the contract is violated so callers get a clear error instead of undefined behavior. Robust code also avoids relying on optional chaining or default values to paper over missing data when the data is required; if the data is required, validate and throw so the bug is obvious. For a homestead dashboard: validate config on load; validate API response shape after fetch; validate user input before sending to the API; throw at each boundary with a message that identifies what was wrong and where. That way when something fails, the error message points to the cause. When you validate, check both presence and type: not only "does the property exist?" but "is it the right type?" (e.g. Array.isArray(config.sensorIds) and, if needed, that each element is a string). When the API or config format changes, update the validation so the error message stays accurate. When you have optional fields with defaults, set the default after you have validated the required parts (e.g. const timeout = config.timeout ?? 5000 only after you have confirmed config exists and required keys are present). When you call a function that throws, either catch and handle it at a boundary (e.g. top-level or UI layer) or let it propagate and ensure the caller is prepared; do not catch and ignore. When you write tests, strict mode and validation help: invalid input should throw, and the test can assert on the error message or type. When you document a function, say what it expects and whether it throws so that callers can use try/catch or checks appropriately. When the codebase grows, having strict mode and validation everywhere means that new code that violates assumptions will fail at the boundary instead of deep in a call stack with a cryptic error.

## 5) When to Use Strict Mode and Robust Habits

Use strict mode in all new code. If you use ES modules, you already have it. If you use a script without modules, add "use strict" at the top of the file. If you work in a codebase that is not fully strict, you can enable strict mode per function while migrating. The benefits (no accidental globals, duplicate parameters caught, predictable this) outweigh the small cost of fixing any code that relied on loose behavior. For robust habits: use const by default and let only when reassigning; avoid var. Declare variables in the smallest scope. Validate at boundaries and throw when invalid. Do not swallow errors; log or rethrow. Prefer explicit checks over assuming (e.g. check that an array is non-empty before using index 0 if the contract allows an empty array). Use optional chaining and nullish coalescing when the value is truly optional and you have a sensible default; when the value is required, validate and throw instead of defaulting silently. When you refactor, add strict mode and fix any errors that appear; they are usually real bugs (typos, missing declarations) that would have caused subtle issues later. When you write a new file, start with "use strict" or use a module so the whole file is strict. When you use a linter or formatter, many are configured to warn or error on var, undeclared variables, and other strict-mode-related or robust-code patterns; that helps keep the codebase consistent. When you work in a legacy codebase that is not strict, enabling strict mode for the whole file may produce many errors (undeclared globals, duplicate parameters, etc.); you can fix them in batches or enable strict mode per function as you touch the code. When you bundle or transpile, the output may add "use strict" if the target supports it; the source can be modules (which are strict) and the bundle will preserve that. When you run scripts in the browser without a build step, add "use strict" at the top of each script tag's content if the script is not a module. When you use Node and CommonJS (require/module.exports), the file is not a module in the ES sense, so add "use strict" at the top if you want strict mode. When in doubt, enable strict mode; the errors it surfaces are almost always real bugs or bad patterns that are worth fixing.

## 6) Homestead Examples

At the top of your main script or config loader, use "use strict" if the file is not a module, or rely on module strictness. When loading config, validate and throw: if (!config.sensorIds || !Array.isArray(config.sensorIds)) throw new Error("config.sensorIds must be an array"); so the app fails at startup with a clear message instead of failing later when you iterate over undefined. When you receive an API response, validate the shape before using: if (!data || !Array.isArray(data.zones)) throw new Error("Invalid API response: missing zones array"); so you do not pass invalid data to the rest of the app. Use const for config, sensorIds, and any binding that does not change; use let only when you accumulate (e.g. in a loop) or replace a value. When you have a function that takes a sensor id, throw if the id is missing or wrong type: if (id == null || typeof id !== "string") throw new TypeError("sensor id must be a non-empty string"); so callers get a clear error. When you read from localStorage or a file, validate after parse (Chapter 3.16) and throw with context if the data is invalid. When you have optional config (e.g. theme), use const theme = config.theme ?? "default"; that is a deliberate default for an optional value, not a way to hide missing required data. When you refactor an old script, add "use strict" at the top and fix any ReferenceErrors (usually a typo or a variable that was never declared); the fix is often adding the correct declaration. When you write a small utility that does not use modules, still add "use strict" so that any future typo or mistake is caught. Each of these practices makes the program fail fast and predictable. When you have a function that takes an options object, validate the options at the start: if (options == null || typeof options !== "object") throw new TypeError("options must be an object"); then validate required keys. When you read from process.env or a similar source, check that required variables are present and non-empty before using them; throw at startup with the variable name so deployment fails fast. When you parse JSON from an API or file, validate the parsed result (Chapter 3.16) and throw with a message that includes what was wrong (e.g. "API response must have a 'data' array") so the caller knows what to fix. When you use default parameters in a function (e.g. function load(id = null)), the default only applies when the argument is undefined; if the caller passes null explicitly, the parameter is null. So for required parameters, do not rely on defaults; throw inside the function if the value is invalid. When you have a list of validation rules (e.g. for a form), you can collect errors and throw once with all of them, or throw on first failure; the former gives the user a full list, the latter is simpler. When you refactor and add "use strict" to an old file, run the code (or tests) and fix each error; most are undeclared variables (add const/let) or duplicate parameters (rename one). The result is a file that is easier to maintain and less prone to subtle bugs.

## 7) What Breaks When Strict Mode or Robust Habits Are Missing

If you do not use strict mode and you typo a variable name, you create a global. That can cause bugs that are hard to find: another part of the code might read that global and behave oddly, or you might overwrite a real global. Strict mode makes the typo an error at the point of assignment. If you use var in a long function and reuse the same name in a block (e.g. a loop), the variable is shared across iterations and can cause bugs; let is block-scoped so each iteration or block can have its own binding. If you do not validate at a boundary and pass invalid data through, the failure happens later (e.g. "cannot read property 'x' of undefined") and the stack trace may not point to where the data came from; validating and throwing at the boundary gives a clear message and location. If you use optional chaining and default values for data that is actually required, you hide bugs: the code might run with undefined or wrong data and fail in a confusing way later. Reserve defaults for truly optional values; for required data, validate and throw. If you have a mix of strict and non-strict code (e.g. strict function that calls a non-strict library), the strict function still gets strict behavior; the non-strict code runs in its own mode. If you concatenate or bundle multiple scripts and one has "use strict" at the top, only that script is strict; the others are not unless they also have the directive. So for consistency, enable strict mode for the whole unit (file or module). If you delete a variable in non-strict mode it might silently fail or behave oddly; in strict mode delete variableName is a syntax error, so you do not accidentally delete something you did not mean to. So: use strict mode everywhere, prefer const/let and small scope, validate at boundaries and throw, and avoid hiding required-data bugs with defaults. When you enable strict mode in a file that previously was not strict, watch for this in functions: in non-strict mode, a function called without a receiver (not as a method) gets the global object as this; in strict mode, this is undefined. So if the code relied on this being the global (e.g. to read a global variable), it will break; fix by passing the value explicitly or by using a different pattern. When you have nested scripts (e.g. inline script in HTML), each script is independent; the inner script needs its own "use strict" if it should be strict. When you use a minifier, it may strip "use strict" in some configurations; ensure the minified output is still strict if the source is, or that the runtime (e.g. module loader) enforces strictness. When you write a library that others will use, publishing ES modules or adding "use strict" to your UMD or IIFE bundle ensures that consumers who use your code in a strict context do not get mixed strict/non-strict behavior. When you run tests, run them in the same mode (strict or not) as production so that strict-mode-only bugs are caught before release.

## 8) Checklist

When you work with strict mode and robust code: (1) Enable strict mode in every file: add "use strict" at the top or use ES modules (which are strict by default). (2) Prefer const for bindings that do not change; use let only when you need to reassign. (3) Avoid var. (4) Declare variables in the smallest scope that needs them. (5) Validate at boundaries (config, API response, user input) and throw with a clear message when data is invalid. (6) Do not use optional chaining or defaults to hide missing required data; validate and throw. (7) Document the contract of functions (what they expect and whether they throw) so callers can use them correctly. (8) When refactoring, add strict mode and fix any errors that appear. (9) Use a linter or formatter that enforces or suggests strict-mode and const/let habits. (10) Chapter 3.21 (Debugging and the Console) will show how to inspect state and trace failures; strict mode and clear validation errors make debugging easier.

## Common Pitfalls

Skipping strict mode: Without it, typos create globals and some mistakes are silent. Use "use strict" or modules everywhere.

Using var: Function-scoped and hoisting can cause subtle bugs. Prefer const and let.

Not validating at boundaries: Invalid data then causes failures later with unclear messages. Validate and throw at the boundary.

Hiding required data with defaults: Using ?? or || for required config can mask missing data. Validate and throw for required fields.

Declaring variables too high in scope: Declare near use so scope is clear and you do not leak names.

Assuming data shape: After parse or fetch, check that required fields exist and have the right type before using.

## Summary

Strict mode is enabled with "use strict" at the top of a script or function; ES modules and class bodies are strict by default. Strict mode disallows accidental globals (assignment to undeclared variables throws), duplicate parameters, delete of variables, and other loose behaviors. Use strict mode in all new code. For robust code: prefer const and let (avoid var), declare in the smallest scope, validate at boundaries and throw when invalid, and fail fast so bugs are visible. Chapter 3.21 (Debugging and the Console) covers tools and techniques for finding and fixing bugs; strict mode and validation make those bugs easier to see and trace.
