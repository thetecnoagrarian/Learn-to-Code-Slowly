# Section B Phase 3 · Chapter 3.21: Debugging and the Console

This chapter covers how to inspect and debug JavaScript: console methods (log, error, warn, table, dir, time/timeEnd), setting breakpoints and stepping through code in the browser DevTools or Node inspector, and how to debug async flow and state. It builds on Chapter 3.20 (Strict Mode and Robust Code), where you made failures visible with strict mode and validation; here you learn how to use the console and debugger to trace those failures and inspect variables and the call stack. Chapter 3.22 (Expressions, Statements, and Program Flow) then clarifies the grammar of the language; when you step through code in the debugger, understanding statements and expressions helps you know where execution will go next. Using the console for quick checks and the debugger for systematic tracing makes finding and fixing bugs much faster.

## Learning Objectives

By the end of this chapter, you should be able to:
- Use console.log, console.error, console.warn, console.info, and console.debug to output values and messages; use console.table for arrays and objects; use console.dir for object inspection; use console.time and console.timeEnd for timing.
- Set breakpoints in the browser DevTools Sources panel or in Node with the inspector; use conditional breakpoints when you need to stop only when a condition holds; step over, into, and out of function calls and inspect the call stack.
- Inspect variables and state at a breakpoint; use watch expressions to track values; debug async code (promises, async/await) and understand how the call stack and async stack appear in the tools.

## Key Terms

- **console**: A built-in object (in browsers and Node) that provides methods for writing output. console.log(message, ...values) is the most common; console.error, console.warn, and others are for different levels. Output appears in the browser DevTools Console tab or in the Node terminal.
- **breakpoint**: A place in the code where execution pauses so you can inspect state. You set a breakpoint in the DevTools Sources panel (or in the editor when using Node inspector) by clicking the line number or using a debugger statement. When execution hits the breakpoint, the debugger stops and you can step, inspect variables, and view the call stack.
- **call stack**: The list of function calls that led to the current point of execution. When you pause at a breakpoint, the call stack shows the current function and its callers. Stepping "out" goes up the stack; stepping "into" goes into a function call. Useful for understanding how you got to the current line and what the caller passed in.
- **step over / step into / step out**: Step over runs the current line and stops at the next line in the same function (without entering any function call). Step into goes inside a function called on the current line. Step out runs until the current function returns and stops in the caller. Used to follow execution line by line.

## 1) Console Methods

console.log takes one or more values and prints them to the console. You can pass strings, numbers, objects, arrays; objects and arrays are often shown in an expandable form so you can inspect properties. console.log("message", variable) is a common pattern to label what you are logging. console.error and console.warn are like log but typically appear with different styling (e.g. red for error, yellow for warn) and may be filtered separately in the console UI; use error for failures and warn for things that might be wrong. console.info and console.debug are similar; some environments treat them as distinct levels so you can filter by level. console.table(arrayOrObject) displays an array or object as a table: for an array of objects, each object is a row and each property a column, which is useful for arrays of similar objects (e.g. a list of readings or zones). For a plain object, table shows key-value pairs. console.dir(object) shows the object in a format that expands properties; it can be more useful than log for deeply nested objects when the environment’s log flattens or truncates. console.time(label) and console.timeEnd(label) measure time between the two calls with the same label; use them to see how long a block of code or an async operation takes. console.trace() prints the current call stack to the console so you can see how execution reached that point. In production, avoid leaving noisy or frequent logs; they can clutter the console and sometimes affect performance. Use a logging level or build step to strip or gate logs in production, or guard logs with a flag (e.g. if (DEBUG) console.log(...)). For a homestead app, log at key points: after loading config, when a fetch completes, when an error is caught. Use error for caught exceptions and warn for recoverable or unexpected conditions (e.g. missing optional config). Use table when you want to inspect an array of sensor readings or zones in one view. You can pass a second argument to console.table to specify which columns to show (an array of property names), so you can limit a wide object to the keys you care about. console.group(label) and console.groupEnd() wrap a block of logs under a collapsible group so you can structure output (e.g. group "fetch zones" and inside it log the request and response). console.clear() clears the console output, which can help when you are re-running and want a fresh view. In Node, console output goes to stdout (log, info, debug) or stderr (error, warn); that matters when you redirect output or when a process manager captures stderr separately. When you log multiple values in one call (e.g. console.log("id", id, "value", value)), the format depends on the environment; for complex objects, logging them one per line or using table/dir can be clearer. When you use template literals in a log message (e.g. console.log(`Sensor ${id}: ${value}`)), the string is built at log time and you get a single string in the output; when you pass the variables as separate arguments, some environments will let you expand the object in the console. Choose based on what you need to inspect.

## 2) Breakpoints and Stepping

In the browser, open DevTools (often F12 or right-click and Inspect), go to the Sources (or Debugger) panel, and open the file that contains your code. Click the line number to set a breakpoint; a marker appears and execution will pause when that line is about to run. You can also insert a debugger statement in your code; when the debugger is open and execution hits that line, it pauses as if you had set a breakpoint there. Once paused, you can inspect variables in the scope panel (local and global variables, closure variables), view the call stack (the list of functions that led to this point), and use the stepping controls. Step over runs the current line and stops at the next; use it when the current line calls a function you do not need to enter. Step into goes inside the function called on the current line; use it when you want to trace into that function. Step out runs the rest of the current function and stops in the caller. Resume continues execution until the next breakpoint or until the program ends. You can set a conditional breakpoint: when creating the breakpoint, you can specify an expression (e.g. id === "sensor1") so execution only pauses when the condition is true; that is useful when the line runs many times (e.g. in a loop) and you care about one case. In Node, run node --inspect script.js (or node --inspect-brk to pause on the first line); then open chrome://inspect in Chrome and click the link to attach the DevTools to the Node process. You get the same Sources panel, breakpoints, and stepping as in the browser. So you can debug server-side code with the same tools. For a homestead script that runs in Node (e.g. a config loader or a script that fetches sensor data), use --inspect to set breakpoints in that code and inspect why a value is wrong or why a path is not taken. You can also set breakpoints programmatically in some environments (e.g. by calling a debugger API), but for most use cases clicking in the UI or using debugger is enough. When you use a build step (e.g. bundling or transpilation), the code that runs may not match the source file line-for-line; source maps map the running code back to the original source so that breakpoints and stack traces show the right file and line. Ensure source maps are generated and that the debugger can load them so you can set breakpoints in your source rather than in the transformed output. When the script is short (e.g. a few dozen lines), you might use debugger at the point you care about and run with the inspector; when the script is long, setting breakpoints in the UI is often easier than searching for the right spot. When you step and the next line is not where you expect (e.g. you step and land in a different file), that may be due to inlined code or a callback; use the call stack to see where you are in the overall flow.

## 3) Inspecting State and the Call Stack

When execution is paused at a breakpoint, the Scope panel (or equivalent) shows the variables in the current scope: local variables, function parameters, and any closed-over variables (closure). You can expand objects and arrays to see their properties and elements. The call stack shows the chain of calls: the top is the current function, below it is the caller, then the caller’s caller, and so on. Clicking a frame in the call stack switches the view to that frame so you can see that function’s local variables and the line where it called the next function. That helps when the bug is "the caller passed the wrong value" or "I don’t know how we got here." You can also add watch expressions: expressions (e.g. a variable name, or config.sensorIds.length) that are evaluated in the current context and shown in a list; they update as you step so you can track how a value changes. When you hover over a variable in the source code (in some UIs), you get a tooltip with its value. When the value is an object, you can expand it to see properties. When you step through a line that assigns to a variable, the Scope or Variables view updates after the step so you can confirm the new value. For async code, the call stack may show "async" or "Promise" frames; the debugger often has an "async" or "promise" stack that shows both the synchronous call stack and the async continuation, so you can see how execution reached the current callback or async function. Use that when debugging a fetch callback or an async function: set a breakpoint inside the callback or after an await and inspect the state when that code runs. When you set a breakpoint in a promise callback (e.g. inside .then), the call stack may show "Promise" or "microtask" at the top; the parent stack will show the code that created the promise. When you set a breakpoint in an async function after await, the stack will show the async function and possibly the promise that resumed it. When the bug is "this runs too early" or "this runs too late," the order of breakpoint hits (or logs) will show the actual order of execution; compare that to the order you expected. When you have nested async (e.g. await inside a loop, or multiple awaits in sequence), set breakpoints after each await to see the values at each step and to confirm the order. When the debugger shows "Paused in promise" or similar, you are in an async continuation; the Scope will show the local variables of that continuation (e.g. the async function’s locals after the await). When you evaluate an expression in the console while paused, you are in the same scope as the current frame; so you can type a variable name to see its value or call a function to see what it returns (but be careful not to change state in a way that confuses the rest of the run).

## 4) Debugging Async and Event-Driven Code

Async code runs later, so when you set a breakpoint inside a callback or after an await, execution may not be in the same "stack" as the code that started the operation. The debugger’s call stack will show the async stack (e.g. the promise reaction or the microtask that ran your callback) and often a separate section that shows the "parent" async chain (e.g. the fetch that led to this then or the async function that did the await). Use that to understand "this code ran because that promise resolved." When you debug an async function, set a breakpoint on the line after an await; when execution pauses there, the local variables will reflect the value that was awaited and any state after it. When you debug a .then or .catch callback, set a breakpoint inside the callback and run; when the promise settles, execution will pause and you can inspect the callback’s argument (the fulfillment value or rejection reason). When the bug is "this callback never runs," check that the promise is actually settling (e.g. log in the callback to see if it runs) and that you did not forget to return a promise or that the promise is not rejecting before it gets to your callback. When the bug is "the value is wrong when we get here," inspect the value at the breakpoint and look back at where it was set (e.g. the response from fetch, or the result of a previous await). For event-driven code (e.g. a click handler), set a breakpoint in the handler and trigger the event; when execution pauses, the event object and any closure variables are in scope. For a homestead dashboard, you might set a breakpoint in the loadDashboard async function after the fetch and inspect the parsed data; or in an error handler to see the caught error and the state when the error occurred. When you have a race condition (e.g. two async operations and the order matters), logging or breakpoints at the start and end of each operation can show the order they actually ran. When you debug in the browser, the Console tab and the Sources (or Debugger) tab often work together: you can run code in the Console while paused (in the current scope) or when running (in the global scope). When you need to see what a function returns without stepping into it, step over the line that calls the function and then inspect the variable that holds the return value, or add a log for that value. When you suspect the bug is in a library or in code you do not control, you can still set breakpoints in that code (if the source is available) or set a breakpoint in your code just after the call and inspect the arguments you passed and the return value; that often narrows down whether the bug is in your code or in the library. When the app is slow, use console.time/timeEnd around suspected blocks or use the debugger’s profiling tools (e.g. Performance or CPU profiler) to see where time is spent; profiling is a separate topic but time/timeEnd is a quick way to check one or two operations. When you have a bug that only happens sometimes, add a conditional breakpoint or a log that only runs when a condition is true (e.g. when a value is null or when a count exceeds a threshold) so the next time it happens you capture the state.

## 5) When to Use Console vs Breakpoints

Use the console when you want a quick check: "what is the value of this variable at this line?" or "does this code path run?" Add a log, run the code, and look at the output. Logs are also useful when you cannot easily reproduce the bug in the debugger (e.g. it only happens in production or after many steps); add logs, reproduce, and inspect the log output. Use breakpoints when you need to explore: you want to step through line by line, inspect several variables, or see the call stack. Breakpoints are better when the bug is subtle and you need to see state at multiple points or when you are not sure which path was taken. Use console.error or console.warn for errors and warnings so they stand out and can be filtered. Use console.table when the value is an array of objects and you want to see it in tabular form. Use time/timeEnd when you suspect a performance issue and want to measure a block or an async operation. Remove or guard verbose logs before committing or before production so the console is not flooded and so you do not leak sensitive data. For development, leaving a few strategic logs (e.g. "config loaded", "fetch completed") can help you confirm the flow; for production, use a proper logging solution that can be configured by environment. When you use the debugger, you can also evaluate expressions in the console while paused: type a variable name or an expression and the console evaluates it in the current scope. That is useful for trying a fix or checking "what if" without editing the code and rerunning. When you are not paused, the console runs in the global scope (or the scope of the current execution context); when paused, it runs in the selected stack frame’s scope. When you need to understand a large object, logging it and expanding in the console can be easier than setting a breakpoint and expanding in the Scope panel, or vice versa depending on the tool; use whichever lets you navigate the structure more easily. When you work in a team, agree on a convention for debug logs (e.g. a prefix like "[DEBUG]" or a wrapper that checks an env var) so that temporary logs are easy to find and remove. When you use Node and your script exits quickly (e.g. a one-off script), use --inspect-brk to pause on the first line so you have time to open DevTools and set breakpoints before execution continues. When the script is a long-running server, --inspect is enough; the script will run and you can attach and set breakpoints before triggering the code path you care about. When you hit an exception, the debugger can be set to pause on exceptions (e.g. "Pause on caught exceptions" or "Pause on uncaught exceptions"); that way you land exactly where the error is thrown and can inspect the state at that moment.

## 6) Homestead Examples

When config loading fails, add a log in the catch block with the error message and stack (or use console.error) so you see why it failed when you run the app. When a fetch returns but the data looks wrong, log the response (e.g. console.log("response", data)) or set a breakpoint after the await and inspect the parsed data in the Scope panel. When a zone or sensor list is empty when it should not be, set a breakpoint where the list is built or where it is used and inspect the array and its length; check the call stack to see where the list came from. When an event handler does not run, add a log at the start of the handler to confirm it is attached and firing; if it does not log, the event is not reaching the handler (e.g. wrong selector or event type). When a value is undefined when you expect it to be set, set a breakpoint where the value is read and look at the Scope to see what is in scope; then step back or look at the call stack to find where the value should have been set. When you are debugging async load order (e.g. config then zones), use console.time("load") at the start and console.timeEnd("load") when both are done, or set breakpoints after each await and note the order in which they hit. When you have a validation error (Chapter 3.19), the thrown error and message are visible in the console and in the debugger when you break on the throw or in the catch; use that to see the exact message and the state when validation failed. When you use Node to run a script that reads config or calls an API, run with node --inspect and set a breakpoint in the script to step through and see why a value is wrong or why a request fails. Each of these uses ties together the console and debugger with the error handling and validation from earlier chapters.

## 7) What Breaks When Debugging Is Wrong

If you leave many console.log calls in hot paths (e.g. inside a loop that runs every second), the console can slow down the app or fill with noise; remove or guard logs in production. If you log an object that changes later (e.g. you log state and then mutate it), the console may show the object in its current state when you expand it, not the state at log time; in that case log a copy (e.g. JSON.stringify) or a specific property. If you set a breakpoint and it never hits, the code path may not be running (e.g. the condition is false, or the event is not firing); add a log before the breakpoint to confirm. If the call stack is confusing (e.g. many async frames), focus on the top frame (your code) and the variables there; the async stack is there to show how you got there. If you debug in one environment (e.g. browser) but the bug only appears in another (e.g. Node), try to reproduce in the environment where you can debug, or add logs and reproduce in the other environment. If you forget to remove a debugger statement, the app will pause when the debugger is open and that line runs; remove debugger before committing or guard it. If you log sensitive data (tokens, passwords), it can end up in logs or in a user’s console; avoid or redact. So: use console for quick checks and breakpoints for systematic tracing; remove or guard verbose and sensitive logs; and use the call stack and scope to understand state and flow. When the bug is intermittent, add enough logging to capture the next occurrence (e.g. log when a condition is true) so you can see the state when it happens. When you debug a function that is called from many places, a conditional breakpoint with an expression that identifies the caller (e.g. a unique argument or a stack trace check) saves you from stepping through every call. When the problem is "nothing happens" (e.g. a handler never runs), add a log at the very start of the handler or at the point where the handler is registered to confirm that the code runs and that the handler is attached; then work backward from there. When you have minified or bundled code and the stack trace shows line 1 or a single large line, source maps are essential; without them you have to work with the transformed code or add strategic logs to narrow down the location. When you fix a bug, remove or comment out the debug logs and breakpoints you added so the next person (or you later) does not have to wade through them; or keep a minimal set that is useful for support (e.g. "version" and "config loaded") and gate the rest behind a debug flag. The goal is to make the program observable when you need it and clean when you do not.

## 8) Checklist

When you debug: (1) Use console.log for quick inspection of values; use console.error and console.warn for errors and warnings. (2) Use console.table for arrays of objects; use console.dir for nested object inspection. (3) Use console.time/timeEnd to measure duration. (4) Set breakpoints in DevTools (Sources) or use debugger in code; use conditional breakpoints when you need to stop only for a specific case. (5) Step over, into, and out to follow execution; use the call stack to see how you got to the current line. (6) Inspect variables in the Scope panel and use watch expressions to track values. (7) For async code, use the async stack and set breakpoints in callbacks or after await to inspect state when async code runs. (8) Remove or guard verbose logs and debugger statements before production. (9) In Node, use node --inspect to attach DevTools and debug server-side code. (10) Chapter 3.22 (Expressions, Statements, and Program Flow) clarifies the grammar so you know what "one step" means when stepping. Use the console and debugger together with the error messages and validation from earlier chapters to find and fix bugs efficiently.

## Common Pitfalls

Leaving too many logs: Noisy logs slow the app and hide important output. Remove or gate logs in production.

Logging objects that change: The console may show current state when expanded. Log a copy or a primitive if you need the value at log time.

Breakpoint never hits: The code path may not run. Add a log to confirm, or check the condition for a conditional breakpoint.

Forgetting to remove debugger: The app pauses when the debugger is open. Remove or guard debugger statements.

Logging sensitive data: Tokens or passwords in logs can leak. Avoid or redact in production.

Ignoring the call stack: The stack shows how you got there. Use it to find wrong arguments or wrong call order.

## Summary

Use console.log, console.error, console.warn, and related methods to output values and messages; use console.table for arrays of objects and console.time/timeEnd for timing. Set breakpoints in the DevTools Sources panel (or with debugger) and step over, into, and out of calls; use the call stack and Scope to inspect state. In Node, use node --inspect to attach DevTools. For async code, use the async stack and breakpoints in callbacks or after await. Prefer console for quick checks and breakpoints for systematic debugging; remove or guard logs and debugger in production. Chapter 3.22 (Expressions, Statements, and Program Flow) explains the structure of the language so that stepping and breakpoints make more sense.
