# Section B Phase 3 · Chapter 3.22: Expressions, Statements, and Program Flow

This chapter clarifies the difference between expressions (which produce a value) and statements (which perform an action and do not produce a value, or whose value is discarded). It also covers how execution order—top to bottom, conditionals, loops, function calls—shapes program flow, and how side effects (mutation, I/O, logging) fit in. It builds on Chapter 3.21 (Debugging and the Console), where you stepped through code line by line; each step corresponds to evaluating an expression or executing a statement, so understanding the grammar helps you predict where execution goes next. Chapter 3.23 (JavaScript in Practice) then ties the phase together with practical patterns; the flow and expression/statement distinction underpin how you read and write real code. Keeping flow clear and limiting side effects to boundaries makes programs easier to reason about and to test.

## Learning Objectives

By the end of this chapter, you should be able to:
- Distinguish expressions (they produce a value: literals, operators, function calls, identifiers) from statements (they perform an action: if, for, return, const, let; they do not produce a value or the value is discarded).
- Understand where JavaScript expects an expression (e.g. inside ${} in a template literal, the right-hand side of an assignment, the condition of a ternary) versus where it expects a statement (e.g. the body of an if, the body of a for loop).
- Understand execution order: single-threaded, synchronous run-to-completion; async work is deferred to the event loop (recap from Chapters 3.13 and 3.14).
- Recognize side effects and prefer keeping them at boundaries (I/O, DOM updates) so that core logic is easier to test and reason about.

## Key Terms

- **expression**: A piece of syntax that produces a value when evaluated. Literals (1, "a", []), operators (1 + 2, x === y), function calls (fn()), and variable references (x) are expressions. Expressions can be composed (e.g. a + b, fn(1, 2)). Where JavaScript expects a value, you use an expression.
- **statement**: A piece of syntax that performs an action. if, for, while, return, const, let, and block { } are statements. Statements do not produce a value (or their value is discarded). Where JavaScript expects an action (e.g. the body of an if, the body of a loop), you use a statement. Some constructs (e.g. an expression followed by a semicolon) are expression statements: the expression is evaluated for its side effect and the value is discarded.
- **program flow**: The order in which the program executes. Normally top to bottom; conditionals (if/else, switch) and loops (for, while) change which line runs next; function calls push a new frame and return pops it. Async work is scheduled and runs when the event loop runs it (Chapters 3.13, 3.14).
- **side effect**: An effect that goes beyond producing a value: modifying a variable or object, writing to the console, sending a network request, updating the DOM. A function that only returns a value and has no side effects is "pure"; one that mutates or does I/O has side effects. Side effects are necessary (you need to fetch and display) but keeping them at boundaries (e.g. at the edge of the app) makes the rest of the code easier to test and reason about.

## 1) Expressions and Statements

An expression is something that evaluates to a value. A number literal is an expression; a string literal is an expression; a variable name is an expression (it evaluates to the variable’s value). An operator applied to expressions is an expression: 1 + 2, x * y, a === b. A function call is an expression: the call returns a value (possibly undefined). So anywhere you need a value—on the right side of an assignment, inside ${} in a template literal, as an argument to a function, or as the condition of a ternary (condition ? a : b)—you use an expression. A statement is something that does something. An if statement runs one branch or another; a for loop repeats a body; a return statement exits a function and optionally supplies a value; const x = 1; is a declaration statement. Statements do not "return" a value to the surrounding code in the way an expression does; the value of a return is used by the caller, but the return statement itself is not an expression. Some contexts expect only an expression: inside the parentheses of a ternary (condition ? expr : expr), inside ${} in a template literal, or as the body of an arrow function when you omit the braces (e.g. x => x * 2). In those places you cannot put an if or a for; you must use an expression (e.g. a ternary for a conditional, or a function call). Other contexts expect a statement: the body of an if (after the condition), the body of a for loop, or the body of a function. There you can have multiple statements (e.g. a block with several lines). An expression can be used as a statement: you write the expression followed by a semicolon (e.g. fn(); or x + 1;). The expression is evaluated (and any side effects happen), but the value is discarded. So "expression statement" means "run this expression for its side effect." For a homestead example: when you write const reading = getReading(id), the right-hand side is an expression (the call produces a value); the whole line is a declaration statement. When you write `Sensor: ${reading.value}`, the part inside ${} must be an expression (reading.value). When you write the body of an if, you use statements (e.g. return; or updateDisplay(value);). Knowing which is which helps you avoid syntax errors (e.g. putting an if inside ${} where only an expression is allowed) and helps you read the debugger (each "step" is typically one statement or the evaluation of one expression). Some constructs are both: an assignment (x = 1) is an expression (it evaluates to the assigned value) but is usually used as part of an expression statement (x = 1;) for its side effect. The comma operator (expr1, expr2) evaluates both expressions and produces the value of the second; it is rarely used for clarity reasons. The void operator (void expr) evaluates the expression and produces undefined; it is sometimes used when you need an expression but want to discard the value. In practice you will mostly see simple expression statements (function calls, assignments) and full statements (if, for, return, const, let). When you read a line of code, ask: "Is this producing a value that is used somewhere (expression), or is it doing something (statement)?" That distinction will clarify why certain syntax is allowed in one place and not another. When the body of a function is a single expression, the concise arrow form (x => x * 2) is shorter; when the body needs multiple steps, you need a block and return. The same idea applies everywhere: expression contexts want one value, so you need one expression (which can be a call or a ternary that itself contains logic).

## 2) Where Expressions and Statements Are Allowed

In a template literal, ${} must contain an expression. So you can write `${reading.value}` or `${condition ? "OK" : "Low"}` (a ternary is an expression), but you cannot write `${if (x) "a"; else "b"}` because if/else is a statement. Use a ternary or a function call when you need logic inside the template. In an arrow function, if you use a concise body (no braces), the right-hand side must be an expression: x => x * 2 is valid because x * 2 is an expression. If you use a block body (with braces), you have a statement list and must use return explicitly to send a value back: x => { return x * 2; }. In the condition of an if, for, or while, you need an expression (that evaluates to a truthy or falsy value). In the body of an if or loop, you have statements (often a block containing several statements). In an assignment, the right-hand side is an expression: x = someExpression. The left-hand side is a target (a variable or property) that receives the value. In a return statement, return optionally followed by an expression gives that value to the caller. So return x + 1; is a statement that includes the expression x + 1. In a const or let declaration, the initializer (after =) is an expression. So const id = config.sensorId; has the expression config.sensorId. For a homestead example: when you map an array to strings, the callback can be a concise arrow (r => `${r.id}: ${r.value}`) because the template literal is an expression; if you need multiple steps inside the callback, you use a block and return: r => { const v = r.value ?? "—"; return `${r.id}: ${v}`; }. When you have a long conditional, you might use an if/else (statements) instead of a nested ternary (expression) for readability, even though both are valid in their respective contexts. In some languages, if is an expression and produces a value; in JavaScript, if is a statement and does not produce a value. So you cannot write const x = if (a) b else c; you must use const x = a ? b : c; (ternary) or use an if/else and assign inside each branch. In a logical expression (a && b, a || b), the operands are expressions; the result is one of them (short-circuit). So condition && doSomething(); runs doSomething() only when condition is true. In a for loop, the initializer, condition, and update are expression contexts; the body is statements. The grammar consistently puts value-producing pieces in expression position and actions in statement position.

## 3) Program Flow: Order and the Call Stack

Execution is single-threaded and synchronous until you hit async work. The program runs from top to bottom; when it hits an if, it evaluates the condition (an expression) and then runs either the then-branch or the else-branch (statements). When it hits a loop, it evaluates the condition and runs the body (statements) repeatedly. When it hits a function call (an expression), it pushes a new frame onto the call stack, runs the function body (statements), and when the function returns, it pops the frame and continues in the caller. So the flow is: run one statement (or expression statement) at a time; conditionals and loops choose which statement runs next; function calls transfer control into the function and return transfers it back. There is no parallel execution of your code; only one line runs at a time. When you use async (promises, async/await), the synchronous part runs to completion and then returns; the continuation (the .then callback or the code after await) runs later when the event loop runs it. So the "flow" of the program includes those later runs: first the top-level and the initial call stack run, then when a promise settles, the continuation runs (possibly with a different call stack that reflects the async boundary). When you step through in the debugger (Chapter 3.21), each step advances by one statement (or by one expression evaluation when the statement is an expression statement or when the engine breaks down a line into sub-expressions). The call stack in the debugger shows the current path of function calls that led to this point. For a homestead app: the main script runs, maybe calls loadDashboard(), which awaits fetch and then runs more code; the flow is linear within each synchronous chunk, and the async boundaries are where execution is "paused" until the event loop runs the continuation. Understanding that helps you set breakpoints and interpret the stack. When a function is called, the arguments (expressions) are evaluated first, from left to right, and then the function runs with those values. So the order of evaluation of arguments is defined (left to right), but the order relative to other expressions in the same statement can be subtle when there are multiple function calls; in practice you rely on "arguments are evaluated before the function runs." When you have a chain of method calls (e.g. a.b().c().d()), each method is called in order: first b() on a, then c() on the result, then d() on that result; the flow is left to right. When you have a short-circuit expression (a && b), b is only evaluated if a is truthy; so the flow can skip part of the expression. When you have a ternary (a ? b : c), only one of b or c is evaluated depending on a; so again the flow is conditional within the expression. That is why you can use a && fn() to call fn() only when a is true; the expression is evaluated left to right and stops when the outcome is determined. For the debugger: when you "step over" a line that contains a function call, the whole call (including the function body) runs and you get the return value; when you "step into," you enter the function. So one "statement" can involve many expression evaluations and nested calls; stepping lets you go as deep as you need to find where the flow or value goes wrong.

## 4) Side Effects and Where They Occur

A side effect is any change that is visible beyond the value an expression produces: modifying a variable, mutating an object, writing to the console, sending a network request, updating the DOM. Assigning to a variable is a side effect (the variable’s value changes). Calling console.log is a side effect (output appears). Calling fetch is a side effect (a request is sent). A function that only computes and returns a value, and does not mutate shared state or do I/O, is "pure": same inputs always give the same output, and calling it has no observable effect besides the return value. Pure functions are easy to test (pass inputs, check output) and easy to reason about. In practice, you need side effects: you need to fetch data, update the DOM, and log. The idea is to keep side effects at boundaries: the code that talks to the network, the code that updates the UI, the code that reads or writes config. The code in between—validation, transformation, business logic—can be as pure as possible so that you can test it with inputs and outputs and not worry about the network or the DOM. For a homestead dashboard: the function that fetches from the API has a side effect (the request); the function that parses and validates the response can be pure (given a string, return a parsed object or throw); the function that renders the list has a side effect (DOM update). So you structure the flow so that "fetch" hands data to "parse/validate" (pure) and then "render" (side effect). When you have a bug, you can often isolate it to the side-effectful part (e.g. "is the fetch failing?" or "is the DOM update wrong?") or to the pure part (e.g. "is the transformation correct?"). When you write tests, you test the pure parts with different inputs and assert on the output; the side-effectful parts you may mock or test with integration tools. So: recognize where side effects happen (assignment, I/O, DOM, log), prefer pure logic in the middle, and keep effects at the edges. A function that reads from the DOM or from a global variable is not pure (its result depends on external state), but you can still keep the "core calculation" pure and have a thin layer that reads inputs and writes outputs. A function that mutates its argument (e.g. sorts an array in place) has a side effect; if you want to keep the caller’s array unchanged, use a copy (e.g. [...arr].sort()) so the mutation is local. When you refactor, pulling side effects to the top or bottom of a function (e.g. "read config, then call pure validate(config), then write result") makes the flow obvious: first get inputs, then compute, then do outputs. When you have a mix of sync and async, the sync part runs to completion and the async part runs later; so the "flow" has two phases. When you use async/await, the function appears linear (statement after statement), but the flow is "run until await, then pause and later resume"; the debugger reflects that by showing the async stack when you are in the continuation. When you write tests for the pure part, you pass in mock data and assert on the return value; you do not need to mock the network or the DOM for that part. When you write tests for the side-effectful part, you may need to mock (e.g. mock fetch) or test in an environment that has the real dependency (e.g. a test browser). Separating the two makes both kinds of tests simpler.

## 5) Flow and Control Structures Recap

Conditionals (if/else, switch) and loops (for, while, for...of) are statements; they control which block runs next. The condition of an if or loop is an expression; the body is one or more statements (often a block). A block { } groups statements and creates a scope for let and const. When you nest blocks (e.g. an if inside a for), the inner block can see variables from the outer block; the flow goes into the block when the condition is true and exits when the block finishes. return exits the current function immediately and optionally provides a value (an expression). So the flow of a function is: run statements until you hit a return or the end of the function; then control goes back to the caller. When you have multiple return points (e.g. if (error) return; ... return result;), each return is a separate exit. When you use try/catch/finally, the flow can jump to catch when an exception is thrown and to finally when the try (and catch if present) finish; throw and return affect flow in the same way as in Chapter 3.12. For a homestead example: the flow of loadDashboard might be: check config (if invalid, throw), then await fetch (async boundary), then parse (maybe throw), then update state and render (side effects). Reading the code from top to bottom and following the conditionals and function calls gives you the flow; the debugger lets you follow it at runtime. When you see a bug ("this code never runs" or "this runs in the wrong order"), thinking in terms of flow—what condition was true, what function was called, what returned—usually points to the cause. When you have a long function with many branches, the flow can be hard to follow; extracting a branch into a named function (e.g. handleSuccess(data) and handleError(e)) makes the main flow a sequence of calls and makes each branch testable. When you use early return (if (!valid) return; ... rest of function), the flow is "exit early on invalid, otherwise run the rest"; that avoids deep nesting and makes the happy path clear. When you have a loop that breaks or returns, the flow exits the loop or function at that point; the rest of the loop body or function does not run. When you trace a bug, ask: "At this point in the code, what path was taken to get here? What were the values of the conditions? What did each function return?" The call stack and the variables at each frame (from the debugger) give you that. When you design new code, drawing a simple flow (e.g. "load config → validate → fetch → parse → render") helps you place expressions and statements in the right order and keep side effects at the boundaries. The grammar (expression vs statement) and the runtime (order, call stack, async) together define how your program runs; understanding both makes debugging and refactoring much easier.

## 6) Homestead Examples

When you write a function that fetches a reading, the call to fetch is an expression (it returns a promise); the await is part of an expression statement that pauses until the promise settles. The flow is: enter the async function, hit the await, leave the function (return a promise), later the continuation runs with the result. When you write a conditional display (e.g. show "OK" or "Low" based on a threshold), you use an expression in the template literal: `${value >= threshold ? "OK" : "Low"}` because ${} expects an expression. When you have several steps (get config, then fetch, then render), each step is one or more statements; the flow is linear within the async function. When you validate config at the boundary, you use statements (if (!config.x) throw ...) and then the rest of the code assumes valid data; the "throw" changes flow by jumping to the nearest catch. When you map over an array of readings, the callback is a function; if it is a concise arrow (r => r.value), the body is the expression r.value; if it is a block (r => { ... }), the body is statements and you return a value explicitly. When you have a loop that accumulates a value (e.g. sum of readings), the loop body is statements that update a variable (side effect) and the loop condition is an expression. When you structure the app so that "load config" runs first (maybe at top level or in an init function), then "fetch data" then "render," the flow is explicit and you can set breakpoints at each step to see the state. When you keep "parse response" and "validate" as pure functions (given data, return transformed data or throw), the flow is easy to test: call the function with mock data and assert on the result. Each of these ties the expression/statement distinction and flow to the patterns you use in a real app. When you use a library that takes a callback, the callback is usually a function (expression: a function value); the library decides when to call it (flow: your code runs later). When you pass a callback that does several things, the callback body is statements; when you pass a callback that only returns a value (e.g. .map(x => x.id)), the body is a single expression. When you chain .then handlers, each handler is a function that runs when the promise settles; the flow is "first .then runs, then the next .then runs with the returned value," and so on. When you use async/await, the flow looks like a straight line of statements, but each await is a point where the function yields and resumes later. When you validate at a boundary (Chapter 3.19), the flow is "if invalid, throw (flow jumps to catch); else continue." When you use optional chaining (obj?.prop), the expression short-circuits to undefined if obj is nullish, so the flow skips the rest of the chain. All of these are consistent with "expressions produce values, statements perform actions, and execution proceeds in order with branches and function calls." Keeping that mental model in mind when you read unfamiliar code or when you step through in the debugger will make the behavior of the program predictable and the bugs easier to locate.

## 7) What Breaks When Flow or Expressions Are Misused

If you put a statement where an expression is required (e.g. inside ${} or as the body of a concise arrow), you get a syntax error. Use an expression (ternary, function call) or switch to a context that allows statements (e.g. use a block body for the arrow and return a value). If you expect a value from a statement that does not produce one (e.g. if (x) { ... } is a statement; it has no value), you cannot assign it or use it in an expression; use an expression (e.g. ternary) when you need a value. If you confuse the order of execution (e.g. you assume a callback runs before the next line after the call), remember that callbacks run when they are invoked (e.g. when the promise settles), not in source order; the flow is "run this, then later run that." If you have side effects deep inside what you thought was pure logic, tests may be flaky or the behavior may depend on order; push side effects to the boundary so the middle is deterministic. If you have many nested conditionals or returns, the flow can be hard to follow; simplify with early returns or by extracting branches into named functions. If you use an expression for its side effect (e.g. fn() that mutates something) and also use its return value, make sure the return value is what you expect; the side effect and the return value are two different things. So: use expressions where a value is required, use statements where an action is required, keep flow explicit (order, conditionals, returns), and keep side effects at boundaries so the core logic is clear and testable.

## 8) Checklist

When you read or write code: (1) Identify expressions (they produce a value) and statements (they perform an action). (2) In template literals and ternary conditions, only expressions are allowed; use a ternary or function call for conditionals there. (3) In arrow functions, a concise body (no braces) must be a single expression; use a block and return when you need multiple statements. (4) Execution is single-threaded and synchronous until async; then the continuation runs later on the event loop. (5) Follow flow: top to bottom, conditionals choose branches, function calls push and return pops. (6) Recognize side effects (assignment, I/O, DOM, log) and prefer keeping them at boundaries. (7) Keep validation and transformation as pure as possible so they are testable. (8) When debugging, each step is a statement or expression evaluation; the call stack shows the current flow. (9) Use early returns and clear conditionals to keep flow readable. (10) Chapter 3.23 (JavaScript in Practice) will tie these ideas to concrete patterns and a small application. The expression/statement distinction and flow underpin everything you write.

## Common Pitfalls

Statement where expression required: Putting if/else or for inside ${} or in a concise arrow body causes a syntax error. Use a ternary or block body with return.

Expecting a value from a statement: if and for do not produce a value. Use an expression (e.g. ternary) when you need to use the result in a larger expression.

Confusing execution order with source order: Callbacks and async continuations run later. Flow includes "when" each chunk runs.

Side effects in "pure" code: Mutating or I/O inside logic that you want to test makes tests flaky. Push effects to boundaries.

Deep nesting: Many nested if/else or callbacks obscure flow. Use early returns, named functions, or flatten structure.

## Summary

Expressions produce values; statements perform actions. Use expressions where a value is required (${}, assignment RHS, ternary, concise arrow body); use statements where an action is required (if body, loop body, function body). Execution is single-threaded and synchronous within each run; async work runs later via the event loop. Program flow is top-to-bottom with branches (conditionals, loops) and function calls (call stack). Keep side effects at boundaries (fetch, DOM, log) and keep core logic as pure as possible for clarity and testability.
