# Section B Phase 3 · Chapter 3.23: JavaScript in Practice

This chapter ties the concepts from Phase 3 into practice: how to structure a small script or module, how to combine variables, types, conditionals, loops, functions, objects, arrays, async, and error handling into one coherent program, and what habits keep code readable and maintainable. It builds on Chapter 3.22 (Expressions, Statements, and Program Flow), which clarified flow and side effects; here you apply that by organizing data, helpers, and boundaries in a real script. Chapter 3.24 (From Script to Application) then looks at growing from a single script to a small application; this chapter focuses on making one script or module clear and correct. Using a consistent structure and good habits makes your code easier to debug, test, and change.

## Learning Objectives

By the end of this chapter, you should be able to:
- Structure a small script or module with a single purpose: separate data and config from logic, define helpers and an entry point, and keep I/O and side effects at boundaries.
- Combine variables (const/let), types, conditionals, loops, functions, objects, arrays, async (fetch, await), JSON parse, validation, and error handling in one coherent flow.
- Apply habits for readability and maintainability: name well, keep functions focused, validate at boundaries, handle errors explicitly, avoid deep nesting, and comment why not what.

## Key Terms

- **entry point**: The place where the script or module starts doing work. In a small script it might be a top-level call to main() or init(); in a module it might be the code that runs when the module is loaded or when an event fires. The entry point wires together config, helpers, and the main flow.
- **boundary**: The edge of your program where it meets the outside world: reading config or env, calling an API, reading or writing the DOM, logging. At boundaries you validate input and handle errors; inside the boundary you can assume valid data (Chapter 3.19, 3.20).
- **helper (or utility)**: A small function that does one thing and is used by the main flow or by other helpers. Keeping logic in named helpers (e.g. parseConfig, validateReading, formatForDisplay) makes the main flow read at a high level and makes each piece testable.
- **main flow**: The sequence of steps that the script performs: load config, fetch data, validate, transform, update state or DOM. Written at a high level (calling helpers) so the order and intent are clear.

- **single purpose**: A script or module does one main thing (e.g. "update the dashboard" or "load and validate config"). When it does more than one thing, split into separate scripts or modules so each has a clear responsibility and can be tested or reused independently.

## 1) Structuring a Script

Give the script a single purpose: "load config and validate it," "fetch sensor readings and display them," or "check thresholds and raise alerts." Then separate the pieces: data and config (constants, or values loaded at startup), helper functions (pure or mostly pure logic), and the main flow (the sequence of steps that uses the helpers). Put I/O and side effects at the boundaries: the code that reads a file or fetches from the API, and the code that writes to the DOM or logs. The code in between—parsing, validating, transforming—can be functions that take input and return output (or throw). In a single file you might order it as: constants and config at the top, then helper functions, then the main flow (e.g. an async function main() that is called at the end or from an event). When the script grows (many helpers or several distinct concerns), split into modules (Chapter 3.15): one module for config loading, one for API calls, one for rendering; the main script imports them and runs the flow. When the script is small (e.g. a few dozen lines that load config and do one thing), a single file is enough. For a homestead example: a "dashboard updater" script might have loadConfig (boundary: read file or env), validateConfig (pure: throw if invalid), fetchReadings (boundary: fetch API), parseAndValidate (pure: parse JSON and validate shape), and render (boundary: update DOM). The main flow is: config = await loadConfig(); validateConfig(config); readings = await fetchReadings(config); data = parseAndValidate(readings); render(data). Each step is one or two lines and the flow is easy to follow. When you add a new feature (e.g. alerts), you add a helper (e.g. checkAlerts(readings, thresholds)) and call it in the main flow; the structure stays the same. When the script runs in the browser, the entry point might be DOMContentLoaded or a button click that triggers the first async flow; when it runs in Node, the entry point might be the top level (with top-level await in a module) or a call to main() at the bottom of the file. When you have both "init on load" and "refresh on button click," the same main flow (load config, fetch, parse, render) can be extracted into a function runDashboard() that is called once on load and again when the user clicks refresh; that avoids duplicating the sequence. When you have shared state (e.g. the current list of readings), keep it in a variable or in a small object at module scope (or in a closure) so that the main flow and the render step can read it; update it in one place (e.g. after fetch and parse) so the source of truth is clear. When the script is part of a larger page (e.g. a dashboard widget), the boundary might be "read from this div" or "write to this container"; keep the rest of the script independent of the exact DOM shape so you can test the logic with mock data. When you document the script (e.g. a short comment at the top or a README), describe the purpose, the entry point, and what the script expects (e.g. "Expects config.json with sensorIds and apiBase") so that the next person knows how to run and configure it.

## 2) Combining the Pieces: Types, Functions, Arrays, Objects, Async

Use variables (const by default, let when you reassign) to hold config, intermediate results, and state. Use the right type for the job: strings for ids and messages, numbers for readings and thresholds, booleans for flags, objects for structured data (e.g. a reading with id, value, unit), arrays for lists (e.g. array of readings or zone ids). Use conditionals (if/else, ternary where an expression is needed) to branch on state or validation. Use loops (for...of, or array methods like map, filter, reduce from Chapter 3.17) to process collections. Use functions to name behavior: a function that fetches, one that parses, one that validates, one that formats. Use objects to group related data (e.g. config with sensorIds and apiBase) and to pass options. Use arrays to hold ordered data (readings, zones) and to transform with map/filter/reduce. Use async/await for the flow: load config (maybe async), fetch data (async), parse (sync but may throw), validate (sync, may throw), render (sync side effect). Use try/catch at the boundary (e.g. in main() or in the event handler) so that a failure in fetch or parse is caught and shown to the user or logged. Use template literals (Chapter 3.18) for messages and display strings. Use JSON.parse for API responses and config files, and validate the result before using it (Chapter 3.16). Use strict mode and validate at boundaries (Chapter 3.20, 3.19) so that invalid data fails fast with a clear error. For a homestead dashboard flow: load config (async), validate config (throw if invalid), fetch zones and readings (async, e.g. Promise.all), parse and validate responses (throw or return error result), transform data for display (map/filter), render to DOM (side effect). Each step uses the right construct: await for async, throw for invalid, array methods for transformation, and a single place that updates the UI. When you read the code from top to bottom, you see the flow; when you need to change one step (e.g. add a new sensor type), you find the right helper or the right place in the flow and change it there. When you use optional chaining or nullish coalescing (e.g. config?.timeout ?? 5000), use them for genuinely optional values; for required data, validate and throw so that missing config does not silently become a default and cause confusion later. When you have several async operations that can run in parallel (e.g. fetch zones and fetch readings), use Promise.all and await the result so the flow stays linear and the total time is the maximum of the two, not the sum. When you have operations that must be sequential (e.g. load config first, then use config.apiBase to fetch), await each step in order so the dependency is explicit. When you format data for display (e.g. temperature with one decimal, or a date string), do it in a small helper (formatReading(r)) or in the map step so the render step receives ready-to-display strings and does not mix formatting with DOM updates. When you handle errors, decide at the boundary whether to show a generic message ("Something went wrong") or a specific one ("Failed to load sensors"); include enough context (e.g. the error message or a retry hint) so the user or the log is actionable. When you use array methods (map, filter, reduce), keep the callback focused (e.g. map to transform, filter to remove invalid); if the callback grows, extract it to a named function so the flow stays readable.

## 3) Readability and Habits

Name variables and functions so that their role is clear: config, sensorIds, fetchReadings, validateConfig, formatTemperature. Avoid single letters except for loop counters or very short callbacks (e.g. r for reading in a map). Keep functions focused: one function does one thing (e.g. "parse the response" or "check if any reading is below threshold"). If a function is long or does several unrelated things, split it into smaller functions and call them from a higher-level function. Use early returns to avoid deep nesting: instead of if (valid) { ... many lines ... } else { ... }, use if (!valid) return; or if (!valid) throw ...; then the rest of the function is the "happy path" at the top level. Prefer const and let in a small scope (Chapter 3.20). Comment why, not what: the code shows what it does; a comment should explain why (e.g. "API returns Celsius; we display in Fahrenheit" or "threshold is exclusive so 0 means 'off'"). Avoid magic numbers: use named constants (e.g. const MAX_RETRIES = 3) so the meaning is clear. Use consistent patterns across the script: if you validate one API response with a function that throws, do the same for others; if you format one kind of value with a helper, use the same helper elsewhere. For a homestead app, use the same shape for sensor data (e.g. always { id, value, unit, timestamp }) so that helpers and the UI can assume that shape. When you handle errors, use the same pattern: log, show user message, and optionally rethrow or return a fallback. When you add a new feature, follow the same structure (helper + call in main flow) so the codebase stays consistent. When you are done with a change, remove or comment out debug logs and leave the code clean so the next person (or you later) can read it without noise. When you use template literals for messages, keep the expression short (e.g. `${name}: ${value}`); if the message is complex, build it in a variable or a small helper so the template stays readable. When you have a list of options or enums (e.g. status: "ok" | "warning" | "error"), use constants or a small object so you do not scatter string literals; that way a typo is caught (e.g. if you use a constant and misspell it, the reference is undefined) and the meaning is documented in one place. When you pass options to a function (e.g. fetchReadings({ sensorIds, timeout })), validate the options at the start of the function and throw with a clear message if a required option is missing; that keeps the contract explicit. When you return a value that might be null or an empty array, document it (e.g. "Returns the list of readings, or [] if none") so callers know whether to check for length or null. When you write a function that can throw, document it (e.g. "Throws if config is invalid") so callers know to use try/catch or to ensure valid input. When the flow has a retry (e.g. fetch with retries), put the retry logic in a small helper (e.g. fetchWithRetry(url, n)) so the main flow stays simple and the retry behavior is reusable. When you have timeouts (e.g. Promise.race with a timeout promise), handle the timeout case explicitly (e.g. show "Request timed out") so the user knows what happened.

## 4) When to Split into Modules and When One File Is Enough

One file is enough when the script is short (e.g. under a hundred or so lines), has a single purpose, and the helpers are few. Split into modules when: the file is long and hard to navigate, you have distinct layers (e.g. config, API, render) that could be tested or reused separately, or several scripts share the same helpers. When you split, put the entry point in one file (e.g. main.js or index.js) that imports from the others and runs the flow; put config loading in a module that exports loadConfig or getConfig; put API calls in a module that exports fetchReadings, fetchZones, etc.; put rendering or DOM updates in a module if that logic is substantial. The main file then reads like: import { loadConfig } from "./config.js"; import { fetchReadings } from "./api.js"; ... await loadConfig(); ... await fetchReadings(...). So the flow stays visible in one place and the details live in modules. When you are learning or prototyping, a single file is often simpler; when the script grows or you want to test helpers in isolation, split. When you work in a team, agree on the structure (e.g. "config and api in modules, main flow in index") so everyone knows where to find and add code. When you have shared types or constants (e.g. sensor shape, default timeout), put them in a small module or at the top of a shared file so they are defined once and imported where needed. When you split, avoid circular dependencies: the main script imports from config and api; config and api should not import from each other or from main. If two modules need to share a type or constant, put it in a third module (e.g. constants.js or types.js) that both import. When you run the script, ensure the entry point is the one that gets executed (e.g. in the browser, the script that calls init() is loaded; in Node, the file you run with node is the entry point). When you have multiple entry points (e.g. one script for "check alerts" and one for "dashboard"), they can share the same modules (config, api) and each have their own thin main flow that calls the shared helpers. When you test, you can import and call the pure helpers with mock data and assert on the output; the boundary code (fetch, DOM) you may mock or test in an integration environment. The structure (clear flow, boundaries, helpers) makes both manual testing and automated testing easier because you know where to inject mocks and where to assert.

## 5) Homestead Examples: Putting It Together

A config loader script: read config from a file or env (boundary), parse JSON (may throw), validate required keys (throw with clear message), export or return the config. The main flow is: load, validate, then the rest of the app uses config. A dashboard updater: load config, validate, fetch readings for config.sensorIds (e.g. Promise.all of fetch calls), parse each response and validate shape, combine into an array of readings, pass to a render function that updates the DOM. Errors: catch in main(), log, and show "Failed to load" or show partial data. An alert checker: load config (thresholds), fetch current readings, run a pure function checkAlerts(readings, thresholds) that returns a list of alerts (e.g. [{ sensorId, message }]), then display or send the alerts (boundary). A zone controller: user clicks a button, event handler calls startZone(id), which fetches the API (async), on success update UI, on failure catch and show "Could not start zone." In each example, the flow is: get input (config or user action), validate or interpret, do the work (fetch, compute), then output (DOM, log, or API call). The same pattern scales: add more helpers for more features, keep the main flow high-level, and keep boundaries in one place so validation and error handling are consistent. When you debug, you know where to look: if the data is wrong, check the boundary (fetch, parse, validate); if the logic is wrong, check the helper; if the UI is wrong, check the render step. When you add a new sensor type or a new API endpoint, you add a helper or extend an existing one and plug it into the flow. When the dashboard shows "loading" and then "error" or "data," keep the loading state in a variable (e.g. let loading = true; then false after fetch) and update the DOM in one place (e.g. render({ loading, data, error })) so the UI reflects the current state consistently. When you have form input (e.g. user enters a threshold), read the value at the boundary (event handler), validate (e.g. must be a number in range), and then pass the value to the logic or state; do not mix DOM reads deep inside pure logic. When you persist something (e.g. user preference in localStorage), do it at the boundary (after a user action or after loading data) and read it at startup so the rest of the script sees a single "preferences" object. When you log for debugging, use a prefix or a level (e.g. console.log("[Dashboard]", message)) so you can filter logs by feature; remove or gate these in production. When you collaborate, agree on the structure (where config lives, where API helpers live, how errors are surfaced) so that everyone's code fits the same pattern and the codebase stays coherent as it grows. The goal is a script that does one thing well, is easy to read from top to bottom, and is easy to change when requirements evolve.

## 6) What Breaks When Structure or Habits Are Wrong

If the script has no clear entry point or the flow is scattered (e.g. things happen in random event handlers with no main sequence), it is hard to see what the script does or in what order. Define a main() or init() and call it, or have one clear place (e.g. DOMContentLoaded) that runs the flow. If validation is missing or done too late, invalid data propagates and causes confusing errors deep inside. Validate at the boundary and throw with a clear message so the failure is visible at the edge. If helpers do too much (e.g. one function that fetches, parses, validates, and renders), the function is hard to test and hard to change. Split so each helper has one job. If naming is vague (e.g. data, temp, fn), the code is hard to read. Use names that reflect the role (config, reading, formatTemperature). If errors are swallowed (empty catch or catch that only returns), failures are invisible. Always log or rethrow or show a user message. If the main flow is buried in nested callbacks or deep conditionals, the order of steps is hard to follow. Use async/await and early returns to keep the flow flat. If side effects are mixed with pure logic (e.g. a function that fetches and also does a calculation), the logic is hard to test. Push I/O to the boundary and keep the middle pure. So: have a clear structure (data, helpers, main flow, boundaries), validate at boundaries, name well, keep functions focused, handle errors explicitly, and keep the flow readable. When you come back to the script in six months or when someone else reads it, the structure and habits will make it easier to understand and change. When the script fails in production, having a clear boundary and error handling (log and user message) will give you something to look at (e.g. "Failed to load config: ..." in the log) instead of a silent failure or a generic crash. When you add a new environment (e.g. a second API or a different config source), you add a new boundary function (e.g. loadConfigFromEnv()) and plug it into the same flow so the rest of the script is unchanged. When you optimize (e.g. cache config or batch requests), you do it inside a helper or at the boundary so the main flow stays the same and the optimization is localized. The structure is not just for the first version; it pays off every time you debug, extend, or hand the code to someone else. ## 7) Checklist

When you write or refactor a script: (1) Give it a single purpose and structure it with data/helpers/main flow and clear boundaries. (2) Use const/let, the right types (strings, numbers, objects, arrays), and conditionals and loops (or array methods) as needed. (3) Use async/await for async steps and try/catch at the boundary to handle failures. (4) Validate at boundaries (config, API response, user input) and throw with clear messages. (5) Keep helpers focused (one job each) and name them clearly. (6) Use early returns to avoid deep nesting; keep the happy path obvious. (7) Comment why, not what; use named constants instead of magic numbers. (8) Use the same patterns for validation, errors, and data shape across the script. (9) Split into modules when the file is long or when layers (config, API, render) would benefit from separation. (10) Chapter 3.24 (From Script to Application) will look at growing from one script to a small application with multiple views or features. The habits here (structure, boundaries, readability) apply at that scale too.

## Common Pitfalls

No clear entry point: The flow is scattered. Have a main() or init() and call it so the order of execution is obvious.

Validation too late: Invalid data causes errors deep inside. Validate at the boundary and throw so failures are visible.

Helpers that do too much: One function that fetches, parses, and renders is hard to test. Split into one job per function.

Vague names: data, temp, x. Use names that reflect the role so the code is self-explanatory.

Swallowing errors: Empty catch or catch that only return. Log or rethrow or show a message so failures are visible.

Deep nesting: Many levels of if/else or callbacks. Use early returns and async/await to keep the flow flat.

Side effects in the middle: Logic mixed with fetch or DOM. Push I/O to the boundary so the middle is pure and testable.

## Summary

Structure a script with a single purpose: data and config, helpers (focused functions), main flow (the sequence of steps), and boundaries (I/O, validation, error handling). Combine variables, types, conditionals, loops, functions, objects, arrays, async, and errors in one coherent flow: load config, validate, fetch, parse, validate again, transform, render. Use habits for readability: name well, keep functions focused, validate at boundaries, handle errors explicitly, use early returns, comment why. Split into modules when the script grows or when layers can be reused or tested separately.
