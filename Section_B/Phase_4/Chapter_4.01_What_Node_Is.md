# Section B Phase 4 · Chapter 4.01: What Node.js Is

This chapter describes what Node.js is: a JavaScript runtime built on V8 and libuv that lets you run JavaScript outside the browser. It starts Section B Phase 4 and sets the mental model for the Node environment; Chapter 4.02 (Running Node and the REPL) then covers how to run scripts and use the REPL. You already know the language from Phase 3; Node adds the APIs and the runtime for servers, tools, and scripts. Understanding what Node is (and what it is not) helps you choose the right environment for each part of a project and avoids confusion between browser and Node APIs.

## Learning Objectives

By the end of this chapter, you should be able to:
- Describe Node.js as a JavaScript runtime: V8 (engine) plus libuv (event loop and async I/O) plus Node’s core modules and APIs.
- Explain what Node provides (process, global, fs, http, and other built-in modules) and what it does not provide (no DOM, no window).
- Use process and global as the top-level environment and know when you need them (env vars, CLI args, current directory).
- Relate Node to Phase 3: same language; Node is the host that runs your JavaScript on the server or in the shell.

## Key Terms

- **Node.js**: A JavaScript runtime that runs outside the browser. It combines the V8 engine with libuv and adds built-in modules (fs, http, path, process, etc.) so you can run JavaScript on the server, in the command line, or in build tools.
- **V8**: The JavaScript engine used by Chrome and by Node.js. It parses and executes JavaScript. Node does not implement the language itself; it embeds V8 and adds APIs on top.
- **libuv**: A library that provides the event loop and asynchronous I/O (files, network, timers). Node uses libuv so that file and network operations do not block the single JavaScript thread; when I/O completes, your callbacks or promise reactions run.
- **process**: A global object in Node that represents the current process. It exposes process.env (environment variables), process.argv (command-line arguments), process.cwd() (current working directory), and process.exit().
- **global**: The global object in Node (similar to window in the browser). Top-level var declarations and some older patterns attach to it; in modern code you prefer modules and avoid polluting global.

## 1) V8 and libuv

Node.js is not a new language. It is a runtime that runs JavaScript. The engine that executes your code is V8—the same engine used in Google Chrome. V8 parses JavaScript, compiles it, and runs it. So the language (syntax, types, functions, async) is exactly what you learned in Phase 3; Node simply runs that language outside the browser. When you write a Node script, you are writing JavaScript; the only difference from the browser is which host object and APIs are available.

V8 handles only JavaScript execution. It does not know about files, networks, or timers. It has no concept of process.env or of reading from disk. Node adds a second layer: libuv. Libuv is a C library that provides the event loop and non-blocking I/O. When your code calls fs.readFile or when Node’s http module waits for a request, the actual waiting is done by libuv and the operating system. Your JavaScript does not sit in a busy loop; it returns control to the runtime, and when the file is read or the request arrives, libuv queues a callback (or resolves a promise), and V8 runs your JavaScript again. So Node is V8 (run the code) plus libuv (run the event loop and do I/O without blocking) plus C++ bindings and core modules (fs, http, path, process, and others) that expose those capabilities to JavaScript. The same event-loop model you saw in Phase 3 (Chapters 3.13 and 3.14) applies: one thread of JavaScript, async work scheduled by the host, and callbacks or promise reactions run when I/O completes.

Because I/O is non-blocking, a single thread of JavaScript can handle many operations: start a file read, then handle a network request, then run a timer callback, without waiting for each one to finish before doing the next. That fits servers and tools well. A server can accept a request, start reading a file or querying a database, and while that I/O is in progress it can accept another request. When the first I/O completes, the callback runs and the response is sent. You do not need multiple threads of JavaScript; you use async APIs and the event loop schedules your callbacks when I/O completes. That makes Node efficient for I/O-heavy workloads: APIs, file processing, proxying, and scripts that wait on network or disk. So Node is single-threaded for your JavaScript, but it uses the operating system and libuv to do I/O in the background; your code runs when the event loop gives it a turn. If you do long-running synchronous work (e.g. a heavy loop with no await or no I/O), you block that single thread and nothing else runs until it finishes; the same rule as in the browser. So in Node as in Phase 3, you keep the main thread short and use async for anything that waits.

## 2) Node as Runtime

You run Node by executing the node program and passing it a script file: node script.js. Node loads the file, runs it, and exits when the script finishes (or when you call process.exit()). If the script starts a server or waits for input, the process stays alive until you stop it (e.g. Ctrl+C). You can also run node without a file to start the REPL (read-eval-print loop), where you type JavaScript and see results immediately; Chapter 4.02 covers that. On Windows you might run node.exe; on macOS and Linux, node is typically installed so that the command node is available in the terminal. The entry point is always the file you pass (or the REPL if you pass no file). That file can require or import other files; Node resolves paths and runs your code in order. So "running Node" means running the node binary with your script; the binary embeds V8 and libuv and loads your code and any modules it depends on.

Node does not provide browser globals. There is no window, no document, no DOM. There is no fetch in older Node versions (Node 18+ provides a global fetch). Instead, Node provides its own globals and modules: global (the global object), process (the current process), and built-in modules you load with require or import (e.g. fs, http, path). So the same JavaScript language runs, but the environment is different: in the browser you have document and fetch; in Node you have process and require("fs") or import fs from "fs". When you write a script for Node, you use Node’s APIs for files, networks, and the process; when you write code for the browser, you use the DOM and web APIs. Phase 3 gave you the language; Phase 4 (this phase) gives you the Node environment. If you copy a snippet from a Node script into a browser page, you must remove or replace Node-only APIs (require, process, fs); if you copy browser code to Node, you must remove or replace DOM or window usage. The curriculum uses both environments: Phase 3 was the language; Phase 4 is Node; Phase 8 is the DOM. When you see "run this in Node" or "run this in the browser," that is a reminder of which host and which globals apply.

Node is used for servers (HTTP APIs, web back ends), command-line tools (scripts that process files or call APIs), and build tooling (bundlers, dev servers, test runners). It is not used for manipulating a web page’s DOM; that is the browser’s job (Phase 8). For a homestead project, you might use Node to run a small server that your dashboard talks to, or a script that reads sensor data from a file or API and logs or forwards it. The language is the same; the host and the available APIs are what change. You might have one codebase that shares validation or formatting logic between browser and Node (e.g. via modules that use only the language and no host-specific APIs), and separate entry points: one for the browser (the dashboard page) and one for Node (the server or CLI script). That separation is why understanding "what Node is" matters: you know where your code runs and what you can call there.

## 3) process and global

In Node, the top-level environment includes process and global. You will use process often; global rarely.

process is an object that represents the current Node process. It is available in every Node script without requiring or importing. process.env holds environment variables. When you run node script.js, the process inherits the environment of the shell (e.g. NODE_ENV, PATH, or custom variables you set in the shell or in a .env file loaded by a tool). You read them when you need configuration from the environment: for example process.env.NODE_ENV to know if you are in development or production, or process.env.PORT for the port to listen on, or process.env.API_KEY for a secret. Environment variables are a common way to pass config into a Node process without hardcoding values in the script. process.argv is an array of command-line arguments. argv[0] is the path to the node executable, argv[1] is the path to the script file, and argv[2] onward are any arguments you passed (e.g. node script.js arg1 arg2 gives argv[2] === "arg1", argv[3] === "arg2"). You use argv when you write a CLI tool that takes options or file paths. process.cwd() returns the current working directory—the directory from which you ran node. That is useful when you need to resolve relative paths (e.g. "config.json" in the current directory); you often combine it with the path module (Chapter 4.03) to build absolute paths. process.exit(code) exits the process immediately. Pass 0 for success and a non-zero number for failure (e.g. process.exit(1) after an error). The shell or process manager can use that exit code to know whether the script succeeded. You can also listen for process events. process.on("uncaughtException", (err) => { ... }) is a last-resort handler when an exception is not caught; it does not replace proper try/catch and error handling, but it can log or clean up before the process exits. Relying on it for normal flow is a bad idea; use it only to log and exit gracefully when something unexpected escapes. process.on("unhandledRejection", ...) is for promise rejections that no .catch or try/await handled; again, fix the code to handle rejections rather than relying on this. So process is your link to the process and the environment; use it for env vars, CLI args, cwd, and exit codes.

global is the global object. In the browser, the global object is window; in Node, it is global. Top-level var declarations and assignments to undeclared variables (in non-strict mode) can end up on global. In modern Node code you use "use strict", const, and let, and you use modules (import/export), so you rarely need to touch global. Avoiding global pollution keeps your script from clashing with other code or with Node’s own internals. If you need to share something across modules, export it from one module and import it in the others; do not attach it to global. Some older code or tutorials might set global.something; when you see that, prefer refactoring to a module export. Node itself attaches a few things to global (e.g. process, Buffer in some versions, and in Node 18+ fetch); your code should not add more unless you have a very good reason (e.g. a legacy script that must run in a shared context). So: use process when you need the process or the environment; avoid relying on global for your own state. When you debug, you can inspect process and process.env in the REPL or in the debugger to see the current environment and arguments; that is often the first place to look when a script behaves differently in production than locally (e.g. a missing or different env var).

## 4) Why Node for Servers and Tools

Node uses the same language as the browser. If you know JavaScript from Phase 3, you can write Node scripts without learning a new syntax. The event loop and async model (callbacks, promises, async/await) are the same; Node’s fs and http modules use the same patterns. So one language can power both the dashboard in the browser and the server or script that the dashboard talks to. That reduces context switching when you work on both sides of a project: same variables, same functions, same error handling with try/catch and throw.

Non-blocking I/O fits the request/response model of a server. When one request is waiting for a file read or a database call, Node can handle another request. You do not need multiple threads of JavaScript; you use async APIs and the event loop schedules your callbacks when I/O completes. That makes Node efficient for I/O-heavy workloads (APIs, file processing, proxying). CPU-heavy work (e.g. large computations) can still block the thread; for that you would use worker threads or offload to another process in advanced setups. For most homestead and small-server use cases, the single thread and async I/O are enough.

Node also has a large ecosystem. npm (Chapter 4.07, 4.08) is the package manager that ships with Node; you can install libraries and tools from the npm registry. Many frameworks (e.g. Express) and utilities run on Node. Later in Phase 4 you will use built-in modules (path, fs, http) and optionally npm packages; the same structure and habits from Phase 3 (validation at boundaries, async/await, error handling) apply. When you run a server in Node, you are still writing JavaScript; you just have different APIs (listen on a port, read the request, send the response) instead of DOM APIs. The curriculum will introduce those APIs in later chapters; here the point is that Node is the runtime that makes server-side and CLI JavaScript possible, and that the language you learned in Phase 3 is the same one you use in Node. Choosing Node for a server or a script does not mean learning a new language; it means running the same language in a different host and using Node’s built-in and npm-provided APIs for I/O, process, and network. That continuity is why Phase 3 (JavaScript) comes before Phase 4 (Node): once you have the language and the async model, adding Node is a matter of learning the host’s APIs, not a new syntax or a new execution model.

## 5) Homestead Examples: Where Node Fits

On a homestead you might have a web dashboard that shows battery voltage, coop status, or drip irrigation. The HTML and the logic that updates the page (e.g. fetching sensor data and filling in values) run in the browser as JavaScript (Phase 8). The server that hosts that dashboard and that might aggregate data from ESP32s or a database runs in Node.js: same language, different environment. So Node is the host for the server process. A small utility that reads a config file and generates a report runs in Node from the command line: you run node report.js and it reads config, fetches or reads data, and writes output. Scripts that run on a Raspberry Pi to poll sensors or control a relay are also often Node (or Python); Node gives you JavaScript and npm packages for hardware or HTTP. So Node appears wherever you need to run JavaScript outside the browser: on a server, in a CLI tool, or on a device.

For example, a coop door controller might run on a Pi: Node talks to hardware (via GPIO or a library) and keeps state; a browser-based admin page runs JavaScript in the browser to show status and send commands. The server that receives those commands and talks to the Pi might be Node. A dashboard that displays freezer temps or poultry net voltage might be a static HTML page with a script that fetches JSON from an API; the API is served by Node or another backend. So the split is consistent: user interface and in-page behavior in the browser (Phase 8), server and device logic in Node (Phase 4). You will write JavaScript for both sides; only the host and the APIs change. Soil moisture or drip irrigation data might be collected by an ESP32 or a Pi and then exposed via an HTTP API; a Node script could poll that API and log or forward the data, or the browser dashboard could fetch it directly. Electric fence or solar monitoring might be shown in a small dashboard: the numbers come from the server (Node or another backend), and the browser script only renders them and handles user input. In every case, Node is the runtime when your JavaScript runs on the server or in the shell; the browser is the runtime when your JavaScript runs in the page. Knowing which runtime you are in tells you which APIs you can use (process and fs in Node, document and fetch in the browser) and how to structure and deploy your code.

A config loader that runs at server startup is a classic Node use case: the script or server reads config from a file (using fs) or from process.env, validates it (using the same validation habits from Phase 3), and then the rest of the app uses that config. A cron job or scheduled task that runs every hour to check sensor thresholds and send an alert is another: the task is a Node script that runs from the command line or from a job scheduler, reads from an API or a file, and logs or sends a notification. A small HTTP server that your dashboard calls to get the latest readings is Node: the server listens on a port, receives requests, fetches or computes data, and returns JSON. None of that involves the DOM; it all runs in Node. When you deploy, you run the Node process (e.g. on a VPS, a Pi, or a container); the process stays alive and handles requests or runs on a schedule. So "What Node is" is not just a definition—it is the runtime you choose whenever your JavaScript needs to run outside the browser, with access to the file system, the process, and the network as a server or a CLI.

## 6) What Breaks When You Ignore What Node Is

If you assume browser APIs in Node, your code will fail. There is no document, no window, no DOM. If you try to use document.querySelector or window.alert in a Node script, you get a ReferenceError. If you assume Node APIs in the browser, same problem: no require (unless you use a bundler that emulates it), no process.env in the same way, no file system. Always know your host. When you copy a snippet from a Node tutorial into a browser script without replacing Node-only calls, the browser will throw. Similarly, code that uses document or window will not run in Node. So: match your code to the host. Node scripts use process, fs, path, and http; browser scripts use document, fetch, and the DOM.

If you forget that Node is single-threaded and do long synchronous work (e.g. a loop that runs for seconds), you block the process. No other requests are handled, no other callbacks run, until that work finishes. Use async APIs (fs.readFile with callbacks or promises, or async/await) so that I/O does not block. The same rule as in Phase 3: keep the main thread short and use async for anything that waits. If you rely on process.env for required config and do not check that the variable exists, the script may run with undefined and fail in a confusing way later. Validate at the boundary: if (process.env.API_KEY) { ... } else { throw new Error("API_KEY required"); }. If you use process.exit() in the middle of a server, the process stops immediately and in-flight requests may be lost; reserve exit for CLI scripts or for shutdown after cleanup. If you pollute global with many variables, you risk clashing with Node’s own properties or with other modules; prefer modules and explicit exports. So: know that Node is the runtime for server and CLI JavaScript, that it has no DOM, that process and built-in modules are your environment, and that the same language and async habits from Phase 3 apply. When you run into "undefined is not a function" or "Cannot read property of undefined," check whether you are using a browser API in Node or a Node API in the browser; that is a very common cause. When you run into "module not found," you are in Node and the path or module name is wrong; we will cover that in Chapter 4.02 and 4.03.

If you run an older Node version, some APIs or syntax may be missing. For example, ES modules (import/export) need a recent Node or "type": "module" in package.json; global fetch exists in Node 18+. The curriculum assumes a current Node LTS or recent release. Check your version with node --version and upgrade if needed so that the features and APIs we use are available. If you run Node in a restricted environment (e.g. a sandbox or a minimal container), some built-in modules might be stubbed or missing; test in an environment that matches where you will deploy. If you mix CommonJS (require) and ES modules (import) in the same file, Node will throw; a file is either one or the other. If you expect a script to run in the browser and it uses require or process, it will not run there unless you use a bundler that compiles Node-style code for the browser; for learning, keep browser and Node code clearly separated by host so you always know which APIs are valid.

## 7) Checklist

When you start a Node script or work in a Node project, confirm: (1) Node is the runtime—no DOM or window; you have process and built-in modules. (2) You know how to run the script (node script.js or node --experimental-modules for ESM if needed). (3) You use process.env for environment-based config and process.argv for CLI arguments when relevant. (4) You use process.cwd() or the path module when you need to resolve paths relative to the current directory. (5) You do not rely on browser globals (document, window, fetch in older Node); use Node’s equivalents (fs, http, or global fetch in Node 18+). (6) You keep the single-threaded model in mind: avoid long synchronous work; use async/await or callbacks for I/O. (7) You validate required env vars or config at startup and throw with a clear message when something is missing. (8) You avoid polluting global; use modules and exports for shared state. Chapter 4.02 (Running Node and the REPL) continues with how to run scripts, use the REPL, and how Node resolves modules and file paths.

## Common Pitfalls

Assuming browser APIs in Node: There is no document, window, or DOM. Use Node’s built-in modules (fs, http, path) and process. Code that works in the browser will not run unchanged in Node without replacing host APIs.

Assuming Node APIs in the browser: There is no require or process in the browser (unless provided by a bundler). Use import for modules and do not rely on process.env or the file system in browser code.

Blocking the Node thread: Long synchronous loops or heavy computation block the entire process. Use async I/O and keep CPU work short or offload to workers. In a server, blocking delays or drops requests.

Relying on uncaughtException or unhandledRejection: These are last-resort handlers. Fix the code to handle errors with try/catch and .catch so that failures are handled explicitly and the process exits or recovers in a controlled way.

Polluting global: Attaching many variables to global causes name clashes and makes dependencies unclear. Use modules: export what others need and import what you need.

Ignoring process.exit codes: Use 0 for success and non-zero for failure so that scripts can be composed (e.g. in a shell script or by a process manager) and the caller knows whether the script succeeded.

## Summary

Node.js is a JavaScript runtime: V8 runs the language, libuv provides the event loop and non-blocking I/O, and Node adds core modules (fs, http, path, process, etc.). There is no DOM or window; you have process, global, and built-in modules. Use process for environment variables, CLI arguments, current directory, and exit codes; avoid relying on global for your own state. Node is used for servers, CLI tools, and build scripts; the same JavaScript you learned in Phase 3 runs there, with Node as the host. Keep the single-threaded, async model in mind and validate at boundaries so your Node scripts are predictable and debuggable.
