# Section B Phase 4 · Chapter 4.07: npm — Package Management

Chapters 4.01–4.06 introduced Node’s runtime, built-in modules (path, fs, http), process, Buffer, and the event loop. To add third-party libraries (frameworks, utilities, CLI tools), Node uses **npm**: the package manager that ships with Node. This chapter covers the basics: creating a **package.json** with **npm init**, defining **scripts** to run your app and tests, adding **dependencies** with **npm install**, and understanding **package-lock.json** and **semantic versioning**. By the end you will have a project that declares what it needs and how to run it, and you will be ready for Chapter 4.08 (installing and using specific packages).

## Learning Objectives

By the end of this chapter, you should be able to:

- Run **npm init** (or **npm init -y**) to create a **package.json** and understand its core fields: **name**, **version**, **description**, **main**, and **scripts**.
- Add and run **scripts** (e.g. **start**, **test**, **dev**) with **npm run &lt;script&gt;** (and **npm start** / **npm test** for the special names).
- Install packages with **npm install &lt;pkg&gt;** and record them in **dependencies**; understand that **node_modules** and **package-lock.json** are created or updated.
- Explain **package-lock.json**: it locks exact versions for reproducible installs; commit it to version control.
- Use **semantic versioning** (major.minor.patch) and understand version ranges in **package.json** (e.g. **^1.2.3**, **~1.2.3**, or exact **1.2.3**).
- Set **"private": true** when the project is an app (not a library to publish) to avoid accidental **npm publish**.

## Key Terms

- **npm**: Node Package Manager. The default package manager for Node.js. It installs packages from the npm registry, creates **package.json** and **package-lock.json**, and manages **node_modules**. You get it when you install Node.
- **package.json**: A JSON file at the project root that describes the project: name, version, scripts, dependencies, and more. Created by **npm init** and updated when you **npm install** a package.
- **package-lock.json**: A file generated by npm that records the exact versions of every installed package (and their dependencies). Ensures **npm install** produces the same **node_modules** on every machine; commit it.
- **semantic versioning (semver)**: A version scheme **major.minor.patch**. Breaking changes = bump major; new features = minor; bug fixes = patch. In **package.json**, versions can be ranges (e.g. **^1.2.3** = “compatible with 1.2.3,” typically allow minor and patch updates).

## 1) What npm Is and Why It Matters

Node’s built-in modules (fs, path, http) are enough for many scripts. When you need a web framework, a testing library, a CLI tool, or a utility that someone else maintains, you install it from the **npm registry**—a huge public repository of JavaScript packages. **npm** (the command-line tool) talks to the registry, downloads packages, and puts them in **node_modules** in your project. It also writes and updates **package.json** (your project’s manifest) and **package-lock.json** (exact dependency tree). So “using npm” means: (1) having a **package.json** that describes your project and its dependencies, (2) running **npm install** to install those dependencies, and (3) using **require** or **import** in your code to load installed packages. This chapter focuses on creating and maintaining **package.json** and the install workflow; Chapter 4.08 goes deeper into finding, installing, and using specific packages.

## 2) Creating a Project: npm init

Before you can install packages, your project needs a **package.json**. The standard way to create one is **npm init**.

### 2.1 npm init (Interactive)

In your project directory (the folder that will contain your app or script), run:

```bash
npm init
```

npm will prompt you for **name**, **version**, **description**, **entry point** (main), **test command**, **git repository**, **keywords**, **author**, and **license**. You can press Enter to accept the default (shown in parentheses) or type a value. When you are done, npm creates **package.json** with those fields. Default **name** is derived from the directory name; default **version** is **1.0.0**; default **main** is **index.js**.

### 2.2 npm init -y (Skip Prompts)

If you want a **package.json** with defaults and no prompts:

```bash
npm init -y
```

This creates **package.json** with **name** = current directory name (sanitized), **version** = **"1.0.0"**, and a few other default fields. You can edit the file afterward. For learning and small projects, **npm init -y** is often enough; you add scripts and dependencies as you go.

### 2.3 Core Fields in package.json

After **npm init**, **package.json** might look like:

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}
```

- **name**: Required for publishing to npm. Use lowercase, no spaces; hyphens and underscores are allowed. For an app you do not plan to publish, the name is just for your own reference.
- **version**: Required. Follows semantic versioning **major.minor.patch** (e.g. **1.0.0**). You bump it when you release changes.
- **description**: Short description of the project; optional but useful for others and for **npm search**.
- **main**: The entry point when someone does **require("your-package")**. For an application (not a library), **main** is often **index.js** or the file you run with **node**; it matters less than **scripts.start**.
- **scripts**: Commands you can run with **npm run &lt;name&gt;**. See the next section.
- **private**: If you set **"private": true**, **npm publish** will refuse to publish. Use this for apps and internal projects so you do not accidentally publish to the registry.
- **engines** (optional): You can specify required Node (or npm) versions, e.g. **"engines": { "node": ">=18.0.0" }**. npm will warn (or, with **engine-strict**, fail) if the current Node version does not match. Useful for projects that rely on features from a specific Node version.

You can add **"private": true** by hand to any **package.json** that is an application, not a library you intend to publish. If your project uses ES modules (import/export), you will add **"type": "module"** to **package.json** (Chapter 4.08 and later); that is a separate field from **main** and **scripts**.

## 3) Scripts

The **scripts** field in **package.json** lets you define named commands. Instead of typing **node index.js** every time, you run **npm start** (or **npm run start**). That makes it easy for others (and for you later) to know how to run the project.

### 3.1 Defining Scripts

Example **scripts** section:

```json
"scripts": {
  "start": "node index.js",
  "test": "node test.js",
  "dev": "node --watch index.js"
}
```

- **start**: Often used to run the main application. You invoke it with **npm start** (or **npm run start**).
- **test**: Often used to run tests. You invoke it with **npm test** (or **npm run test**). npm treats **start** and **test** as special and allows the short form without **run**.
- **dev**: A common name for a “development” command (e.g. run with auto-reload). You run it with **npm run dev** (there is no **npm dev** shorthand).

You can add any key: **"build"**, **"lint"**, **"serve"**, etc. The value is a single string: the command that runs in the shell when you **npm run &lt;key&gt;**. So **npm run dev** runs **node --watch index.js** in the project directory. If the command has multiple parts (e.g. **node index.js --port 3000**), put the whole string in the script; npm runs it with the system shell. Long scripts are sometimes split into a small shell script or a separate Node file that you call from the script (e.g. **"dev": "node scripts/dev.js"**).

### 3.2 Running Scripts

- **npm start** — runs the **start** script.
- **npm test** — runs the **test** script.
- **npm run &lt;name&gt;** — runs the script named **&lt;name&gt;** (e.g. **npm run dev**, **npm run build**).

npm sets the **PATH** so that **node_modules/.bin** is included. So if you install a CLI package (e.g. a test runner), you can put **"test": "mocha"** or **"test": "node test.js"** in scripts and **npm test** will find the right executable. Scripts run with the current working directory set to the project root (where **package.json** lives). So a script like **"start": "node index.js"** will look for **index.js** in the project root. If your entry point is in a subfolder (e.g. **src/index.js**), use **"start": "node src/index.js"** or adjust the path accordingly.

### 3.3 Why Scripts Matter

Scripts document how to run and test the project. Anyone who clones the repo can run **npm install** and then **npm start** or **npm run dev** without guessing the right file or flags. For a homestead or team project, that consistency is valuable. You can also chain commands (e.g. **"pretest": "node check-env.js"**) using npm’s lifecycle script names; for now, **start**, **test**, and **dev** are enough.

## 4) Dependencies and npm install

The main reason to use npm is to install **dependencies**: other packages your project needs.

### 4.1 Installing a Package (Add Dependency)

To add a package and record it in **package.json**:

```bash
npm install <package-name>
```

Example:

```bash
npm install express
```

npm will:

1. Download **express** (and its own dependencies) from the npm registry.
2. Put them in **node_modules** in the project directory.
3. Add **express** to the **dependencies** field in **package.json** (e.g. **"express": "^4.21.0"**).
4. Create or update **package-lock.json** with the exact versions installed.

You can then **require("express")** or **import express from "express"** in your code (Chapter 4.08 covers using installed packages). The **^** in **^4.21.0** is a version range: “compatible with 4.21.0,” usually meaning “allow minor and patch updates (4.x.x) but not major (5.x.x).” The lock file stores the exact version (e.g. 4.21.0) so future installs are reproducible.

### 4.2 npm install (No Package Name)

If you run **npm install** with no package name, npm reads **package.json** and **package-lock.json** and installs all dependencies listed there. Use this when you clone a project or switch branches: **npm install** restores **node_modules** to match the lock file. Everyone on the team should get the same dependency tree if they use the same lock file.

### 4.3 Where Things Live

- **package.json**: Project manifest; lists dependency **ranges** (e.g. **^4.21.0**). You edit this when you want to change what the project “needs” (or add scripts).
- **package-lock.json**: Generated by npm; lists **exact** versions of every package in the dependency tree. Do not edit by hand; let npm update it when you **npm install** or **npm update**. Commit this file so installs are reproducible.
- **node_modules**: Directory containing the actual installed packages. Do not commit **node_modules** (it is large and reproducible from **package.json** + **package-lock.json**). Add **node_modules/** to **.gitignore** if it is not already there.

When you **require("express")** or **import express from "express"** in your code, Node (and the module resolution algorithm) looks for **node_modules/express** (or **node_modules/express/package.json** and its **main** entry). So **npm install** is what populates the tree that **require**/ **import** walk. Without **node_modules**, your code cannot find installed packages and you get “Cannot find module 'express'.” Running **npm install** fixes that as long as **express** is listed in **package.json** (or the lock file).

## 5) package-lock.json and Reproducible Installs

**package-lock.json** is a large JSON file that records the exact version of every package that was installed, including nested dependencies. When you or someone else runs **npm install** later, npm uses the lock file (if present) to install those exact versions. So “reproducible installs” means: same **package-lock.json** → same **node_modules** on every machine and at every time. That avoids “works on my machine” bugs caused by different dependency versions.

You should **commit package-lock.json** to version control. Do not commit **node_modules**. When you add or remove a dependency (**npm install** or **npm uninstall**), npm updates both **package.json** and **package-lock.json**; commit both. Some projects use **yarn** or **pnpm** instead of npm; they have their own lock files (e.g. **yarn.lock**). The curriculum uses npm and **package-lock.json**.

## 6) Semantic Versioning (semver)

Versions are **major.minor.patch** (e.g. **1.2.3**).

- **Major** (1): Breaking changes; code that worked with 1.x might not work with 2.x.
- **Minor** (2): New features, backward compatible. Code that worked with 1.2.x should work with 1.3.x.
- **Patch** (3): Bug fixes, backward compatible. 1.2.3 → 1.2.4 is typically safe.

In **package.json** **dependencies**, you can write:

- **"1.2.3"** (exact): Install exactly 1.2.3. No updates unless you change the string.
- **"^1.2.3"** (caret): “Compatible with 1.2.3.” npm typically allows any version **>=1.2.3** and **<2.0.0** (minor and patch updates, not major). This is the default when you **npm install &lt;pkg&gt;**.
- **"~1.2.3"** (tilde): “Approximately 1.2.3.” Often allows patch updates only: **>=1.2.3** and **<1.3.0**.

The **package-lock.json** stores the exact version that was installed (e.g. 1.2.7). So even if **package.json** says **^1.2.3**, the lock file might say 1.2.7; **npm install** will install 1.2.7 until you run **npm update** to refresh within the allowed range. For applications, committing the lock file and using **npm install** (which respects the lock file) is the recommended practice. For libraries, authors often use **^** or **~** so consumers get patch or minor updates without changing the library’s **package.json** every time. To refresh dependencies within the ranges in **package.json**, you can run **npm update**; npm will update **package-lock.json** and **node_modules** to the latest versions that still satisfy the ranges. If you want to upgrade a package to a new major version (e.g. 1.x → 2.x), you typically change the version in **package.json** (or run **npm install &lt;pkg&gt;@2**) and then run **npm install**; read the package’s changelog for breaking changes.

## 7) devDependencies (Optional but Useful)

Some packages are only needed while developing or testing (e.g. a test runner, a linter). You can install them as **devDependencies** so they are not installed in production (e.g. when you run **npm install --production** or when a deployment only installs production deps):

```bash
npm install --save-dev mocha
```

This adds **mocha** to **devDependencies** in **package.json**. For a full application, you might put **express** in **dependencies** and **mocha** in **devDependencies**. When someone runs **npm install**, both are installed by default; when they run **npm install --omit=dev** (or **--production**), only **dependencies** are installed. Distinguishing **dependencies** (needed at run time) from **devDependencies** (needed only for development) keeps production installs smaller and clearer.

## 8) What Breaks When You Ignore npm Basics

If you do not have a **package.json**, **npm install &lt;pkg&gt;** will still create **node_modules** and a **package-lock.json**, but npm may create a **package.json** from scratch with only that one dependency; your project name and scripts may be wrong. Always run **npm init** (or **npm init -y**) first in a new project. If you run **npm install** in the wrong directory (e.g. one level above or below the project root), you may create or update a **package.json** in the wrong place and end up with **node_modules** there; always **cd** to the directory that contains (or will contain) **package.json** before running npm commands. If you do not commit **package-lock.json**, another machine or CI might install different minor/patch versions and behavior can change; commit the lock file. If you commit **node_modules**, the repo becomes huge and merges can be painful; add **node_modules/** to **.gitignore**. If you remove a dependency by deleting it from **package.json** but do not run **npm install** (or delete it from **node_modules**), the lock file and **node_modules** can get out of sync; use **npm uninstall &lt;pkg&gt;** to remove a dependency properly. If you forget **"private": true** and run **npm publish**, you might publish an app to the registry by mistake; set **private** for non-library projects.

## 9) Homestead Example: Small Node API Project

Imagine a small Node API for your homestead dashboard. You might:

1. Create a folder **homestead-api** and **cd** into it.
2. Run **npm init -y** to create **package.json**.
3. Add **"private": true** and set **"main": "index.js"** (or **server.js**).
4. Add scripts: **"start": "node index.js"**, **"dev": "node --watch index.js"**.
5. Run **npm install express** (or another framework) so it is added to **dependencies**.
6. Commit **package.json** and **package-lock.json**; ignore **node_modules**.

Anyone who clones the repo runs **npm install** and **npm start** (or **npm run dev**) and gets the same environment. Chapter 4.08 will show how to **require** or **import** the installed package and use it in code.

### 9.1 Checking npm and Node

Before relying on npm, confirm it is available: **npm --version** (and **node --version**). npm is bundled with Node, so if you installed Node from the official installer or a version manager (nvm, fnm), npm should be there. If **npm** is not found, reinstall Node or fix your **PATH**. On some systems, **npm** is installed separately; for this curriculum, the Node installer is enough. You do not need to install npm globally as a separate step.

### 9.2 npx (Run a Package Once)

npm ships with **npx**. You can run a package’s binary without adding it to **scripts** or installing it globally: **npx &lt;package&gt;** (e.g. **npx cowsay "Hello"**). npx will use a locally installed package if present, or download and run it temporarily. For one-off tools (e.g. a generator or a linter run), **npx** is convenient. For repeated commands, adding a script to **package.json** is clearer. Chapter 4.08 may reference **npx** when running installed CLI tools.

## Common Pitfalls

- **Forgetting npm init**: Without **package.json**, your project has no manifest; run **npm init -y** at the start.
- **Committing node_modules**: Bloat and merge hell. Use **.gitignore** for **node_modules/**.
- **Not committing package-lock.json**: Without it, installs can vary; commit it for reproducible builds.
- **Editing package-lock.json by hand**: Let npm manage it; run **npm install** or **npm update** to change it.
- **Publishing a private app**: Set **"private": true** so **npm publish** fails.
- **Assuming npm is installed**: It ships with Node; if **node** works, **npm** usually does. Check with **npm --version**.
- **Running npm in the wrong directory**: **package.json** must be in the current directory (or a parent) for **npm install** and **npm run** to apply to the right project. If you get “no such file or directory” for a script, check that you are in the project root.

## Practice: Try These

1. Create a new folder, **cd** into it, and run **npm init -y**. Open **package.json** and add **"private": true**. Add a script **"start": "node index.js"** and create a minimal **index.js** that logs **"Hello"**. Run **npm start** and confirm it works.
2. Run **npm install express** (or any small package). Check that **package.json** has **dependencies** and that **package-lock.json** exists. Look at **node_modules/express** (or the package you installed) to see its **package.json**.
3. Delete **node_modules** and run **npm install** again. Confirm **node_modules** is restored and matches what you had before (same versions as in the lock file).
4. In **package.json**, change the **express** (or other) version from **^4.21.0** to **4.21.0** (exact). Run **npm install** and confirm the lock file still has an exact version. Then change it back to **^4.21.0** if you like.
5. Add a **dev** script (e.g. **"dev": "node --watch index.js"**) and run **npm run dev**. Stop it with Ctrl+C. This reinforces that only **start** and **test** have the **npm &lt;name&gt;** shorthand; other scripts use **npm run &lt;name&gt;**.
6. Add **node_modules/** to **.gitignore** if it is not there. Confirm **package-lock.json** is not in **.gitignore** (you want to commit it).

These exercises lock in **package.json**, scripts, **npm install**, and the lock file before you install and use specific packages in Chapter 4.08. If **npm install** fails with network or registry errors, check your internet connection and that the registry URL is correct (**npm config get registry**; default is https://registry.npmjs.org/). If you get “EACCES” or permission errors, avoid using **sudo** with npm; fix your npm global directory permissions or use a version manager so installs stay in your home directory. If **package-lock.json** and **package.json** disagree (e.g. after a manual edit), run **npm install** again so npm reconciles them and updates the lock file.

## Summary

**npm** is Node’s package manager. You create a project manifest with **npm init** (or **npm init -y**), which creates **package.json** with **name**, **version**, **main**, and **scripts**. The same **package.json** is used by other tools (e.g. CI, deployment) to install and run your project. Add **scripts** (e.g. **start**, **test**, **dev**) so you can run **npm start**, **npm test**, and **npm run dev**. Install dependencies with **npm install &lt;pkg&gt;**; they are recorded in **dependencies** (or **devDependencies** with **--save-dev**) and installed into **node_modules**. **package-lock.json** locks exact versions for reproducible installs—commit it and do not commit **node_modules**. Use semantic versioning (major.minor.patch) and version ranges (**^** and **~**) in **package.json**; the lock file stores exact versions. Set **"private": true** for apps you do not intend to publish. Use **npm update** to refresh dependencies within the allowed ranges and **npx** to run a package binary once without a script. With this foundation, you are ready to install and use specific packages in the next chapter.
