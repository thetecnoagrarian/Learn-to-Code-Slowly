# Section B Phase 4 · Chapter 4.13: Node in the Wild

Node is not just syntax. It runs in the real world: on your laptop, on a Raspberry Pi, in a container, or on a server. This chapter puts Phase 4 in front of your eyes: running the raw HTTP server you built, hitting it with curl, watching logs and process behavior, and seeing where Node and npm show up in a real project or on a homestead device. No new APIs—you use what you learned in Chapters 4.01–4.12. Here you observe and apply it: how the server behaves when you start it, how requests look when they hit it, how config and JSON flow from env and files, and how this same stack appears when you move from development to a Pi or a small VPS. Section B Phase 4 ends with this: Node in the wild, so you can run and debug your server anywhere and know what to look for when something goes wrong.

## Learning Objectives

By the end of this chapter, you should be able to:
- Run a Node HTTP server (from Chapter 4.12) locally and observe what you see: listening message, process in the terminal, and responses when you send requests with curl or a browser.
- Use curl to drive and debug your API: send GET and POST, inspect status and headers, and relate what you see to the server code (routing, body parsing, status codes).
- Interpret common failure modes in the wild: connection refused, 404, 500, invalid JSON, and missing or wrong env (e.g. PORT), and know where to look (server logs, curl output, .env).
- Describe where Node runs in practice: development (your machine), a Raspberry Pi or small device, or a VPS; and how env and config (dotenv, process.env) differ in each context.
- Explain how the raw server fits into a project (one file, add routes, when to stay raw vs move to Express) and how npm (package.json, scripts, node_modules) and JSON (config, API bodies, file storage) show up in a real codebase.
- Bridge to Phase 5: what stays the same (req, res, HTTP) when you move to Express and what Express adds (routing, middleware, body parsing) so you are ready to build larger apps.

## Key Terms

- **in the wild**: Running and observing Node and your server in real environments (terminal, Pi, server), not only in theory. You see process, logs, requests, and failures as they actually happen.
- **connection refused**: Error when no process is listening on the given host and port (e.g. server not started, wrong PORT, or firewall). curl or the browser cannot open a TCP connection.
- **request/response cycle (observed)**: What you see when you send a request: the server receives it, runs the handler, and sends a response; you observe this via curl output, server logs, or DevTools.
- **process in the terminal**: When you run **node server.js**, Node is a foreground process; you see stdout (e.g. "Listening on http://localhost:3000") and stderr (e.g. errors). Ctrl+C stops it. In production you often run it under a process manager (e.g. systemd, PM2) so it stays up and logs go to a file or journal.

## 1) Running the Server in the Wild

You built a minimal HTTP server in Chapter 4.12: it loads **PORT** from the environment (dotenv and **process.env**), creates a server with **http.createServer**, and listens. In the wild, you run it. From your project directory you run **node server.js** (or **node server** if the extension is resolved). Node starts, loads **dotenv** so **.env** is applied to **process.env**, parses **PORT**, and calls **server.listen(port, ...)**. The listen callback runs when the server is bound to the port; typically you **console.log** something like **Listening on http://localhost:3000**. That message is the first thing you see: the server is up and accepting connections. The process stays running. It does not exit. The terminal is blocked in the sense that you do not get the prompt back until you stop the process (Ctrl+C). That is normal. The server is a long-running process; it waits for incoming TCP connections and, for each connection, runs your request handler. If you close the terminal or kill the process, the server stops and any client trying to connect will get **connection refused**. So "in the wild" the first observation is: run **node server.js**, see the listening message, and leave that terminal open (or run the server in the background, e.g. **node server.js &**, or under a process manager). If you do not see the listening message, check that **PORT** is valid and that nothing else is already using that port (e.g. another instance of the server or another app). On Linux and macOS you can run **lsof -i :3000** (or your port) to see which process is listening; on Windows you can use **netstat** or similar. If the port is in use, change **PORT** in **.env** or stop the other process. If **PORT** is invalid (e.g. **abc** or **99999**), your server should have exited at startup with **process.exit(1)** and an error message (as in Chapter 4.11 and 4.12). So the very first "in the wild" check is: start the server and confirm it logs that it is listening; if it does not, fix port or env before going further.

## 2) Hitting the Server with curl

Once the server is listening, you send requests. The simplest way from the command line is **curl**. **curl http://localhost:3000/** sends a GET request to the root. You should see the response body in the terminal (e.g. **Hello from raw Node**). That is the server in the wild: you issued a request, the server received it, matched the path and method, and sent a response. To see more than the body, use **curl -v** (verbose). You see the request line (e.g. **GET / HTTP/1.1**), request headers (**Host: localhost:3000**, **User-Agent: curl/...**), the response status line (**HTTP/1.1 200 OK**), response headers (**Content-Type: text/plain**), and the body. That is the full HTTP exchange. When you hit **GET /api/health**, you see **200** and **Content-Type: application/json** and a JSON body like **{"status":"ok","time":...}**. When you hit a path that does not exist (e.g. **curl http://localhost:3000/other**), you see **404 Not Found** and a JSON body **{"error":"Not Found"}**. So in the wild you observe: the status code and headers and body that the server actually sent. That is how you verify that your routing and response logic are correct. For POST with a JSON body you run something like **curl -X POST http://localhost:3000/api/echo -H "Content-Type: application/json" -d '{"x":1}'**. You see **200** and **{"received":{"x":1}}**. If you send invalid JSON (e.g. **-d 'not json'**), you see **400** and **{"error":"Invalid JSON"}**. So curl is your observation tool: you drive the server with exact requests and see exact responses. No browser, no front end—just the HTTP layer. When your dashboard or an ESP32 later calls the same server, they are doing the same thing: sending a request and reading the response. If something fails in the app, you can replay the same request with curl and see whether the server returns the same status and body. That isolates whether the bug is in the client (wrong URL, wrong headers, wrong body) or in the server (wrong route, wrong status, wrong body). In the wild, get into the habit: server not behaving as expected? Reproduce with curl and look at status and headers and body. That is observation-first debugging, same idea as "Seeing HTTP in the Wild" in Phase 1.

## 3) Logs and What to Emit

The raw server in Chapter 4.12 does not log every request by default. You can add logging so that in the wild you see what is happening. For example, at the start of the request handler you might log **req.method** and **req.url** (or the parsed pathname) and when you send the response you might log the status code. That way, when you run the server in the terminal you see a line per request: **GET / 200**, **GET /api/health 200**, **POST /api/echo 200**, **GET /other 404**. That helps when you are developing (you see which routes are hit) and when you are debugging (you see if a request ever reached the server and what path it had). Do not log the full body in production for every request (it can be large and may contain sensitive data); logging method, path, and status is usually enough. In the wild, logs might go to stdout (terminal) when you run **node server.js** directly, or to a file or a journal if you run under systemd or PM2. The important thing is: you have a place to look when something goes wrong. If a client reports "the API returned 500," you check the server logs to see if that request arrived and what error was thrown. If the logs show no request at all, the problem may be network or client (request not reaching the server). If the logs show the request and then an error stack, the problem is in your handler. So in the wild, add minimal request logging (method, path, status) and use it to correlate client behavior with server behavior.

## 4) Where Node Runs: Dev, Pi, VPS

Node runs in different environments. On your development machine you run **node server.js** in a terminal, with **.env** in the project directory and **PORT=3000** (or similar). You hit **http://localhost:3000** with curl or a browser. That is dev: one process, one machine, easy to stop and restart and to see logs in the terminal. On a Raspberry Pi or another small device you might run the same server. You copy the project (or clone it), run **npm install**, put a **.env** on the Pi with **PORT=80** or **PORT=3000** and any other config (e.g. path to a data directory, API keys). You start the server (e.g. **node server.js** or via systemd so it starts on boot). From your laptop you hit **http://pi.local:3000** or **http://192.168.1.10:3000**. The server is the same; the environment is different. The Pi might have a different **NODE_ENV**, different **PORT**, or different paths for data files. So in the wild you learn: the same code runs in multiple places; config (env, .env) is what changes. On a VPS (e.g. a Linode or DigitalOcean droplet) you do the same: clone the repo, install dependencies, set env (or use a .env file with proper permissions), and run the server, often behind a reverse proxy (e.g. nginx) that forwards to **localhost:3000**. The raw server does not care whether the request came from localhost or from the proxy; it sees **req.url** and **req.headers** as the proxy sent them. So "Node in the wild" means: your server can run anywhere Node runs; you control behavior with env and config, not by changing code for each environment. Use **.env** for local dev (and do not commit it); use environment variables set by the host or a process manager in production so secrets and port are not in the repo. Chapter 4.11 (Environment and Config) gave you the pattern; in the wild you apply it on each machine or container where the server runs.

## 5) The Raw Server in a Real Project

In a real project the raw server might be a single file (**server.js**) that you grow by adding more **if (pathname === "..." && method === "...")** blocks. You might have a **data/** directory with JSON files (e.g. **readings.json**) that the server reads with **fs.promises.readFile** and **JSON.parse** and serves via **GET /api/readings**. You might have a **config** object built from **process.env** (port, data path, optional API key) and validate it at startup. The project has **package.json** with **"main"** or **"scripts": { "start": "node server.js" }**, and **node_modules** for **dotenv** (and any other deps). So in the wild the layout is: one entry file (server.js), config from env, routes in one handler, and optional file-based storage (JSON files). You do not need a framework for a small API (a few routes, read/write JSON files). When the number of routes grows or you need middleware (e.g. auth, logging, body parsing for many routes), you may switch to Express (Phase 5); the **req** and **res** objects are the same, so the mental model carries over. So "in the wild" also means: know when the raw server is enough (small, simple API) and when to plan for Express (many routes, shared middleware, larger app). You can always start raw and refactor to Express later; the HTTP and request/response concepts do not change.

## 6) npm in the Wild

In the wild your project has **package.json** and **node_modules**. You run **npm install** to get dependencies (e.g. **dotenv**). You might run **npm start** (which runs **node server.js** if you defined that script). You do not commit **node_modules** (it is in **.gitignore**); you commit **package.json** and **package-lock.json** so that **npm install** on another machine or on the Pi produces the same tree. Scoped or private packages, if you use them, require auth (e.g. **npm login** or **.npmrc**); for Phase 4 you typically only need public packages like **dotenv**. If you add a new dependency (e.g. a library for dates or validation), you run **npm install <name>** and then **require** or **import** it in your server file. So in the wild npm is the way the project declares and installs dependencies; the server runs with **node server.js** and Node resolves **require("dotenv")** from **node_modules**. When you deploy to a Pi or VPS you run **npm install** (or **npm ci** for a lockfile-faithful install) in the project directory so **node_modules** is populated there. No magic—just the same commands you use locally, in a different directory and often with different env.

## 7) JSON in the Wild: Config, Bodies, Files

JSON shows up in three main places in the wild. First, config: you might have a **config.json** that you read at startup with **fs.promises.readFile** and **JSON.parse**, or you might use **.env** and no JSON file (dotenv loads env; you build a config object from **process.env**). Both are valid; the server in Chapter 4.12 uses **.env** for **PORT**. Second, request and response bodies: clients send JSON in the body of POST (or PUT) and the server parses it with the chunk-collect and **JSON.parse** pattern; the server sends JSON in the response body with **res.setHeader("Content-Type", "application/json")** and **res.end(JSON.stringify(...))**. So in the wild you see JSON on the wire: **Content-Type: application/json** and a body that is valid JSON. Third, file storage: the server might read or write **data/readings.json** to persist data. You read with **fs.promises.readFile** and **JSON.parse**, and you write with **fs.writeFile** and **JSON.stringify(data, null, 2)** (or **fs.promises.writeFile**). So in the wild JSON is the interchange format for API bodies and often for config and file storage. You already know the rules from Chapters 4.09 and 4.10: valid JSON only (no trailing commas, no single quotes, no undefined); **JSON.parse** in try/catch for untrusted input; **JSON.stringify** for output. When something breaks (e.g. 400 Invalid JSON), you look at what the client sent (curl or DevTools) and at the server’s parse error; when a file read fails, you check that the file exists and is valid JSON. Observation: the JSON is either valid or it is not; the server and client must agree on encoding (UTF-8) and on **Content-Type**.

## 8) Homestead: Node on a Pi or Small Device

Imagine your raw server running on a Raspberry Pi. The Pi has the project (server.js, package.json, .env, maybe a data/ directory). You run **npm install** and **node server.js** (or start it with systemd so it runs on boot). The Pi’s IP is **192.168.1.10** (or you use **pi.local** if mDNS works). From your laptop you run **curl http://192.168.1.10:3000/api/health** and get **{"status":"ok",...}**. You run **curl -X POST http://192.168.1.10:3000/api/echo -H "Content-Type: application/json" -d '{"sensor":"battery","v":12.1}'** and get the echo back. So in the wild the server is on the network; any device on the same LAN can hit it (subject to firewall). Your dashboard (running in a browser on your laptop) might fetch **http://192.168.1.10:3000/api/readings** to display sensor data. An ESP32 or another device might POST readings to the same server. The server does not care who the client is; it reads **req.method**, **req.url**, and the body and responds. Config on the Pi (**.env**) might set **PORT=3000**, **DATA_DIR=/home/pi/homestead/data**, or similar. So "Node in the wild" on a homestead means: one small Node process on a Pi (or similar) serving a minimal API that reads and writes JSON (files or in-memory), with config from env, and with you observing and testing via curl from your laptop. When something fails (e.g. dashboard gets 404), you SSH to the Pi, check that the server is running (**ps** or **systemctl status**), check logs, and maybe run curl from the Pi to **localhost:3000** to see if the server responds locally. Then you run curl from your laptop to the Pi’s IP to see if the network is the issue. That is debugging in the wild: isolate process, then network, then client.

## 9) What You See When It Breaks

In the wild things break in observable ways. **Connection refused**: curl or the browser cannot connect. Usually the server is not running, or it is listening on a different port, or a firewall is blocking the port. Fix: start the server, check **PORT** and **.env**, and check **lsof** or **netstat** to see if something is listening. **404 Not Found**: the server is running but the path (or method) does not match any route. You see **404** and often a JSON body **{"error":"Not Found"}**. Fix: check **req.url** and your routing (pathname and method). Maybe the client is calling **/api/healthz** but your server only has **/api/health**; fix the client or add the route. **500 Internal Server Error**: the server threw an exception. You see **500** and maybe an error body if you sent one. Fix: check server logs for the stack trace; fix the bug in the handler (e.g. missing null check, **JSON.parse** on invalid data, or **fs.readFile** on a missing file). **400 Bad Request** (e.g. invalid JSON): the server parsed the body and rejected it. You see **400** and **{"error":"Invalid JSON"}**. Fix: ensure the client sends valid JSON and **Content-Type: application/json**. **Invalid PORT or missing env**: the server exits at startup with **process.exit(1)** and a message. Fix: set **PORT** (and any required env) in **.env** or in the environment. **Hanging request (no response)**: curl or the browser spin and never get a response. Usually the server never called **res.end()** for that request (e.g. a branch that forgot to send a response, or an async path that never completed). Fix: ensure every code path in the handler calls **res.end()** exactly once; add logging to see which path was taken. **Slow response**: the server eventually responds but after a long time. Maybe the handler is doing blocking work (**readFileSync**, heavy loop) or waiting on a slow I/O. Fix: use async APIs (**fs.promises**) and avoid blocking the event loop (Chapter 4.06). So in the wild every failure has a symptom (connection refused, 404, 500, 400, startup exit, hang, or slow). You observe the symptom (curl output, browser, logs) and you know where to look (process, port, route, body, env, or missing/slow **res.end()**). That is the payoff of "Node in the Wild": you are not guessing; you have a map from symptom to cause.

## 10) Process and Ports: One Server, One Port

A single Node process runs one **http.createServer**. That server listens on one port (e.g. 3000). So in the wild you have one process and one port. If you want to run two different "apps" (e.g. two different servers), you run two processes on two different ports (e.g. 3000 and 3001), or you run one server that has routes for both logical apps. You cannot bind two servers to the same port in the same process. If you get "address already in use" when you call **server.listen**, it means another process (often another instance of your server) is already listening on that port. Fix: stop the other process or change **PORT**. So in the wild, remember: one listener per port per process. When you use a reverse proxy (e.g. nginx) in front of Node, the proxy listens on 80 or 443 and forwards to **localhost:3000**; the Node process still listens on 3000. The proxy is a separate process. So you might have nginx (port 80) and Node (port 3000) on the same machine; they cooperate by the proxy forwarding to Node. That is a common production setup; for development you usually just run Node on 3000 and hit it directly.

## 11) Staying Raw vs Moving to Express

The raw server is enough when you have a handful of routes, simple body parsing (one or two POST routes), and no need for shared middleware (auth, request logging, CORS) across many routes. You can add more **if (pathname === "..." && method === "...")** blocks and maybe a small helper to collect the body and parse JSON so you do not repeat that code. In the wild many small APIs stay that way for a long time. When you have many routes (e.g. dozens), or you want middleware (e.g. every request logged, or every request checked for an API key), or you want to plug in body parsers and error handlers without writing them yourself, Express (Phase 5) is the next step. Express gives you **app.get**, **app.post**, **res.json**, and middleware; under the hood it is still **http.createServer** and the same **req** and **res**. So "Node in the Wild" includes the choice: stay raw for a small API or move to Express when the app grows. You are not wrong to stay raw; you are not wrong to switch. The skills from Phase 4 (env, config, http, streams, JSON, the request/response cycle) apply in both. Phase 5 will teach you Express; when you use it, you will recognize the same **req** and **res** and the same idea of "one response per request." This chapter closes Phase 4 by putting that server in the wild—running it, observing it, and knowing what you see when it works and when it breaks.

## 12) Process Managers and Running in the Background

When you run **node server.js** in a terminal, the process stops when you close the terminal or press Ctrl+C. In the wild on a Pi or a server you usually want the server to keep running and to restart if it crashes. A **process manager** does that. **systemd** (on Linux) lets you define a service unit that runs **node server.js** (or **npm start**) and restarts it on failure; logs go to **journalctl**. **PM2** is a Node-based process manager: you run **pm2 start server.js** and the process runs in the background; **pm2 logs** shows output, **pm2 restart server.js** restarts it. You do not need these for local development (running in the foreground is fine and you see logs directly), but on a Pi or VPS they are how you keep the server up. The server code does not change; you just start it via the process manager instead of typing **node server.js** in a terminal. Env and **.env** are still read when the process starts (PM2 and systemd can also inject environment variables). So "in the wild" includes: dev = foreground process in a terminal; production or device = same process started by systemd or PM2 so it survives disconnects and restarts on crash.

## 13) Observation Checklist: Node in the Wild

Before you consider Phase 4 complete, run through this in the wild. (1) Start your server (**node server.js**) and see the listening message. (2) Hit **GET /** and **GET /api/health** with curl and see 200 and the expected bodies. (3) Hit **POST /api/echo** with valid JSON and see 200 and the echoed body; hit it with invalid JSON and see 400. (4) Hit an unknown path and see 404. (5) Use **curl -v** and confirm you see the status line and **Content-Type** for JSON routes. (6) Change **PORT** in **.env** (or unset it to test default), restart, and confirm the server listens on the new port. (7) Intentionally break something (e.g. wrong path in the client or invalid JSON) and observe the failure (404 or 400), then fix it. (8) If you have a Pi or another machine, run the server there, set **PORT** and any config, and hit it from your laptop with curl. (9) Optionally add one line of request logging (method, path, status) and watch the log lines as you send requests. (10) Know what "connection refused," 404, 500, and 400 mean and where to look (process, route, body, env). When you can do all of that, you have Node in the wild: not just code in a file, but a running server you can observe and debug. Phase 4 is complete. Next is Phase 5 (Express), where you will build on the same HTTP and request/response model with routing and middleware.

## Practice: Try These in the Wild

1. Start your Chapter 4.12 server with **node server.js**. In another terminal run **curl http://localhost:3000/**, **curl http://localhost:3000/api/health**, and **curl http://localhost:3000/nonexistent**. Note the status and body for each. Then run **curl -v http://localhost:3000/api/health** and identify the response status line and **Content-Type** in the output.
2. With the server still running, run **curl -X POST http://localhost:3000/api/echo -H "Content-Type: application/json" -d '{"test":true}'** and confirm you get **200** and **{"received":{"test":true}}**. Then run the same URL with **-d 'invalid'** (no **-H** for JSON) and confirm you get **400** and an error body (and, if you added the Content-Type check, **415** when the header is missing).
3. Stop the server (Ctrl+C). Run **curl http://localhost:3000/** again and note "connection refused." Restart the server and confirm curl works again. That is the in-the-wild observation: no process, no response.
4. Add one line of logging in your server: when you send a response, log **method**, **pathname** (or **req.url**), and **res.statusCode**. Restart the server and send a few requests with curl; watch the terminal and see one log line per request.
5. If you have a second machine or a Pi on your network, copy the server project there, run **npm install**, set **PORT** in **.env**, and start the server. From your laptop run **curl http://<other-machine-ip>:3000/api/health**. If you cannot use another machine, change **PORT** to **4000**, restart, and hit **http://localhost:4000** with curl to confirm the server listens on the port you set.
6. Intentionally cause a 404 (wrong path) and a 400 (invalid JSON) and note exactly what curl prints (status line and body). Then fix the "bug" (correct URL or valid JSON) and confirm you get 200. That reinforces the map from symptom (404, 400) to cause (route, body) and back to fix.

## Common Pitfalls

- **Not actually running the server**: You edit server.js but forget to start it (or you stopped it). Then curl gives "connection refused." Always confirm the process is running and listening.
- **Wrong port or wrong host**: You hit **http://localhost:3000** but the server is on 4000 (or you hit the Pi’s IP but the server is on localhost only). Check **PORT** and that you are curling the right host and port.
- **Assuming the client sent what you think**: When the server returns 400 or 404, look at what the client actually sent (curl -v or DevTools). Often the URL has a typo, the method is wrong, or the body is not valid JSON.
- **Ignoring server logs**: Add minimal logging (method, path, status) and use it. When something fails, the log tells you whether the request reached the server and what path it had.
- **Env not loaded**: If you rely on **.env** but run **node server.js** from a different directory, dotenv might not find **.env**. Run from the project root or set **PATH** to the project dir; or set env in the shell before starting Node.
- **Treating "in the wild" as optional**: Running and observing the server is how you verify that Phase 4 is solid. Do not skip actually starting the server and hitting it with curl; that is where theory becomes practice.

## Summary

Node in the wild means running your Phase 4 server and observing it: start it and see the listening message, hit it with curl (GET and POST), see status and headers and body, and know what you see when it breaks (connection refused, 404, 500, 400). Logs (method, path, status) help you correlate client and server. The same server can run on your laptop, on a Pi, or on a VPS; config (env, .env) changes per environment. npm and JSON show up in real projects as dependencies, scripts, config, API bodies, and file storage. You know when to stay raw (small API) and when to plan for Express (many routes, middleware). Phase 4 ends here: you have Node, npm, JSON, env, and a raw HTTP server that you can run and debug anywhere. Next, Phase 5 (Express) builds on the same **req** and **res** with routing, middleware, and helpers so you can build larger web applications with less boilerplate.
